# Modeling Domain

本文定义建模模块的核心领域语义。结构重构不能因为类移动或角色拆分改变这些含义。

## Physical Model(物理模型)

`Model` 是建模模块的核心资产,**一个模型对应一张物理表**(口径 A1,逆向导入"一表一模型"、ER 画布"模型即实体"均由此推导)。

- `modelKey`:业务可稳定寻址的键,持久化列 `model_code`,**项目空间内唯一**;`id` 是持久化标识。
- 模型携带目标方言(`dialect`)与可选的目标数据源引用;DDL 生成、方言校验均以方言为准。
- 表结构由表基础信息(表名/注释/描述)、字段列表、主键、索引、分区、表属性构成;字段按序保持稳定顺序。
- **表名(`table_name`)与模型编码(`model_code`)是两个概念**:编码是平台内稳定键,表名是落地物理表的名字;表名为空时按 `model_code` 兜底。
- **字段(ColumnDefinition)**:名称(模型内唯一,比较不区分大小写)、数据类型(必填)、长度/小数位、可空、默认值、注释、业务描述;保存采用**全量替换**语义(请求携带完整字段列表,按顺序落 `sort_order`),供编辑器整体保存。
- **主键(primaryKey)**:字段名列表(单/复合);列必须存在于字段列表;随表结构整体保存,持久化为 `pk_columns`。
- **索引(IndexDefinition)**:名称(模型内唯一,比较不区分大小写,`PRIMARY` 为保留名禁用)、字段组合(必须存在于字段列表)、唯一性、索引类型(方言相关,可空);全量替换保存,持久化为 `yak_modeling_model_index`。
- **分区(PartitionSpec)**:类型/字段列表/表达式;列必须存在于字段列表;按方言标注支持情况(编辑器按方言降级),持久化为模型行上的 `partition_*` 列。
- **表属性(tableProperties)**:键值对集合,键非空;按方言可选能力,持久化为 JSON。
- 字段被删除时的联动:主键/索引/分区引用的列随全量替换语义自然失效,编辑器在删除引用列时提示并同步清理。
- **方言合法性校验(ticket 07)**:校验结果分两级 —— `ERROR`(阻断保存)与 `WARNING`(提示不阻断);校验范围:表名/字段名/索引名的标识符与保留字、字段类型是否在方言类型目录内、长度/小数位与类型匹配、主键/索引/分区引用有效性。类型目录与保留字按方言维护(`StructureDialectCatalog`),编辑器类型下拉同源;校验结果结构化(issue 含级别/对象/定位),前端列表化展示并支持定位。
- **建库脚本(DDL,决策 D3)**:由模型结构生成为纯文本,**平台内不执行**;表名留空按 `model_code` 兜底;类型/长度/默认值/注释直用保存的结构;默认值语义:纯数字或 CURRENT_TIMESTAMP 开头裸写,其余按字符串加引号转义;主键/二级索引/分区(MySQL HASH/KEY 完整生成,RANGE/LIST 输出注释提示补充分区定义)/表属性(键值直拼)按方言语法渲染;生成器按方言模板化(`DdlGenerator`,共用骨架 + 各方言钩子),已落地 MySQL/PostgreSQL/Oracle/Doris/StarRocks/ClickHouse 六个模板(ticket 10);保存的类型不在目标方言目录时按跨方言偏好链解析,仍不可用则该能力降级为脚本内注释提示而非报错,细节矩阵见 REQUIREMENTS.md「Ticket 10」。
- 模型可携带 `sourceRef`(来源标记:数据源/库/schema/表),由逆向导入写入,是后续源端结构变更比对(ticket 27)的依据;手工创建的模型没有 sourceRef,不参与变更比对。
- **技术列**:模型工作台自动补充的管道必需列,包括 `process_time`(数据处理时间)与 `event_time`(业务事件时间);ODS 逆向导入时自动追加,目标层派生时按分层规则补齐;不参与继承(ODS 的技术列不带到目标层),不计入治理率。
- 模型归属项目空间(`projectId` 只取服务端可信上下文);跨项目不可见。

## Logical Model(逻辑模型)

`LogicalModel` 表达业务视角的设计,与物理模型解耦、不绑定具体数据库:

- `Entity`(实体):标识/中文名/业务含义/责任人。
- `Attribute`(属性):名称/逻辑类型/业务定义/是否主标识。
- `EntityRelation`(实体关系):两端实体与属性对、基数(1:1/1:N/N:N)、业务含义。

逻辑 → 物理生成(单库单方言,决策 D10):一个逻辑模型落地为**一个目标库、一个方言**下的一组物理模型(一实体一表);逻辑类型按集中维护的映射规则转换为方言类型,不可映射必须显式报错,不得静默降级;实体关系转化为模型关联关系。

## Model Relation(模型关联关系)

两个模型之间的关联:字段对、基数、关系类型(外键/逻辑关联)、备注。ER 画布的连线即本实体,持久化后供画布与模型详情还原。

## Directory(模型目录)与 Tag(标签)

分层/主题域引入前(决策 D6),目录树 + 标签承担模型组织职责:

- `ModelingDirectory`:自定义层级目录,`parent_id=0` 表示根;同一父目录下名称唯一;**删除要求目录为空**(无子目录且无模型);移动禁止落到自身或其子孙(环禁止)。
- `ModelingTag`:项目空间内名称唯一的可复用标签;一个模型可打多个标签;删除标签同时解除全部关联。
- 组合过滤语义:目录 = 精确归属(含"未分类"= `directory_id` 空);标签 = 命中任一所选标签(OR);与名称/编码关键字可叠加。

## Source Mapping(来源映射)

物理模型字段 ← 源端表字段 的字段级映射,可附转换表达式。映射是加工 SQL 生成(ticket 21)的唯一事实来源;未映射字段必须显式标识,不允许隐式补齐。

## Model Version(模型版本)

发布产生**不可变**的结构快照(字段/主键/索引/分区/关系),版本号自增;已发布版本只读,草稿继续可编辑。版本对比(草稿 vs 版本、版本 vs 版本)以结构 diff 表达。

## 状态语义

- 模型生命周期:`草稿 → 发布 → (再编辑 → 再发布)`;删除为**软删除**,进入回收站,可恢复或彻底删除;回收站内模型在目录/画布/搜索/列表等所有入口不可见、不可引用。
- 编码唯一性由**服务层存活行校验 + DB 唯一键兜底**共同保证:软删除时改写存储编码(`原编码__del__<id>`,原编码存 `original_code`)为存活编码腾位,恢复时写回;恢复前校验存活行无同码冲突,冲突则拒绝;并发穿透由唯一键与 DataIntegrityViolation→DUPLICATE_CODE 兜底。
- 恢复到原目录:若原目录已被删除,回退为"未分类",不阻塞恢复。
- 模型基础信息(名称/方言/描述)可编辑;**编码(`model_code`)不可编辑**(稳定键,DOMAIN 见 modelKey)。
- 血缘登记:模型血缘资产**不自动登记**(决策 D7),仅在用户确认后登记;登记幂等,重复执行不产生重复资产。
- 变更感知:仅覆盖有 sourceRef 且被模型引用的源表;发现变更只产生变更事件与通知,**绝不自动修改模型结构**(决策 D4)。


## F-023 场景 Skill 标准匹配

F-023：原标准助手消费 AI 类型候选，仅带入当前未保存字段。模型定义仍由 Modeling 拥有，ModelSuggestionQueryApi 以授权事务锁读取定义指纹；编辑上下文同时给出结构与指纹，保存可携带 If-Match，在原结构事务/审计之前拒绝过期定义。原发布快照与审批指纹序列化保持兼容。

依赖：Agent runtime → toolset → gateway → semantic.api / modeling.api；源域不依赖 Agent，不新增状态机或第二业务真相。合同见 [F-023](../../docs/product/features/F-023-skill-standard-match.md)。

F-023 编辑上下文条件保存返回同一事务的结构/指纹回执；保存期间继续编辑保留草稿并仅推进该回执基线，避免下一次保存使用过期基线或覆盖后来他人的修改。
