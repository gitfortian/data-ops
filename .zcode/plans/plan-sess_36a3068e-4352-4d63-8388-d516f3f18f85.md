# 每个业务模块的 Flyway 迁移合并为单文件

## 一、现状（已核实）

173 个源迁移文件分布在 30 个 Flyway location 上。**每个模块有各自独立的 Flyway bean、location 和历史表**（如 `flyway_schema_history_agent`），所以各子目录版本号从 V1 起算是安全的，且**这次合并完全不需要动 Java 装配**。

### 已经是单文件、无需改动的（12 个）
`yak-alert`、`yak-analysis`、`yak-approval`、`yak-asset`、`yak-audit`、`yak-dashboard`、`yak-data-development`、`yak-datasource`、`yak-digital-screen`、`yak-resource`、`yak-realtime-sync`、`yak-task-catalog`

### 需要合并成 1 个的（16 个业务 + 2 个安全树，共 18 个）

| 模块 | 原文件数 | 说明 |
|---|---|---|
| boot `yak-security/db/migration` | 39（38 V + B2044） | 全站最大的一坨 |
| `yak-modeling` | 23（22 V + B28） | 还要吸收 impact 组 3 个目录 |
| `yak-modeling-history-impact` / `-impact-snapshot` / `-impact-foundation` | 3 / 1 / 1 | 新库实际走的就是这组（见下） |
| `yak-mdm` | 17（16 V + B16） | |
| `yak-semantic` | 15（14 V + B13） | 种子数据 DML 最多 |
| `yak-metric` | 8（7 V + B7） | |
| `yak-offline-sync` | 7（6 V + B6） | |
| `yak-data-service` | 5（4 V + B4） | |
| `yak-workflow` / `yak-metadata` / `yak-dataset` / `yak-consumption` | 各 4 | |
| `yak-agent` / `yak-security` / `yak-quality` / `yak-lineage` / `yak-lifecycle` | 各 3 | |
| framework `yak-security/db/migration` | 4（3 V + B3） | Security bootstrap |

### 会被删除的
- **17 个 `B*__*baseline.sql`**：`B2__agent`、`B2__lifecycle`、`B2__lineage`、`B2__quality`、`B2__security`(business)、`B3__consumption`、`B3__dataset`、`B3__metadata`、`B3__workflow`、`B4__data_service`、`B6__offline_sync`、`B7__metric`、`B13__semantic`、`B16__mdm`、`B28__modeling`、`B2044`、`B3__security_standalone`。**它们从未被执行过**——29 个 Flyway bean 全设了 `baselineOnMigrate(true)` + `baselineVersion("0")`，baseline 迁移只会被解析为 `IGNORED`。这是侦察中最重要的发现。
- **modeling 的 5 个 legacy 专属目录**（共 10 个文件）：`history-logical`(3)、`history-logical-foundation`(1)、`history-logical-snapshot`(1)、`history-v22-foundation`(1)、`history-v22-meta`(1)。`ModelingPersistenceConfiguration.migrationLocations()` 按历史表在两组里二选一，**空库固定走 impact 组**，legacy 组只服务走另一条路的老库。

**合并后：173 → 30 个文件。**

## 二、合并规则（每个模块产出一个 `V1__<module>_baseline.sql`）

1. **按数值版本号升序拼接该模块所有 `V*` 文件**的原文 SQL，块间插入 `-- Source: <原路径>` 注释（沿用 `B2044` 已有的先例格式）。
2. **裸 `CREATE TABLE` → `CREATE TABLE IF NOT EXISTS`**。全库 318 条 CREATE TABLE 里已有 303 条带 `IF NOT EXISTS`，剩下 15 条集中在 modeling 树（`V22/V23/V24/V27/V28`）、会与同组其它文件重复建表。
3. **DML 原样保留**：`yak-semantic` 的 V2 种子 → V12/V13 更新是**顺序依赖**的（V12 先跑会让修复永久失效），升序拼接天然保序；业务树无 `DROP TABLE`/`RENAME TABLE`，mdm 的 3 条 `DROP COLUMN` 全部有 `information_schema` + `PREPARE/EXECUTE` 守护，对空库无害。
4. **占位符原样保留**：`yak-quality` 的 `${table}/${column}/${where}` 继续由该 bean 的 `placeholderReplacement(false)` 兜住，Security 的 `${appName}` 继续由 `.placeholders()` 提供。**因为每个模块仍用自己的 Flyway 实例，两者不冲突**——这是"每模块一个文件"相比"全局一个文件"最大的好处。
5. **交叉依赖为 0**：130 个业务迁移文件里 grep `yak_security_*` 为空，Security 也不反向引用业务表。唯一需要保序的是 Security 树内部：framework `V1`(建 16 张 `yak_security_*`) 必须先于 boot `V1000`(直接 UPDATE 这些表)。

## 三、唯一的 Java 改动

`ModelingPersistenceConfiguration.migrationLocations()` 简化为只返回 `COMMON_MIGRATION_LOCATION`——legacy 5 个目录删除后，动态挑选逻辑失去对象。**其余 28 个 Flyway bean、`@DependsOn("opsDataSourceFlyway")` 锚点、历史表名、`spring.flyway.enabled: false` 全部不动。**

## 四、测试改动（≈15 个类）

- **4 个文件清单锁需改**：`AgentFlywayContractTest`、`DataServiceFlywayContractTest`、`DatasetFlywayContractTest`、`OfflineSyncFlywayContractTest`（断言 `containsExactly(V*列表)` + `contains("B*__baseline.sql")`）。data-development / datasource / resource 三个本来就是单文件，只需顺带核对。
- **约 11 个按路径读 SQL 的内容断言需改**：`YakOpsSecurityCatalogMigrationTest`、`YakOpsSecurityMigrationVersionCompatibilityTest`、`YakOpsLegacyPermissionMenuMigrationTest`、`YakOpsPermissionMenuMigrationTest`、`DataServiceAccessMenuMigrationTest`、`DataServiceApiCallMenuMigrationTest`、`MenuMigrationIsolationTest`、`MessageCenterMigrationTest`、`PermissionMenuMigrationTest`、`AnalysisProjectSpaceContractTest`、`AuditMigrationContractTest` 等——改为读合并后的文件并断言同等内容仍在。
- **无需改**：断言配置字面量的 `DataSourceConfigTest`、`DataDevelopmentFlywayContractTest`、`DataSourceFlywayContractTest`（locations / 历史表名都没变）。

## 五、验证（关键：不能只看编译通过）

1. **取基准**：pymysql（机上有 MySQL 8.0、无 mysql CLI，但 pymysql 可用）从当前 `yak_security` 库导出「表名 + 列名/类型 + 索引」全集。
2. **新建空库** `data_ops_migrate_check`，按上述顺序执行合并后的 30 个文件，导出同样维度，与基准**逐表 diff，必须零差异**。
3. **实体启动**：后端指向该库启动，验证登录、权限菜单可用、抽查标准/指标/质量/MDM 各一个页面能出数据。
4. `mvnw -pl <受影响模块> -am -DskipTests install` + 跑上述测试类；前端 `tsc` 基线回归（本次不动前端）。
5. 用完删除对比库。

## 六、取舍与风险

- **放弃老库升级**：合并后老库的 `flyway_schema_history_<module>` 里 V1..V15 与新的 `V1__baseline.sql` checksum 不一致，Flyway validate 会失败。你说用新库，所以接受；但请确认没有别的环境还在用旧库。
- **权限/菜单种子数据**全部来自 Security 树，合并顺序必须 framework → boot，这一点写进生成脚本。
- **17 个死 `B*` 文件消失**没有运行时影响，但依赖它们存在的测试断言要同步删。
- 单模块最大的是 boot Security（38 V 合成 1 个，约 9000 行）和 modeling（22+5 V 合成 1 个）。体积大但可审。

## 七、执行顺序

写生成脚本（读 V 文件 → 升序拼接 → 裸建表加 `IF NOT EXISTS` → 写 `V1__*_baseline.sql`）→ 改 modeling Java 配置 → 删 17 个 B 文件 + 5 个 legacy 目录 → 更新测试 → 新库结构 diff 验证 → 启动验证 → 提交 PR 合并。
