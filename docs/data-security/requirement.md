# 第一部分：需求文档

## 一、背景

### 1.1 现状

Yak Ops 已具备数据源、集成、开发、质量、建模、语义（含 `SECURITY` 安全标准）、指标、主数据、审计、对外数据服务等能力，但缺少**贯穿式的数据安全治理**：

- 语义中心定义了"安全标准"（等级编码 `level_code` + 建议脱敏规则），但只是**字典**，没有落到"哪张表哪个字段属于哪一级、谁配的、按什么规则发现"。
- 平台 RBAC（`data-security`）管的是**菜单/接口权限**（能进哪个页面、调哪个 API），管不到**数据级权限**（某个用户能不能读某张敏感表的某一列）。
- 数据预览/数据服务对外吐数时，敏感字段（手机号、身份证）**明文直出**。
- 谁在什么时间访问了哪些敏感数据，**没有专门的安全审计视角**。
- 是否满足"敏感数据必须分级、必须脱敏、访问必须留痕"这类合规要求，**无法量化**。

### 1.2 数据安全解决什么

把"数据安全"从**分散的约定**变成**平台内可管理、可执行、可审计、可度量**的闭环：

> 分级分类（是什么级别）→ 权限管理（谁能访问）→ 数据脱敏（怎么访问）→ 访问审计（访问留痕）→ 合规管理（是否达标）→ 反哺分级分类。

## 二、需求目标

| 目标 | 说明 |
|------|------|
| 定级 | 给数据资产（表/字段）打上安全等级 + 数据分类标签 |
| 发现 | 按规则自动识别敏感字段，降低人工分级成本 |
| 控权 | 定义"谁（用户/角色）对什么数据有什么访问权"的数据级策略 |
| 脱敏 | 按等级/分类/访问者身份决定脱敏算法，对外吐数前生效 |
| 留痕 | 敏感数据的访问/授权决策全程审计，可查询、可统计 |
| 合规 | 用规则持续体检，量化合规率、暴露缺口 |
| 闭环 | 分级 → 权限 → 脱敏 → 审计 → 合规 → 反哺 |

## 三、核心需求

### 3.1 数据分级分类（基础）
- **安全等级（分级）**：可维护的等级字典（如 L1 公开 / L2 内部 / L3 敏感 / L4 机密），带序位 `rank`。
- **数据分类（分类）**：可维护的分类树（如 个人信息 / 财务 / 经营 / 业务）。
- **资产分级标签**：把某个数据对象（数据源/库/表/列）绑定到"等级 + 分类"，记录来源（人工/发现/继承）、打标人。
- 等级字典可与语义中心 `SECURITY` 标准对齐（引用 `level_code`），不重复造字典。

### 3.2 敏感数据发现与识别（补充能力）
- **发现规则**：按字段名/注释/内容正则 + 目标等级/分类，配置匹配规则。
- **扫描执行**：对选定数据资产跑规则，产出候选分级标签，用户确认后并入资产分级。

### 3.3 权限管理（谁能访问）
- **数据访问策略**：主体（用户/角色）× 客体（数据源/库/表/列/等级）× 动作（读/写/导出）× 效果（允许/拒绝），含有效期、申请/审批。
- **访问裁决**：给定（用户、数据对象、动作）→ 允许/拒绝/需审批，命中策略走审计留痕。
- 与平台 RBAC 分层：RBAC 决定"能否进入/调用"，本模块决定"能否访问这份数据"。

### 3.4 数据脱敏（怎么脱敏）
- **脱敏算法字典**：内置常见算法（部分遮蔽、哈希、全遮蔽、置空、保留格式、替换、加密占位），可参数化。
- **脱敏策略**：按（等级 / 分类 / 字段匹配）绑定算法，带优先级与作用范围。
- **脱敏裁决 SPI**：对下游（数据服务/预览）暴露"给定字段上下文 + 访问者 → 应施加的算法"，并提供 `mask(value)` 纯函数能力。

### 3.5 访问审计（谁访问了）
- **敏感访问流水**：记录数据级访问/授权决策/脱敏施加（时间、用户、对象、动作、等级、决策、是否脱敏）。
- **复用底座**：配置类生命周期（新建/修改策略、等级）走 `BusinessAuditService`；数据级访问留痕由本模块自有流水承载。
- **安全视角查询**：按用户/对象/等级/时间检索；统计 TOP 访问者、拒绝次数、敏感读取次数。

### 3.6 合规管理（是否合规）
- **合规规则**：如"L3 及以上字段必须已定级""敏感字段必须有脱敏策略""敏感访问必须留痕""定级覆盖率 ≥ N%"。
- **合规体检**：对分级/脱敏/审计数据跑规则，产出检查结果与缺口清单。
- **合规报告**：服务端聚合，输出合规率与待办缺口，供总览展示。

### 3.7 安全总览与对外 SPI（闭环入口/出口）
- **安全总览**：定级覆盖率、各等级分布、策略数、脱敏命中、合规缺口等服务端聚合指标。
- **对外 SPI**：`MaskingApi`（脱敏裁决与执行）、`AccessDecisionApi`（数据级访问裁决）、`ClassificationQueryApi`（读某对象的安全等级/分类），供其他模块消费。

## 四、需求范围

| 能力 | 内容 |
|------|------|
| 分级分类 | 等级字典、分类字典、资产分级标签 |
| 敏感发现 | 发现规则、扫描确认并入 |
| 权限管理 | 数据访问策略、访问裁决、申请审批 |
| 数据脱敏 | 算法字典、脱敏策略、脱敏裁决 SPI |
| 访问审计 | 访问流水、安全视角查询与统计 |
| 合规管理 | 合规规则、体检、报告 |
| 总览出口 | 安全总览、对外 SPI |

## 五、用户角色

| 角色 | 场景 |
|------|------|
| 数据安全负责人 | 定义等级/分类体系、合规规则、审批策略 |
| 数据安全员（DPO） | 资产定级、脱敏配置、发起合规体检、查审计 |
| 数据开发/分析师 | 申请数据访问、消费脱敏后的数据 |
| 审计/合规人员 | 查访问留痕、看合规报告 |

## 六、关键决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | 等级字典对齐 semantic `SECURITY`，不重复建 | 语义是"标准"，本模块是"落地资产标签" |
| D2 | 平台 RBAC 与本模块数据级权限分层 | RBAC 管入口，本模块管数据对象 |
| D3 | 脱敏以 SPI 暴露给下游，本模块不拦截 SQL | 由 data-service/预览在吐数处调用 `MaskingApi` |
| D4 | 访问审计双轨：配置走 BusinessAuditService，数据访问走自有流水 | 关注点分离，避免污染操作审计 |
| D5 | 合规=规则引擎对现有安全元数据做体检 | 不引入外部规则引擎，最小实现 |
| D6 | 所有统计服务端聚合，禁止无界 list 后内存统计 | 遵守 home-overview-contract |
| D7 | 全表 `project_id` 隔离，取自可信上下文 | 遵守 PROJECT_SCOPE |

## 七、和现有模块的关系

| 模块 | 关系 |
|------|------|
| semantic | 等级字典引用其 `SECURITY` 标准 `level_code`（对齐，不强绑定） |
| datasource / dataset | 提供数据资产（库/表/列）作为分级对象；预览消费脱敏 SPI |
| modeling | 模型字段可回显安全等级；消费 `ClassificationQueryApi` |
| data-service | 对外吐数前调用 `MaskingApi` + `AccessDecisionApi` |
| audit | 配置生命周期复用 `BusinessAuditService`；本模块补数据访问流水 |
| yak-security(RBAC) | 页面/接口权限用 `@RequiresPermission`；本模块策略是其上的数据层 |

## 八、本期范围外

| 事项 | 说明 |
|------|------|
| 动态 SQL 改写拦截 | 由下游调用 SPI，本模块不做查询改写 |
| KMS/密钥托管、列级加密落库 | 仅算法占位，真实加密后续 |
| 数据水印/溯源 | 后续 |
| 跨项目安全策略共享 | 本期项目内 |
| 前端页面 | 本目标聚焦后端；菜单/权限注册为后端契约 |

## 一句话总结

> **数据安全**把"分级分类→权限→脱敏→审计→合规"变成平台内可管理、可执行、可审计、可度量的闭环：
> 对内以等级/分类字典 + 资产标签为基座，用发现规则规模化定级，用数据级策略控权、用脱敏 SPI 在吐数处生效、用访问流水留痕、用合规规则体检；
> 对外以 `MaskingApi` / `AccessDecisionApi` / `ClassificationQueryApi` 三个 SPI 让数据服务、预览、建模消费安全能力，形成业务闭环。
