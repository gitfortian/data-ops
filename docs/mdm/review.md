## 一、P0：业务流程不通畅（先修这些，其他都排队）

### 1.1 主数据审批菜单已注册但前端无页面 → 用户点菜单 404

- V2028 已在 `data-security` 注册 `mdm-approval`（route `/mdm/approval`，visible=1，`V2028__register_mdm_approval_menu.sql:48`），但 `navigation.ts` 无该路由、`securityMenuCodes.ts` 无 `mdmApproval`、页面目录不存在；`navigationMenuContract.test.ts` 的 `CATALOG_EXTENSION_MIGRATIONS` 只列到 V2027 → **契约漂移 + 线上可见菜单直接点开 404**。
- **建议**：ticket 60 前端落地为独立"主数据审批"页（待我审批 / 我发起的 / 全部三个分节 + 变更内容 diff 视图 + 通过/拒绝/撤回），并把 V2028 加入契约清单。这是审批闭环（D5）唯一入口。

### 1.2 加工 SQL 无法执行——"采集→记录"是全模块第一卡死点

`MdmRecordService.generateMasterSql` 生成的 SQL（`MdmMasterSqlGenerator.java:59-77`）有三个执行层面硬伤：

1. **表名不存在**：写入 `` `mdm_record` ``，实际表是 `yak_mdm_record`（V6 migration）。
2. **跨库不成立**：`FROM 业务库.表` 与 `INSERT INTO 平台库记录表` 在一条 MySQL SQL 里引用两个不同连接的库，数据开发任务无法直接执行。方案 A（D-M11"交数据开发执行"）没有定义**执行形态**：应当是 sync 式"源连接读→平台连接写"的回流任务，而不是一段裸 SQL。这是设计缺口，不修则记录 Tab 永远为空，清洗/审批/分发/服务全部没有承载对象。
3. **`source.schema()` 被忽略**：拼 `database.table`，带模式的源（PG/SQLServer/Oracle 语义）直接错表。

- **建议**：把"生成加工任务"升级为**注册数据开发/集成任务草稿**（携带源 datasourceId、目标 yak_mdm_record、列映射、master_id 计算规则），复用 modeling 44"派生建模→生成加工任务→任务目录"成熟模式；"生成 SQL 文本"最多作为开发者排障后门，不再作为主流程。

### 1.3 无字段映射：MDM 的第一业务场景没有实现

需求核心例子是 `CRM.cust_id → 客户ID`、`交易.cust_no → 客户ID`（requirement 1.3/3.3），但加工 SQL 假设**来源列名 = 属性编码**（`MdmMasterSqlGenerator.java:49-51`）。D-M9 把"字段映射"划给 sync 复用，而 55a 加工是 MDM 自己生成的 INSERT...SELECT，两边一拼，**映射在谁那里都不存在**。多源同名不同列时整条链路失效。

- **建议**：`mdm_source` 增加 `field_mapping`（属性编码 → 源列名，JSON；与 54 回退的"采集配置映射编辑器"不是一回事——那是 sync 采集任务的映射，这是 MDM 加工读侧的最小映射），识别确认来源时从源表列结构**自动按名称相似预填**（能默认就默认），弹窗内校对即可。

### 1.4 记录"查不到、看不懂"——后续一切环节失去承载

- `MdmRecordRepositoryAdapter.page` 的 keyword 只 LIKE `master_id`（MD5 32 位串）。业务人员想找"客户 张三 / 手机号 138xxx"完全不可能；对外服务 API 的"条件搜索"同名同实。
- 前端记录列表直接展示 `attributes`/`source_ids` 原始 JSON（`RecordTab.tsx:99-100`），来源显示 `{1: "C001"}`。
- **建议**：记录查询支持按属性值检索（`JSON_UNQUOTE(JSON_EXTRACT(attributes,'$.code'))` LIKE，属性编码走白名单校验，复用 `DedupSql.isValidAttrCode` 的防注入思路）；列表按实体属性定义渲染动态列（前 N 个属性 + 其余收纳），`source_ids` 解析为"数据源名: 原始 ID"。

### 1.5 审批是"半闭环"：通过之后可能什么都没发生

`MdmApprovalService.applyChange`（`MdmApprovalService.java:236-259`）：

- **CREATE/MERGE 通过后是空操作**，但提交端点接受这两种类型 → 申请人以为生效了，实际只改了 change 状态。要么实现，要么在提交校验中明确拒绝并提示走清洗合并/加工任务入口。
- `approvalLevel=2` 静默降级为 1 级（`MdmApprovalService.java:74-75`），一级通过即终态 → 与需求"一级数据管理员→二级治理负责人"不符。
- UPDATE 应用为**无界 JSON putAll**（`:262-267`）：不校验属性编码合法性、可以改 PK 属性 → PK 一改，attributes 与 master_id（=MD5(PK)）分家，来源追溯断裂。建议：拒绝改 PK、未知编码拒绝、只接受实体已定义属性。
- `applyChange` 用 `findByMasterId`（仅 ACTIVE）——记录若已被合并/删除，审批永远卡 PENDING 报错。需要终态策略（自动失效 + 通知申请人）。
- 状态校验-再更新非原子（无 version/状态条件更新），两审批人并发可双通过；错误码几乎全部借用 `RECORD_NOT_FOUND`（"内容超长"也抛"记录不存在"），44005 APPROVAL_FAILED 闲置 → 前端提示与排障全被误导。
- `withdraw` 用客户端 body 传 `operator`（`MdmApprovalController.java:86-87`），同实体其他人可冒名撤回；其余端点都走 `CurrentUserProvider`，标准不一致，属安全漏洞。

### 1.6 清洗：后端 57 全好、前端为零，且会打崩现有列表

- 标准化/补全规则只有 `/rules/typed`、`/transform/*` 端点，`services/mdm/api.ts` 无任何对应调用、清洗页无入口 → ticket 57 前端交付为零。
- 更糟：一旦经 API 建了 STANDARDIZE/COMPLETE 规则，它会混进清洗页去重规则列表，VO 的 `fields=null`（`MdmCleanRuleVO.java:44-50`）让 `record.fields.map` 直接抛错（`cleansing/index.tsx:323`）。前端至少要按 `ruleType` 过滤 + 分型渲染。
- **需求里的"保留/忽略该组"没有实现**：忽略只在前端选主记录时间接存在，重复组每次发现都会再出现，管理员处理不完也标不完"已知非重复"。需要 `mdm_dedup_ignore`（组键 + 规则 + 原因），并提供"撤销忽略"。
- `MdmMatchType.FUZZY` 仅 trim+lower，而产品文案写"姓名相似"（需求示例即"姓名相似"）——名不符实；短期把文案改成"去空格小写"，中期再考虑编辑距离/拼音。

### 1.7 采集状态与总览：入口页缺失（menu.md 设计的主流程地图没有）

- `CollectStatusTab` 采集状态列恒 `<Tag>待接入</Tag>`（55b sync 标签任务未做），"最近采集时间" nowhere 展示。
- 总览页是 ticket 50 占位（`overview/index.tsx`），后端 `/api/v1/mdm/overview` 已就绪。menu.md 3.1 的六卡（实体/采集/质量/分发/变更/血缘）一个未接。**总览是 menu.md 定的"主数据视角入口"，缺失导致用户只能靠 4 个平铺菜单自己拼流程**。
- **建议**：先接后端已有的实体分布/分发/订阅/待审批四卡 + 空态引导，采集/质量/血缘卡以"跳转 + 待接入"明示，不要显示假的 0。

### 1.8 分发与服务的"假闭环"比不通更危险

- `MdmDistributionService.execute` 什么都不推送，却写入 `last_distribute_time + 0 成功/0 失败` 并返回成功（`MdmDistributionService.java:222-234`）→ 运维/业务方看监控会认为"分发正常"。占位执行应返回"未接入"，**不得写成功时间戳**；`DAILY/HOURLY` 频率字段无任何调度实现，配置即摆设（要么接 job 调度，要么 UI 只放 MANUAL 并说明）。
- 查询 API `mdm:read` 平台权限 + 项目空间上下文，外部业务系统没有凭证通道；订阅 `notifyMode=WEBHOOK` 无通知实现、创建订阅 `operator` 硬传 null（`MdmServiceController.java:78`）丢审计。**分发/服务对接 data-service 的增量应升级为 P0 依赖**——否则"分发回各系统"（D6）与"供各系统调用"（D7）两条腿都是断的。
- 前端：分发配置 Tab、订阅区均为空态（`detail.tsx:106`），后端 58/59 API 全在——先把 Tab 接上。

### 1.9 删除引用校验挂点全部为空 → 可随时制造孤儿数据（数据完整性）

`MdmEntityService.isReferenced=false`（`MdmEntityService.java:200`）：删实体不检查属性/来源/记录/规则/分发/订阅/变更；来源解绑、规则删除同类挂点皆空。51/53/56 写"本期空实现"时后续 ticket 已完成，**挂点未回填是当前的实质缺陷而非计划内欠账**。删除一个有 10 万条记录的实体不会有任何警告。P0 补齐（有属性/来源/记录即阻断），并把错误码 44012/44014/44020 真正用上。

## 二、P1：业务闭环与建模缺口（流程通了之后补"可信"）

1. **合并后无 crosswalk，下游引用断裂**：被合并记录变 MERGED 后，按其 master_id 查询返回"不存在"（`findByMasterId` 过滤 ACTIVE），分发/订阅方拿旧 ID 无法解析。MDM 的立身之本是"旧 ID → 统一 ID"永远可查。建议：服务 API 对 MERGED 返回重定向语义（`mergedInto: 新master_id`），落 `mdm_record` 合并指向（merge_log 已有原料，缺高效查询结构）。
2. **master_id = MD5(PK 值) 与需求命题冲突要正面回答**：需求痛点是"同一客户在多系统 ID 不一致"（C001/cust_001/1001）。现方案下不一致的 ID 天然是三条记录，全靠人工去重合并收敛，且合并后每次重跑加工又会把被合并记录 UPSERT 回 MERGED 行（status 不回 ACTIVE，正确但需明示）。这是"规则统一 ID + 人工兜底"的混合模型，可以接受，但要在需求文档里把口径改写清楚，并给"待合并重复组存量"一个统计入口（治理视角的 backlog）。
3. **源系统删除无回流**：UPSERT 型加工没有差集下线逻辑，源删了主数据仍 ACTIVE。建议加工任务带批次号，支持"本批未命中 → 标记待核（DELETED 候选）"，配合审批下线。
4. **来源角色 MAIN/AUXILIARY 无约束也无消费**：可绑多个 MAIN；合并策略、补全优先级（"手机号缺失从交易系统补"）都应消费角色语义。当前角色纯装饰。
5. **版本管理达不到 requirement 3.5 的 v1/v2/v3 对比**：版本历史=change 列表（只有 patch 增量），无每次生效后的 attributes 快照，回看不了"当时长什么样"。建议 approve 应用后落快照（或 change 记录 before/after 双份）。
6. **并发与幂等**：`recordRepository.update` 无 version 条件 → 合并、标准化执行、审批应用可互相覆盖且无提示。记录表已有 version 列，做成乐观锁成本极低。
7. **57 的批量执行契约问题**：`listActiveByEntity` 一次 `LIMIT 10000` 全载内存处理，违背 home-overview-contract 的有界聚合原则；预览注释写"前 N 条"实际返回全部明细。改为 DB 侧统计受影响数 + 采样预览 + 分批应用（大实体上这是唯一可行形态）。
8. **治理 owner-check 不落地**：`operator` 由查询参数传入、空即放行（`MdmGovernanceService.java:54-60`），且只有 GET 消费它，写操作全不校验。要么把 owner 纳入写链路（并服务端取当前用户），要么砍掉该概念只信 RBAC——现状是最坏折中。
9. **实体状态机无门禁**：无属性的 DRAFT 实体可直接"生效"；"停用"不影响加工任务、订阅、分发。建议：生效前置检查（≥1 属性且 PK 唯一、≥1 来源）+ 停用提示下游影响面。
10. **加工 SQL 幂等细节**：`ON DUPLICATE UPDATE attributes=VALUES(attributes)` 会用来源覆盖清洗结果——今天跑标准化、明天重跑加工就被打回。需要"已清洗字段保护"（清洗后记录打标或以来源优先级合并），否则"清洗→加工→再清洗"循环里清洗成果不可沉淀。

## 三、P2：交互友好（对照 docs/INTERACTION_PRINCIPLES：能默认就默认、能选择就不填写）

1. **以实体为中心的流程动线**：识别/清洗/（分发/审批）都要各自重选实体、实体下拉都是 200 条全量拉。建议：URL 带 `?entityId=`；记住上次实体；实体详情页 Tab 内嵌记录/清洗入口（"该实体有 37 个待处理重复组"直达清洗页定位）。
2. **详情页空态 Tab 接真数据**：分发配置、变更记录、标准引用（后端 API 均已有）；质量/血缘按 menu.md 做成"跳转卡片"而不是空 Tab。
3. **属性归属用户选择器**：实体 owner 目前应为手输（`modeling/index.tsx` 表单直传字符串），应换平台用户选择组件；治理 owner-check 也依赖这个值。
4. **合并弹窗默认值与危险度**：默认第一条为主记录合理，但"被合并记录"默认全选 + 红色按钮——建议默认全选但把"预览"前置为必经步骤（现已禁用到有预览才可点，✅ 保持），并在预览里高亮将丢失的字段差异。
5. **去重发现动线**：规则列表行内直接放"执行发现"，别让用户在列表下方再选一次规则；规则改动后保留结果并提示重跑。
6. **加工 SQL 弹窗**："在数据开发中新建任务"目前裸跳转不带 SQL（`RecordTab.tsx:171-176`），用户复制粘贴易丢；改为注册草稿后跳任务编辑页（与 P0-1.2 同方案）。
7. **表格行键/时间格式**：重复组 rowKey 用 `matchBasis-total`（可为空串/重复）；时间 ISO 手工 `slice` 散落各处，统一平台格式化。
8. **搜索即得**：记录搜索框 placeholder"按 master_id 搜索"暴露了实现的贫弱——随 P0-1.4 升级为"名称/手机号/编码"多字段智能框（属性白名单）。

## 四、P3：UI 高级感与业务贴合

1. **总览讲成一个故事**：顶部横向"闭环管线"组件（采集→清洗→审批→分发，节点上挂实时计数与异常红点），下方实体卡片墙（每实体一卡：记录量、来源数、重复组待处理、订阅方）。比六个数字卡片更贴"主数据视角"，也让 P0/P1 各断点自然可视化成红色节点。
2. **审批/合并的 diff 语言**：变更内容与合并预览统一为"字段 × 各来源"矩阵 + 高亮差异（清洗页预览已有雏形），审批页直接复用——一套 diff 组件贯穿"合并/审批/版本"三处。
3. **状态语义统一**：DISABLED 红、DELETED 红、MERGED 金、DRAFT 灰——建议全局"错误红/中性灰/过程金/成功绿"语义审查；Tag 文案全中文（记录预览里现在直接展示 `ACTIVE` 枚举名）。
4. **色值 token 化**：`#242731/#667085/#f6f7f8` 硬编码遍布 mdm 页面，收敛到平台主题变量。
5. **空态引导保持并升级**：现空态文案（"先到建模定义实体，再到识别接入数据源"）方向对，补一键跳转按钮，形成页面间"指路"闭环。
