# 第一部分：需求文档

## 一、背景

### 1.1 现状

Yak Ops 数据平台已具备：
- **数据源管理**：连业务库
- **数据集成**：同步业务库到数仓
- **数据开发**：ETL
- **数据质量**：质量检查
- **数据建模**：数仓表设计
- **语义中心**：数据标准、业务过程、字段库
- **指标中心**（规划）

**缺口**：没有**主数据管理**，导致：
- 同一实体（客户、商品）在多系统里 ID 不一致
- 跨系统分析困难（同一客户被算成多个）
- 数仓维表从业务库直接抽，未统一多源

### 1.2 主数据是什么

**主数据**（Master Data）是**跨系统共享、相对稳定、描述核心业务实体**的数据。

**例子**：客户、商品、供应商、组织、员工、门店。

**特点**：
- **跨系统**：多个系统都用
- **相对稳定**：不像订单每天新增
- **核心实体**：描述业务的核心对象

### 1.3 主数据管理解决什么

**问题**：
- CRM 的客户是 `C001`
- 交易的客户是 `cust_001`
- 支付的客户是 `1001`

**后果**：
- 无法跨系统分析
- 同一客户被算成 3 个
- 数据不一致

**主数据管理解决**：统一"客户"的**唯一标识**和**核心属性**，各系统引用同一个主数据。

## 二、需求目标

| 目标 | 说明 |
|------|------|
| 统一 | 跨系统实体统一，唯一标识 |
| 一致 | 多源数据清洗、合并，形成一致性视图 |
| 可信 | 主数据质量可控、可追溯 |
| 分发 | 主数据同步回各业务系统 |
| 服务 | 提供主数据 API，供各系统调用 |
| 闭环 | 采集 → 清洗 → 审批 → 分发 → 反哺 |

## 三、功能设计

### 3.1 主数据建模

**界面**：主数据实体 + 属性 + 关系。

```
主数据建模
├── 实体：客户
│     ├── 属性：
│     │     ├── 客户ID（PK）
│     │     ├── 客户名称
│     │     ├── 手机号
│     │     ├── 地址
│     │     └── 等级
│     └── 关系：
│           ├── 客户 → 订单（1:N）
│           └── 客户 → 地址（1:N）
```

**要求**：
- 属性引用数据标准（类型、单位、码值、安全）
- 支持关系定义
- 属性可标记必填

### 3.2 主数据识别

**界面**：从数据源发现主数据。

```
主数据发现

├── 识别候选：
│     ├── CRM.customer → 可能是"客户"主数据
│     ├── 交易.order → 业务数据
│     └── ...
└── [确认为主数据]
```

**要求**：
- 扫描数据源
- 识别候选主数据
- 用户确认

│     ├── 采集频率：每天
│     └── 字段映射：
│           ├── CRM.cust_id → 客户ID

**要求**：
- 支持多源采集

### 3.4 主数据清洗

**界面**：去重、合并、标准化、补全。

```

├── 去重：
│     ├── 发现 100 组重复客户

│     └── [合并/保留]
├── 合并：
│     ├── C001（CRM）+ cust_001（交易）
│     └── → 合并为 C001
├── 标准化：
│     ├── 性别：M/F → 1/2
│     └── 地址：浙江省杭州市 → 浙江杭州
└── 补全：
      ├── 手机号缺失 → 从交易系统补
      └── 等级缺失 → 默认"普通"
```

**要求**：
- 去重规则可配置
- 合并策略可配置
- 标准化引用数据标准
- 补全规则可配置

## 九、关键设计决策

### 决策 1：主数据从业务库取，不是从数仓取

**理由**：业务库是源头，数仓是消费层。

### 决策 2：主数据和数仓维表是上下游关系

**理由**：dim_customer 引用 MDM.customer，不重复采集。

### 决策 3：主数据有唯一 ID（master_id）

**理由**：跨系统统一。

### 决策 4：主数据有来源映射（source_ids）

**理由**：记录各系统原始 ID，便于追溯。

### 决策 5：主数据变更需审批

**理由**：保证质量。

### 决策 6：主数据分发回各业务系统

**理由**：形成闭环。
