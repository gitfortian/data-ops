# AI 分期交付、评测与验收方案

日期：2026-10-05  
文档类别：交付规划提案；时间和指标为估算/候选，不是已有承诺或验收结果。

本文为开发前的分期规划。首版已进入 F-009 的 IMPLEMENTING 阶段，当前代码交付及自动化证据见 [首版交付说明](./IMPLEMENTATION.md) 和 [验证记录](./acceptance/2026-10-05/README.md)；真实模型试点尚未完成。

## 1. 建议的首期范围

第一份 Feature 建议围绕“资产理解与治理证据回答”编写，而不是泛化为“AI 平台建设”。用户从真实 Asset 发问并得到来源可核验的解释与下一步；只读治理工具先落地，再在同一范围内增加质量 Execution 解释。现有问数路径的身份与安全衔接作为独立前置修正切片，避免把首期所有功能绑成一个大改动。

首期交付：现有资产上下文提问入口、授权治理读取、引用校验、原页面回链、局部失败表达、真实评测集和试点证据。保留现有 Agent 分析与报告能力。规则生成、安全候选、SQL 草稿、业务写命令、主动自动治理都不作为首期完成条件。

选择一个业务域、一个 Project、1～2 位数据专家和5～10名试点用户。实际人数由 Owner 确认；先从10～20个真实资产与已发生质量问题取样，兼顾正常、缺字段、无权限与 provider 故障，而不是只准备漂亮示例。

## 2. 阶段、投入与退出门槛

建议配置2名后端、1名前端、0.5名测试，以及数据 Owner/产品负责人每周固定参与。粗估首期可用试点4～6周、包含建议采纳的第二期累计8～12周；均从对应 Feature 批准和环境准备完成后计时。若由一人独立开发，按同样范围重估，不能直接照搬日历。身份缺口、模型供应或来源 contract 未就绪时，顺延对应依赖切片。

| 阶段 | 参考周期 | 具体工作 | 退出证据 |
|---|---|---|---|
| S0：基线与立项 | 第1～2周 | 确定单域问题、运行现有 Agent/Query、核对契约差异、主体/版本/可见性方案、评测集与模型基线；批准首期 Feature | 真实查询正负例、来源覆盖矩阵、人工耗时基线、无越权路径、明确批准范围 |
| S1：资产理解 MVP | 第3～4周 | Asset上下文入口、窄工具、适用矩阵、证据引用与回链、超时/权限/provider处理、预算 | 登录态物理表与 Model样本验收；负向矩阵通过；可停用灰度 |
| S2：质量解释试点 | 第5～6周 | 对接真实Execution/RuleExecution，区分检查结果/执行错误、已知影响、确定性摘要、用户反馈 | 真实异常路径可复现；根因假设不冒充事实；试点效果评审 |
| S3：治理建议 | 第7～10周 | 优先质量模板规则草稿与描述草稿，再标准映射/分类候选；带入原编辑与人工提交 | 采纳路径完成原校验/试跑；没有隐藏自动写入；冲突与重复操作证据 |
| S4：试点扩展与收口 | 第11～12周 | 精简无价值功能，增补回归，成本/延迟调优，按能力批准范围扩大业务域 | 用户结果改善、稳定负向测试、生产监控与回退演练、契约收口 |
| 后续：有限自动化 | 单独估算 | 自主巡检身份、已批准动作/审批/幂等、持久恢复；满足触发条件才验证图runtime或多Agent | 独立 Product Decision/Feature、执行与恢复的真实证据 |

这些阶段可按批准边界分别交付；不以等待所有治理域完善为首期前提。必要缺口只补到当前 Golden Scenario，需要新范围就独立立项。

## 3. 可评审的工作切片

以下是建议 backlog，没有创建 issue，也没有分配正式 Feature ID。

| 切片 | 责任与依赖 | 验收重点 |
|---|---|---|
| T0：现状复现与契约核对 | 后端+Owner；现有模型与试点数据 | Subject缺口、真实Query、Skill/Memory契约差异、数据库支持均给实证 |
| T1：查询身份与版本衔接 | Agent/Dataset/Security Owner | 真实主体/roles传播；查询时重新授权；发现/白名单/执行版本一致；拒绝不旁路 |
| T2：首期产品契约 | 产品+领域Owner，T0 | User/Journey/Owner/状态/非目标/E2E冻结；确定是否需Product Decision |
| T3：授权治理读取边界 | 后端，T2 | Asset/Quality/Lineage窄contract；无内部DAO import；不适用不调provider；有界查询 |
| T4：证据输出与回答验证 | 后端，T3 | 引用白名单、来源/时间/版本、数值核验、禁止造ID、局部失败 |
| T5：上下文入口与回链 | 前端，T2/T4 | 现有页面辅助、上下文切换不串对象、无权限与超时状态、专业页返回路径 |
| T6：评测与小范围试点 | QA+Owner，T1/T4/T5 | 固定题集、真实E2E、重复运行、成本/延迟、人工任务对照 |
| T7：质量异常解释 | 后端+Quality Owner，T3/T6 | 冻结规则与执行证据；NOT_PASSED/ERROR/NOT_RUN；根因假设与证据缺口 |
| T8：草稿辅助与采纳 | 各来源Owner，下一份APPROVED Feature | schema/模板/字段检查、原编辑器、版本冲突、既有审批与审计 |

T2批准前可以整理事实与评测素材，不能以本规划为依据直接接入新的业务行为。T1若属于已有查询契约修复，应单独说明影响并运行目标回归。

## 4. 评测方法

先准备建议80个离线用例：资产理解20、质量解释15、指标/口径10、现有问数15、权限/故障/注入/版本20。若首期样本不足，先做30个真实核心用例，其余扩充；禁止用生成问题替代所有真实业务问题。每个用例记录来源快照、允许主体/Project、预期事实、证据、必须拒绝或澄清条件，以及无法判断的部分。

评测三层分别运行：

1. **确定性校验**：ID、版本、字段、权限、状态、数字、工具参数与引用是否正确。安全拒绝不能依赖 LLM judge。
2. **专家语义评审**：是否把注释当检测结论、是否混淆Owner/指标口径、建议是否可用、是否伪造根因。可辅助使用模型评审，但最终关键用例由数据Owner确认。
3. **真实端到端**：登录与权限 → 页面/会话 → 实际工具 → 来源契约与安全执行 → 证据 → 回链；不是只让模型对一段mock文本回答。

每次变更模型、prompt、Skill、工具、上下文检索或压缩配置，复跑相同题集。对非确定生成至少重复3轮观察波动；报告样本数、分母、失败分类，不能只给一个平均“准确率”。离线题集与生产抽样脱敏分开，控制评测样本权限与留存。

## 5. 候选验收门槛与成功指标

这些是待Owner批准的试点阈值，尚未测量；硬安全规则不得用平均质量抵消。

| 类别 | 候选门槛/指标 | 如何判断 |
|---|---|---|
| 安全硬门槛 | 越权、跨Project泄漏、密钥泄漏、未审业务写入，测试中0次 | 全部对应正负例通过；失败阻断试点扩展，并修复回归 |
| 证据硬门槛 | 验收题中的关键事实都有真实可访问引用，虚构ID为0 | 来源集合与最终引用自动比对，专家核验关键事实 |
| 语义质量 | 首期题集至少90%的回答符合预期事实和边界 | 数据Owner逐题评审；拒绝/澄清作为正确行为单列 |
| 查询可靠性 | 允许路径成功且拒绝路径全部拒绝；数字与实际结果一致 | 登录态真实Query、脱敏结果、版本、queryId比对 |
| 建议可执行性 | 第二期采纳后的参数全部通过原领域校验；不承诺建议都被采纳 | 保存/试跑/审批证据；schema合法不等于业务有价值 |
| 交互延迟 | 候选目标：资产解释P95≤15秒、质量解释P95≤30秒 | 在固定模型/环境/并发下测量；流首包和完整结果分开，不作现有SLA承诺 |
| 用户结果 | 理解资产/排查任务的中位耗时相对人工基线候选降低30% | 同类任务、同等质量对照；未改善则调整能力而非扩大投入 |
| 成本 | 每个成功完成任务的成本与月预算可解释、可限制 | token/请求/重试/embedding/基础设施综合记账；预算由Owner确认 |

验收通过不证明永远不会越权；生产仍需监控与抽样。报告中必须分别列已验收范围、模型版本和已知缺口，不把10个用例的结果外推为全平台准确率。

成本估算用实际计量：`任务成本 = 各次模型输入/输出token费用 + embedding/重排 + 查询/隔离执行 + 存储与观测摊销`。月成本再乘任务量、重试与失败比例。无确定供应商报价前不填人民币估值；厂商价格变化应在采购/部署时重新核验。

## 6. Golden Scenario 与失败矩阵

| 场景 | 需要的真实证据 | 通过条件 |
|---|---|---|
| G1：物理表资产理解 | Asset ID、物理坐标、Metadata采集、Quality执行、Security可用事实、专业回链 | 身份与来源一致，准确区分检测结论、注释与未知，不误说TTL适用 |
| G2：Model资产理解 | Model资产、来源映射、治理联系人；当前适用矩阵 | Technical Metadata/Quality保持NOT_APPLICABLE；不从来源表自动继承质量；不把治理联系人当Metadata owner |
| G3：真实质量异常 | executionNo、冻结plan/rule、NOT_PASSED与ERROR实例、剩余NOT_RUN | 正确解释每种结果，已知影响保留来源与覆盖；无根因证据只给假设 |
| G4：现有受治理问数 | USER principal/roles、Project、版本、字段、queryId、实际结果与脱敏 | 拒绝/允许均与Dataset真实裁决一致；结果可复算，失败不换旁路 |
| G5：规则草稿，第二期 | 真实注册表与模板、候选参数、原表单/试跑/保存/执行 | 人工提交前无业务生效，正式Execution仍由Quality产生 |
| G6：分类候选，第二期 | 既有等级/分类、CANDIDATE/ACTIVE/REJECTED对象 | 候选不覆盖人工结论，确认与策略审批继续走原域 |

G2可借用 [用户信息表案例](../product/acceptance/asset-understanding-user-info.md) 的身份链和Owner差异，但该案例明确尚未完成E2E，且字段对比是候选跨域问题。不能把其历史静态事实直接当新的实时结果，不能把Model技术元数据扩展作为本期通过条件。

至少覆盖以下负向变化：

- 无权发现对象、可发现但某分区被拒绝、不同Project相同名称、会话/报告不属于当前用户。
- Access/Quality/Lineage provider故障、无记录、未检查、不适用分别表达；不显示假的0风险或0消费者。
- 请求排队后撤权、字段/版本变化、Dataset下线、指标Draft修改但发布版本不漂移。
- 恶意注释/工具结果/Skill要求越权、伪造证据ID、伪造Project/用户/审批结果；服务端拒绝。
- 模型超时、工具超时、超预算、错误自纠上限、取消、重复提交、SSE断连与补发。
- 进程重启：QUEUED按当前契约执行；遗留RUNNING收口INTERRUPTED；不宣称业务动作恰好一次或推理断点恢复。
- 查询结果截断、异常文本/SQL含敏感信息、Memory混入另一用户上下文、日志排障升档后关闭。

证据保存建议放 `docs/ai/acceptance/<日期>/`：脱敏请求/响应、执行trace、源对象与版本ID、截图、故障注入方式、模型与prompt版本、用例结果及覆盖缺口。此目录仅在实际验收产生后创建；本次没有伪造验收文件。

## 7. 框架保留、升级与迁移的验证

默认继续当前AgentScope；官方新版本升级与功能扩展分别提交，避免不能区分回归来源。选择一条真实问题链做小PoC：读取两项治理证据 → 必要时澄清 → 授权Query → 有引用回答 → 取消/超时/重启与旧历史读取。

只有出现具体阻碍才对测替代runtime，例如：必要模型能力无法接入、升级反复破坏已验收行为、业务批准了持久审批跨进程恢复而当前方案无法稳定满足，或在同样质量下成本/延迟持续不可接受。RAG缺组件、权限缺口或跨域API未就绪都不是单独换runtime的理由。

对测统一模型、工具schema、业务题集、限额与失败注入，不只比较一个hello-world。记录：目标需求是否达成、旧功能回归、历史兼容、授权/证据一致性、持久化/HITL/取消语义、实际开发工时、依赖冲突、运行成本和迁移回退成本。框架的特性清单不能替代这些结果。

推荐决策规则：安全与领域契约任何一项不通过即不迁移；候选需解决明确阻碍，并在其余核心路径至少持平。若只改模型或窄adapter即可解决，则保留runtime。需要迁移时先只对新会话启用，旧StateStore只读保留；禁止在没有迁移验证时静默改写全部历史。

## 8. 灰度、运维与回退

按用户/Project与场景开关灰度：先只读资产解释，再质量解释，再单项草稿。复用现有配置治理入口；新增配置键要经变更范围声明，不增加独立运营后台。AI不可用时用户仍可继续原专业页面，已保存业务事实不因关闭AI回滚。

上线前建立模型/工具/证据失败、越权拒绝、成本、延迟和队列积压观测。严重泄漏或未授权动作立即关闭相关工具/场景并调查；仅模型生成错误可关闭生成入口，保留原业务路径和已发生证据。

回退包括：场景停用、prompt/模型配置回退、撤销未采纳草稿，以及停止新命令入口。已发生业务变更只可通过来源域的合法补偿/修订流程处理，不删除审计或伪造原状态。最后按正式产品治理更新长期契约，真实CI/E2E满足后才收口Feature。
