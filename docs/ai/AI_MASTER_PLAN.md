# DataOps AI 建设总纲：从可信问答走向数据工作的智能辅助

日期：2026-10-07

类别：DOCS / 战略规划提案

状态：供产品与研发确定下一阶段方向；本文不批准新业务行为，也不替代 ACCEPTED Product Decision、APPROVED / IMPLEMENTING Feature 或领域契约。

基线：`main @ 944da89a`，V12～V14 已合并；工程交付、真实模型验收、产品收益分别记录。

方向补充：用户明确采用“固定流程拆场景、Skill 适配业务、Agent 完善通用底座”；框架能力优先复用 AgentScope Java。本次 2.0.3 依赖升级与能力调研单独验证，详见 [官方能力复用分析](./AGENTSCOPE_2_0_3_REUSE_RESEARCH.md)。下述场景框架扩展仍须按 Feature 实施。

## 1. 核心判断

**最终目标是让 DataOps 成为能辅助用户完成数据生产与治理工作的智能平台：用户提出目标，AI 帮助理解上下文、准备设计、填写配置、检查差异、解释问题；用户在原业务流程中确认，平台依照原权限和领域规则生效，并能回到真实结果核验。**

对话查询分析是重要入口，也是当前 Agent 的基础能力。AI 的长期产品价值还应体现在标准维护、模型设计、指标定义、开发配置和治理处置等日常工作中，直接减少重复查找、手工录入、逐字段映射与跨页面核对。

建议用三个层次理解产品形态：

| 产品形态 | 用户如何使用 | 主要产出 |
|---|---|---|
| 当前工作台里的 AI 辅助 | 在字段、标准、模型、指标、执行详情旁发起一个具体任务 | 可核对的解释、结构化候选、差异、检查项；可选择带入当前未保存表单 |
| 现有 Agent 中的跨域对话 | 描述目标、发现对象、澄清问题，进入正确的专业工作台 | 带来源的回答、任务建议和稳定回链；保持当前范围与授权边界 |
| 以后按授权开展的主动辅助 | 在既有告警、待办、审批或运行入口看到建议 | 待人工核查的异常摘要与变更影响；有限执行另行批准 |

三种形态复用同一套身份、证据、模型运行、预算和观测能力。标准、模型、指标仍由各自源域拥有；不需要先为每个菜单创建一个独立 Agent 或新的一级 AI 门户。

**建设方式采用“原业务流程控制生效 + 场景 Skill 描述工作方法 + AgentScope 提供执行机制 + 平台适配守住业务边界”。** 固定流程中的确定性步骤交给程序执行，理解、匹配、解释和草稿创作交给加载相应 Skill 的 Agent。业务方法和输出说明尽量通过 Skill 迭代，新权限、新领域规则和新执行能力仍通过代码契约实现。

## 2. 服务谁、解决什么、结果由谁拥有

| 必答项 | 总纲的回答 |
|---|---|
| 用户（User） | 数据标准管理员、数据建模人员、指标 Owner、数据开发人员、治理与运维人员、数据分析人员 |
| 问题（Problem） | 业务知识分散，配置字段多，标准匹配与来源映射耗时；定义不一致容易在后续发布、运行和消费中暴露；用户需跨页面拼上下文 |
| 能力（Capability） | 在既有“标准、指标与建模”“开发与运行”“数据资产与治理”“数据消费与服务”中加入任务级智能辅助 |
| 用户旅程（Journey） | 优先改善 J2 的标准→模型→指标→验证→发布→消费；保留 J4 排查与 J6 证据问答，并逐步覆盖 J1/J3/J5 |
| 期望结果（Expected Outcome） | 更快完成经用户确认、通过源域校验的真实业务任务，减少重复输入和返工；产物有来源、可编辑、可核验 |
| 事实归属（Truth Owner） | Semantic 拥有标准与业务语义；Modeling 拥有模型和版本；Metric 拥有指标、验证、发布与引用；其它事实仍由原域拥有。AI 候选不成为第二份业务真相 |
| 生产方 / 消费方 | 源域公开查询、校验、命令及运行证据生产事实；AI 消费授权上下文；用户和原工作台消费 AI 候选；保存后由源域回读结果 |
| 复用 | Project Space、RBAC、原标准助手、导入/派生/映射、版本与 diff、源域校验、既有审批适用路径、审计、告警、Dataset 查询、现有 Agent 运行底座 |
| 端到端证据 | 原任务入口→真实授权读取→有依据候选→用户修改/选择→原源域保存/验证→回读一致结果；包含无权限、漂移、歧义、失败与重复提交反例 |

## 3. 当前走到哪里，为什么看起来主要在做聊天

### 3.1 已有工程能力

| 方向 | 当前实现事实 | 仍不能据此宣称 |
|---|---|---|
| 对话分析 | Dataset 发现、字段读取、结构化查询、澄清、分析报告、执行追踪；Python 默认关闭且另有运行限制 | 任意物理库自由问数、直接 SQL 执行、所有指标都可直接查询 |
| 治理理解 | 从资产和质量历史执行进入；只读源证据、五态说明、事实卡与回链 | 自动确认根因、全量治理覆盖、自动修复 |
| 治理创作 | 资产描述与质量规则候选；原编辑器人工核对、带入、条件保存；规则候选固定停用 | 标准、模型、指标已经具备同等 AI 创作闭环 |
| 任务可靠性 | 轮次身份、同轮反问、预算、精确停止、历史关联、断线核对、晚响应隔离、报告安全导出 | 真实模型质量和用户收益已验证、运行中崩溃可原地续跑 |
| 标准/建模/指标的业务底座 | 已有规则版标准推荐、标准字段绑定、模型导入/派生/结构校验/版本、指标定义验证/精确版本发布 | 这些既有功能本身就是 LLM 能力，或已对 Agent 开放全部读取/写入 |

V1～V14 是工程迭代编号，不能等同于 14 类新的业务智能能力。近期 V5～V14 大量工作用于让现有建议、会话、证据与留存可靠，业务覆盖面增长相对有限。这个投入解决了真实工程问题，但下一阶段的新增价值应更多来自业务工作量下降。

**当前重心是“对话分析 + 只读治理解读 + 两类人工采纳候选”；下一阶段建议把主要产品投入转向“标准、建模、指标中的工作台辅助”。** 现有问答继续维护和针对错题改进，会话通用能力优先处理已证明影响用户任务的缺口。

### 3.2 证据与文档的边界

V12～V14 的最终工程 CI 通过，前端 712 项测试、Agent 262 项测试通过（含 MySQL、零跳过），见 [#329](https://github.com/gitfortian/data-ops/pull/329)、[#330](https://github.com/gitfortian/data-ops/pull/330)、[#331](https://github.com/gitfortian/data-ops/pull/331)。真实模型、登录态端到端及专家语义评分仍待完成，不能从测试数量推导业务正确率或效率收益。

历史 [首期规划](./AI_PRODUCT_PLAN.md) 中“治理读取待设计”等表述是当时快照，当前治理读取与描述/质量规则候选以 F-009/F-010 及后续 IMPLEMENTING Feature 为准。历史计划里写到的标准映射、指标解释、主动巡检仍是提案，不因列入路线自动成为已实现能力。

当前部分架构说明也带有早期阶段描述。例如 Metric 文档列举 `MetricQueryApi`，实际可核对的只读 SPI 位于 `data-ops-common`，且仅有按 ID 读取启用指标的视图；`ModelQueryApi` 只有模型概要与最新版本号。不能把接口名称当成“已提供精确版本全文、授权搜索与证据”的证明。立项时按当前领域规则核对源码，缺少的窄契约先由 Owner 明确，不直接扩大 Agent 权力。

## 4. 最终目标与能力进阶

建议按用户能够完成的工作深度演进。下表是规划分级，不是新增业务状态机、权限级别或产品术语。

| 阶段 | 用户结果 | 典型例子 | 进入下一阶段的依据 |
|---|---|---|---|
| 理解 | 能解释对象、定义和问题，找到来源 | 解释一个指标的口径、版本、已知依赖和缺失证据 | 固定真实案例中，事实引用、权限和未知项表达可核对 |
| 创作 | 能准备可编辑候选，减少录入 | 为一批字段推荐已有标准；为指标准备完整定义草稿 | 候选符合源域结构，用户修订后能保存，收益可测 |
| 协同完成 | 能沿已有路径完成多步业务任务 | 标准引用→模型字段→指标定义→人工验证与发布→消费回链 | 每一步均可回源，版本不漂移，局部失败可定位 |
| 主动辅助 | 能在问题发生或变更前提供检查建议 | 将已有告警和已知影响整理成待办 | 检查范围、执行身份、权限变化、误报与成本有依据 |
| 有限执行 | 在明确批准的范围内执行特定动作 | 将来对低风险且可撤销的动作提供受控提交 | 逐动作完成产品决策、授权、幂等、审计、失败核对与补偿设计 |

**中期目标是做到“高质量创作 + 原流程协同完成”。** 全自治治理不作为当前承诺；是否开放执行，按具体任务价值与可控性决定。完成标准是业务任务有真实产物和结果，模型停止输出只是推理结束。

## 5. 数据标准：从逐项维护到有依据的批量准备

### 5.1 主要任务与产品形态

| 高频工作 | AI 辅助内容 | 用户看到的产物与下一步 |
|---|---|---|
| 为字段找标准 | 结合字段名、描述、类型、业务过程及已有标准，推荐已有标准/标准字段 | 原字段→候选引用→匹配理由→冲突/缺口；逐项选择，带入当前编辑器 |
| 补描述和命名 | 生成业务描述、命名候选，说明与已有命名规则的关系 | 当前值与候选值并列；用户可编辑，编码已创建不可改的规则保持 |
| 准备标准字段 | 推荐角色、类型、单位、码集等已有引用，指出缺少的前置标准 | 标准字段表单草稿；角色相关必填和不适用项由 Semantic 校验 |
| 整理新标准草案 | 将用户明确提供的业务说明整理为六类标准中相应的结构 | 既有标准对照、草稿、待确认项；复用原新建/沉淀入口人工提交 |
| 排查重复与冲突 | 提示同名异义、同义异名、单位/码集差异和已知引用 | 比较清单；人工决定复用或另建，不自动合并、删除或批量改引用 |

第一切片建议从**“在模型字段编辑器里批量推荐已有标准”**开始：既有源字段与人工采纳点清晰，可以复用规则版 `StandardRecommendApi`、标准发现与标准助手。先做小批量候选核对，再扩展标准字段和新标准创作。

### 5.2 规则与模型如何分工

规则引擎负责已有精确匹配、类型约束、启用状态与合法性判断；LLM 补充同义表达理解、业务上下文匹配解释和描述草稿。不能为了使用 LLM 替换已有确定性规则，不能让模型绕过类别校验。

候选必须引用当前项目可读、类型匹配的真实对象。码集引用使用 `code_set_code`，其它标准使用对应 ID，不能把码值行 ID 当码集。标准字段的角色约束沿用 Semantic：类型必填；度量单位必填、默认口径可选；指标最终口径可以覆盖字段默认口径。

“支付金额”缺少匹配标准时，应列出缺项并进入人工创建标准路径。不能编造一个标准 ID，也不能自动创建单位、口径、安全等级以使表单看起来完整。`StandardCaptureApi` 已有写能力，不意味着允许模型直接调用。

### 5.3 验收与前置条件

固定案例覆盖：精确匹配、同义字段、一词多义、无匹配、错误单位、停用标准、跨项目、撤权、草稿已修改、同一候选重复采纳。成功路径必须到达原编辑器保存及回读。

先核实授权且有界的标准/标准字段搜索、标准详情与版本证据契约；当前 `StandardQueryApi` 的单项读取与标签解析不足以单独承载完整搜索。新增源读取停在 Agent gateway，按 Feature 更新依赖约束。默认只用元数据和业务说明，不读取业务行样本。

## 6. 数据建模：从手工拼结构到设计与映射辅助

### 6.1 主要任务与产品形态

| 高频工作 | AI 辅助内容 | 产物与人工决策点 |
|---|---|---|
| 从业务过程开始建模 | 梳理粒度、实体、字段角色与尚未明确的业务假设 | 原建模向导中的设计候选；先确认粒度与来源，再带入字段 |
| 逆向导入后治理 | 为原字段准备标准绑定、注释和类型差异说明 | 原字段列表内逐项核对，不替换源端采集事实 |
| 来源字段映射 | 结合真实上游字段与目标字段给出映射/转换候选 | 一行一个明确来源与候选表达式；未匹配、歧义保持可见 |
| 表关联设计 | 对用户选定的表说明关联候选、键与基数假设 | 关系候选，不凭名称相似确认外键；需要用户核查和原域校验 |
| 分层设计与派生 | 解释现有分层、业务过程、标准字段和上游模型的组合 | 复用现有 ODS 导入与各层派生预览，用户选择后保存 |
| 变更核对 | 解释源结构/模型版本 diff，整理受影响映射和检查项 | 原版本/影响页面中的说明，用户决定如何修改和再发布 |

建议先做**已有模型的字段治理与来源映射**，再做“自然语言业务需求→逻辑模型/多表设计”。前者有实际字段和源域规则可核验，后者涉及粒度、主键、关联基数和历史处理策略，需要更强业务确认。

### 6.2 源域边界

- 一个物理模型仍对应一张物理表；逻辑到物理的生成沿用原能力。
- 来源映射是加工 SQL 生成的事实来源；AI 候选被人工保存前不成为来源映射事实。
- 字段顺序、主键、索引和分区引用必须经原结构校验；AI 不能因修正某一字段而静默删除或重排其它字段。
- 模型结构保存为全量替换。实施前必须验证源域并发前置条件；不能将 Asset/Quality 已有指纹保护当作 Modeling 自动具备的能力。缺少时先在 Modeling 明确最小保存保护，避免旧 AI 候选覆盖新结构。
- DDL 继续由保存后的模型结构按方言生成文本，平台内不执行；源变化不自动修改模型；血缘登记保持既有人工确认规则。
- Development 才拥有加工任务与执行。AI 映射建议、DDL 文本、加工草稿与真正执行保持区别。

### 6.3 验收与前置条件

固定一个包含同名列、金额单位差异、空值、缺少关联键的业务过程：导入→标准匹配→映射候选→人工选择/修改→原结构与映射校验→保存回读→原版本预览。额外核对切换模型、草稿修改、目标方言变化、源字段消失和并发保存。

模型概要 SPI 不能替代精确结构、映射与版本读取。先由 Modeling 提供窄的授权读契约和候选校验位置；对无法证明基数或转换语义的项，明确保持待确认。

## 7. 指标：从填定义表单到口径澄清与验证辅助

### 7.1 主要任务与产品形态

| 高频工作 | AI 辅助内容 | 产物与下一步 |
|---|---|---|
| 查找和复用指标 | 从业务问题匹配已有指标，解释适用范围 | 候选指标、精确发布版本、差异、回链；无稳定消费映射时不取数 |
| 新建指标 | 澄清业务事件、粒度、时间、金额/数量单位、过滤条件、退款与去重规则 | 原指标编辑器中的结构化定义草稿；未知项列为待确认 |
| 选择定义依赖 | 推荐已有业务域/过程、口径、单位、模型、上游指标 | 真实引用及其版本；与当前表单对照后人工采纳 |
| 组合与派生 | 生成符合已有 ATOMIC/DERIVED/COMPOSITE 类型约束的候选 | 原类型字段或组成 token；环、角色、引用与必填由源域校验 |
| 解释验证失败 | 将源域定义验证的阻断项与警告解释成具体修改步骤 | 指向字段、依赖、精确版本的检查清单；用户修改后重新验证 |
| 发布前核对 | 比较 Draft 与 active published version，解释单位/口径/依赖变化和已知影响 | 版本差异与影响清单；原发布操作由有权限用户明确执行 |

建议顺序：**先指标口径/版本/验证结果解释，再做指标定义草稿。** 新建草稿不能只生成一个漂亮名称和公式；至少把粒度、时间口径、过滤、单位、引用和未知项表达清楚。

### 7.2 关键产品约束

指标是受治理的业务定义，不能直接等同于可执行 Dataset。依据 [PD-003](../product/decisions/PD-003-business-semantic-metric-contract.md)：

- `Metric`、不可变 `MetricVersion`、Validation、Publication 分别表达不同事实；保存、启用、验证通过均不自动等于发布。
- AI 解释必须明确读取的是当前 Draft、某个历史版本还是 active published version。新下游稳定引用遵守原精确发布版本契约。
- 定义合法性由 Metric 校验；LLM 自检不写为 Validation PASSED。
- 数据/执行验证仅在实际存在授权 provider 时进行；不可用或不适用不能伪造通过。分析取数继续经 Dataset 结构化查询，不新建语义查询引擎。
- 指标引用记录、技术血缘、实际消费证据分开解释；缺失 provider 不表示“零影响”。

### 7.3 验收与前置条件

固定“支付金额”案例，让用户明确是否扣除退款、按支付还是下单时间、币种/单位、交易粒度与重复支付处理。AI 必须先展示/询问缺项；按用户明确选择准备草稿，经原校验保存。之后验证精确版本、由用户发布，再修改 Draft，确认发布版本与下游引用保持稳定。

先核对 Metric 已有版本、validation、publication、readiness 与 impact 的可用授权契约。源码中按 ID 读取启用指标的 `MetricQueryApi` 不足以提供全部上下文，不能用当前定义补写历史版本。新增读取和候选填入按独立 Feature 扩展。

## 8. 其它功能如何获得 AI 能力

以下是能力候选地图，不是本次授权的实现范围。每个场景仍需源域契约、权限与验收。

| 工作环节 | 优先适合 AI 的工作 | 保留给原流程的生效点 | 建议顺序 |
|---|---|---|---|
| 元数据与资产 | 描述草稿、字段含义、重复描述核对、治理覆盖说明 | 原描述/标签维护；不覆盖物理采集事实 | 复用已有描述能力，按试点扩展 |
| 质量 | 规则参数准备、历史结果解读、排查清单；后续比较两次执行 | 原模板校验、保存、显式运行；跨执行只比真实冻结证据 | 维护已有；源比较契约就绪后扩展 |
| 数据开发 | 来源映射、转换表达式/任务配置草稿、错误说明、发布前检查 | 原开发编辑器、校验、预览、发布与运行 | 在模型/指标路径之后；SQL 创作另设 Feature 与归属边界 |
| 同步与集成 | 字段映射、类型差异、配置说明、运行错误解释 | 原同步配置与启动；不向模型暴露连接凭据 | 只在当前有效集成契约内立项，PD-004/F-006 未批准的变化暂缓 |
| 安全治理 | 基于元数据和既有字典的敏感分类候选、策略差异说明 | 原分类确认、权限与策略适用流程 | 另行试点；不因模型置信度授予权限 |
| 血缘与影响 | 汇总已知依赖、订阅、引用、实际使用，准备变更核查项 | 关系事实由各源域维护，用户核查未知覆盖 | 与指标/模型变更解释协同 |
| 主数据 | 规则/属性草稿、冲突说明；后续疑似重复与保留值候选 | 原受保护字段规则、人工确认及适用审批 | 涉及记录样本与合并时单独立项 |
| 生命周期 | 解释既有策略、使用证据与影响，提供人工检查项 | 原适用对象与预演/确认动作 | 更后续；无使用证据不认定闲置，不自动删除 |
| 分析与消费 | 问题澄清、发布口径引用、受治理取数、结果解释、报告 | 原 Dataset/消费权限与使用证据 | 持续根据真实错题改进 |

## 9. 共用的交互闭环：让 AI 直接减少工作量

```mermaid
flowchart LR
    A[在原工作台选择具体任务] --> B[读取授权对象与当前草稿]
    B --> C[澄清缺项并生成结构化候选]
    C --> D[展示依据、差异和待确认项]
    D --> E[用户选择并带入未保存表单]
    E --> F[源域重新授权和校验后保存]
    F --> G[按原流程验证、发布或运行]
    G --> H[回读真实结果并查看来源]
```

标准、建模、指标的按钮应表达用户动作，如“推荐标准”“准备映射”“生成指标草稿”“解释验证问题”。自由对话保留为补充方式；日常高频任务尽量通过选择、表格核对和少量补充完成。

候选的共同呈现要求是：原对象与来源、当前值、建议值、引用依据、未知项、可选动作。批量场景提供逐项选择和局部结果，不强迫用户复制聊天 Markdown 再手工拆成几十个字段。

AI 可以读用户当前未保存的草稿用于建议，但必须标明“当前表单输入”，不能当成服务器已经保存的定义或历史执行事实。带入时重新检查草稿是否变化，不覆盖用户后续编辑；保存时由源域核对当前版本/前置条件。普通手工操作与 AI 采纳走同一个业务生效入口。

对于批量处理，要分别说明“生成候选的批次”和“保存到源域的动作”。首期推荐一个业务对象内部的小批量，限制对象数与上下文预算。跨对象没有事务能力时，展示每项实际结果和重试范围，不能承诺一次全部成功或全部回滚。

## 10. 能力如何接入各模块

### 10.1 复用运行底座，按业务任务开放工具

现有 AgentScope Java 运行边界、轮次/消息/证据归属、HITL、预算、停止、trace 可继续复用。当前没有证据表明“标准/建模/指标辅助”必须更换框架；下一阶段的主要缺口是业务上下文、源域契约、结构化候选与真实验收。

建议的职责关系是：

```text
原工作台的具体任务 / 现有 Agent 对话
  → 服务端确认任务范围、认证主体、项目与对象
  → 在 gateway 读取源域窄 API，取得有界上下文与证据
  → 规则匹配 + LLM 理解/创作 + 确定性候选校验
  → 原工作台展示、用户修改并选择
  → 原源域命令重新校验后生效
  → 回读业务结果 + 原审计 + Agent trace
```

这是职责示意，不要求现在新建通用服务、Maven module 或跨域建议库。先落地标准匹配和模型映射两个真实任务，再判断哪些交互与校验确实重复，按仓库规则抽取稳定共用能力。

### 10.2 每个任务至少明确的约束

| 约束 | 设计时需要回答 |
|---|---|
| 任务与目标 | 用户要完成什么；服务端如何确认原对象；是否涉及新建对象的原编辑草稿；不能只用聊天文本猜目标 |
| 可读上下文 | 哪些对象、字段、版本、业务说明可读；搜索上限、分页、超长输入、部分缺失如何处理 |
| 输出类型 | 描述、标准引用、字段映射、指标定义等分别采用源域可校验的结构；不靠任意 Markdown 解析决定保存 |
| 校验归属 | 身份/范围/预算由运行入口守住；字段与引用合法性、保存前置条件由源域守住；LLM 解释不替代校验 |
| 权限与版本变化 | 读取、采纳、保存各阶段如何重新授权；已删除、停用、陈旧版本与草稿变化如何阻止误用 |
| 生效与结果 | 带入、保存、验证、发布、运行分别是什么动作；何处读取真实成功结果；失败后如何继续 |
| 留痕 | 证据与版本、模型/Skill 实际配置、trace、源保存结果如何定位；是否含敏感内容与保留期限 |

现有 `GovernanceTarget` 仅支持 Asset/Quality 的当前任务，不能将 modelId、metricId 或 standardId 塞入 assetId 字段，也不能靠增加自由文本 purpose 绕过工具矩阵。扩展需经对应 Feature、领域与架构约束，旧会话行为保持明确。

### 10.3 知识、Skill 与模型的作用

- 平台当前事实优先从授权 API 读取；项目标准、模型和指标不从模型记忆里取版本或权限。
- Skill 承载任务方法、输出要求和核对步骤；不能新增权限或代替正式业务口径。
- 文档检索在“确实缺少非结构化业务说明”时再引入；检索需保留来源、版本、项目访问控制和撤权，不将向量索引当标准库。
- 规则负责可确定的判断，模型负责理解与创作；批量候选要受调用数、输入量、时间和费用预算约束。
- 多 Agent 与框架迁移按同一真实题集的收益和已复现限制评估，不能从页面数量推导需要多少 Agent。

### 10.4 固定流程、Skill、执行底座与源域各管什么

| 层次 | 拥有的职责 | 可变化的内容 |
|---|---|---|
| 原业务流程 | 入口、对象选择、人工编辑、保存、验证、发布/运行及结果回读 | 复用各模块现有旅程；具体 Feature 明确 AI 插入点 |
| 场景 Skill | 如何理解任务、读取何种已授权信息、何时澄清、如何比较和组织候选、如何表达未知项 | 方法步骤、解释重点、案例、措辞、缺项清单与输出说明 |
| AgentScope SDK | 推理循环、工具注册/调用、动态 Skill 加载、RuntimeContext、StateStore、HITL、事件与中间件扩展 | 使用官方已有 API，通过小范围适配连接平台；不再造第二套运行引擎 |
| 平台执行适配 | 服务端场景绑定、对象/项目/身份、允许的 Skill/工具范围、预算、候选结构和领域校验衔接、trace | 少量稳定契约，按真实场景逐步完善；不在通用 Runtime 硬编码每项业务方法 |
| 源业务域 | 真实标准/模型/指标、权限裁决、校验、条件保存与实际执行结果 | 业务规则仍由原 Owner 维护，Skill 不覆盖、复制或重新定义 |

“用 Skill 处理固定流程”并不意味着让模型自由决定是否保存、跳过验证或执行发布。程序确保必经步骤和顺序，Skill 辅助其中需要语言理解与业务判断的步骤。AgentScope 2.0 已移除旧 `core.pipeline.*`，不照搬 v1 Pipeline；复用原领域用例控制确定性步骤，通过官方 agent call / middleware 连接推理。平台数据生产 Workflow、业务审批与 Agent 推理编排仍有不同归属，官方 Service 控制平面的 Workflow 也不是当前 SDK 的即插即用能力。

### 10.5 按用户任务拆 Skill，而非按模块堆一个大 Skill

建议先形成以下场景目录；名称仅为规划标识，不是已注册技能，不要求新增导航或表。

| 场景 Skill | 输入与适用入口 | 主要输出 |
|---|---|---|
| `standard-match` | 原字段编辑器中的已选字段、类型、业务描述与可读标准候选 | 已有标准引用、匹配理由、冲突与待确认项 |
| `standard-field-draft` | 原标准字段编辑器中的角色、业务说明与合法标准选项 | 标准字段草稿；缺少前置标准时明确停止补全 |
| `model-source-mapping` | 原映射编辑器中的授权上游/目标字段与当前映射 | 逐字段映射候选、转换说明、未匹配与歧义 |
| `model-change-review` | 原模型版本/源变化页面的真实 diff 与已知依赖 | 变更解释与人工检查清单 |
| `metric-caliber-review` | 原指标详情的精确发布/Draft 版本、验证与依赖证据 | 口径、差异、验证阻断与覆盖限制说明 |
| `metric-definition-draft` | 原指标编辑器的业务需求、可读依赖与用户澄清 | 类型适配的定义草稿与待确认项 |
| 既有资产/质量场景 | 现有已批准目标、只读证据和原采纳面板 | 保留现有行为；将任务方法逐步整理成可评测 Skill |

项目行业习惯、描述风格、核对步骤优先用 Skill 表达。业务口径与单位仍通过 Semantic/Metric 的真实引用获得；即使某份 Skill 写了“金额默认人民币”，也不能替用户批准该业务定义。

新增业务场景的目标是复用现有底座，仅补场景方法、必要源域窄 API 和原编辑器连接。只有已有工具/上下文/结果类型无法承载时才扩展代码。反之，仅修改 Skill 文案也不能凭空获得尚未实现的标准搜索或模型映射校验能力。

### 10.6 优先补齐的框架适配能力

当前在线 Skill 管理、DB 仓储适配、SDK 动态加载、启停与乐观更新已存在，继续复用。当前只开放启用技能的 `SKILL.md` 正文，文件资源与额外工具自动激活不在已批准范围。以下是下一阶段提案，不是本次已实现能力：

1. **明确场景选择。** 原页面按钮指定场景，由服务端核验入口、对象及权限，得到允许 Skill 和工具范围。普通对话可以推荐场景，但不依据自由文本静默切换到更大能力。
2. **按需加载 Skill。** 优先用官方 `RuntimeContext` 的 `SkillFilter.class` 与已有 Repository / DynamicSkillMiddleware 给出当前场景目录，再加载正文。目录过滤只控制提示可见性，加载器仍需检查本轮允许集合与启用状态；SDK 过滤 hook 异常时可能回退全量目录，不能充当授权。共享 Agent/Toolkit 不能因某个请求而全局启停工具或技能；必须验证并发会话隔离。
3. **记录实际执行版本。** 复用已有 Skill 版本与实际提示/加载内容哈希；针对同轮反问、编辑中更新与停用设计一致性规则。当前热更新不能被描述为已经具备不可变 Skill 发布/回滚；若需历史版本或灰度，独立设计。版本快照也不能代替停用、撤权时的实时守卫。
4. **结构化结果衔接。** 优先核验并采用固定 SDK 版本已有的 structured output/工具 schema，而非自造 JSON 输出引擎。字段引用、对象匹配、精度/单位、组成环与保存冲突仍由源域确定性校验；JSON 可解析不代表业务正确。
5. **固定步骤显式执行。** 入口读取、必需校验和人工交接用原程序路径保障；Skill 中的“先查后写”不是强制顺序的证明。不为这一点先建通用可视化流程引擎。
6. **同题评测与配置留痕。** 每份 Skill 有正常/歧义/缺项/越权/注入/陈旧输入案例，沿已有评测目录和 trace 比较版本，不复制一套评测平台。

Skill 正文中可以说明所需工具与结果格式，但“允许工具”“输出硬约束”“身份/项目/预算”“审批或发布规则”只有服务端明确校验并执行后才成立。资源脚本、Shell、网络访问和工具组自激活不会因采用 Skill 架构而默认开放。

### 10.7 框架复用的落地纪律

先建立“需求→官方固定版本 API→仓库已有接线→必要平台适配”的核对表。SDK 已提供的 SkillRepository / DynamicSkillMiddleware、AgentStateStore、Toolkit、HITL、消息事件、Compaction 等直接复用；`SkillBox` 在 2.0.3 已标记待移除，新建设不围绕它扩展平台管理接口。业务授权、源证据、精确轮次和保存保护继续由平台负责。

官方 quickstart 推荐 HarnessAgent，但不能直接用它的默认本地 workspace、文件状态、记忆、Shell 和工具集合替换本平台已有持久化与安全契约。本次升级先保持现有 ReActAgent 与已复用的 harness 组件；是否切换 builder 根据官方固定版本和现有接线做等价性验证，不以换类名作为完成目标。详细依据见 [2.0.3 复用调研](./AGENTSCOPE_2_0_3_REUSE_RESEARCH.md)。

| V20 | 串联一条 J2：标准→模型→指标→验证/发布→已有消费回链 | 各源专业路径已就绪；稳定 ID 与回链；发布及消费契约可验证 | 多步真实任务每步有产物和来源，局部失败不伪造后续成功 |
| V21 | 将已证明有效的任务扩展到更多字段/对象，改善质量/开发等高频辅助 | 前述真实题集、用户任务收益与成本有证据；批量局部失败语义明确 | 同任务人工对照中减少耗时和返工，权限与错误率不退化 |
| V22 | 从既有质量/运行告警和变更事件准备主动检查建议 | 独立 Feature；既有事件/调度入口、授权身份、通知范围、去重与预算 | 建议可回到实际告警/变更，误报可评估，撤权后停止读取；不自动处置 |

推荐先确认 V15～V19 的业务重点：**用标准匹配验证 Skill 底座 → 复用到模型映射 → 复用到指标解释与创作**。每新增场景先检查能否仅增加 Skill、上下文读取及原编辑器连接；确需新增通用机制时再扩展。V20 是任务串联而非建设新的通用工作流产品；V22 是主动建议而非自动修复。遇到源契约缺口，先处理完成当前任务所必需的最小能力，不补齐整个模块。

真实模型环境尚未提供期间，可以继续完成获批的工程实现、CI 与明确的验收待办；上线推广、效果结论与更大自动化范围则必须依据真实验收。本文不将待环境当作用户已拒绝建设，也不把模拟模型测试当作真实质量验证。

## 12. 一条贯穿业务的验收案例

以某项目“统一支付金额指标”为 Golden Case。名称只是场景占位，实际选择已有业务域和非敏感测试对象；以下语义由业务 Owner 确认，不能当默认行业定义写入平台。

1. **明确业务目标。** 用户选择交易业务过程，说明使用场景；AI 列出时间口径、退款、币种、交易粒度、状态与去重的缺项，用户逐项明确。
2. **准备标准引用。** AI 读取当前项目已有金额类型、单位、状态码集、时间字段等，给出匹配候选；没有适用标准时进入原创建路径，由用户决定。
3. **准备模型。** 在真实导入的订单/支付来源上选择粒度，核对字段与标准；AI 给出来源映射，缺主键或关联依据时请求确认，不编造关联事实。
4. **准备指标。** 在原指标编辑器选择类型、口径、单位、模型/上游指标，填入结构化草稿；AI 的解释与引用分别可回源。
5. **验证与发布。** 用户保存后调用原定义验证，修正源域指出的问题，再显式发布精确版本。数据验证 provider 不可用则保留该限制。
6. **交接消费。** 有真实稳定映射时进入原 Dataset/消费契约，按权限查询并查看证据；没有则说明尚未落地可查询数据，不临时生成 SQL 绕行。
7. **检查变更影响。** 修改 Draft 后确认旧发布版本和下游引用未漂移；分别核查技术血缘、声明引用与真实使用覆盖。

每一步记录对象 ID、版本、读取主体、源页面、候选与人工修改、源保存/验证/发布结果及对应 trace。验收不要求一次聊天自动完成全部步骤，要求用户能沿原流程完整完成且知道每个结果是否真实生效。

## 13. 如何判断建设有价值

### 13.1 北极星与效果指标

建议的北极星是：**每单位用户工时完成并通过源域校验的目标业务任务数量，同时保持可接受的业务返工水平。** 必须按“字段标准绑定”“模型映射”“指标定义”等任务分别统计，不能把一条描述和一个完整指标视为等量工作。

| 指标 | 记录方法 | 防止误读 |
|---|---|---|
| 完成耗时与人工操作量 | 同一固定任务，记录人工与 AI 辅助的起止、查找/编辑/核对时间 | 包含用户复核时间，不只统计模型响应时间 |
| 真实任务完成率 | 达到预先约定的源保存/验证出口的任务 / 已开始任务 | 输出候选、带入表单、聊天完成不算全部完成 |
| 候选可用性 | 可采纳数、需修改项、拒绝理由、缺项/歧义表达，由领域专家核对 | 采纳率不能单独证明正确性，不能为了提高采纳率省略风险 |
| 质量与返工 | 原校验通过情况、业务复核问题、观察期内修订/撤回 | 结构合法不等于业务口径正确 |
| 来源可核验 | 候选引用存在、版本明确、证据状态正确、能回到源对象 | 引用合法不等于全部语义得到证明 |
| 成本与体验 | 每个成功任务的调用量/token/耗时、取消/失败/重试 | 结合任务结果统计；不同模型/Skill 配置分开比较 |
| 范围与权限 | 跨项目、撤权、非法引用、注入及源漂移反例 | 不以“模型通常遵守”替代服务端拒绝证据 |

基线与目标值目前未采集。建议每个首期场景准备一组可重复的真实任务，先记录人工基线，再由相同领域角色评审 AI 结果；如采用数值推广门槛，应在试点方案中先约定并记录为目标，不能倒写成已达成收益。

### 13.2 三类验收分别出结论

1. **工程验收：** 协议、权限、项目归属、预算、并发、晚响应、依赖边界、数据库和发行 CI。
2. **真实任务验收：** 实际模型与登录用户完成正反例，候选语义由领域专家核对，源审计和真实保存结果一致。
3. **产品效果评估：** 与人工基线比较耗时、完成率、返工和成本，确定是否扩大覆盖。

当前已有工程成绩属于第一类；后两类独立待完成。各阶段采用现有发布治理，不因本文提出路线而将 Feature 标记 SHIPPED。

## 14. 必须经过决策的边界与下一次立项

本文建议沿用 ACCEPTED PD-001/PD-002/PD-003 和现有专业工作台，下一步为具体任务建立 Feature，再更新源域与 Agent 契约。以下变化需要先完成适用的产品决策，而非直接写入实现：

- 新增一级 AI 门户、通用跨域任务中心或改变默认跨域用户路径。
- 创建拥有标准/模型/指标定义的第二份 AI 业务库，或新的长期跨域建议/审批状态机。
- 开放通用质量发布门禁、扩展消费安全映射或生命周期处置范围；PD-005/006/007 当前仍是 PROPOSED。
- 将 Metric 作为新 Data Product source、建设新的语义查询运行时、跨物理库自由 SQL 或平台内执行 DDL。
- 后台自主修改标准、模型、口径、权限，自动发布、合并主数据或删除数据。逐动作明确身份、授权、幂等、真实结果核对、审计可靠性和补偿；既有 fail-open 审计不能被当作自动执行的强保证。

下一次实施建议从 **V15：已有标准匹配与解释** 立项。Feature 应固定首个业务过程、输入对象、候选上限、可读 API、草稿保护、人工采纳路径、源域保存边界及验收编号。业务 Owner 与样本优先从现有项目选；当前总纲不预先替用户决定真实口径、样本数据外发政策或业务发布规则。
