## 1. 建议：让用户完成质量排查的下一步

**下一轮集中建设“历史质量执行结果 → 有依据的排查步骤 → 返回源页面核对”。** 先利用当前公开证据，帮助用户判断应核对什么、证据还缺什么；真实试点证明需求后，再考虑增加跨执行对比等读取能力。

继续沿用仓库当前 AgentScope Java 2.0.2。这是基于现有接线、已完成回归和迁移成本的工程判断，没有新的替代框架对测结论。当前主要待验证问题是任务效果和证据是否够用，暂不把迁移框架、多 Agent 或 RAG 当成下一版的前置条件。

| 产品问题 | 本轮提案 |
|---|---|
| User | 需要判断质量检查异常并安排下一步的质量治理人员；辅助核对的表维护人员 |
| Problem | 已能读到执行结果并获取解释，但解释是否能帮助用户完成排查尚无真实基线；只有结果状态时，模型容易把推测原因说成结论 |
| Capability | 将所选历史执行的可核对事实、待验证假设、缺失信息和人工检查步骤组织成任务结果，并回到原执行页面核对 |
| User Journey | 质量执行详情进入 → 固定 executionNo → 读取授权历史证据 → 澄清排查目的或业务背景 → 核对事实与建议 → 原页面查看详情；需要改规则时，由用户另行进入当前监控任务 |
| Expected Outcome | 用户知道哪条规则发生了什么、哪些原因尚未证实、下一步在哪里检查；能指出证据不足而不是得到虚构根因 |
| Truth Owner | Quality 拥有历史执行及规则证据、当前 Monitor/Rules/Settings；Security 拥有权限；官方 StateStore 拥有消息，Agent turn 拥有轮次生命周期。排查建议不成为新的事故或处置事实 |
| Producer / Consumer | Quality 公开授权 API → Agent 证据与事实核验 → 当前对话和源页面回链；用户提供背景 → 本轮澄清。模型建议不能反向修改源事实 |
| Existing capabilities to reuse | 原质量入口、GovernanceTarget、任务策略、预算、HITL、SSE/取消、证据台账、服务器事实卡、回答守卫、源页面链接、Skill 管理、评测执行器 |
| E2E acceptance evidence | 固定执行的事实/假设区分、澄清后同目标同预算继续、源页面核对、历史不被当前定义替换、授权失败/截断降级、源审计确认零业务写入；详见 [实施清单](./AGENT_V4_BACKLOG.md) |

## 3. 首批用户体验

沿用当前“AI 解读结果”入口，首批不增加任务中心或一级导航。结果优先沿用现有事实卡与对话表达，减少新协议面：

1. **本次执行事实。** 展示所选 executionNo、读取时点、执行状态与规则结果；关键状态/数值由本轮服务器核验事实支持。
2. **优先核对的规则。** 从已读取的 NOT_PASSED、ERROR、NOT_RUN 中说明需要关注的对象；不能把未读取规则概括成全部结果。必要时由用户选择关注规则。
3. **可能原因与证据缺口。** 逐项说明“假设是什么、还缺什么证据”；没有样本或上游事实时不确认原因。
4. **人工检查步骤。** 每项写清在哪里检查、检查什么、看到什么结果后再判断。缺少明确入口时说明需表维护人员核对，不编造按钮或 URL。
5. **源页面下一步。** 使用已有服务器/前端受控路由回到本次执行详情。需要调整当前规则时，由用户在源页面选择当前监控并发起独立 QUALITY_RULES 任务；历史解释轮不切换工具权限。

例：某规则记录 `NOT_PASSED`、metricValue=`12`、expectedValue=`0`。回答可以确认“该规则实际值 12，期望值 0，未通过”，并建议在原规则结果查看字段和业务条件。若没有模板、样本或上游证据，不能把 12 说成“12 行脏数据”，不能断言“上游同步漏数”。

`ERROR` 表示执行异常，需要查看源执行详情进一步确认；当前证据没有错误类别，不能判断是权限、连接还是 SQL 问题。`NOT_RUN` 表示未执行，不能判定数据质量；虽领域规定 STOP 可产生 NOT_RUN，当前公开证据没有冻结失败策略和触发原因，不能仅据 NOT_RUN 确认本次 STOP 因果链。

用户口述的背景明确标为用户提供的信息，不升级为 Quality 历史事实，不自动保存为长期记忆。源证据不足时，允许结果停在“需要人工核对”；这是正确降级，不是默认任务成功。

## 4. 证据够用的范围与缺口

以下判断来自当前契约和源码，而非真实模型测试：

| 可复用证据 / 能力 | 可以支持 | 尚不能支持 |
|---|---|---|
| [QualityEvidenceQueryApi](../../data-ops-business/data-ops-business-quality/src/main/java/io/yak/ops/business/quality/api/QualityEvidenceQueryApi.java) | 所选历史执行、规则名称/字段/结果、实际值/期望值、时点、耗时；最多 100 条规则并标记截断 | 原始错误、SQL、失败行样本、冻结模板语义、失败策略原因、上游任务状态、跨执行比较 |
| [证据 Gateway](../../data-ops-business/data-ops-business-agent/src/main/java/io/yak/ops/business/agent/gateway/GovernanceEvidenceGateway.java) 与事实核验 | 本轮引用、来源/时点/状态、受控源链接、可核验的字段路径 | 所有规则都能进入事实卡：当前字段收集和文本长度还有上限；不能因 API 返回了 100 条就宣称完整展示/核验 |
| [质量执行详情](../../data-ops-ui/src/pages/data-quality/execution/detail/index.tsx) | 现有详情、历史切换、监控信息与 AI 入口，供用户人工进一步核对 | 详情拥有的信息不等于 Agent 已读取；当前质量证据 API 不提供 monitorId，不能按模型文本拼监控跳转 |
| [quality-explanation Skill 材料](./skills/quality-explanation/SKILL.md) | 现有历史事实/假设/缺口表达基础，可做同题改进候选 | Skill 不能增加读取授权、补出不存在的事实或替代源域策略 |

当前证据仍需 live user/project 授权，显式历史任务仍只读取所选 execution。首次迭代不取 Dataset 行、不运行 Python、不自动保存、启用、执行或通知；这些范围沿用现有约束。

如果试点表明多数有效步骤必须依赖错误类别或执行对比，由 Quality Owner 先定义最小、脱敏、历史绑定的只读契约。Agent 只能通过既有 gateway → 公开 API 扩展；不能直接调用 Quality DAO、从普通问数绕路取样或自动读取关联资产。新的默认跨域路径/长期治理规则按 Product Decision 流程处理。

## 5. 迭代顺序与交付门槛

| 顺序 | 工作 | 开始条件 | 完成证据 |
|---|---|---|---|
| V4-0 真实基线准备 | 保留 V3 验收待办，标注质量题、准备固定测试对象映射、记录当前解释作为对照 | 可立即进行文档与离线准备；真实执行依赖测试环境 | 题集事实条件、评分规则、绑定核验清单；真实未跑仍 NOT_RUN/PENDING |
| V4-1 排查任务契约 | 固定本轮输出、澄清、缺口、源回链及降级；确认用户确实需要这条路径 | 用已有证据和用户反馈准备 Feature；新增行为按现有流程批准 | 获批 Feature 与对应 Domain/Requirements，明确复用边界 |
| V4-2 工程实现与 CI | 调整当前任务提示/可选 Skill、结果表达和受控回链；补同目标 HITL/历史/缺口回归 | V4-1 范围获批 | 单个窄 PR，相关 Agent/前端/架构/Product 检查通过；真实状态单列 |
| V4-3 真实试点 | 同模型同题比较当前版本和排查版本；专家和实际使用者核验 | 当前 F009～F011 对相关路径验收达到门槛；部署/账号/模型具备 | 源审计、专家评分、用户是否完成有效下一步、失败分布；决定开放范围 |
| V4-4 有条件扩展 | 错误类别或两次执行比较，二选一 | V4-3 记录证据缺口且用户收益明确，源 Owner 认可 | 独立只读契约和 Feature；相关对象由用户显式选定、服务器绑定，不扩大历史任务默认读取 |

用户已明确代码与 CI 可先完成、真实模型验收单独记录待完成。环境等待不阻塞已授权的工程准备；也不视为真实验收通过。V4-1～V4-2 是本提案的后续实施批次，当前没有新建或伪标 APPROVED Feature。

首批投入估算：一名熟悉仓库的工程师与产品/质量人员参与，V4-0～V4-2 约 6～10 个工程工作日；环境就绪后小规模试点另约 2～3 个工作日。估算不含等待、源 API 扩展或复杂 UI 协议；以 V4-1 定稿后再拆工时，不作为交付承诺。

## 6. 评测与收益判断

先新增 **16 个质量排查标注场景**，与当前 12 例任务策略基线分开计数；复用 [执行器](./evaluation/README.md) 和 [人工量表](./evaluation/rubrics.md)。输入变化但断言相同的重复题不算新增覆盖；多步澄清和源审计仍由操作者在原页面执行，不为脚本方便自动答 HITL。

比较时固定源 fixture、账号能力、模型配置、部署 commit 和实际 Skill 哈希，仅改变被评估方案。建议首次 16 例各跑一次；选 4 个澄清/拒绝/混合结果案例追加两次，共最多 24 次尝试/方案。实际调用量和费用须在运行前核验，usage/单价缺失时费用 unknown。

试点最低建议门槛：所有必测例都有人工/源证据；现有量表列出的严重错误为零；事实支持与引用匹配逐例达标；缺口澄清和任务完成低分例逐例处理或明确限制范围。样本不足不推断生产可靠率，安全负向题未执行不能算通过。开放范围由产品/Quality Owner 根据基线评审确定，不能由评分脚本自动批准。

记录四类结果：事实正确性、步骤可用性、用户实际完成下一步、耗时/usage。生成数、打开源页面数、用户确认有用数和实际保存/执行数分别统计；页面点击不等于问题解决。没有真实对照时不宣称节省比例、采纳率或成本下降。
