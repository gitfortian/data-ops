## 交叉观察

1. **"内部实现泄漏"是全分区最系统性的问题（12 处证据）**：`index=tableColumn + parentAssetId 收窄`（列视图横幅）、`SOURCE_GONE`（变更说明）、`LIFECYCLE/SECURITY/USAGE/QUALITY/TECHNICAL_METADATA`（支持 Section 列）、`LAYER_DEFAULT` / `DRIFT` / `status:DRAFT` / `dialect:MYSQL` / `latestVersionNo`（详情）、`s_num_1/s_str_2/...`（实体属性）、`预检令牌 5 分钟内有效`（上架）、`0 0 3 * * ?`（调度）、`确认无数据`（空态标题）。产品缺一个统一的"枚举 → 人话"文案层；建议在 `docs/product` 里定一条面向用户的术语字典约束，而不是逐页打补丁。
2. **1440 视口下"表格 + 右固定操作列"反复被迫横向滚动**：资产台账 `clientWidth 828 / scrollWidth 1240`（9 列）、采集与对账 `1520 > 1414`（**只有 6 列**）。两处 `overflowX` 都是 `false`（滚动藏在表格容器内），所以自动诊断容易漏判。根因一致：列宽写死而非弹性 + 操作列动作过多（采集页一行 6 个按钮）。这是**组件层缺陷，应统一修 `Table` 列宽/省略号策略**，不要逐页调；同时说明任务书所问的"小屏可用性"在列表页已经是**未达标状态**。
3. **反馈与确认的门禁方向装反了**：普通/低风险动作有一等一的二次确认（下架、删除目录、删除标签、确认变更、忽略变更），而**真正危险的同步类动作（全部对账、对账此源、立即运行）一个确认框都没有**；反过来，写操作成功/失败又普遍**没有任何 toast**（taxonomy 保存实测 `msg:[]`）。即"该问的不问、该说的不说"。建议分区统一：不可逆/全域动作 → `Modal.confirm` + 影响面预览；所有写操作 → 成功/失败 message。
4. **状态流转的"闭环可见性"未达标（本分区核心目标）**：`已上架✓ → 运营中未完成 → 归档策略✓` 的顺序倒挂 + 前置 4 阶段红⚠，加上 `下发状态 DRIFT` 无解释、健康度"不适用(剔出分母)"与 `0/15` 并存，导致**用户在台账/详情里无法回答"这个资产现在到底走到哪、下一步做什么"**。而"变更是否可见可追溯"同样未达标（差异摘要 `{}`）。这两条合起来构成 P2 集中区，是修复优先级最高的功能项；血缘闭环则因 0 证据无法判定。
5. **两处"看起来是 bug"其实是环境挤线，报告中已剔除但值得记录**：（a）表体整块空白无兜底（`{all:0, empty:false, txt:""}`）出现在 401 瞬间——全局拦截器最终会带 `returnTo` 跳登录，方向正确，但**失败瞬间列表既无空态也无错误占位**，建议补测（可用只读账号或 mock 401 验证）；（b）第一次 `QA-S4A-测试目录` 保存"静默失败"。二者均不计入产品问题，但（a）的兜底缺失值得产品侧确认。
6. **证据完整性提示**：digest 末行 `[screenshots taken: 28]`，实际目录只有 **25 个文件**（差 3 张，推断为同名覆盖或未落盘，例如 `02-catalog.png` 与 `02-catalog-default.png` 对应同一页两阶段）；`18-taxonomy-after-create.png` 只有 **39KB**（其余 100~194KB），内容与文件名不符，**高度疑似为弹回登录页的那一瞬**（与 S4a-21 的 401 时间点吻合）。引用该图时不可作为"创建成功"的证据（创建成功证据是 `19-taxonomy-qa-created.png` + 文本 `hasQA:true`）。另：本分区多数问题靠 `diag`/`innerText` 数字证据成立，console 类问题（S4a-35）与"上次命中 15 vs 17"（S4a-29）**无对应截图**，属可接受的文本证据。
