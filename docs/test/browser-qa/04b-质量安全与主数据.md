## 交互与共性问题（本分区抽象）

1. **表格列宽与 1440 视口长期不匹配**（S4b-01 / 03 / 09 + 13 列执行表）：同一病根在 4 个页面复现，且被裁掉的偏偏是「最近状态 / 注册信息 / 启用开关 / 操作列」这类**决策与操作型列**，把列表页降级成只读页。建议统一列治理：必显列固定、次要列收进「详情」或可配置列。
2. **反馈节奏不一致**：创建/更新类成功有 toast（质量监控已创建 / 已更新 / 已注册 1 张数据表），但导出、删除入口、测试运行、取消等要么静默、要么 3 秒即散（S4b-02 / 13），用户无法确认「刚才那一下到底成不成」。
3. **状态默认值不解释**：执行页左树自动选中某数据源（S4b-07）、报告默认落在「昨天」（S4b-05）、总览三块各用各的时间窗（S4b-11）——都是「筛选已经生效，但用户以为系统没数据」。建议空态文案带上当前生效条件（如「客户库 / F1-CRM 源下无记录，清空筛选」）。
4. **占位符规范不统一**：无数据时 `通过率 --` 与 `0% 通过率` 同时存在（S4b-06），重要度跨页 `弱规则` / `--` 不一致（S4b-18）。
5. **高危与低频操作藏在图标菜单**（S4b-17）：删除、刷新、操作日志全靠 `aria-label` 才能程序化定位，真实用户更容易漏；同时该页无文字标签输入控件偏多（S4b-20）。
6. **术语三处三样**：菜单/页面标题/返回链接（S4b-19），加上向导实际是锚点长表单而非「多步向导」，需求描述与实现之间需要对齐一次口径。

1. **「创建 → 生效 → 可见结果」在质量子域是真的**：注册表 → 建监控 → 从模板加规则（检查字段来自真实 schema）→ 测试运行 → 执行记录出现「通过 / 监控值 100%」→ 执行详情耗时 145 ms。这条主链没有被 S4b-02 的重复约束打断，可作为后续回归的最小脚本；但安全与主数据的等价链路**零证据**。
2. **质量报告与运行记录对「今天」的处理相反**：详情页「最近执行」立刻更新为 10-01 12:30:48，而质量报告 Tab 与执行列表分别因默认日期 / 默认数据源筛选看不到同一条记录 —— 同一系统内三处对「刚发生的事」可见性不一致（S4b-05 / 07）。
3. **审计主体写成 `system`（S4b-08）与安全子域强相关**：本分区还没测 `/data-security/audit`、`/data-security/access`，而质量侧已出现「手动触发归属系统」的先例，补测时应把「谁做的」这条字段作为贯穿安全域的固定检查项。
4. **主数据已有发布动作在生产数据里跑着，却无人验证状态可见性**：旁证显示存在「主数据分发已发布 / 分发 API 已发布至数据服务 `/mdm/customer/1`，订阅方可持 API Key 实时取数」的系统消息，同时 `客户库` 下已有 `mdm_landing_customer_1`（MDM 采集落地表）出现在数据表监控里。**质量域能看到落地表、消息中心能收到发布通知，但 `/mdm/overview` 与 `/mdm/modeling` 是否把「已发布 / 已生效」讲清楚，完全未证**——这正是本分区要求重点回答的问题，须优先补测。
5. **列宽溢出是全仓库性问题的又一例**：本分区 4 处（1815 / 1658 / 1651 / 13 列）与其他分区证据里「表格 right 1508 > vw 1414、`overflowX:false`」现象同构，建议在仓库层面统一 antd 表格列治理，而不是逐页打补丁。

### 闭环判定（任务点名项）

「分级分类 → 脱敏规则 → 访问/审计 → 合规结论」是否真的联动：

1. **等级字典 → 资产定级：半断。** 定级数据存在（客户手机号 → #6/机密，与总览「机密 1」、审计 L3 同源，数字对得上），但该等级 L1~L4 已停用而引用无约束（R4-07），且定级来源=「人工」——敏感发现规则为 0 条，「规则命中 → 自动定级」这条链路**当前无任何数据能证明可用**（R4-10 相关）。
2. **资产定级 → 脱敏策略：断。** 脱敏策略「手机号脱敏」的适用条件是「等级:- · 列:*phone*」，等级条件为空，只按列名通配匹配；即使唯一的机密字段被定级，脱敏也不消费等级信息（R4-17）。
3. **脱敏策略 → 实际执行：判定已修正（源码复核后撤回「没人被脱敏」的结论）。** 服务端确实存在真实生效的脱敏执行点：`data-ops-business-dataset/.../query/DatasetQuerySecurityGate.java:285` 解析脱敏指令、`:228-241` 用 `securityGateway.mask` 改写结果单元格、`:272-274` 记录实际结果，链路在 `DatasetQueryCoordinator.java:127-138`，适配器 `SecurityDatasetAdapter.java:51-59` → `SecurityMaskingApi`。审计页那一列读的是 `DsecAccessLogPO.masked`（`AccessLogController.java:36`，列定义 `V2__create_dsec_tables.sql:153`，写入语义见 `AccessLogService.java:51` 与 `data-ops-business-security/REQUIREMENTS.md:49`），它是**「本次是否真的执行了脱敏」的事实标记**，被拒/返回 0 行/未输出该列时本就为 0（`DatasetQuerySecurityGate.java:281-300`、`:262`）。因此「两条 phone READ 显示明文」不是策略失效的证据。真正剩下的缺陷被收窄为两点：①前端把 `masked=0` 一律渲染成「明文」（`data-ops-ui/src/pages/data-security/audit/index.tsx:74`），把「不适用/未输出该列」和「读了明文」混为同一措辞，属**语义误导**（P2，可解释性缺陷）；②执行点目前**只覆盖 Dataset 查询这一条路径**，其它读取路径（SQL 直连、导出、数据服务 API）是否在 gate 之外，本分区无证据、必须在补测中确认——这才是「策略与执行之间」真实存在的风险。试算面板参数失效（R4-14）仍为独立真缺陷，不受本条修正影响。
4. **访问策略 → 审计裁决：通，但「默认放行」缺可解释性。** 服务端裁决与审计字段链路是真实的：无策略命中时的姿态是**设计上的默认放行**（`AccessDecisionService.java:100-105`，文档见 `data-ops-business-security/REQUIREMENTS.md:38`，并有 `AccessDecisionServiceTest.java:87-95` 钉住），裁决对象携带 `matchedPolicyId`（`AccessDecision.java:7`，命中时在 `:91/:99` 赋值、默认放行时在 `:104` 置 null），前端也确实在试算面板打印命中依据（`data-ops-ui/src/pages/data-security/access/index.tsx:312`）。**因此「tom 与 bob 逐字相同」这条观察被收窄**：只要 tom 的策略真的命中，两者显示必然不同（命中条件包含 status=APPROVED / 主体 / 资源范围 / 有效期，见 `AccessDecisionService.java:62-83`），实测相同说明当时 tom 的策略未命中或已失效——这是**默认放行缺省依据字段 + 界面不解释「无策略命中」含义**（P2 可解释性缺陷），不是「策略不生效」。若要判言「策略是否被消费」，需要补一条带 APPROVED 策略的对照实验（列入补测清单）。
5. **前四域 → 合规结论：断。** 合规规则 C001 从未执行，发现明细为空，无调度机制（R4-18），总览合规缺口恒为 `—`。
6. **总览页数字与子页一致性：通过。** 安全等级 5、脱敏策略 1、生效访问策略 1、机密 1、合规 `—` 均与子页实况吻合——**静态计数联动是真的，动态裁决/执行联动是假的**。

1. `识别` 绑定 `crm_db.crm_customer`（主来源）→ `采集` 落地 `已采集 2026-09-19 20:20:09 · 3060 行`；
2. `清洗` 用 `手机号重复检测` 找出重复组（实测执行去重发现返回多组 `2 | 100% | 手机号=+86…(EXACT)`），历史合并日志 `合并 1 条记录`；
3. `3060 − 1 = 3059`，与总览「生效记录 3,059」、分发「3059 条可服务」**三处数字精确对上**，说明清洗结果真的进了生效集；
4. `变更审批` 走通用流程 `MDM_CHANGE`：`v3 基线快照 → 变更单#1 改 gold → v4 → 变更单#3 改 diamond → v5`，台账有状态（已生效/已撤回）、有审批人、有审批意见，详情页能跳到 `/approval/instance/10`；
5. `分发` 复用数据服务（API `/mdm/customer/1`）、`订阅` 复用站内信，且后端**确实按实体生效状态拦截发布**（`主数据实体未生效，不能发布或刷新供数 API`）；
6. `血缘` 三段（`crm_customer → mdm_landing_customer_1 → MDM主数据加工-customer → yak_mdm_record`）在 `/data-analysis/lineage` 里真实存在。

断掉的部分：

- **状态机断层（R5-06）**：实体是 `草稿`，分发配置却挂着绿色的 `生效 / 已发布 / 3059 条可服务`。后端拦得住发布，前端却把状态显示成"在供数"，用户无法判断对外 API 到底活着没有。
- **审批被绕过（R5-21）**：管线图画成 `采集→加工→清洗→审批→分发`，但标准化/补全类清洗「直接更新 534 条生效记录、不生成变更审批单、不可回滚」，清洗这一环跳过了它下游的审批。
- **加工环节空心（R5-01 + 详情「记录」Tab 说明）**：MDM 侧无真相表，总览显示 `-`，要靠人手动点「生成主数据加工任务」再去数据开发运行。
- **映射不可维护（R5-14）**：识别只做成一次性动作，映射存进去就再也打不开，改一个字段要解绑重来。
- **审批看不见内容（R5-30）**：变更台账的核心列「变更内容」被压成 0 宽，审批人面对一张不知道改了什么的表。
- **同域互不相干（R5-13 vs R5-35）**：血缘数据在血缘模块里活着，MDM 实体详情的「血缘」Tab 却只有两个按钮、零内容。

### 结论摘要

- **P0 2 / P1 6 / P2 16 / P3 19（合计 43 条；R5-19 一条初判经实测+源码核对后撤回，不计入）**
  - 口径校正（并入时机器复核，原文数字保留以便追溯）：逐行数 R5 问题清单表格实际为 **P0 3 / P1 5 / P2 17 / P3 18**，共 43 条、43 个不重复 ID。差异原因是原文把 R5-05（乱码主键）记在 P1、把两条白屏类记作一条 P0。**本分区顶部的 85 条汇总以机器统计为准**，不用本行自报口径。
- 一句话结论：**主数据 6 页全部打开并跑通了 CRUD 与只读链路，接口零 4xx/5xx、零横向溢出（这一域明显比 04b 的质量域干净），但被 3 类问题卡住验收 —— ① `/ai-agent` 白屏且会污染整个 SPA（P0，全局入口触发）；② 主键属性名乱码 + 审批台账核心列 0 宽 + 草稿实体显示已发布（P0/P1 级数据与状态错误）；③ 危险动作的二次确认在同一个仓库里忽有忽无（识别的解绑、审批流程的删除有；分发的重新发布、流程的停用开关没有）。**
- 本轮 9 个页面**全部完成**，无环境干扰导致的未覆盖页；唯一未实测项是 `/mdm/approval` 的「撤回」二次确认（当前无 `审批中` 在途变更单，数据不具备）。

### 共性问题（跨页抽象）

1. **危险动作的二次确认全凭开发者个人习惯**：有确认的 —— 识别「解绑」（文案说明影响面）、审批流程「删除」（说明软删除+在途阻断）、建模「删除实体」、清洗「执行清洗」（说明条数+不可回滚+绕过审批）；没确认的 —— 分发「重新发布」（实测直接下发）、流程「启用/停用」Switch（源码直连 API）。同一仓库两种标准，建议把 `Modal.confirm` 收敛成一个 `useDangerAction` 之类的统一封装。
2. **antd 表格列宽治理仍是最大面积问题，但形态变了**：04b 是"列太多塞不进 1440"，R5 是"列太少但硬编码宽度不自洽"—— `/mdm/approval` 因为唯一没写 `width` 的列被挤成 0px 而**整列消失**。建议仓库级规则：要么全列固定宽 + `scroll.x`，要么全列不写宽，禁止混用。
3. **数字口径跨页一致，符号口径跨页不一致**：`3060 → 已合并 1 → 3059 → 3059 条可服务` 这条链精确得可喜；但 `-` 到底表示"查询失败""不适用""未配置"还是"空"，在总览、实体详情、识别、清洗四页各有解释（R5-01/R5-29）。
4. **内部实现细节泄漏到用户界面**：`随 ticket 52 接入`、`assetKey table:3:crm_db..crm_customer`、`来源 ID mdm-collect-1`、`数据源 3`、裸 JSON 属性快照、32 位 master_id 哈希 —— 技术元数据页尤其严重。
5. **可访问性欠账集中在 Select 搜索框**：`noLabel:["search ant-select-selection-search-input"]` 在 `/mdm/modeling`、`/mdm/identification`、`/mdm/cleansing`(×2)、`/mdm/approval`、`/data-analysis/lineage` 六页复现，属一处公共组件缺 `aria-label` 的批量问题。
6. **`diag 全绿 ≠ 页面正常**：`/ai-agent` 白屏时 `overflowX/clipped/tiny` 全部为空，因为根本没有 DOM。浏览器 QA 必须把 `body.innerText.length` / `#root.children.length` 作为第一道判据。
