## I-1 ｜P2｜业务域接口返回子域数据，UI 树不渲染子节点

**模块**：语义中心 · 业务域（/semantic/domains）
**现象**：新建子域成功后，接口已返回子节点数据，但页面树中父节点被渲染为**叶子节点**（无展开箭头、无子节点），新子域无法在树上被查看、选中、编辑或删除。完整刷新页面后依旧不显示。

**复现步骤**：
1. 进入 /semantic/domains，选中「交易域」使「新建子域」可点；
2. 新建子域（编码 `qa_test_sub`，名称 `QA测试子域`），保存；
3. 观察树：父节点下不出现子节点；F5 刷新后仍不出现。

**证据**：
- 应用自身请求 `GET /api/v1/semantic/domains/tree` 返回 200，`data` 中 `qa_test_domain` 的 `children` 含 `qa_test_sub`（id 52）；
- DOM 检查：`.ant-tree-treenode` 仅 2 个真实节点，父节点 className 含 `ant-tree-treenode-leaf`，`hasChildren: false`，无 `.ant-tree-child-tree`；
- 删除父域时后端正确提示被阻断（证明子域数据真实存在），但前端始终拿不到可显示的子节点。

**影响**：子域创建后即「消失」，用户无法管理；若依赖树做后续操作（业务过程挂子域）会受阻。
**建议**：排查前端 `toTreeData`/Tree 的数据注入与渲染链路（重点核对 children 映射与节点 key），补充「创建后树刷新并展开至新节点」的验收用例。

## I-2 ｜P2｜业务域/业务过程保存成功后弹窗不关闭，确认按钮卡 loading

**模块**：语义中心 · 业务域、业务过程（新建/编辑 Modal）
**现象**：点击「保存」后接口成功（toast「已创建」、列表/树已更新），但 Modal 不关闭，OK 按钮停留在 loading 态；再次点击保存无任何请求发出、无任何反馈，界面进入「假死」状态，需手动取消。

**复现步骤**：
1. /semantic/domains 或 /semantic/processes 点「新建」，填有效数据；
2. 点「保存」；
3. 观察到：成功 toast + 数据落库，但弹窗仍开、按钮转圈卡死；再点保存无反应。

**证据**：
- 接口日志：`POST /api/v1/semantic/domains` 200、`POST /api/v1/semantic/processes` 200，响应体 success；
- 保存后 `.ant-modal-wrap` 仍存在（opacity 1、表单保留旧值），footer 按钮 className 含 `ant-btn-loading`；
- 二次点击保存：fetch 监视器无任何请求。

**影响**：用户会误判「没保存成功」而重复提交；界面假死需手动取消，体验差且可能造成重复数据。
**建议**：核查 `submitEditor` 的 promise 链路（`validateFields` → 请求 → `setEditorOpen(false)` → 列表刷新 → `finally setSaving(false)`）在本环境下未收敛的原因；补充「保存成功后弹窗关闭、按钮 loading 复位」的回归用例。

## I-3 ｜P2｜预置标准可被删除，无 preset 保护

**模块**：数据标准（/semantic/standards）
**现象**：`preset=true` 的平台预置标准可通过删除接口直接删除（HTTP 200），没有任何保护或二次确认上的预置提示。UI 删除按钮点击预置行同样可达后端删除。

**复现步骤**：
1. 取任一预置标准（如 `naming_table_ods`，id 457）；
2. `DELETE /api/v1/semantic/standards/457`（带项目头与登录态）；
3. 返回 `{"code":200,"message":"成功"}`，标准被删除。

**证据**：接口响应 200；删除后列表该标准消失；`preset/initialize` 可幂等补回（本次测试已恢复，无重复）。
**影响**：预置种子是平台能力的初始配置（命名规范六件套、通用码值等），误删后普通用户无从感知差异；UI 删除确认文案也未区分预置。
**建议**：后端对 `preset=true` 的标准拒绝删除（或仅允许管理员删除并强提示）；前端对预置行隐藏/禁用删除，或在确认弹窗中标注「预置标准」。

## I-4 ｜P2｜码集名称数据不一致（列表「是否-是」vs 详情「是否-否」）

**模块**：数据标准 · 码值标准
**现象**：`yes_no` 码集在列表/`code-set/page` 中名称为「是否-是」，在 `code-set/yes_no` 详情中名称为「是否-否」，接口同时返回 `nameInconsistent: true`。前端编辑弹窗已能提示「该码集历史名称不一致，保存后将统一」，但根因数据未治理。

**证据**：
- `POST /standards/code-set/page` → `{codeSetCode:"yes_no", name:"是否-是", ...}`；
- `GET /standards/code-set/yes_no` → `{codeSetCode:"yes_no", name:"是否-否", nameInconsistent:true, ...}`；
- 编辑弹窗与码值编辑器均展示「是否-否」。

**影响**：同一码集在列表与编辑/引用处名称不同，用户会困惑选择哪一个；引用方（标准字段下拉等）展示名可能不一致。
**建议**：排查预置初始化/码值拆分入库时码集名的写入来源，做一次数据订正使列表与详情同名；`nameInconsistent` 作为临时兜底可保留，但不应长期依赖。

## I-5 ｜P3｜标准详情抽屉（含用度统计）无任何入口

**模块**：数据标准列表页
**现象**：详情抽屉组件 `StandardDetailDrawer`（含全量字段 + 「引用/绕过」统计）与 `_openDetail`（其内部会调 `GET /standards/{id}/usage`）在页面中存在，但 `_openDetail` 从未被任何地方调用——死代码。用户无法查看任一标准的用度（引用/绕过）统计。

**证据**：源码 `pages/semantic/standards/index.tsx` 中 `_openDetail` 定义后无引用；行点击、编码列均未绑定打开逻辑；接口 `GET /standards/{id}/usage` 后端可用。
**影响**：ticket 32 设计的「引用/绕过统计与反哺建议」能力对用户不可见；后端接口闲置。
**建议**：为表格行/编码列绑定详情打开入口（打开时拉取 usage），或明确下线该抽屉与接口，避免死代码误导。

## I-6 ｜P3｜API 缺项目空间请求头返回 999，而非约定的 40010

**模块**：语义中心 API / 项目空间上下文
**现象**：不带 `X-YAK-SECURITY-PROJECT-ID` 头调用 `/api/v1/semantic/standards/page` 等接口时，返回 `{"code":999,"message":"系统异常，请稍后重试"}`；而 `docs/architecture/PROJECT_SCOPE.md` §9 约定此类场景应返回 400 `PROJECT_REQUIRED`（core 中已定义 40010）。

**证据**：同请求带项目头（值 2）即 200 成功；不带头稳定 999。多接口一致（page/create）。
**影响**：外部 API 调用方拿到的是无信息量系统异常，无法据此判断是缺项目上下文；与设计契约不符。
**建议**：项目上下文缺失/非法时统一走 `ProjectContextError`（40010/40410/40310）语义，不要落成 999。

## I-7 ｜P3｜新建标准表单可选全部六类，但字段模板固定为命名标准

**模块**：数据标准 · 新建表单
**现象**：新建弹窗的「类别」下拉可选命名/类型/码值/单位/口径/安全六类，但无论选哪类，表单字段始终是「规则表达式 + 示例」（命名标准专属），码值类不给码值录入区、类型类不给类型字段、口径类不给口径字段。前端源码注释亦表明「首期开放完整管理的类别：命名+类型」（MANAGED_STANDARD_KINDS）。

**证据**：类别切到「码值标准」后 labels 仍为 类别/编码/名称/排序/描述/适用范围/规则表达式/示例，无码值编辑表格。
**影响**：用户若用此表单建码值/口径/安全标准会产出缺字段的半成品；表单类别选项与可用字段不一致，易误用。
**建议**：要么按类别屏蔽不可新建的类别（只留命名/类型 + 引导码值走「码集管理」），要么按类别渲染专属字段；同时在页面上明示管理边界。

## I-8 ｜观察｜停用/启用不产生版本记录

**模块**：数据标准 · 版本历史
**现象**：对标准执行停用后，版本历史仍只有编辑产生的 v1 快照，没有状态变更记录。版本弹窗文案为「每次修改前自动记录修改前的完整状态」，未明确是否含状态变更。

**证据**：id 597 标准编辑后版本 1→2，再停用，`GET /standards/597/versions` 仍仅 1 条（v1 快照）。
**影响**：审计追溯状态变更只能靠 updateTime/操作日志，版本链路不完整。
**建议**：明确版本记录范围（是否含状态变更）；如含，补状态快照；如不含，在版本弹窗文案中注明。

## I-9 ｜观察｜测试期间服务两次不可达

**现象**：15:55–16:01 约 6 分钟 `http://198.19.63.66:8000` 连接失败（curl exit 7，ICMP 通），期间页面操作出现「操作失败，请稍后重试」与登录失效；16:01 后自动恢复，同操作重试全部通过。另有一次短暂 fetch 不可用后自愈。

**影响**：可用性抖动；确认弹窗/会话被中断时的错误提示文案（「操作失败，请稍后重试」）合理，但网络异常与业务异常的 toast 无法区分。
**建议**：核查该时段服务/容器状态；前端可对网络层失败与业务失败给差异化提示。
