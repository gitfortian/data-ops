## M-1 ｜P1｜中文命名的指标编码自动生成缺陷，同前缀指标必然创建失败

**模块**：指标中心 · 指标管理（新建指标）
**现象**：指标编码「选填，系统自动生成」，但生成算法对中文名称只提取拉丁字母前缀：
- 「QA测试原子指标」→ 生成编码 `qa`（无语义、不可读）；
- 再建任何一个中文前缀相同的指标（如「QA测试复合指标」→ 同样生成 `qa`）必然冲突报错；
- 纯中文名称（如「订单量」）生成结果为空，直接创建失败。

**证据**：
- 创建「QA测试原子指标」后列表编码列为 `qa`；
- 复合指标提交请求被服务端拒绝：`POST /api/v1/metrics` → `{"message":"指标编码已存在：qa","code":44002}`（fetch 监控捕获）；
- 源码根因：`Metric.java:34` `generateCode(name)` = `name.toLowerCase().replaceAll("[^a-z0-9]+", "_")` 后 trim——所有非拉丁字符折叠成一个 `_` 再被裁掉，中文部分全部丢失。

**影响**：中文语境下「系统自动生成」基本不可用——要么产出无意义编码，要么直接失败；与列表里人工编码的规范（`ord_cnt_1w`、`pay_amt_1m` 带过程/度量/周期语义）严重不符。
**建议**：生成算法改为有语义的组合（如 `{过程码}_{度量}_{周期}` 或对中文名做拼音/哈希兜底），并在编码 placeholder 明示生成规则；纯中文名至少给出明确错误提示而非空编码异常。

## M-2 ｜P1｜业务错误被前端吞掉，指标创建失败完全无提示（静默失败）

**模块**：指标中心 · 指标管理（新建/编辑提交）
**现象**：表单填写完整、点击「创建」后：弹窗关闭、无成功/错误 toast、无字段级错误、列表不刷新——界面没有任何失败迹象，用户完全无法感知创建未成功。

**复现步骤**：
1. 新建指标，类型选「复合指标」，填名称「QA测试复合指标」、业务域、公式 `ord_cnt_1d + pay_amt_1d`；
2. 点「创建」；
3. 观察：弹窗关闭，无任何提示，指标总数不变（未创建）。

**证据**：
- fetch 监控：`POST /api/v1/metrics` 实际返回 `{"message":"指标编码已存在：qa","code":44002}`（HTTP 200 + 业务错误码）；
- 界面侧：`.ant-message-notice` 为空、`.ant-form-item-explain-error` 为空、列表统计不变；
- 源码根因：`MetricEditModal.tsx:487` `catch { // API 报错已由全局错误提示统一展示 }`——错误被吞且注释声称的全局提示实际未出现（业务错误码 44002 未走 message.error 通道）。

**影响**：任何创建/更新失败（编码冲突、校验拒绝、服务端异常）都表现为「点了没反应」，用户会反复重试或以为已成功；复合指标在当前数据下 100% 无法创建成功且无解释。
**建议**：提交失败时必须把后端 message 透出（`message.error`）；对已知业务码（44002 重复编码等）给出字段级提示和修正建议（如自动追加序号）；补一条「创建失败必须有可见反馈」的回归用例。

## M-3 ｜P2｜血缘图谱不渲染「数据来源模型」依赖，模型→指标上游链路缺失

**模块**：指标中心 · 指标血缘
**现象**：原子指标创建时自动登记了 MODEL 依赖（依赖表可见），但血缘图谱中该模型不出现在上游：上游计数为 0，图谱只渲染中心节点并提示「暂未采集到上下游关系」。而 METRIC 类依赖（复合子指标）能正常渲染为上游节点。

**证据**：
- 指标 qa（原子，依赖 MODEL dwd_orders_create）：血缘页显示「上游 0」，依赖表明细有 1 条「数据来源模型 dwd_orders_create」；
- 指标 优惠占比（复合，依赖 2 个 COMPOSITION）：血缘页显示「上游 2」，两个 METRIC 节点正常渲染。

**影响**：页面宣传的全链路「模型 → 原子指标 → 派生/复合指标 → 消费方」中，「模型→指标」这一段在图谱中不可见；用户无法从图谱判断指标的数据来源，影响溯源。
**建议**：图谱渲染补齐 MODEL/CALIBER/UNIT 等非 METRIC 依赖节点（可用不同类型图标区分）；依赖表与图谱计数保持一致。

## M-4 ｜P2｜影响分析无法得出结论：当前版本全为「-」，状态永远「待检查」

**模块**：指标中心 · 影响分析
**现象**：选择指标并「执行分析」后，依赖表中每个依赖的「当前版本」列显示「-」，「变更状态」全部为「待检查」，汇总「有变更 0」——分析器没有拿到上游依赖的当前版本，任何输入都得到同一结果。

**证据**：优惠占比（依赖 ord_amt_1d/discount_amt_1d，注册版本均 v1）执行分析后：两行均「当前版本 - / 待检查」，有变更 0。

**影响**：影响分析是「评估指标是否需要重新校准」的核心功能，当前输出无信息量，无法支撑任何决策。
**建议**：排查上游依赖当前版本的解析逻辑（依赖快照里的 subMetricId → 当前 Metric 版本的查询链路）；确实无法获取时应明确提示「无法获取当前版本」而非显示「待检查」；补充一条「上游指标升级版本后，影响分析能标出变更」的验收用例。

## M-5 ｜P3｜详情页「计算规则」展示错误字段，普遍显示「-」

**模块**：指标中心 · 指标详情
**现象**：详情页「计算规则」渲染的是 `metric.calRule`（口径规则，引口径标准时才有值），而不是用户创建时填写的度量表达式（聚合函数+字段+过滤条件）。因此所有未引口径标准的指标，计算规则都显示「-」，与其真实计算逻辑不符。

**证据**：指标 qa 创建时度量表达式为 COUNT(order_id)（编辑表单回填验证无误），详情页「计算规则」显示「-」；源码 `detail/index.tsx:172` `children: metric.calRule || '-'`。
**影响**：详情页无法回答「这个指标怎么算的」，是指标定义的核心信息缺失。
**建议**：计算规则展示 measureExpr/filterExpr（可格式化为 `COUNT(order_id) WHERE ...`），calRule 作为单独的「口径规则」字段展示。

## M-6 ｜P3｜「业务域」字段实为业务过程名，与语义层概念混淆

**模块**：指标中心 · 新建/编辑指标、列表列
**现象**：指标的「业务域」字段通过树形选择器填充，但可选节点里混列了业务域（交易域/用户域…）与业务过程（订单/支付/退款…），且实际填入的值是过程名（列表「业务域」列显示 订单/支付）。与语义中心的「业务域」（交易域）不是同一概念，一词二义。

**证据**：列表 20 个指标业务域列取值均为 订单/支付/未分类（过程名）；新建表单业务域下拉选中「订单」后即作为业务域保存。
**影响**：跨模块数据对不齐（语义层业务域 vs 指标业务域）；用户按「交易域」筛选指标时找不到按过程归档的指标。
**建议**：明确指标「业务域」的取值域（要么只允许选语义业务域、过程单独一栏，要么改名「业务分组」并统一各模块用法）。

## M-7 ｜P3｜标签编码与指标编码的自动生成策略不一致

**模块**：指标中心 · 指标服务（标签管理）
**现象**：标签编码自动生成保留中文（「QA测试标签」→ `qa测试标签`），而指标编码生成剥离中文（M-1）。同类「编码自动生成」能力在两个模块行为相反。
