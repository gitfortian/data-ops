## 二、问题诊断（按严重度）

### P1 一级菜单爆炸，且分区逻辑讲不通
17 个一级组远超「7±2」认知上限。更致命的是分区语义失效：「任务区」里塞着建模/语义/主数据/指标/生命周期——这些是**治理标准域**，不是任务；「管理区」里塞着资产/质量/安全——这些才是治理。新用户看着两排菜单，无法回答"数据从进到出，我该走哪条路"。

### P2 同一能力多个入口，用户不知道"东西在哪找"
- **目录三处**：元数据-目录浏览、数据资产-资产目录、数据消费-数据目录（隐藏）。用户找一张表应该去哪里？答案不该是"看运气"。
- **血缘三处**：数据消费-数据血缘（全局）、指标中心-指标血缘、建模-变更影响分析（隐藏）。
- **审批两处**：主数据管理-主数据审批、审批中心-待办中心。后端已选「存量代码 + 审批中心开关」的集成方式，前端却还保留双入口。
- **权限两处**：数据安全-权限管理、系统管理-资源授权。
- **运行记录四处**：数据开发、数据质量、生命周期、数据服务各有一套，没有统一"今天跑批怎么样了"的入口。

### P3 有幽灵页：能力已开发，菜单不可见
`pages/alarm`（告警列表，150 行）、`pages/ai-agent`（智能体，984 行）、`pages/metrics`（运行指标，389 行）均无任何路由/菜单登记——做完的功能用户看不到，等于没做。告警缺位还造成连带问题：**运行异常没有跨域汇聚入口**，只能靠各域页面里翻。

### P4 无角色视角
四类用户（数据开发、数据 Owner/治理员、分析师/业务消费方、平台管理员）各有各的主路径，但菜单只有一套"平台能力清单"视角。典型后果：分析师找张报表数据得穿过集成/建模/主数据一路图标；治理员每天在资产、质量、安全、审批四组之间横跳。

### P5 首页不承担"工作台"职责
home 目前只有数据中心概览组件，没有待办、告警、运行健康的汇聚。首页本应是跨域入口，现在却和菜单问题互补：菜单不聚合，首页也不聚合，用户没有"一站式早上开工页"。

### P6 细节问题
- 命名含糊：「数据消费」vs「数据服务」一线之隔，实际一个是 BI 侧、一个是 API 侧；「资源管理」只有一页文件资源，撑不起一个组。
- 图标复用严重：`project` 用于 3 个组、`database` 用于 6 个组、`api` 用于 2 个组，侧边栏视觉无法区分。
- 审批中心 order=36 硬插在质量/安全与数据消费之间，无信息架构含义。
- 数据源管理游离于组外作为顶级项，与集成域强绑定的它应该归位。

## 三、设计原则

1. **按数据生命周期分区**：接入 → 开发编排 → 标准建模 → 治理 → 资产 → 消费服务 → 系统。每个一级域回答一个问题："数据这一阶段的状态是什么、我该做什么"。
2. **一级 ≤7，二级 ≤6**：超过即合并或下沉为页内 Tab。
3. **一能力一家，其余皆链接**：目录、血缘、审批、告警各只有唯一归属地；其他域需要时用带参跳转，不复制入口。
4. **首页=工作台**：待办、告警、今日运行健康、常用入口的跨域汇聚，是每天的第一屏。
5. **角色走"动线"不走"菜单"**：不为角色建菜单（会重回爆炸老路），而是靠工作台快捷入口 + 各域内向导式空态承接。
6. **路由 path 是契约，菜单归属不是**：本次重排尽量不动 path，只动 menuGroup/order/命名，降低 RBAC 与外链破坏面。

## 四、新信息架构（推荐方案）

> 7 个业务一级域 + 首页 + 系统管理。标注 ⬇ 表示从原位置移入；标注 ★ 表示需新建/改造。

### 0. 工作台（首页，改造 ★）

## 五、关键取舍与自曝缺口

1. **治理域 18 个页面 vs 二级 ≤6 的矛盾**：**已决策（2026-09-20）→ 扩三级菜单**：侧边栏组件支持 group→subgroup→route，治理域按主数据/质量/安全/生命周期四个子域展开，一次性改造、所有域受益。
2. **menuCode 是 DB 持久化 RBAC 契约**：组的 re-parent 需要在 yak-security 出新的幂等迁移 SQL 重新登记父子关系；已应用的 V 文件不可改（会卡启动）。前端 `navigationMenuContract.test.ts` 需同步。
3. **目录合并（P2 三合一）是页面级工程**，不在菜单重排范围内，列为 M2。
4. **零侵入底线**：所有 path 不变、所有既有权限码不变，只做归属/命名/图标调整；被砍入口（mdm 审批、指标血缘、元数据目录浏览）先 redirect 一个版本再摘除，保收藏与外链。

### M0 落地记录（2026-09-20）

实际范围相对上表有两处调整：**M1 的菜单树迁移随 M0 一并交付**（契约测试硬性要求前端 menuGroup 与 DB parent_code 一致，纯前端重排无法过门），即 `V2036__domain_navigation_regroup.sql`（幂等 upsert：新登记 data-governance 组、10 个组 re-parent、data-source/data-analysis-lineage 页面重挂、mdm-approval 置 visible=0 active=0 退役、root 角色补授权 + 子孙⇒祖先两级授权推导）。

与计划的偏差：

1. **alarm 未接入工作台**（推迟到 M2）：前端 `pages/alarm/service.ts` 调 `/api/v1/alarm`，后端实际暴露 `/api/v1/alert`（`AlertConstants.API_PREFIX`），路径不一致，现在挂菜单等于上线一个报错页。M2 先对齐接口再上入口。
2. **指标血缘/影响分析未隐藏**：指标详情页尚无承接 Tab，隐藏后功能无处可去；保留在指标中心组内，M2 做详情页 Tab 时一并收口。
3. **mdm-approval 的退役已于 2026-09-21 撤销**（`V2038__reinstate_mdm_change_ledger_menu.sql`）：M0 当时判定「主数据审批页并入审批中心」并删除前端路由、由 `config/routes.ts` 的 `/mdm/approval → /approval/todo` redirect 承接。该前提只对一半——「通过/拒绝」确实在审批中心待办，但**变更单台账（按状态查全部 MDM 申请）与「撤回在途变更」审批中心各页都没有**，redirect 之后整页零 UI 入口。现菜单以「主数据变更」名接回 `mdm` 组（order 50，menuCode 仍为 `mdm-approval` 不改 RBAC 契约），redirect 删除，页面标题随之改名以免与「待办中心」重名却功能不同；依据见 `docs/mdm/reuse-plan.md` R7 ⑩。
4. ai-agent 顶栏入口（Sparkles 按钮 → `/ai-agent`）已在 M0 完成。

V2036 生效条件：IntelliJ 重新构建 + 重启后端（迁移在启动时执行）；重启前 root 账号不受影响（`security:root` 旁路菜单校验），非 root 角色的菜单树以重启后为准。

## 七、角色动线验收（新菜单后应能一句话回答）

- **数据开发**："接一个新库"→ 数据接入-数据源；"今天的任务跑挂了吗"→ 首页今日运行/告警。
- **数据 Owner**："我部门有哪些表没上架/没人认领"→ 数据资产-盘点上架；"这条变更申请谁批"→ 首页待办。
- **分析师**："有没有订单明细"→ 数据资产-资产目录（唯一答案）；"要个接口"→ 消费与服务-API 集市。
- **管理员**："给新同事开权限"→ 系统管理-角色与权限 + 资源授权。
