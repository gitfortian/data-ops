# 数仓建模功能需求规格

> 来源:[ori-model.md](./ori-model.md)(需求侧原始描述,共 7 条)
> 状态:**v1.0 —— 需求侧 10 项决策已确认(2026-09-09),可进入技术方案设计**
> 决策记录见第 7 节;本期范围外清单见第 4.9 节。

## 1. 背景与目标

平台已具备数据源管理、数据集成(离线/实时同步)、数据开发、工作流调度、数据质量、血缘、数据集/分析/数据服务等能力,覆盖"连接 → 同步 → 开发 → 编排 → 校验 → 服务"链路。数仓建模功能的定位是补上链路最前端的"模型层":让用户在平台内完成**数仓模型的设计、落地、加工与治理**,使模型成为贯穿开发、质量、血缘、数据服务的统一资产,而不是散落在库表和文档里。

一句话目标:**正向从业务出发设计模型,逆向把存量库表导入治理,逻辑模型一键落地物理库,模型资产全域可视。**

## 2. 原始需求解读(结合已确认决策)

| # | 原始描述 | 解读 | 落地口径(已确认) |
| --- | --- | --- | --- |
| 1 | 可视化建模,数据模型管理、模型加工任务管理,在线进行物理模型来源数据映射配置 | 三个子能力:①可视化建模(画布);②模型目录管理;③"模型加工任务"= 把源端数据加工成目标模型的任务(含字段级映射配置) | 映射配置生成 SQL,交数据开发任务体系执行(决策 D2) |
| 2 | 数据模型在线编辑(创建、删除、查询) | 模型 CRUD 基础能力,"编辑"隐含更新 | 按常规实现 |
| 3 | 实体对象、属性信息编辑、映射,逻辑模型配置完成后直接生成物理模型 | 正向建模主链路:逻辑模型(实体/属性/关系)→ 一键生成物理模型 | 逻辑模型为建模模块独立实现(本体/语义功能已从当前分支移除,不关联);单个逻辑模型仅落地单个目标库、单一方言(决策 D1/D10) |
| 4 | 从数据库加载元数据,读取元数据信息生成物理模型 | 逆向建模:复用数据源 catalog 能力(库/schema/表/字段),勾选导入生成模型 | 数据源模块已具备完整元数据读取能力,直接复用 |
| 5 | 与源端各业务系统集成,自动生成建库脚本,动态感知源端表结构变化,及时提示 | 三个子能力:①物理模型 → DDL 建库脚本(多方言);②源端表结构变更感知;③变更通知 | 脚本仅生成/复制/下载,不直接执行(决策 D3);变更感知仅覆盖模型引用的源表,提示后仅通知、不自动同步(决策 D4) |
| 6 | 全域数据模型集中化视图,模型资产统一管理、全局可视;多维度模型统一视图,表结构、关联关系、血缘链路可视化 | ①模型详情的整合视图(结构/关系/血缘);②跨模型的全域资产视图 | 模型归属项目空间,视图在项目空间范围内;血缘不自动登记,引导用户选择(决策 D7/D8) |
| 7 | 正向建模(从业务需求出发)+ 逆向建模(现有库表解析),兼顾新模型构建与存量模型治理 | 是 3 和 4 的总纲,强调双向 | 存量治理本期仅支持导入,不做 diff 对比与同步(决策 D9) |

## 3. 用户角色与核心场景

| 角色 | 场景 |
| --- | --- |
| 数据建模工程师 | 接到业务需求 → 正向创建逻辑模型(实体/属性/关系)→ 一键生成物理模型(选定目标库)→ 生成建库脚本(复制/下载)→ 配置来源映射 → 发布加工任务 |
| 数据开发工程师 | 在开发任务中引用模型;模型结构变化时收到通知并自行调整任务 |
| 存量治理负责人 | 把已有数仓库表(单表勾选或整 schema 批量)导入为模型资产 → 补充业务描述与归属 → 统一管理 |
| 数据分析师/消费者 | 在全域模型视图中找到需要的模型,查看表结构、关联关系、血缘,确认可信后消费 |

## 4. 功能需求清单

优先级:P0 = 首期必须;P1 = 第二批;P2 = 后续增强。

### 4.1 模型管理

| 编号 | 需求 | 说明 | 优先级 | 原始需求 |
| --- | --- | --- | --- | --- |
| FR-01 | 模型目录与 CRUD | 模型的创建/删除/查询(列表+详情)/编辑;支持目录树或列表管理、搜索过滤、回收站 | P0 | 2 |
| FR-02 | 模型分类组织(分层/主题域) | 数仓分层(ODS/DWD/DIM/DWS/ADS,允许自定义)与主题域归属。**本期不做(下一期)**;P0 期以目录树 + 标签临时承担组织职责 | 下一期 | 6(衍生) |
| FR-03 | 模型版本与发布 | 对齐数据开发模式:草稿 → 发布(生成不可变版本)→ 版本历史,结构变更可对比;无审批流 | P1 | —(平台模式一致性) |

### 4.2 物理模型编辑

| 编号 | 需求 | 说明 | 优先级 | 原始需求 |
| --- | --- | --- | --- | --- |
| FR-04 | 表结构在线编辑 | 字段(名称/类型/长度精度/可空/默认值/注释/业务描述)、主键、索引、分区、表属性;按目标库方言做合法性校验 | P0 | 1/2/3 |
| FR-05 | 模型 ER 关系画布 | 模型间关联关系(外键/逻辑关联)在画布上呈现与编辑;画布支持从模型目录拖入建模 | P0 | 1/6 |

### 4.3 正向建模(逻辑 → 物理)

| 编号 | 需求 | 说明 | 优先级 | 原始需求 |
| --- | --- | --- | --- | --- |
| FR-06 | 逻辑模型管理 | 实体对象、实体属性、实体间关系的编辑;每个元素带业务定义(中文名/业务含义/责任人);与物理模型解耦,不绑定具体数据库。**独立实现,不与本体/语义层关联** | P1 | 3 |
| FR-07 | 逻辑 → 物理生成 | 逻辑模型配置完成后一键生成物理模型:**单个逻辑模型仅落地单个目标数据源、单一方言**;字段类型自动映射(逻辑类型 → 方言类型),生成结果允许调整后再保存 | P1 | 3 |

### 4.4 逆向建模(库表 → 模型)

## 5. 与现有平台能力的关系

### 可直接复用的底座

| 现有能力 | 位置 | 支撑的功能 |
| --- | --- | --- |
| 数据源元数据读取(databases/schemas/tables/columns/searchTables) | `DataSourceCatalogController`、SPI `DataSourceCatalog` | FR-08 逆向建模、FR-15 变更比对的数据来源 |
| 任务生命周期(草稿→发布 revision→执行)+ TaskPlugin SPI | data-development 模块、`DevelopmentNodeType`、`TaskPlugin` | FR-03 版本模式对齐、FR-13 模型加工任务的挂接点 |
| 血缘存储与登记(`yak_metadata_asset` / `yak_metadata_relation`,evidence 机制)+ SQL 解析血缘 | lineage 模块 | FR-14 模型血缘(引导式登记) |
| reactflow 画布(血缘工作台、工作流编辑器已用) | data-ops-ui | FR-05 ER 画布、FR-12 映射可视化 |
| 通知/告警基础设施 | alert 模块 | FR-16 变更提示 |
| 项目空间规范 | docs/architecture/PROJECT_SCOPE.md | 模型表 project_id 归属设计(D8) |

### 能力缺口(需新建)

1. **建模域本体**:模型/实体/属性/关系/映射的存储与管理(新后端模块,建议 `data-ops-business-modeling`,自持 Flyway,从 V1 起编)。
2. **逻辑 → 物理的类型映射**:逻辑类型到各方言类型的映射规则(单库单方言场景,一次生成一个目标)。
3. **DDL 生成器**:模型 → 多方言建库脚本(与现有 `buildSqlTemplate` 方向相反;仅生成不执行)。
4. **源端结构变更感知**:数据源模块目前只有配置变更时的缓存失效,无 DDL diff 机制,需建模模块自建定时比对(仅覆盖模型引用的源表,快照范围可控)。

## 8. 建议分期

- **P0 —— 地基(可视可管)**:FR-01、FR-04、FR-05、FR-08、FR-10。模型目录(目录树 + 标签)+ 物理模型在线编辑 + ER 画布 + 逆向导入 + 建库脚本生成。完成后即具备"把存量库表变成平台内模型资产"的最小闭环。
- **P1 —— 链路(用得起来)**:FR-03、FR-06、FR-07、FR-12、FR-13、FR-14、FR-17。版本发布(对齐数据开发)+ 逻辑建模与一键落地(单库单方言)+ 来源映射与 SQL 加工任务(接入数据开发)+ 引导式血缘登记 + 模型统一视图。完成后打通"设计 → 落地 → 加工 → 溯源"主链路。
- **P2 —— 治理(管得住)**:FR-09、FR-15、FR-16、FR-18。批量导入、变更感知与通知(仅引用源表)、项目空间内全域视图。
- **下一期**:FR-02(数仓分层、主题域、命名规范)。

## 9. 技术落点建议(供评审,不属于需求)

- 后端:新建 `data-ops-business-modeling` 模块,自持 Flyway(`db/migration/yak-modeling`,V1 起);变更感知用定时任务 + catalog 比对(仅模型引用的源表),不依赖源端 DDL 监听。
- 加工任务:`DevelopmentNodeType` 登记新节点类型 + 实现 `TaskPlugin`(ServiceLoader SPI),复用 data-development 的发布/执行/调度。
