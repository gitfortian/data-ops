## 二、乱象发现清单（结构级，先发现不治理）

> 走查方式：意图契约（01 的 S 规矩）vs 代码/路由/菜单现实。按严重度排。

### R-1 ｜两套指标页面，旧套已成孤儿 🔴 高 → ✅ 已治理（2026-09-21）

- **现象**：前端存在 `src/pages/metric/`（在用：manage/lineage/impact/service/detail 四页）和 `src/pages/metrics/`（7 个 tsx：index/BarChart/SummaryCards…）两套页面；路由表只注册 `/metric/*`，**`pages/metrics` 无任何路由引用、无任何文件 import**。
- **影响**：新人改错页面改不动；`metrics/index.tsx:94` 的吞错 catch 就是从这个孤儿页里扫出来的（虚惊一场但暴露维护成本）；代码库噪音。
- **治理动作**：整目录删除 `pages/metrics`。删除前三重检查（无 import/无路由/无测试快照），删除后 `tsc --noEmit` 错误数 183 与删前一致（零新增），git 已记录删除。与 `pages/user/login` 遗留页处理同先例。

### R-2 ｜元数据目录/搜索入口并入资产目录 ⚪ 待办 → ✅ 已收尾（2026-09-21）

- **现象**：路由表里 `/data-metadata/catalog` 和 `/data-metadata/search` 重定向到 `/data-asset/catalog?view=entity`；「元数据管理」挂「数据资产」组。
- **定性（review 后改写）**：这不是失控乱象，是**菜单重设计 M2-2「目录三聚一」的既定决策**——V2037 迁移（`V2037__retire_metadata_catalog_menus.sql`）退役两菜单、能力并入资产目录「元数据实体」视图，旧地址保留 redirect。设计目标即“目录只有一本”。
- **收尾动作（已完成）**：资产目录「元数据实体」视图副标题已标注“数据由元数据模块采集提供”，用户可知能力出处。
- **翻案路径**：若坚持恢复独立入口，作 D-6 翻案议题，不进治理候选队列。

### R-3 ｜指标中心入口挂「消费与服务」组 🟡 中 → ✅ 已治理（2026-09-21）

- **现象**：指标归③（标准与建模），菜单 `menuGroup` 却把它挂在「消费与服务」（data-analysis）下。
- **影响**：用户按“定指标”去找，会去消费组找；产品经理讲架构时菜单和主轴对不上。
- **治理动作**：`navigation.ts` 指标中心组 `parentGroupId` 由 `data-analysis` 改为 `modeling`（标准与建模），子组 order 55（排在「数仓标准体系」50 之后，匹配主心骨③段“标准→指标→建模”顺序）。tsc 基线不变（183）。**注意：菜单改动需重新构建前端才在测试环境生效**。

### R-4 ｜大屏与仪表盘：无共享实现，且发布语义两套 🟡 中 → ✅ 已核实（2026-09-22）

- **核实结论**（读码，未跑功能）：
  1. **零共享**：两侧各有一整套平行的 `XxxVersion`（PO/Mapper/Repository/Adapter）+ `XxxPublisher`，`common`/`core`/`spi` 无任何“发布/版本”契约类——确系各写一套；
  2. **发布语义不同**（这不是抄漏，是两种模型）：
     - 仪表盘：**保存即追加不可变版本**（`DashboardVersionAppender` 每次保存草稿 appendVersion 并推 current 指针），`publish` 只翻 published 指针；restore/activate 操作历史版本；
     - 大屏：**发布才固化版本**（`DigitalScreenPublisher.publish` 时 nextVersionNo+insert），草稿态只有 revision；另有 offline/rollback（rollback=恢复草稿+插新版本，append-only）；
  3. **端点全集两侧都有**（仪表盘 versions/publish/restore/activate；大屏 versions/publish/offline/rollback），命名单有差异。
- **影响**：任何“版本/发布”机制改动要改两遍，必漏——此为原判断，成立。但核实后要修正结论：**这不是简单的代码重复，而是产品语义未统一**。
- **治理建议（修正后）**：顺序不能反——**先统一发布模型**（“保存即版本”还是“发布才固化”，二选一，产品裁定），再谈代码下沉共用；若产品允许两种模型并存，则抽共享的“版本表+指针”机制、两侧各配发布模型。**在语义未定前不动代码**（动了就是第三次返工）。
- **附带发现**：`docs/multi_version.md` 的 P3 统一范式（publish/offline/versions/activate）与两侧现状都对不上——该文档的范式落地本身也是待办。

### R-5 ｜“业务域”一词二义 🟡 中（部分已修）

- **建议**：D-2 拍板后彻底治理（一词一义+洗数）；这是 R 系列里唯一已进修复线的。

### R-9 ｜“安全等级”一词二义 🟢 低 → ✅ 已裁决（2026-09-22，语义缺口单 01）

- **现象**：语义 SECURITY 标准（level_code/mask_rule）与数据安全 `yak_dsec_security_level` 曾并行两套、零接线——建模列标了安全标准，数据安全页不认。
- **裁决（B+）**：核实后二者**不是同一事物**——dsec 等级是项目级**等级字典**（rank_no 定序，脱敏/分级/访问策略按 level_id 消费，真源=dsec）；语义 SECURITY 标准是**字段级分级/脱敏模板**（预置 25 条按敏感字段类别）。不整源合并，改为把桥接上：
  1. dsec 等级 `std_security_id` 引用语义 SECURITY 标准（松散 ID），`SecurityLevelService` 经 `StandardQueryApi` 校验存在+SECURITY+ENABLED（仿 MDM validateKindRef）；
  2. 分级页等级表单“关联数据标准”下拉修正为语义 SECURITY 标准（原错绑 dsec 自身等级列表）；
  3. SECURITY 标准 `mask_rule` 定性为参考文案，脱敏执行口径唯一在 dsec 脱敏算法（`StandardKind`/编辑弹窗已注记）。
- **遗留（登记不阻断）**：`StandardRecommendationService` 按 level_code 下划线分段匹配关键词的逻辑与 L2/L3/L4 现实错位；`StandardQueryApi.get` 不校验项目作用域（跨项目可查）。

### R-11 ｜派生指标登记式、修饰词无受控模型 🔴 高 → ✅ 已裁决（2026-09-22，指标缺口单 02）

- **现象**：派生指标表单只选一个原子指标+手填 dimConstraint 自由文本，派生自身 measureExpr/filterExpr/modelId 全空、口径/单位只展示不落库；全仓无"修饰词/业务限定"受控对象（semantic 六类标准无修饰词类）；建模反推 metricDraft 因派生无 modelId/measureExpr 而吃不到派生（指标盘点 §3.2/§3.10）。
- **裁决（metric 内结构化条件，不动 semantic）**：修饰词不入 semantic 标准体系——限定条件本质是"字段+运算符+值"的取数条件，与 semantic 的编码/命名/口径等"标准模板"不同物；且入标准体系需新建一类标准+CRUD+作用域迁移，侵入面大、收益低。改为 yak_metric 新增可空列 `qualifiers_json`（V3），派生保存时后端 `DerivedMetricAssembler` 由"原子 measureExpr/filterExpr + 限定条件"自动组装出派生的 measureExpr（继承原子）、filterExpr（原子 filter AND 限定条件，缺省 WHERE 1=1 时省略）、modelId/caliberId/unitId（继承原子），组装成功即派生拥有完整取数要素。
- **兼容**：存量派生（qualifiers_json 空、dimConstraint 自由文本）不迁移不组装，dimConstraint 保留展示；组装产物 filterExpr 即 03 试算的消费契约（标准 SQL 片段，零私有语法）。建模反推因组装落库 modelId/measureExpr 自动吃到派生，零改动。
- **遗留（登记不阻断）**：修饰词若将来需要跨指标复用（同名限定条件集中治理），再升级为 semantic 受控对象，届时 qualifiers_json 可作迁移来源。

### R-12 ｜指标定义不过审批闸 🟡 中 → ✅ 已裁决（2026-09-22，指标缺口单 08，方案 B：明确不过闸）

- **现象**：指标启用/停用两态即时生效、无审批；`ApprovalFlowCodes` 五个流程码无 METRIC 流，04 图亦无 MTR→APR 边——现状自洽，但与③段其他模块（模型/标准/安全/MDM 变更审批）纪律不一致，需拍板过闸与否。
- **裁决（方案 B：不过闸）**：①指标"保存即版本快照+乐观锁+停用/删除引用阻断"已构成台账型治理，审批闸在缺"发布态"模型下只能拦住"保存"这一步，治理增量有限；②审批真正该约束的是"已被消费指标的口径变更"，属 R-4 发布模型统一（保存即版本 vs 发布才固化）的全平台议题——R-4 未拍板前让 metric 单独过闸，就是第四次返工；③过闸需新增 DRAFT/PENDING 状态机，冲击 ENABLED/DISABLED 语义与停用校验/删除阻断两个面，成本高收益虚。指标资产对外交付的把关走既有 ASSET_PUBLISH 上架审批（间接、通用）即可。
- **重启条件（任一触发即重开本议题）**：①R-4 拍板"发布才固化"后，指标随全平台统一接入发布闸；②01/10 消费接线铺开后出现"外部 SLA/付费 API 直接消费指标定义"场景，需要变更冻结窗口；③审计/合规明确要求指标口径有审批留痕。届时按 §7.5 新增 METRIC_PUBLISH 流程码而非继承资产层，且现有 ENABLED/DISABLED 语义必须保留。
- **相互作用（缺口单 07/03 联动）**：不过闸 ⇒ 版本回滚直接恢复快照并追加新版本记录，**不走审批**；03 试算为只读查询，与闸无关。
- **落档面**：04 图乱象标注补记（图上无 MTR→APR 边=设计如此）；指标盘点 §6 P2 行、结论 5 同步定案。
