# 数据资产 · 现状与能力分析

> 盘点日期：2026-09-21；依据：`docs/v1/04-主脉与模块交互图.md` 图二（横切B治理段）+ 代码走查。后端 `yak-ops-business/yak-ops-business-asset`（46 个 Java 文件），前端 `yak-ops-ui/src/pages/data-asset`。

## 1. 模块概览

- 模块名称：数据资产（菜单名「数据资产」，路由前缀 `/data-asset`）
- 在主脉与模块交互图中的位置：横切B·治理段核心节点，全平台资产「一本账 + 七格状态机」
- 上游模块：全部业务域 Provider 投影（实测在账 7 域）；质量（稽核事实，拉取式）、安全（分级事实）、工作流（运行事实——图中有边、代码零实现）、元数据（目录并入 M2-2）
- 下游模块：审批中心（上架申请 ASSET_PUBLISH）、首页（总览取数）、生命周期（TTL 事实反查）
- 模块一句话定位：只读聚合各域事实、独占推进资产生命周期（发现→归档）的治理台账
- 当前实现状态：**部分实现**——机制层（对账/状态条/审批回调）真实落地，但台账覆盖面（7/24 域在账）远未达到"一本账"承诺
- 主要入口：前端 `/data-asset/overview|catalog|inventory|detail|taxonomy`；API：AssetController、AssetDirectoryController、AssetInventoryController、AssetRuleController、AssetTagController；任务：AssetScheduleEngineBridge/AssetScheduleHandler（健康快照调度）

## 3. 子功能逐个分析

（按分组覆盖，每项含：业务含义/角色/输入/输出/依赖/交互/必要性/理由/问题/建议）

**资产目录（含元数据实体视图）**——业务含义：全平台可发现资产的唯一入口；角色：数据治理、分析、开发；输入：各 Provider 投影 + 元数据实体；输出：目录检索/浏览；依赖：metadata 检索核（AssetExplorer 直接 import，模块边界破口）；交互：元数据采集、审批、生命周期。必要性：**必要**（主脉治理面核心）。问题：检索实现寄居 metadata 模块，"目录一本账"名归资产、实仍跨模块。建议：**保留 + 重构**（把检索核下沉 common 或迁入 asset）。

**资产清单/盘点 + 手动登记 + 详情**——台账基本盘；角色：治理员。必要性：**必要**。问题：手动登记与 Provider 投影的关系（会不会两套真相）需守"只记目录不存内容"契约，代码已守但登记入口使重复入账成为可能。建议：保留，登记项加来源标记与去重。

**分类体系/标签/分配规则**——业务含义：资产分组与检索维度；角色：治理员。必要性：分类与标签**较必要**；自动分配规则当前无使用方证据、无独立管理页。问题：规则引擎空转风险。建议：分类/标签保留；分配规则**过渡**观察一个迭代，无人用则下线。

**七格状态条**——业务含义：回答"这个资产能不能放心用"；角色：治理员、消费方。输入：modeling 事实（AssetStatusModelFacts）、TTL 事实、QualityMonitorReader、血缘、SecurityClassificationQueryApi、ApprovalApi；输出：PASS/FAIL/NA/UNKNOWN 七格。必要性：**必要**（M2 主线）。问题：①只读聚合意味着没有持久化状态——"推进七格"实际是"计算七格"，与 05 #11 的"独占推进"表述不一致，跨页一致性靠现算成本；②任一事实源缺席即 UNKNOWN，目前安全/血缘等域供数面窄。建议：**保留 + 补齐**（如确有运营中/归档诉求，需引入显式状态事件表）。

**上架前检查 + 上架审批 + 下线**——治理闸口三件套；角色：资产 owner、审批人。必要性：**必要**。问题：M2-5 仍处"只读观察期"，闸门未强制；下架后消费方（看板/API）无联动拦截。建议：保留；观察期尽快定去留（挂起即乱）。

**Provider 对账**——台账与源域一致性的根机制；角色：系统。必要性：**必要**（S8 契约载体）。问题：仅 7 域有 Provider，缺的恰是治理最需要的 datasource/quality/security/service/mdm/screen/workflow/sync。建议：补齐（见第 6 节）。

**健康度快照（任务存在，无界面管理）**——角色：治理员。必要性：**较必要**。问题：快照口径依赖在账率，缺席域=无健康数据。建议：保留。

**查看记录**——热度参考；必要性：**较必要**；建议保留。

## 4. 模块真实功能定位

- 实际角色：**治理展示模块 + 状态判读引擎**，而非文档暗示的"资产运营中枢"——它没有自有的生命周期事件流，状态是从别的模块现读现算的。
- 是否主脉关键节点：**是（潜在）**。上架审批闸已接 ASSET_PUBLISH；但消费链路（数据集/看板/API 出账）不引用资产状态，资产状态目前只影响"看不看得见"，不影响"用不用得了"。
- 是否被强依赖：被首页、审批中心依赖；不被任何执行模块依赖。
- 类型归类：治理模块 + 展示模块复合。
- 真实边界：台账+判读+上下架，**不含**内容、权限、质量执行。
- 职责过载/不清：检索核寄居 metadata 造成"目录归谁"边界不清；"七格推进"表述与"七格计算"实现不一致。
- 若下线：目录/盘点/状态条/上架闸消失；各域自身功能不受影响——说明它当前是"观察层"而非"控制层"。

## 5. 与其他模块的交互关系（对齐图二）

- 上游：7 个 AssetProvider（metadata/modeling/metric/development/dataset/analysis/dashboard）→ 目录投影 ✅；质量稽核事实（QualityMonitorReader，拉取式，质量 agent 已证实质量零推送）✅；安全分级事实（SecurityClassificationQueryApi 唯一消费方就是本模块）✅；生命周期 TTL 事实（AssetStatusTtlFacts 由 lifecycle 提供）✅；血缘（LineageQueryService）✅。
- **WFL→AST 运行事实：图中有边，代码零实现**（工作流盘点证实）——七格中"运营中"缺运行维事实源。
- 下游：审批中心 ASSET_PUBLISH（AssetPublishApprovalHandler）✅；元数据目录入口并入（redirect + 标注）✅。
- 数据流：拉取式（asset 主动读各域），控制流：上架/下线在 asset 内发起审批；事件：无事件总线，全同步调用；异步：健康快照调度。
- 共享存储：无（正确——守"只记目录"）。
- 风险点：①拉取式无缓存策略，目录页每渲染打 N 个域；②缺席域让"一本账"变成"部分账"，用户误以为查无即不存在；③与 metadata 的双向 import 是循环耦合苗头。

## 6. 缺失能力分析

| 缺失能力 | 为什么需要 | 影响的业务场景 | 优先级 | 建议实现方式 | 依赖模块 |
|---|---|---|---|---|---|
| datasource/quality/security/data-service/mdm/digital-screen/sync 的 AssetProvider 补齐 | "一本账"承诺；缺席即台账失真 | 资产盘点、影响分析、上架范围 | P0 | 每域实现 AssetProvider 投影 | 各源域 |
| 状态持久化/事件化（当前全现算） | 七格无法回答"何时进入该状态"，审计与 SLA 无从谈起 | 上架审计、运营考核 | P1 | 状态变更事件表，读事实+落轨迹 | workflow |
| 消费链路强制引用资产状态（未上架不可被 API/看板发布引用） | 状态机不闭环，闸门虚设 | 上架治理主线 | P0 | dataset/service/dashboard 发布前查 asset 状态 | 资产→消费域 |
| WFL 运行事实接入 | "运营中/归档策略"格无据可判 | 状态条可信度 | P1 | workflow 提供运行摘要查询，asset 读取 | 工作流 |
| 检索核（AssetExplorer）从 metadata 解耦 | 消除双向 import | 目录性能与边界 | P2 | 下沉 common SPI | 元数据 |
| M2-5 观察期结论落地（强制或撤闸） | 长期"只读观察"= 无闸 | 上架准入 | P1（决策项） | 负责人拍板 | 审批中心 |

## 7. 模块现状总结

- 已实现核心：Provider 对账 + 目录/盘点/详情 + 七格状态条（只读聚合）+ 上架审批回调 + 健康快照。
- 页面已展示未闭环：上架闸门（观察期不强制）；分配规则（无管理页）；"运营中"格（无运行事实）。
- 接口存在无页面：自动分配规则、部分 setting 端点。
- 任务存在无界面：健康快照调度（仅结果上首页环）。
- 冗余或重复：与 metadata 的检索核耦合（非重复但越界）。
- 真实业务定位：治理观察层（读各域、算状态），尚未成为控制层。
- 最大风险：**在账率 7/24 的"一本账"**——用户拿一份缺一大半的台账做治理决策。
- 最该补齐 3 项：①缺席域 Provider；②消费链路强制引用状态；③状态事件持久化。
- 下一步：先补 Provider（机械活，一域一天），同时拍板 M2-5 去留。
