## 1. 模块概览

指标中心是主轴③"标准→指标→建模"中的**指标定义与治理登记层**：统一管理原子/派生/复合三类指标的定义（口径、度量表达式、过滤条件、维度限定、统计周期、负责人），并围绕定义自动登记依赖快照（血缘）、版本快照、标签、使用记录，向前端提供管理/血缘/影响分析/服务四类页面。

- 后端：Maven 模块已接入 reactor（`data-ops-business/pom.xml:42`）并进入 boot 装配（`data-ops-boot/pom.xml:69`）；包结构为 config/catalog/controller/dao/domain/repository/api/tag/version(在 repository 内)/lineage/usage/impact/support/asset（`ARCHITECTURE.md` 与源码目录一致）。
- 数据：自有 Flyway 两段迁移，共 **7 张表**（`V1__create_metric_tables.sql`：yak_metric、yak_metric_tag、yak_metric_tag_rel、yak_metric_version、yak_metric_dependency、yak_metric_composition、yak_metric_usage；`V2__metric_definition_fields.sql` 增补 process_id/measure_expr/filter_expr/dim_model_ids/ref_metric_id/dim_constraint 六个定义字段）。全库再无任何其它迁移触碰 yak_metric* 表（已 grep 核实）。
- 前端：`/metric/*` 路由共 **5 个页面**（菜单页 4 个：manage/lineage/impact/service；隐藏详情页 1 个：`/metric/manage/:id`），注册于 `src/config/navigation.ts:133-137` 与 `.umi/core/route.tsx`（id 114-123）。菜单组 `metric` 的 `parentGroupId` 已改为 `modeling`（`navigation.ts:58`），R-3 治理已落到代码。
- 定性：**"指标定义 + 血缘/版本登记"的台账与工作台已完整落地；"指标计算/指标值查询/指标消费接线"完全未落地。**它是登记簿和依赖快照器，还不是指标计算引擎或查询出口。

## 3. 子功能逐个分析

### 3.1 指标定义 CRUD（§2.1–2.4）
- **业务含义**：把"业务看什么"钉成一条带编码、口径、表达式、周期的正式定义，是全模块的地基。
- **使用角色**：数据/指标管理员（`metric:create/update/delete` 权限，`MetricPermissionCode`）。
- **输入**：名称（编码可自动生成）、业务域（必填，选顶层域）、类型，及按类型的差异字段——原子：业务过程+度量表达式（聚合函数+DWD 模型字段选择器拼装）+来源 DWD 模型+DIM 模型+过滤条件+口径/单位引用；派生：引用原子指标+维度限定文本；复合：公式编辑器（token 流）。
- **输出**：主表行 + 版本快照 v1 + 依赖登记 + 血缘图注册（afterCommit、fail-open）+ 审计（METRIC_CREATE/UPDATE/STATUS/DELETE）。
- **依赖**：semantic（ProcessApi/StandardQueryApi 选域/过程/口径/单位）、modeling（ModelQueryApi + 前端直调模型列表/结构接口）、lineage（登记桥）、audit。
- **交互模块**：SEM、MOD、LIN、APR(否)、审计。
- **必要性**：**必要**。
- **理由/实现度**：三类指标**都有真实的差异化校验**：`validateByType`（MetricCatalogService.java:493-531）强制原子必填 measureExpr+modelId+processId，派生必填 refMetricId 且**只能引用 ATOMIC**，复合走 token 流校验（≥1 个 REF、禁自引用、沿组成图 DFS 环检测，:414-475）。删除/停用有下游引用阻断（:273-287、:478-486）。乐观锁、编码不可改、项目空间绑定均落地。测试报告 M-1/M-2（中文编码冲突、静默吞错）已在 f65d4a6c1 修复（CodeGenerator + `skipErrorHandler` 透传）。
- **问题**：①派生的"生成"仅到"引用+自由文本限定"为止，无修饰词实体、无自动拼接（见 3.2）；②calRule（计算规则）、statDimensions（统计维度）后端字段/接口齐备，但**编辑表单没有输入项**（MetricEditModal 无对应 Form.Item），口径标准选中后也不会"从标准带出 cal_rule"（工单 46 要求）；③编辑弹窗对新建态会整体重置类型相关字段，历史自由文本字段（如 calRule）只能靠 toFormValues 透传保留，易被后续改动破坏。
- **建议**：给 calRule/statDimensions 补表单项或在选口径时自动带出；负责人默认当前用户（M-9 观察项至今未做）。

### 3.2 派生指标机制
- **业务含义**：原子指标 + 维度限定 = 派生，是指标可复算、可对齐口径的关键。
- **现状判定（回答任务问题"派生是否真的从原子+修饰词生成"）**：**否，当前是登记式而非生成式**。表单只选一个原子指标并手填 dimConstraint 文本（MetricEditModal.tsx:630-696），选中原子后仅自动带出业务过程（:391-394）和单位/口径"只读展示"（:663-683，**不写入派生自身的字段**）；派生的 measureExpr/filterExpr/modelId 均为空。没有任何"原子表达式+修饰词→派生 SQL/口径"的组装逻辑，也没有独立的"修饰词/业务限定"标准对象（semantic 六类标准中无修饰词类，`docs/semantic/metrics/` 亦无实现痕迹）。
- **必要性判断**：机制本身**必要**，但当前形态属**过渡**——够用做台账，不够用做治理：详情页计算规则对派生只显示"引用原子指标 X"（detail/index.tsx:47-49），**dimConstraint 这个派生最核心的信息在详情页任何区域都不展示**。
- **问题**：修饰词不受管理、口径不继承、派生定义信息在展示端丢失。
- **建议**：短期把 dimConstraint/继承链展示补全；中期把"业务限定/修饰词"升格为 semantic 受控对象或由原子+结构化条件生成表达式。
- **复核（2026-09-22，缺口单 02）**：已由**生成式**取代——裁决"metric 内结构化条件"（05 清单 R-11），限定条件编辑器（字段/运算符选择器）+ `DerivedMetricAssembler` 保存时自动组装 measureExpr/filterExpr/modelId 并继承口径/单位落库；存量自由文本 dimConstraint 兼容展示不迁移；建模反推随之吃到派生（§3.10）。

### 3.3 指标列表与统计（§2.5）
- 列表 13 列、服务端分页聚合（`GET /stats` countByType），编码/名称搜索+类型/状态筛选可用（manage/index.tsx）。**必要且达标**。问题：工单 47 承诺的"按业务域、负责人筛选"未上页面（域筛选后端 `repository.page(domainId)` 已支持纯缺 UI；负责人筛选后端也没有）；列表不含口径列。

### 3.4 指标详情页（§2.5–2.7）
- 六区齐备（属性/依赖/标签/版本/使用/组成项）+ M2-3 跨域引用摘要条 + "查看血缘"跳全局血缘工作台。**必要**。
- **问题**：对照工单 48"概览必须展示全部定义字段、引用类字段可点击跳转"——业务域/模型/口径/单位的**名称虽在服务端 enrich 了**（MetricController.enrichNames），但详情页 Descriptions 没有渲染这些引用字段，也没有跳转链接；dimConstraint、statDimensions、unitName 不展示。属"后端已备、前端未摆"。

### 3.5 版本快照（§2.10–2.11）
- 每次创建/更新/状态变更写 JSON 快照（`saveSnapshot`，状态变更也记，杜绝漂移），version 严格递增、乐观锁比对。单测覆盖（MetricCatalogServiceTest）。**必要、已达标**。对比/回滚为自认 P1 未做；`GET /{id}/versions/{version}` 有接口无页面。

### 3.6 血缘登记与图谱（§2.12–2.14）
- 双份真相的分工清晰：`yak_metric_dependency` 存**引用时刻快照**（type+id+code+version，服务端解析、best-effort），全局血缘图存**关系边**（模型→指标 CONSUMES、上游指标→本指标 DERIVES_FROM，assetKey=`metric:{id}` 全仓单点生成）。CRUD 事务提交后注册、失败 fail-open、删除时 evidence 清理（MetricLineageRegistrationService）。/metric/lineage 页图谱+依赖表双视图，且图谱会把未注册的 MODEL 依赖合成虚拟节点保证两视图口径一致（M-3 修复，lineage/index.tsx:56-89）。
- **必要性**：**必要**，是主轴③"指标改动可溯源"的落点。**问题**：CALIBER/UNIT 有意不入图（设计注释，可接受）；`/{id}/graph` 端点被 lineage 通用端点取代后成为无调用方的重复面。**建议**：下线或收口 metric 侧 graph 端点。

### 3.7 影响分析（§2.15–2.16）
- 正向分析真实可用：逐依赖比对登记版本 vs SPI 现值，模型/标准/指标三路解析，UNKNOWN 如实标注不假"待检查"（M-4 修复）。**较必要**。
- **问题**：①反向分析（改一个模型/原子指标，波及哪些下游指标与消费方）后端 `findAffectedMetrics` 是返回空列表的**桩**（MetricImpactService.java:109-111），页面也未提供该方向——"影响分析"名不副实，实际只是"我的上游变了没"；②使用引用数因 §5.4 断链恒为 0，摘要三格中一格是死数。**建议**：反向分析可基于 dependency 表的 `idx_yak_metric_dep_target(dependency_type, dependency_id)` 索引直接实现，成本很低。

### 3.8 使用记录（§2.17–2.18）——核心断链
- `MetricUsageApi.record` SPI、`yak_metric_usage` 表、统计聚合、删除阻断全部就绪，**但全仓 grep 证实 dataset/dashboard/data-service/digital-screen 没有任何一方 import 或调用 `MetricUsageApi`**；且这些模块的数据模型里根本没有指向指标中心的引用字段（其 "metrics" 均是字段级聚合绑定 `DatasetMetricBinding(fieldId, aggregation)` 或运行时监控指标，与指标中心无关）。该边是**只有契约、没有接线**（详见 §5.4）。
- **必要性判断**：机制**必要**（否则删除保护、影响面评估、资产"被谁用"全是空的），当前实现为**过渡**（空表自转）。
- **复核（2026-09-22，缺口单 01）**：dataset 侧已按"显式选择"裁决接线（见 §5.4 复核行与 05 清单 R-10），dashboard/data-service 断链仍在。

### 3.9 指标标签（§2.8–2.9）
- 标签本体 CRUD 在 /metric/service 可用、删除有挂载阻断；**assign/remove 接口和 api.ts 封装齐备但无任何页面调用**，详情页标签 Tab 只读、"管理标签"抽屉是占位空壳（detail/index.tsx:360-362）。**较必要**（轻量分组运营用）；**问题**：有标签体系却无处打标，功能闭环断在前端最后一步。

### 3.10 对建模的反推供给 MetricQueryApi（§2.19）
- **业务含义**：主脉图 MTR→MOD"指标反推汇总表"边的实现。SPI 接口置于 **common 层**（`io.yak.ops.common.api.metric.MetricQueryApi`），原因代码注释写明：metric 依赖 modeling，若放 modeling 会成环；实现 `MetricQueryApiImpl` 只回启用指标；建模侧以 `ObjectProvider` 注入、metric 缺席时按"无指标"降级不阻断派生（ModelDeriveService.java:111、892-894）。消费点真实：`GET /modeling/derive/metric-draft`（ModelingDeriveController.java:143-148）→ 建模详情页反推草稿（`pages/modeling/detail.tsx:1015` 调用，产出业务过程+上游模型+统计周期归一 DAY→1d+度量表达式解析 SUM(x)→聚合建议+维度建议，含缺模型时的告警文案）。
- **必要性**：**必要**，且是主轴③顺序（先指标后建模）的技术兑现。**问题**：反推质量依赖原子指标定义质量（未绑模型/表达式不合式则出告警草稿），派生指标因无 measureExpr 不参与反推——与 3.2 的"登记式派生"是同一短板的两个截面。

### 3.11 指标元数据 HTTP API / 指标服务页（§2.20 与 §2.8）
- MetricMetadataController（T54）提供对外元数据四端点，注释称"复用 data-service 鉴权"——**当前无法确认有任何外部消费方**，无页面、无 data-service 接线证据。/metric/service 页实际内容是标签+统计+目录（service/index.tsx），与"指标服务/对外供给"名义不符。
- **必要性判断**：元数据 API 属**较必要**（消费端就绪前的货架）；当前"指标服务"页的统计卡与目录是对 manage 页的重复呈现，**偏冗余**，建议要么把页改名（"标签与目录"），要么把 T54 API 的调试/订阅入口真正做进去。

### 3.12 资产投影与统一编码（§2.21–2.22）
- MetricAssetProvider 以血缘同口径的 `metric:{id}` 键向资产台账投影（asset ticket 94，域编码解析失败不污染指纹）；CodeGenerator 统一名称→编码（中文附 6 位 MD5 短哈希保唯一，有单测 CodeGeneratorTest）。均**必要、已达标**，属 M2 主线（一本账、一物一码）在指标侧的兑现。

## 4. 真实功能定位

**是"指标定义 + 血缘 + 测试工作台"吗？** 部分是。准确说：当前实现是**"指标定义台账 + 依赖快照登记簿 + 只读核验工作台"**。
- "定义台账"名副其实：三类指标差异化校验、版本快照、乐观锁、引用阻断都是真规则，不是空壳 CRUD。
- "血缘"指**依赖登记**而非数据流血缘，实现扎实（快照+图谱双视图、afterCommit、fail-open）。
- "测试工作台"仅指影响分析（上游变没变）与资产摘要这类**核验**功能；**没有指标值试算/预览能力**——没有任何地方能把 measureExpr/dimConstraint/公式编译成 SQL 去 datasource 执行，工单 48 的"数据预览（可选）"未做，也不在任何已实现清单里。

**与建模的双向耦合是否健康？** **健康，是本项目少见的干净设计。**判据：①两个方向各走各的单侧 SPI，无循环编译依赖——metric→modeling 走 modeling 的 `ModelQueryApi`（展示名/引用快照），modeling→metric 走 common 层 `MetricQueryApi`（放 common 是为了断环，注释明示）；②双向都是 `ObjectProvider` best-effort，任一侧缺席只降级不报错；③建模侧不存指标内容，只消费反推草稿；指标侧不存模型结构，只存 modelId+编码/版本快照。风险不在耦合形态而在**数据质量**：反推草稿吃的是原子指标的 measureExpr 和 modelId，若定义潦草（派生无表达式、复合不入反推），MOD←MTR 这条边的实际产出会远低于图面预期。

**结构性短板**是第三章反复出现的同一根轴：指标目前是**纯文本定义**（表达式是给模型/人读的，不是给机器算的），所以既支撑不了派生组装，也支撑不了值查询和消费接线。

## 7. 现状总结（九项）

1. **一句话定位**：指标中心=主轴③的指标定义台账与依赖/版本/血缘登记器，定义校验与血缘登记是实的，计算与消费是空的。
2. **最扎实的部分**：三类指标差异化校验（原子强约束、派生限定 ATOMIC、复合 token 流+环检测）、每次变更必写版本快照、afterCommit 血缘登记 fail-open、编码统一脚手架、项目空间与审计贯穿始终——工程纪律是全仓较好水平。
3. **最大空洞**：MTR→DBH/SVC 假接线（§5.4）。usage 体系整备了 SPI/表/聚合/阻断四件套，等一个不来的上报方；这是③段价值兑现的断点，修它优先于任何新功能。
4. **方法论未兑现点**：派生指标"原子+修饰词"只做到引用+自由文本（P0 缺失之二），连带拖弱 MTR→MOD 反推草稿的实际覆盖面。
5. **闸门现状**：指标启用/停用无审批——**已定案为方案 B「不过闸」**（2026-09-22 缺口单 08，裁决与三条重启条件见 05 清单 R-12）；M2-5 定标闸门、上架审批均不触及指标模块。若重启条件触发，按 §7.5 新增 METRIC_PUBLISH 流程码而不是默认继承资产层。
6. **前后端错位清单**：接口缺页面（tag assign/remove、版本快照、usage 明细、metadata API、metric 侧 graph）；页面缺后端（负责人筛选）；任务缺界面（市场/AI 推荐/反向影响/对比回滚）；R-1 的删除动作在工作区未提交，存在复活风险。
7. **文档与现实的一致性**：REQUIREMENTS/ARCHITECTURE 与代码高度一致（含自曝欠账），R-3 双端已修；唯 ARCHITECTURE "MetricQueryApi 消费方=dataset/dashboard" 与 DEPENDENCIES "被依赖(规划)" 的表述超前于代码现实（真实消费方只有 modeling），阅读时以 §5 核实为准。
8. **孤儿/冗余面**：`/metric/service` 页与 manage 页统计卡重复；`/{id}/graph` 与血缘通用端点重复；detail 页"管理标签"抽屉为空壳。均低风险但计入维护噪音。
9. **风险提示**：在 P0 断链修复前，指标中心的数据会持续呈现"零使用、零影响面"状态，容易被误读为指标资产没价值而降低投入；建议盘点结论明确"先接线、再增数、后谈市场/AI"。
