## 3. 子功能逐个分析

### 3.1 规则模板库与自定义模板（#1/#2）
- **名称**：规则模板库（内置 6 + 自定义 SQL 模板 + 目录树）
- **业务含义**："规则从模板实例化"的供给侧；用户可沉淀组织级质检 SQL 成资产。
- **使用角色**：数据工程师（建监控时选模板）、质量管理员（维护模板库）。
- **输入/输出**：模板 CRUD（SQL、set flag、默认算符/阈值、维度、目录）→ 模板列表/目录统计；规则实例保存模板快照（template_code/rule_type/dimension 冗余进 `yak_quality_rule`）。
- **依赖**：无外部模块；`QualityRulePolicy` 在建规则时校验模板存在且启用。
- **交互模块**：仅被本模块编辑器与 MDM 体检消费（`MdmQualityService` 按 code 反查内置模板）。
- **必要性**：**必要**。内置六类覆盖了行数为空/空值率/唯一率/值域/枚举/自定义 SQL 的核心质检语义，是模块的概念地基。
- **理由**：模板快照式设计使历史规则/历史执行不随模板改版漂移，与 revision 机制同向；自定义模板走独立 Controller 但同表，口径统一。
- **问题**：①自定义模板校验方式仅 NUMERIC/FIXED_VALUE 一种（policy 显式拒绝其它），表达力弱，复杂比对只能退回 CUSTOM_SQL 规则自己写死阈值；②模板删除仅逻辑删，`ruleCount` 统计含历史，库页面可能显示"被引用不能删"却查不到引用方（前端提示未逐一实测）；③内置模板不可禁用（enabled 字段存在但编辑器未暴露，当前无法确认是否刻意为之）。
- **建议**：**保留**。中期给自定义模板补"结果字符串/多列"校验类型前，先在页面文案写明"仅数值单值比较"。

### 3.2 数据表注册与监控绑定（#3/#4/#5）
- **名称**：表资产注册 + 一表一监控
- **业务含义**：质检对象=外部数据源里的**物理表**，绑定键=(数据源,库,schema,表) 四元组；先注册挂账、再挂监控、监控内配规则。
- **使用角色**：数据工程师/表 Owner。
- **输入/输出**：数据源树+候选表分页（排除已注册）→ 注册行；监控保存=基础配置+规则组+运行/通知设置一体提交。
- **依赖**：数据源目录能力（`listTables`/`buildSqlTemplate`）；`QualityTableTargetPolicy` 归一空串库名。
- **交互模块**：MDM（落地表自动注册）；AST（"已稽核"按同一四元组定位监控）。
- **必要性**：**必要**。这是"质检对象"的唯一真相模型，注册表使监控与物理表存在性解耦（表消失可报错而非静默）。
- **理由**：四元组唯一 + "未注册不许建监控" + "有监控不许取消注册"三道闸闭环；`existsMonitorForTarget` 使"一表一监控"成为强约束，报告/告警/盖章语义因此简单（last_result 单值可解释）。
- **问题**：①一表一监控是双刃剑：同一张表无法按"核心规则组/全量规则组"分频巡检，也无法多 Owner 分治；②平台内部产生的对象（数据集、无数据源挂点的表如 `yak_mdm_record`）挂不了监控——MDM 侧已确认此约束并绕行（体检落地表）；③注册时按数据源全量 `listTables` 建内存 Map 对账，超大 catalog 下有一次全表扫（依赖 datasource 侧元数据缓存兜底，未实测）。
- **建议**：**保留**；"一表多监控"若确有场景需连同盖章判据（多监控取最差/最新）一起设计，勿轻改唯一性。

### 3.3 质检执行引擎（#6/#7/#8 共用内核）
- **名称**：编译-执行-评估三件套（`QualitySqlCompiler`/`QualityExecutionWorker`/`QualityMetricEvaluator`）
- **业务含义**：把监控+规则快照编译成单列指标 SQL（`metric_value`），经数据源 preview 通道执行，按算符/阈值判 PASSED/NOT_PASSED。
- **使用角色**：程序（三种触发共用）。
- **输入/输出**：`QualityExecutionPlan`（monitor 快照+rules 快照+失败策略+通知设置）→ 逐规则 `yak_quality_rule_execution`（含 executed_sql）+ 汇总行 + monitor.last_result。
- **依赖**：数据源执行通道（唯一出口 `catalogGateway.preview`）；表引用/列引用/模板反引号方言全部由数据源插件的 `buildSqlTemplate` 决定，质量只拼 SELECT 表达式。
- **交互模块**：DS（强）、JOB/WFL（触发方）、ALR（结果出口）。
- **必要性**：**必要**。这是模块"质检执行器"人格（而非规则台账）的判定依据（详见 §4）。
- **理由**：SQL 全部服务端编译、只读单语句强校验（READ_ONLY_SELECT+分号禁）、WHERE 片段注入黑名单、`markExecutionRunning` CAS 防重、逐规则留 SQL 证据——执行链完整且防御姿态清晰。
- **问题**：①不走任务内核执行通道（无重试/无并发资源治理/无内核超时口径），自建线程池 2/6/100 全局共享，一个慢表大查询可占线程 20 分钟未见 statement 超时由质量侧设置（依赖 datasource 侧 preview 超时，当前无法确认具体值）；②规则串行执行，无并行度；③自定义 SQL 用 `SELECT ... UNION` 之外的首行首列取值，指标列名不匹配 `metric_value` 时静默取第一列，易误读；④`${table}/${where}/${column}` 文本替换后仅校验"以 SELECT 开头且无分号"，子查询读敏感表在只读账号缺位的库里可越权读——安全边界完全押在数据源账号上。
- **建议**：**保留**，中期把执行出口收敛到被审计的统一 SQL 运行时（见 §6 P1）。

### 3.4 手动触发与运行互斥（#6）
- **名称**：立即运行
- **业务含义**：用户在监控工作台点"运行"，异步受理返回执行编号。
- **输入/输出**：monitorId → executionNo（QM-时间-随机）；UI 轮询 `/{no}/status`。
- **依赖/交互**：仅本模块。
- **必要性**：**必要**。配置后即时验证的唯一回路。
- **理由**：受理事务内 `lockMonitor`+`hasActiveExecution` 双保险；队列拒绝也会留下 ERROR 执行记录，不静默丢单。
- **问题**：**无取消口**（cancel 只服务 WORKFLOW 触发，`/execution` 无 cancel 端点、前端无按钮）；重启时处于 WAITING/RUNNING 的执行**无人收尸**——`hasActiveExecution` 把该状态永远视为在跑，该监控之后所有手动/调度触发都会被判"已有运行中的检查任务"，需人工修库解卡（启动 reconciler 只恢复调度计划，不清理在跑执行）。
- **建议**：**补齐**（在途执行启动回收 + 取消端点，见 §6）。

### 3.5 定时调度（#7）
- **名称**：监控级定时（每日/每周/CRON）
- **业务含义**：monitor_setting 是事实源，framework ScheduleManager 只管时间触发；payload 仅 (projectId, monitorId)。
- **使用角色**：数据工程师（配置）、系统（执行）。
- **输入/输出**：设置保存 → `QualityScheduleLifecycle.sync` 注册/暂停/删除计划并回写 next_run_time；到点 handler 恢复项目上下文 → `runScheduled`。
- **依赖**：`yak-schedule-api`（与 MDM 分发、工作流同一基座）。
- **交互模块**：无第三方。
- **必要性**：**必要**。没有它质检只是抽查工具，谈不上"监控"。
- **理由**：口径克制——引擎不可用时优雅降级（warn 跳过）；启动清理孤儿计划、错过触发补跑一次；handler 端二次校验 enabled/runMode，禁用即顺手 pause。
- **问题**：调度粒度=监控粒度（一表一监控 → 一表一频率）；`engine.available()==false` 时页面仍可保存 SCHEDULE 设置但永远不会跑（界面是否提示未能实测确认，属"配置成功≠调度存在"的静默窗口）。
- **建议**：**保留**。

### 3.6 工作流触发 + 目录发布（#8/#14）
- **名称**：QUALITY 任务资产化与内核回调执行
- **业务含义**：监控（启用+有规则）自动发布为任务目录里的 QUALITY 任务；工作流锁版本引用它；DAG 跑到该节点时任务内核经 `TaskExecutionGateway` 回调 `QualityTaskExecutor`，用**冻结的 revision 定义**执行质检，NOT_PASSED 映射为任务 FAILED（可卡住下游）。
- **使用角色**：数据工程师（在工作流画布，不在质量页面）。
- **输入/输出**：监控保存 → revision 快照（SHA-256 去重）→ 目录指针；DAG 触发 → 幂等执行 → TaskExecution 状态/输出（含 passed/failed/error 计数）。
- **依赖**：task-catalog（写）、job（实现其 SPI）。
- **交互模块**：CAT、JOB、WFL。
- **必要性**：**必要**。"发布后跑在编排里、失败卡链路"是质量融入主脉④段的唯一通道，也是 05 #6/#7 两条 ✅ 的实证。
- **理由**：append-only revision + checksum 幂等 + idempotency_key 唯一键（V2）三件套与 DEV 供给口径一致；启停即上下架（`eligible`），账自动跟着状态走。
- **问题**：①质量资产上架后在质量模块内**无版本历史/指针可见面**（发布中心只管 DATA_DEVELOPMENT——任务目录盘点已记 P2，此处互为证据）；②WORKFLOW 触发的执行在工作流侧看是"任务失败"，在质量侧看 check_result 可能是 NOT_PASSED——两处口径的映射文案（"数据质量检查未通过"）只在内核输出里，质量执行列表页对 WORKFLOW 触发方式**未展示**（前端 `TriggerType` 类型缺 'WORKFLOW'，详情页把非 SCHEDULE 一律显示"手动触发"——**接口有值，页面标错**）；③监控被删除/禁用瞬间，已锁版本的在途工作流仍可按快照跑出结果（设计使然，但用户无感知提示）。
- **建议**：**保留 + 补齐**（前端触发方式枚举与标签对齐是十分钟级修补）。

### 3.7 执行结果、监控报告与质量总览（#9/#10/#11）
- **名称**：结果三层读模型（列表/规则明细/报告聚合）+ 项目总览
- **业务含义**：运行记录页看全局执行；详情页看逐规则证据与结构化日志；报告 Tab 看单监控通过率/维度/趋势/字段；总览页看项目健康雷达与问题贡献 Top3。
- **使用角色**：数据工程师、数据负责人。
- **输入/输出**：分页查询/聚合 SQL → VO；日志由 `QualityExecutionLogProjector` 从执行事实**推导**（非存储日志）。
- **依赖/交互**：HOME 模块复用同一批 DAO（`QualityAnalyticsDao`/`QualityOverviewMapper` 被首页读侧共用）。
- **必要性**：**必要**。四页覆盖了"发现问题→定位规则→看趋势"的完整消费面，是模块"页面已展示"最扎实的部分。
- **理由**：结果留存含执行 SQL、指标值、期望值、耗时、错误原文——复盘与对账证据齐备；总览 90 天窗口钳制防失控。
- **问题**：①**没有"质量分"**：模块只有通过率/问题数，用户提示中"结果与评分"的评分项不存在，资产域健康分的质量项也未接线（§5 AST 行）；②报告是**按监控**的，跨表/按数据源/按 Owner 的聚合报告无（总览页部分替代但无 Owner 维度）；③`executed_sql` 明文存 MEDIUMTEXT 并在详情页全量回显，内网工具可接受，若未来有截屏外流合规要求需脱敏（当前无法确认产品态度）。
- **建议**：**保留**；评分归资产域统一出，质量侧不再造（避免两份健康口径）。

### 3.8 告警事件与通知（#12）
- **名称**：失败告警双出口（事件留痕 + NotificationIntent）
- **业务含义**：NOT_PASSED/ERROR 收尾时按通知设置写 `yak_quality_alert_event`，并按结果级别经 boot 统一路由发站内消息/告警中心渠道（钉钉等插件渠道）。
- **使用角色**：监控 Owner（收件人）、平台运营（告警中心）。
- **输入/输出**：plan 的 notifyEnabled/notifyChannel/notifyTarget/alertLevel → 事件行（RECORDED/PENDING 状态）+ intent（含跳转链接 `/data-quality/execution/{no}`）。
- **依赖**：`yak-ops-core` NotificationRouter；alert 模块 `AlertNotificationSink`；boot `DefaultNotificationRouter`（策略解析 fail-closed）。
- **交互模块**：ALR（成立）、HOME（alert-overview 读侧，M2-4）。
- **必要性**：**必要**。05 #16"失败通知 ✅"的实证：ERROR/CRITICAL 会到达 alert 插件渠道。
- **理由**：通知失败只 log 不阻断执行收尾；投递状态如实存 RECORDED/PENDING 不臆造语义（domain 注释明示）。
- **问题**：①**EMAIL/WEBHOOK 渠道是半成品**：通知设置页提供邮箱/Webhook 地址输入并可保存，执行后事件仅以 PENDING 落库——全仓库无任何投递/FAILED/送达回写代码（`delivery_status` 无 UPDATE），属"前端展示，后端缺失"最实的一例；②质量菜单内无告警事件列表页（只有首页卡片透 5 条），`alert_event` 表除 alertOverview 读侧外无查询接口；③NOT_PASSED+EMAIL 组合下用户以为配置了告警实际只有站内 ERROR 通知兜底（NOT_PASSED 还不发 ERROR 之外的 intent——`publishMessageNotification` 条件是 ERROR 结果或渠道=MESSAGE）。
- **建议**：**重构收敛**：要么补投递 worker/接通 alert 渠道配置，要么砍掉 EMAIL/WEBHOOK 两个选项（保留 MESSAGE），二选一别维持"能配不可用"。

### 3.9 资产盖章供数（#13）
- **名称**："已稽核"事实（M2-1 只读盖章）
- **业务含义**：资产状态机七格的第 4 格，判据=模型四元组定位到质量监控且 last_result=PASSED（再与安全分级合取）。
- **使用角色**：资产运营者（在资产详情页状态条）。
- **输入/输出**：`QualityMonitorReader.tableSummaries` → StatusStep(PASS/FAIL/UNKNOWN/NA)+facts。
- **依赖**：AST 直接 import 质量类（ObjectProvider 可选装配）；无事件、无 SPI 接口层（跨模块 import 具体 Reader 而非 spi 包）。
- **交互模块**：AST（唯一盖章消费方）；`AssetLineageSummaryService`"未稽核表数"同判据。
- **必要性**：**必要**。这是"质量结论让人拼出能不能放心用"的落点，M2-1~M2-4 已落地、M2-5 观察期（commit 393e29081）与 05 #11 口径一致——**但 M2-5 观察期内容是定标/上架两格（语义/审批域），与质量格无关**，质量格自 M2-1 起即为拉取式稳定实现。
- **理由**：pull 模型保证零双写：质量不存"盖章状态"，资产不存"质检结果"，两域各守一本账；失败降级 UNKNOWN 不伪造通过，口径注释写得极清醒。
- **问题**：①"盖章"只有**最近一次**结果粒度，无时效衰减（一周前 PASSED 今天照样 PASS——判定是否应加新鲜度窗口属产品决策，当前无法确认已有共识）；②仅 MODEL/TABLE 资产适用，手工登记与元数据来源的资产 quality 格恒 NA，图二"质量结论盖章 AST"的普适表述超出实际覆盖面；③跨模块依赖形态重：asset 编译期依赖 quality 具体类（pom 级），是"横切A→横切B"的实边而非 SPI 虚边，未来质量换表结构会击穿资产域（common-spi 化是重构候选）。
- **建议**：**保留 + 重构**（把 `QualityMonitorReader` 消费面下沉 common 层 SPI，参照语义中心 S2 只读 SPI 先例）。

### 3.10 操作记录（#15）
- **名称**：监控操作日志（合成投影）
- **业务含义**：监控详情内"谁建了监控/存了哪些规则/跑过哪些检查"的时间线。
- **使用角色**：数据工程师/审计自查。
- **输入/输出**：monitor/rule/execution 三表 UNION ALL 拼四类动作（CREATE/UPDATE/SAVE_RULE/RUN）。
- **依赖/交互**：无（刻意不依赖 AUD——该边实际不存在）。
- **必要性**：**过渡**。低成本满足"这表谁在管"的追问，但语义是"对象变更+执行历史"，不是操作审计。
- **理由**：真实审计模块存在且被十余个模块使用，质量未接入。
- **问题**：UPDATE 一条时间戳代表全部历史修改；注册/取消注册表、模板改动、启停切换均无记录；命名"操作日志"名大于实。
- **建议**：**重构**：接统一 `BusinessAuditService`（保存监控/注册/模板写审计事件），页面读审计域；短期至少把 Tab 改名"变更与执行历史"。

## 4. 真实功能定位：质检执行器还是规则台账？

**裁定：它是真的质检执行器，盖章链路成立但形态与图上文案不同。**

1. **执行器证据链完整**：SQL 编译（六种规则各有真实指标 SQL 模板）、执行（经数据源通道取回指标）、判定（算符/阈值评估）、证据留存（逐规则 executed_sql+metric+耗时+错误）、状态机（WAITING/RUNNING/SUCCESS/FAILED × PASSED/NOT_PASSED/ERROR）、互斥与幂等（monitor 锁、active 检查、idempotency_key）、失败即停策略、三触发通道（手动/定时/编排）。"规则台账"只能解释 #1~#5 行，解释不了 #6~#9、#14 那批带执行语义的实现——台账型模块不会自建线程池、不会冻结 revision、不会给工作流提供可取消的执行句柄。
2. **盖章链路是否成立：成立，但是"被盖章"不是"去盖章"**。质量侧没有任何向 AST 的写入/事件（全模块 grep 无 asset 包引用、无 ApplicationEvent 推送）；`QUA-."质量结论盖章".->AST` 的实际机制是 **AST 在资产详情读路径上拉取 `QualityMonitorReader.tableSummaries` 现判**（`AssetStatusFlowService.audited`，M2-1 起）。工程上这是更好的设计（零第二真相、失败降级 UNKNOWN），但图上虚线的主语方向会让人去质量模块找"盖章发布器"而找不到——与 CAT→QUA 边同类的图文偏差。覆盖面上它只支撑七格中的第 4 格，且仅对建模来源的表资产生效；资产健康分（HealthScorer）的质量项是**缺口 G1 未接线**（按 0 分标"数据不可用"），"质量结论→评分"目前止步于"稽核判据"，未到"分值"。
3. **与任务内核的关系**：注册了 QUALITY `TaskExecutor` 适配器、发布锁版本任务、支持内核取消与状态轮询——**编排契约齐**；但执行本体（SQL 下发、线程占用、结果落表）全部自建自管，内核不为其承担资源治理与失败重试。它借目录和内核"挂号"，没有借它们"干活"。
4. **产品人格完成度**：四菜单页（总览/数据表监控/运行记录/规则模板库）+工作台+编辑器构成了自洽的"配→跑→看→追"闭环，是平台里少见的**页面与接口基本等量齐观**的模块（缺口见 §6 列表，均属点状而非结构性）。一句话：**横切A 的执行器侧已坐实，治理侧（盖章/审计/评分）只完成了"被读取"的义务，没完成"被记账"的义务（审计旁路）与"被度量"的义务（健康分 G1）**。

## 7. 现状总结

1. **完成度**：模块闭环成立——模板库/表注册/监控 CRUD/三触发执行/结果留存/报告/总览/告警通知全链路已实现且**后端接口与前端页面基本等量**（4 菜单页+4 隐藏路由覆盖 10/16 子功能）；测试 26 个文件含项目边界 contract test、分层约定 test、代码风格 test，工程纪律属平台第一梯队。
2. **定位判定（本次盘点头号问题）**：**质检执行器**，不是规则台账：自建线程池+SQL 编译+逐规则证据+状态机+幂等取消全真；同时它"借道不靠道"——挂目录与内核的牌，执行本体自管。
3. **盖章链路判定**：成立但为**反向 pull 模型**（AST 拉 `QualityMonitorReader` 现判"已稽核"），质量侧零推送、零事件、零第二真相，是 M2-1"只读聚合"口径的忠实实现；覆盖面窄（仅 MODEL 表资产第 4 格），健康分质量项未接线（G1）。05 #11 状态（M2-1~M2-4 ✅、M2-5 观察期）与代码相符，且 M2-5 观察期内容（定标/上架格）与质量格无关，勿混读。
4. **图文偏差三处**：①CAT→QUA 方向反（质量只写不读，与任务目录盘点互证）；②QUA→AUD **不存在**（无审计依赖、无审计调用、caller 枚举无 QUALITY——"质检规则 SQL 旁路统一审计"核实为真）；③JOB"执行"QUA 实为"触发+状态核对"。04/05 文档需按 §5 修订。
5. **模型取舍的代价集中点**：一表一监控（四元组唯一）换来 last_result 单值可解释与盖章简单，代价是多频率分治、多 Owner 分治与平台内部对象（record 表）挂载全部不可用；MDM 已用"只检实体落地表"绕行并把约束写进文档。
6. **诚实度分层明显**：告警投递状态如实存 PENDING 不装"已发送"、报告降级一律 UNKNOWN 不伪造通过、CustomTemplatePolicy 明写"当前版本仅支持数值+固定值"——但通知设置页的 EMAIL/WEBHOOK 输入框是唯一越过诚实线的展示（前端展示，后端缺失）。
7. **架构形态**：对外交互两种姿势——**供给用 SPI 实现**（目录 revision provider/reconciler、内核 TaskExecutor，接口归属清晰、方向正确），**消费用直 import**（AST 拿 quality 具体类）。后者短期省事，长期是 asset→quality 的编译期强耦合，建议按 S2 语义中心先例下沉 common 只读 SPI。
8. **性能与安全姿态**：读侧查询普遍带 project 收口与 limit 钳制；执行侧串行+全局小线程池（2/6/100）适合当前量级，慢查询治理依赖数据源侧超时（质量侧无独立预算）；自定义 SQL 的只读校验是正则级防线，真正的越权边界押在数据源账号权限上——平台若无只读账号规范，该模块是一个合法的"任意 SELECT 执行面"。
9. **一句话总评**：一个**执行内核干净、账本意识欠缺**的模块——编译/执行/留存/降级全部做得起直读代码的推敲，但它把自己游离在平台的两本总账之外：SQL 不进统一审计账、结论不进评分账、通知配了不进投递账；补的不是功能，是"记账义务"。
