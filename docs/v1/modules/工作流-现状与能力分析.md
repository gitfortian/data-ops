## 1. 模块概览

工作流是主脉④段的「多任务编排 + 定时触发 + 运行台账」层。它自身**不实现** DAG 状态机，也**不实现** cron 计时器：DAG 节点状态机来自外部框架 jar `io.github.weifuwan:data-workflow-engine`（`DefaultWorkflowEngine`、`WorkflowExecution/NodeExecution/NodeAttempt` 三态机、`WorkflowDefinitionValidator`、SPI `ExecutionRepository`/`NodeExecutor`/`ExecutionLock`），cron 触发来自 `data-schedule-api/core` + `data-schedule-plugin-quartz`（`ScheduleManager`、`ScheduleTrigger.cron`、`MisfirePolicy`、`ConcurrencyPolicy`）。模块真正写在自己的代码里的，是这三件事：

1. **控制面真值**：8 张 `yak_workflow_*` 业务表是唯一账本（定义草稿态/版本快照/执行三级/调度/触发台账/补数据批次），引擎仓储与 Quartz 注册表都被明确定位为"可重建投影"（`schedule/WorkflowScheduleReconciler.java` 类注释："业务表是真相，引擎投影可重建"）。
2. **持久化准入**：`yak_workflow_schedule_trigger`（Trigger Ledger，`dedupe_key`/`trigger_id` 双唯一键 + `status` 机）+ 单一启动走廊 `execution/WorkflowLauncher.java`（8 种启动模式全部经它落运行请求与审计后才激活引擎）+ 串行队列头 `schedule/trigger/WorkflowScheduleTriggerAdmission.reserveNextLocked`。
3. **对任务目录的锁版本绑定**：`definition/WorkflowTaskBindingResolver.java` 把节点解析成 job 侧 `TaskVersionSnapshot`（含 `assetId + revisionNo` 强等值校验），运行期由 `runtime/WorkflowRuntime.java` 直接调 job 的 `TaskExecutionGateway` 执行。

**本次核实对"项目记忆提示（告警与调度可能都在内存）"的结论要分两半**：
- 调度**计时层确实是内存的**：`data-ops-boot/src/main/resources/application.yml` 第 27 行 `spring.quartz.job-store-type: memory`，`yak.schedule.engine: quartz`；引擎锁与邮箱也是进程内实现（`LocalExecutionLock`/`LocalExecutionMailbox`），并由 `repository/WorkflowRuntimeSingleMasterGuard.java` 用 MySQL `GET_LOCK('yak-ops-workflow-<sha256(db)>',0)` 强制"第一阶段只支持单 Master"。因此不存在分布式调度、多副本会互踩。
- 但**运行事实是持久化的，不在内存**：`repository/WorkflowRepositoryConfiguration.java` 用 `@Primary ExecutionRepository = new CachingExecutionRepository(durableRepository)` 包在 `WorkflowExecutionRepositoryAdapter`（MyBatis-Plus）之外做 write-through，注释明言"MyBatis 适配器仍是重启与历史的真值源"；且 `runtime/WorkflowRuntime.resolvePersistence` 在 `yak.database.enabled=true` 而缺少持久化 bean 时直接 `throw IllegalStateException("Workflow durable persistence bean is missing...")`，不退化到纯内存。丢失的是"进程内的活跃执行视图"，靠 `WorkflowRuntimeRecovery.recoverPersistedExecutions()` + `WorkflowScheduleReconciler` + `WorkflowScheduleMisfireRecovery` + 台账 `recoverPending` 四层启动补偿重建。

与架构图的一致性：**6 条边中 3 条完全成立**（CAT→WFL 锁版本、WFL→HOM 运行事实、WFL→AUD 操作记录，且 AUD 边比图上写的更深），**1 条为语义偏差**（WFL→DEV 回边运行期不存在），**1 条完全未实现**（WFL→AST 运行事实：无 AssetProvider、无 WORKFLOW 资产类型、asset 模块零引用），**1 条降级**（WFL→ALR 失败通知：只落到站内信，未接告警渠道，05 清单 #16 的 ✅ 结论偏乐观）。

## 3. 子功能逐个分析

### 3.1 定义货架与创建抽屉
- 名称：工作流定义管理（卡片列表 + 汇总）
- 业务含义：④段的资产货架，承担"我有哪些编排、各自什么状态、最近跑成什么样"的第一眼信息。
- 使用角色：数据开发/数据运维。
- 输入：名称、描述；输出：`yak_workflow_definition` 行（`draft_revision`、`latest_version_no`、`active_version_id`、`latest_execution_id/status`）。
- 依赖：`WorkflowDefinitionManager`、`WorkflowDefinitionQuery`。
- 必要性：**必要**。
- 理由：卡片上直接透出生命周期态与最近一次运行结果，是"编排→运行"闭环的门户口径，无冗余。
- 问题：列表接口无分页/排序参数（全量返回后前端过滤），定义量上百后首屏成本线性上升；`latest_execution_*` 是写回定义表的冗余列（非派生视图），存在与 `yak_workflow_execution` 短期不一致的窗口。
- 建议：补服务端分页/筛选参数（与实例列表同一批改造）；把 `latest_execution_*` 视为缓存列并在读路径做一次一致性兜底校验。

### 3.2 DAG 画布编辑器
- 名称：ReactFlow 编排画布
- 业务含义：把已发布、已锁版本的任务按依赖组织成一次可重放运行的唯一图形表达。
- 输入：节点（`WorkflowNodeSpec`）、边（`WorkflowEdgeSpec`）、便签、开始节点；输出：`draft_json`。
- 依赖：任务目录（`WorkflowTaskLibrary` 拉 CAT 资产并客户端钉 revision，`services/workflow/definitions.ts` 的 `pinCatalogNode`/`bindingCache`/`isWorkflowCatalogAsset`）；引擎 `WorkflowDefinitionValidator`。
- 交互模块：任务目录（CAT）。
- 必要性：**必要**。
- 理由：完成度高——拖拽建点、连线、便签、撤销/重做、全屏布局、小地图、"下一步"引导齐备，且 `WorkflowStartGraphCompiler` 把"编辑器看到的图"与"引擎要跑的图"分层，避免不可达节点被物化，这是同类平台常见的坑，这里做对了。
- 问题：图校验只在保存/发布/运行时被动触发（后端抛错），画布上无"当前图是否可运行/成环/有孤立分支"的即时红绿灯；便签节点与业务节点同存 `draft_json`，未来做版本 diff 时噪音较大。
- 建议：暴露一个 `POST /definitions/{id}/validate` 预检接口（复用 `prepare()` 内部逻辑，不新增第二套校验），在工具栏做常驻健康指示。

### 3.3 节点检视面板（锁版本 + 运行策略）
- 名称：节点 Inspector（绑定信息 / 重试 / 异常策略 / 触发规则 / 超时 / 输入映射）
- 业务含义：这是工作流区别于"一堆孤立定时任务"的核心配置面——每节点独立的重试与异常策略、跨节点入参映射。
- 输入：`taskAssetId + taskRevisionId + taskRevisionNo`、`retryEnabled/retryTimes/retryDelaySeconds`、`failurePolicy`、`triggerRule`、`dispatchTimeoutSeconds/executionTimeoutSeconds`、`inputMappingText`（JSON）。
- 依赖：`WorkflowTaskBindingResolver`（`revisionNo` 强等值校验，不一致直接抛"工作流固定任务版本号不匹配"）、`ProjectContextException(PROJECT_NOT_FOUND)` 保证跨项目不可绑。
- 必要性：**必要**。
- 理由：这是全模块质量最高的部分之一。锁版本走"三字段等值 + 快照"，UI 上还有"有新版本"红标与就地"升级到 vN"按钮（`/{id}/nodes/{nodeId}/upgrade-task-revision`，`upgradeToLatest` 拒绝 OFFLINE 资产），版本升级可审计。
- 问题：`inputMappingText` 是自由 JSON 文本域，无 schema 校验、无上游输出字段补全，写错只能在运行时暴露；`WorkflowNodeInspectorSettings.tsx` 的"上次运行"卡片读取的是最近一次实例，非本版本本节点，跨版本对比时易误读。
- 建议：入参加前端 JSON 解析 + 后端结构校验（复用 `WorkflowRunInputScope` 校验链），并给出可选的上游节点输出变量列表。

### 3.4 编排准入策略（哪些任务能进画布）
- 名称：`WorkflowTaskEligibilityPolicy`
- 业务含义：④段与③段产物的类型契约。
- 现状事实：DEV 来源资产白名单 = `SQL / SHELL / HTTP / PYTHON`；非 DEV 来源（`DATA_INTEGRATION`→SYNC、`DATA_QUALITY`→QUALITY）**直接早退放行**（`if (asset.source() != TaskAssetSource.DATA_DEVELOPMENT) return;`）。SYNC/QUALITY 确实各自有执行器（`data-ops-business-sync-offline/.../OfflineSyncTaskExecutor.java`、`data-ops-business-quality/.../QualityTaskExecutor.java`），因此功能上是通的，前端 `isWorkflowCatalogAsset` 也对应三类来源。
- 必要性：**必要**。
- 问题（两点，都很具体）：
  1. 类注释自称 "Fail-closed orchestration policy"，实际对非 DEV 来源 fail-open；任务目录侧 `TaskCatalogService.requirePublishableTaskType` 有**完全相同的早退写法**，形成"双 fail-open"。将来任何新增 `TaskAssetSource` 或新 taskType 都会无校验直接进编排与运行链路。
  2. 类型三头错位：`HTTP` 在编排白名单里、也在目录发布白名单里，但 `data-ops-plugins/data-ops-plugin-task/` 只有 sql/shell/python/java 四个执行器 ⇒ **HTTP 任务能被编排进 DAG，运行时由 job 网关抛不支持**；`JAVA` 有真实执行器，却不在编排白名单里 ⇒ **能被定时、能被手工跑，唯独进不了工作流**。
- 建议：把"可编排类型"的判定权收敛到一处（由任务内核提供 `supportsRuntime(taskType)` SPI，工作流与目录都消费它），彻底消除手工维护的三份白名单。

### 3.5 版本快照与上下线
- 名称：定义生命周期（草稿 → 版本 → ONLINE/OFFLINE）
- 现状：`online()` 仅在 `draftChanged` 时发布新版本；`yak_workflow_version` 存 `run_request_json / task_versions_json / engine_definition_json` 三份快照；`offline()` 只挡新正式运行；`delete()` 在有活跃执行或 ONLINE 态时被拒（`hasActiveExecution` → `executionDao.countActiveExecutions`）。
- 必要性：**必要**。
- 理由：三份快照分列是正确设计——补数据与运维重跑要能还原"当时到底跑的什么"，而不是重算当前草稿。
- 问题：模块内另存在一个进程内 `definitions` Map，代码注释明确 "never an authorization source"，属于性能缓存而非真值，但它与 `active_version_id` 的失效路径依赖调用点自觉，是将来最容易出并发 bug 的地方；版本无保留策略（每次改草稿再上线都新增一行 `yak_workflow_version`，含 3 个大 JSON 列），长期膨胀无归档。
- 建议：给 `yak_workflow_version` 定"保留最近 N 个 + 有台账/补数据引用的永不删"的清理任务（与第 6 节 P2 合并做）。

### 3.6 运行入口（手工 / 测试 / 临时 / 调度 / 补数据）
- 名称：`WorkflowLauncher` 单一启动走廊
- 现状：8 种模式——PUBLISHED、SCHEDULED_PUBLISHED（FOLLOW_ACTIVE + `runConcurrent`）、BACKFILL_PUBLISHED（钉版本，调度离线则阻）、OPERATIONAL_RERUN（钉原版本、忽略当前 ONLINE）、DRAFT_TEST、AD_HOC、RESTART、RERUN_FROM_NODE；统一"先记 trigger context + audit，再激活引擎"。
- 必要性：**必要**，且这是模块架构上最值得表扬的一块。
- 理由：所有入口收敛到一个事务化走廊，杜绝了"某条路径绕过台账直接跑"的乱象，与 05 清单 R-6（避免多入口重复建设）方向一致。
- 问题：AD_HOC（`POST /api/v1/workflows/run`）**前端零调用**——后端把"临时编排运行"当正式模式实现、加了 controller、写了 VO，但没有任何页面暴露。属于"接口有、页面无"的确定项。
- 建议：短期在实例页或编辑器加"按当前 JSON 临时跑一次"入口；若判定不做，则连同 controller 端点一起下线，避免成为僵尸契约。

### 3.7 调度配置与生命周期
- 名称：多调度 + cron 配置抽屉
- 现状：一个工作流可挂多条调度；字段=cron/时区/生效起止/并发策略（PARALLEL|SERIAL_WAIT|SERIAL_DISCARD）/Misfire 策略（SKIP|FIRE_ONCE）/调度级入参；上线前置校验工作流必须已发布且 ONLINE。
- 必要性：**必要**。
- 理由：多调度对"同一 DAG 不同频率/不同入参"是真需求；参数合并优先级实现清楚（WorkflowVersion 入参 < Schedule 入参 < Backfill 入参 < 系统参数，见 `WorkflowScheduleParameterResolver`）。
- 问题：
  1. 触发器**只有 cron 一种**。`WorkflowScheduleEngineBridge` 恒定调 `ScheduleTrigger.cron(...)`，而 `yak_workflow_schedule.trigger_type` 字段 default `'CRON'` 但代码从不写其它值 ⇒ 表结构预留了依赖触发/事件触发，实现为零。
  2. 缺"立即执行一次"：`runNowIfPresent` 无人调用，用户改完 cron 想验证只能等到下一个触发点（或走手工运行，但那不带调度入参与业务日期）。这是运维侧最容易抱怨的一点。
  3. `GET /schedules/{id}` 有后端无前端封装。
- 建议：优先补"立即按调度配置试跑一次（带调度入参、写台账）"，复用现有 `coordinator.submit(..., manual=true)` 路径（`WorkflowScheduleTriggerHandler` 已有 `context.manual()?"MANUAL":"CRON"` 分支，改动很小）。

### 3.8 触发台账与 Misfire 恢复
- 名称：Trigger Ledger（`yak_workflow_schedule_trigger`）
- 现状：`dedupe_key`/`trigger_id` 双唯一键；状态机 RECEIVED/WAITING/LAUNCHING/REACTIVATING/RUNNING/终态/SKIPPED/FAILED；`WorkflowScheduleTriggerAdmission` 在 `@Transactional("yakBusinessTransactionManager")` 内 claim + `ledger.lockWorkflow(...)`；SERIAL_WAIT 靠 `reserveNextLocked` 排队头；`WorkflowScheduleExecutionListener` 在终态事务 AFTER_COMMIT 收敛台账并推进队首；启动期 `WorkflowScheduleReconciler` 用持久化 `next_fire_time` 反算 missedFireTime 交 `WorkflowScheduleMisfireRecovery` 补跑/写 SKIPPED，再 `selectPendingProjectIdsForRecovery` → `coordinator::recoverPending`。
- 必要性：**必要**，且是全模块的架构支点。
- 理由：在"内存 Quartz + 单 Master"的前提下，这是唯一能让定时语义变得可信的做法；去重、补跑、串行不重叠三件事都有确定性证据可查，页面上还有台账抽屉可自证。横向对比：全仓 7 个模块各写了一套 `*ScheduleEngineBridge`（asset/lifecycle/mdm/metadata/quality/offline/workflow），**只有 workflow 有持久化台账 + Reconciler + Misfire 恢复三件套**。
- 问题：可复用性为零——其余 6 个模块的调度在重启窗口内是否丢触发、是否重叠，当前无法确认（不在本次范围）。台账行只增不清。
- 建议：把 Trigger Ledger 抽为共享调度治理组件（放 common 或 core），其余 bridge 逐个接入；这是全仓投入产出比最高的一次收敛（对应 05 清单 R-4/R-6）。

### 3.9 补数据与业务日期重跑
- 名称：区间补数（Backfill）+ 单业务日期重跑
- 现状：`WorkflowBackfillPlanner` 上限 1000 occurrence / 3660 天 / 年份 2199；创建时钉住当时生效版本（`workflow_version_id/no`），每 occurrence 生成一条台账行；`cancel` 只跳过未启动的行；`createBusinessDateRerun` 要求源实例终态且有调度血缘，并复用同一版本钉。启动期 `WorkflowBackfillReconciler`（@Order(15)）恢复 RUNNING 批次继续物化。
- 必要性：**必要**。
- 理由：④段最硬的能力，且实现口径严格（版本钉 + 台账 + 恢复），不存在"补数跑到新版本上"的经典事故。
- 结论修正：**补数据并非"接口无页面"** —— `BackfillDrawer.tsx`（含 preview）、`BackfillHistoryDrawer.tsx`（含 cancel）均已在调度页可见并调用。真正无页面的是 `GET /backfills/{id}` 单查。
- 问题：补数据批次无进度视图（只有 total_count 与台账行，页面上看不到"这个批次已成功多少/失败多少"，需在台账里人肉筛）；`MAX_OCCURRENCES=1000`/`3660 天` 为硬编码常量，无配置项。
- 建议：补数据详情页/进度条（后端已具备聚合条件，属纯前端 + 一个 group-by 查询）；上限改配置化。

### 3.10 实例列表与详情
- 名称：运行台账 UI（列表 + DAG 运行视图）
- 现状：列表 2500ms 轮询、客户端过滤分页；详情走 SSE（EventSource + 1s 轮询兜底），展示节点态、尝试、入参出参、错误、操作记录、触发来源（schedule/backfill/手工）、业务日期。
- 必要性：**必要**。
- 问题：
  1. `GET /api/v1/workflows/instances` **无任何查询参数**（`WorkflowController.instances()` 空签名），页面所有筛选在前端内存做 ⇒ 运行历史增长后必然劣化，且 `describe()` 里的 trigger/backfill 血缘字段在列表场景是浪费。
  2. 无实例保留/归档策略，三级表（execution / node_execution / node_attempt）只增。
- 建议：P0 级补齐服务端筛选 + 分页（status/workflowId/triggerType/businessDate/时间区间/page）；同步给三级表定保留策略。

### 3.11 实例控制动作集
- 名称：暂停/恢复/取消/激活/节点重试/失败重跑/整例重启/从节点重跑/人工放行
- 现状：全部有 controller + 服务实现；除 `continue`（人工放行）外全部在页面有按钮。
- 必要性：**必要**（其中 `activate` 属调度重挂语义，偏运维内部动作但已暴露为接口与按钮）。
- 问题：
  1. **`POST /instances/{eid}/nodes/{nid}/continue` 前端 0 调用**——"人工放行失败节点并继续下游"是一个高价值的生产运维能力（失败但业务上可接受时不修任务直接放行），后端完整实现却没有任何操作面，等价于功能不存在。
  2. 暂停语义有落差：实例级"暂停"只停调度派发，已在跑的节点不下发暂停（`NodeControlResult.UNSUPPORTED`，注释"pausing scheduling only"）。UI 文案目前未把这个差别讲清楚，用户会以为任务也被挂起。
- 建议：给 Inspector「上次运行」/详情页节点操作菜单补"放行并继续"按钮（成本极低，接口现成）；暂停按钮旁标注"仅暂停后续节点派发，运行中任务不受影响"。

### 3.12 失败通知
- 名称：`WorkflowFailureNotificationListener`
- 现状：`@EventListener(WorkflowExecutionTerminalEvent)`，仅 FAILED/TIMED_OUT 生成 `NotificationIntent(projectId, Type.TASK, Level.ERROR, title, workflowName, content, sourceType="WORKFLOW_EXECUTION", sourceId=executionId, link="/workflow/instances/{id}")`。
- 必要性：**必要**。
- 问题：**当前只能到达站内信，到不了告警渠道**。`data-ops-core/.../notification/NotificationPolicy.java` 的 `projectOwnersInApp()` 只含 `Destination.IN_APP`；boot 层 `DefaultNotificationPolicyResolver` 的 `supports()` 恒为 true、order 为 MAX，返回该默认策略；全仓只有 mdm 与 offline-sync 写了自定义 resolver，workflow 没有。alert 模块（`data-ops-business-alert`）只提供渠道配置与 `/send`、`/test-connection`。所以 05 清单 #16「失败通知 ✅」应降级为 🔧（链路只到一半）。
- 建议：新增 `WorkflowNotificationPolicyResolver`（按 `projectId + 调度/工作流配置` 决定是否追加 `Destination.ALERT` 与 `alertChannelIds`），在调度或工作流配置页暴露"绑定的告警渠道"选择器；这是补齐承诺边的最小改动。

### 3.13 对首页供数
- 名称：`WorkflowExecutionOverviewReader`
- 现状：JdbcTemplate SQL 直查 `yak_workflow_*`，产出成功/失败/运行中分组、趋势分桶、最近实例、任务汇总、调度概览；被 home 的 `HomeCockpitReader`、`HomeDataCenterReader` 以 **Java 类型直接 import** 的方式消费（非接口/SPI）。
- 必要性：**必要**（④段运行事实是首页驾驶舱的主要数据源）。
- 问题：跨模块直连具体实现类 + 手写 SQL 读对方表，绕过了仓储层，两侧 schema 变更需靠约定与测试保证（模块内已有 `WorkflowProjectSchemaContractTest` 等，但消费方无契约测试）；且同一模块还承担"通知证据读取"（`WorkflowExecutionNotificationReader`），reader 角色较多。
- 建议：把 overview 提为 home→workflow 之间的只读 SPI（放 `data-ops-spi`），或在 workflow 侧提供 `/api/v1/workflows/overview` 让 home 走接口，避免 SQL 跨模块渗透。

### 3.14 操作审计接入
- 名称：5 处 AuditCoordinator + execution audit bridge
- 现状：定义（`WorkflowDefinitionAuditCoordinator`）、调度（`WorkflowScheduleAuditCoordinator`）、补数据（`WorkflowBackfillAuditCoordinator`）、执行控制（`WorkflowExecutionControlAuditCoordinator`）、执行终态（`WorkflowExecutionAuditBridge` + `WorkflowExecutionAuditTerminalListener`）；`yak_workflow_execution.audit_carrier_json`（V2 迁移）承载关联；读回：`WorkflowInstanceQueryService` 用 `AuditQueryService.firstActorNames("WORKFLOW_EXECUTE","WORKFLOW_EXECUTION", ids, projectId)` 给实例补操作人姓名。
- 必要性：**必要**。
- 理由：这是全仓审计接入最完整的模块之一（对比：数据开发完全未接，见 `数据开发-现状与能力分析.md` 第 5 节），且做到了"写入 + 关联 + 反向读回展示"三件事。
- 问题：`WorkflowExecutionAuditBridge` 的注入路径大量使用 `ObjectProvider`/nullable + 测试专用构造器（controller 里 `executionControlAudit == null ? ... : ...` 的三元判断），生产语义与测试语义混在同一层，可读性差。
- 建议：把"无 audit 环境"的处理下沉到 coordinator 内部（no-op 实现），controller 不再做 null 分支。

## 4. 真实功能定位

**结论：工作流的真实身份不是"调度器"，也不是"DAG 引擎"，而是"持久化触发台账 + 版本绑定 + 单一启动走廊"这三件控制面工作；它把自己降级为框架的编排壳，同时把真值牢牢握在 MySQL 里。这个定位是正确且比架构图表达得更成熟的，但它在"对外治理输出"（资产投影、告警路由）上明显欠账。**

1. **定位成熟度高于图纸**：`README/ARCHITECTURE/DOMAIN/REQUIREMENTS` 四份模块文档 + `WorkflowRepositoryConfiguration`/`WorkflowScheduleReconciler` 的注释，一致地把"业务表是真相、引擎与 Quartz 都是可重建投影"写为不变式。因此 `yak_workflow_execution` 不是"引擎表的复制"，而是重启与历史的唯一来源；`CachingExecutionRepository` 只是热路径加速。这正是 05 清单要防的"内存态当真值"乱象的反例。
2. **单 Master 是明确的阶段性契约，不是疏漏**：`WorkflowRuntimeSingleMasterGuard` 的注释与 `yak.workflow.runtime.single-master-guard-enabled` 开关表明作者知情；`application.yml` 的 `job-store-type: memory` 与之配套。风险在于**该约束没有被架构测试守住**（现有 5 个架构测试关注分层/风格/角色/schema 契约，未见"禁止多副本部署"或"quartz 必须 memory"的断言），未来有人切 `jdbc` job store 或起两副本时不会有任何自动拦截。
3. **与数据开发的职责切分干净、且比 DEV 文档描述得更好**：DEV = 单节点生产闭环；WFL = 锁版本任务的编排/调度/实例。绑定只经 `taskAssetId + revision`（`WorkflowTaskBindingResolver`），**不回读 DEV 草稿**；执行经 job 的 `TaskExecutionGateway`，**不回调 DEV**。补充一点 DEV 盘点未展开的事实：WFL 的可编排来源不止 DEV——SYNC 与 QUALITY 来源的目录资产同样能进画布并执行（三类来源，两类模块的 executor），因此 WFL 实际是 SYN/DEV/QUA 三条产出线的公共收敛点，图上只画了 CAT 一条入口，低估了这一层。
4. **正向越界一处、承诺缺口两处**：越界 = 直接给 home 提供 SQL 级 overview（图上有边，实现方式为直连，方式需收口）；缺口 = WFL→AST 完全未实现、WFL→ALR 只到站内信。
5. **前后端对称性总体良好，缺口小而集中**：4 条前端路由覆盖了定义/编辑/调度/实例主链，42 个前端封装 API 中仅 3 个无页面调用，1 个后端端点（`GET /schedules/{id}`）连封装都没有，1 个后端方法（`runNowIfPresent`）零调用。这与"页面有按钮无后端"的乱象类型（05 清单 R-3）无关——工作流的问题全部是反方向：**能力做完了没接出口**。

## 7. 现状总结

1. **实现完成度：核心链高、治理出口低**。定义→锁版本→校验→发布→调度→台账→启动→执行→三级持久化→重跑/补数据/业务日期重跑→SSE 观测→失败事件，每一环都有实现、有类级注释、有测试（57 个测试类，含 5 个架构约束测试）；缺的集中在"往外送"（资产投影、告警路由）与"最后一步出口"（人工放行无按钮）。
2. **与架构图一致性：6 条边 3 成立 / 1 偏差 / 1 未实现 / 1 降级**。成立：CAT→WFL、WFL→HOM、WFL→AUD（后者强于图）；偏差：WFL→DEV 回边运行期不存在（与 DEV 盘点互相印证，两侧应统一改注为"产物溯源"）；未实现：WFL→AST；降级：WFL→ALR 仅站内信（05 清单 #16 ✅ 需下调）。另有一条图上未充分表达的既成事实：WFL 实际收敛 SYN/DEV/QUA 三条产出线。
3. **"内存 vs 持久化"的最终裁定**：**运行事实已持久化**（`CachingExecutionRepository` write-through → `WorkflowExecutionRepositoryAdapter` → `yak_workflow_execution/node_execution/node_attempt`；缺持久化 bean 时 fail-fast 抛异常）；**调度计时层是内存**（`job-store-type: memory`）+ 进程内锁/邮箱 + MySQL `GET_LOCK` 单 Master。可靠性由四层启动补偿（Runtime 恢复、Schedule Reconcile、Misfire 恢复、台账 pending 恢复、Backfill 恢复）重建。这既是当前最强也最脆弱的地方——强在语义自洽，脆在该模式仅本模块一家做到，且无测试守护其部署前提。
4. **前后端对称性：缺口清晰且小**。4 条路由 + 42 个封装 API；无"页面有按钮无后端"；反向缺口 5 处（`/run` AD_HOC、`nodes/{nid}/continue`、`GET /backfills/{id}`、`GET /schedules/{id}`、`runNowIfPresent`）。**特别更正一项初始判断：补数据已有完整界面**（创建/预览/历史/取消 + 业务日期重跑），不是缺口。
5. **数据模型：8 张表职责干净、关键并发设计齐备**。definition/version/execution/node_execution/node_attempt/schedule/schedule_trigger/backfill 八张，唯一键约束（workflow_id+version_no、dedupe_key、trigger_id）与状态字段设计服务于"可重放、可去重、可追溯"；杂质仅 `audit_carrier_json`（V2 后补的 LONGTEXT 关联载体）与 `definition.latest_execution_*`、`draft_changed` 一类冗余回写列。
6. **代码健康度：高**。包分层（controller/definition/execution/runtime/schedule/backfill/repository/dao/domain/observability）与职责命名（Manager/Coordinator/Admission/Planner/Reconciler/Guard/Bridge）极其稳定，且有 `WorkflowLayeringConventionTest`/`WorkflowRoleConventionTest`/`WorkflowCodeStyleConventionTest`/`WorkflowDependencyBoundaryTest` 把约定钉成测试。主要瑕疵：为测试服务的 null 分支外溢到 controller；`WorkflowRuntime` 单文件 1258 行（引擎适配 + 持久化 + 轮询 + 超时巡检 + 取消下传混在一起），是下一轮拆分的首要目标。
7. **治理与运维接入：审计优、通知半、资产零**。审计五处 coordinator + carrier 列 + 反向读姓名；通知只到 IN_APP（无 resolver）；资产完全无投影。三者进度差异极大，说明"往外送"的方向缺一个统一收口约定，而不是单点忘记做。
8. **对相邻模块的真实代码依赖（pom 事实）**：`data-ops-common`、`data-ops-core`、`business-audit`、`business-job`、`business-datasource`（仅取 `BusinessDatabaseConfiguration` 共享数据源配置，非数据源能力调用）、`business-task-catalog`，加外部 `data-workflow-engine`/`data-schedule-api`；被依赖方只有 `business-home`。无 asset / alert / quality / sync / metadata / lineage 直接依赖。
9. **综合判断：保留并作为"④段调度治理参考实现"来放大，同时对内做三件收口**。第一优先补三件对外出口（资产 Provider、失败告警 resolver、continue 按钮）；第二优先补三项规模化前置（实例服务端分页、调度层可插/受守护的 job-store、数据保留策略）；第三做一次跨模块收敛（Trigger Ledger 抽公共组件、`supportsRuntime(taskType)` 单一真值源取代三份白名单、`runNowIfPresent` 与 AD_HOC 端点去留决策）。本模块不是重灾区，反而是全仓最值得作为"控制面写法样板"的模块，问题在于样板效应尚未被复制，以及自身承诺边欠账。
