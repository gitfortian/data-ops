## 1. 模块概览

数据服务是主轴⑤"消费与服务"段的 **API 发布与在线调用出口**：把上游已发布、带不可变 Revision 的数据资产（当前实际为数据开发 DATA_SERVICE 节点与主数据分发）发布成固定路径的只读 HTTP GET API，对外提供鉴权（IP 准入 + API Key/调用方模型）、集群限流、结果缓存/熔断、调用计量（明细日志+小时汇总）与 OpenAPI 文档能力。

- 后端：Maven 模块已接入 reactor（`yak-ops-business/pom.xml`）并进入 boot 装配（`yak-ops-boot/pom.xml:69` 段）。包结构 access/config/controller/dao/domain/documentation/execution/management/observability/publication/query/repository/runtime；main 134 个 Java 文件、test 27 个（含 5 个 architecture/governance contract test）。pom 声明依赖：common、core、plugin-datasource-api、business-datasource（`yak-ops-business-data-service/pom.xml`）。**不依赖 dataset、不依赖 metric**。
- 数据来源真相：**本模块不自产 SQL**。SQL+数据源只能来自 `DataServiceSourceProvider` 端口（ARCHITECTURE 原则 6"SQL Trust Boundary 在服务端"）。全仓 `implements DataServiceSourceProvider` 仅两处：`DevelopmentDataServiceNodeSourceProvider`（sourceType=DATA_DEVELOPMENT_DATA_SERVICE，managesServiceDefinition=true）与 `MdmDataServiceSourceProvider`（MDM_DISTRIBUTION，同为 managed）。**不存在 dataset 来源 Provider——图二 `DST-->SVC` 边在代码中零实现**（grep `dataset` 本模块 main 零命中）。
- 数据：自有 Flyway 三段迁移共 **12 张表**（V1 baseline：api、api_key、documentation、call_log、rate_window、call_log_hourly；V2：ip_access_policy、ip_access_rule；V3：consumer、consumer_api_grant、consumer_ip_access_policy、consumer_ip_access_rule + api_key 增列改造）。
- 前端：`/data-service/*` 共 **6 个页面**（菜单页 5 个：API 集市 `/data-service`、API 调用 `/data-service/access`、API 调试 `/data-service/debug`、运行概览 `/data-service/overview`、调用记录 `/data-service/logs`；隐藏详情页 `/data-service/api/:id` 五 Tab），注册于 `src/config/navigation.ts:59,82-87`；菜单组挂「消费与服务」（parentGroupId=data-analysis，与主轴⑤一致）。
- 定性：**"发布→调用→鉴权→限流→计量"的运行时闭环已真实落地且工程质量高；但"发布"的入口全部在别的模块工作台（DEV 节点编辑器、MDM 分发页），本模块页面只做消费侧管理；图面声明的上游（数据集、指标）一根都没接。**

## 3. 子功能逐个分析

### 3.1 定义与发布（§2.1–2.6）
- **业务含义**：把"已发布的数据能力"变成可被外部系统长期依赖的稳定 HTTP 契约（路径+参数+响应结构）。
- **使用角色**：数据开发/主数据负责人（发布在来源侧）；API 管理员（配置/启停，`data-service:publish/manage/delete` 权限）。
- **输入/输出**：输入=来源不可变 Revision（DEV 节点：独立 SQL+dataSourceId+参数/响应契约，GET-only，命名参数强制必填，OBJECT 拒绝——`DevelopmentDataServiceNodeSourceProvider.validateContract`）；输出=api 表一行 + SQL/数据源快照 + 契约文档同步。
- **实现度**：**必要**。发布链路是真规则不是空壳：仅 ONLINE 来源可发、必须带有效 Revision 与 dataSourceId（`DataServicePublisher.requirePublishable`）、SQL 过 `validateSelectOnly`、路径全局唯一（uk_path）、同来源幂等 upsert（republish 校验未产生第二身份）。缓存命名空间含 revision+generation，重发布不会吃到旧缓存。
- **问题**：①通用 `/sources`+`/publish` 端点与前端 api.ts 封装构成**双重摆设**——两 Provider 皆 managed、控制器主动拒绝，页面也没有发布入口；②"遗留手工数据服务"（V1 表语义）无发布来源，`republish` 明确拒绝，只能停用或删除；③配置更新对 managed 服务全量拒绝（`Publisher.updateSettings` 抛错），本模块页面实际只剩"启停/删除/访问策略/文档读"可操作。
- **建议**：删除或收口通用 publish 端点与前端死封装（保留 publication/state）；若图二决定"数据集→API"为正式路线，则补 DATASET SourceProvider（见 §6 P0）。

### 3.2 网关调用平面与示例（§2.7–2.8）
- **业务含义**：⑤ 段对外的门。设计为 Public Invocation Plane：不吃 Yak 用户会话与 Project Header，靠全局唯一 path + IP 策略 + NONE/API_KEY 契约防护（`DataServiceInvocationController` 类注释、PROJECT_GOVERNANCE.md）。
- **实现度**：**必要、已达标**。GET-only、参数走 `:name` 命名绑定（防注入）、分页参数（pageNum/pageSize/returnTotalNum）契约自动注入、maxRows 上限 10000、超时上限 3600s、仅允许 SELECT 结果集（`QueryExecutor` 对非结果集抛错）。前端调用示例（curl/Java/Python/JS 四语种）降低接入门槛。
- **问题**：调用平面自身无全局 QPS/配额闸（只有按 Key RPM）；NONE 模式的公开服务在 IP 策略缺省（ALLOW_ALL 判定见 `DataServiceIpAccessAuthorizer`，默认值未实测）时可被任意调用——**默认姿态需在验收环境实测确认**。
- **建议**：为调用平面补服务级/项目级并发与配额上限；把"新建服务默认 auth_mode=NONE+IP 全开"的默认值风险在发布确认弹窗中显式提示。

### 3.3 鉴权体系：IP + Key + Consumer（§2.9–2.11）
- 三层真实且顺序清晰：**IP 硬闸最先**（先于任何 Key 校验，`DataServiceAuthorizer.authorize:32`）→ Consumer 主模型（有 grant 即 fail-closed 接管，禁用调用方仍保护）→ 旧 API-Key 兼容走廊。Consumer 模型带独立 IP 策略、独立 Key、按 API 授权集（V3 四表），并有 access-overview 聚合页。**必要，本模块最完整的一块**。
- **问题**：两套模型并存（legacy key 直绑 api vs consumer+grant）造成 authorize 内 5 分支兼容逻辑，长期是认知负担；密钥仅存 SHA-256 摘要（正确），但无 Key 用量报表/异常调用告警接线（ALR 无 SVC→ALR 边）。
- **建议**：设定 legacy 退役时点；把"调用失败率/鉴权拒绝突增"接入告警。

### 3.4 限流与执行保护（§2.12–2.13）
- 集群限流用 MySQL CAS 分钟窗（无 Redis 依赖）、存储异常 fail-closed、轮换/删除即清窗——**较必要、达标**。缓存/熔断明确留在 node-local（CLUSTER_RUNTIME §2 用命名空间保证跨节点版本安全，不假装分布式）——**诚实的过渡形态**。
- **问题**：Runtime 策略 PUT 端点无页面调用（api.ts 封装闲置），cache/circuit 目前**无界面修改入口**（发布来源仅带 maxRows/timeout；policy 列有默认值）；`invalidate` 只在重发布路径由 generation 隐式完成。
- **建议**：详情 Runtime Tab 补策略编辑表单（后端已全备，纯前端欠账）。

### 3.5 SQL 执行与数据真相（§2.14）
- **关键结论（回答"调用方拿到的数据从哪来"）**：来自**api 表持久化的 SQL 快照 + 直绑 dataSourceId**，经 core 共享 `SqlExecutionRuntime` 直接查业务数据源。DEV 新模型是"节点自带独立 SQL"（standaloneSql），旧 Revision 兼容路径才锁任务目录 TaskCatalog SQL Revision。**不经过 dataset：无锁版本数据集引用，无数据集行列权限继承**。图二 `DST-->SVC` 所承诺的"数据集作为消费单元供给 API"未实现；当前形态实质是**裸 SQL 直连数据源的受控发布**（受控在：SQL 只能来自 DEV/MDM 已发布 Revision、只读、服务端执行）。
- **必要性**：作为机制**必要**（版本锁定、快照不可变都真实）；作为主轴定位**偏离**——它是"数据开发产物的在线化"，不是"数据集的 API 化"。

### 3.6 调试页（§2.15）
- `/data-service/debug` 选服务→按参数契约生成表单→跑 `POST /{id}/test`→表格化结果+endpoint 回显。**较必要**（发布后验收、给调用方演示）。**问题**：test 走 console 上下文、跳过鉴权/限流/缓存/熔断（`Invoker.test` resilient=false），"调得通"≠"外部调得通"，与真实调用平面存在行为差。**建议**：调试页增加"以 API Key 走真实调用平面"的对照模式。

### 3.7 计量与可观测（§2.16–2.18）
- 明细日志（含 caller_type PUBLIC/API_KEY/CONSOLE/LEGACY、参数脱敏、失败原因）→ 小时汇总 → 概览（卡+趋势+Top API），保留期清理走夜间维护。**必要、达标**，且概览契约被首页复用（home-overview-contract.md），避免首页私查表。**问题**：日志页为纯前端过滤（`logs/index.tsx` filter），未按项目/时间做服务端分页筛选（recent 接口限量）；无调用方维度的账单式统计（谁花了多少配额）。
- **建议**：call_log 服务端分页+按调用方聚合视图。

### 3.8 文档与 OpenAPI（§2.19）
- 参数/响应契约由 DEV 发布时自动同步（syncSourceContract），手工文档端点保留；OpenAPI 3 渲染器+单测齐备但**无页面按钮**。**较必要**；建议详情总览 Tab 挂"下载 openapi.json"。

### 3.9 治理与测试（§2.20）
- 五个架构契约测试（依赖边界/Flyway/治理/集群运行时/代码风格）+ 模块内七份治理文档（README/DOMAIN/ARCHITECTURE/DEPENDENCIES/REQUIREMENTS/MIGRATIONS/RUNTIME_RELIABILITY/PROJECT_GOVERNANCE/CODE_STYLE 谱系完整）。**必要、达标**，是全仓模块治理范式的样板之一。

## 4. 真实功能定位

**它不是"数据集的 API 货架"，而是"数据开发/主数据发布产物的在线查询运行时"。** 图二把 SVC 画在 `DST-->SVC` 上，代码现实是 `DEV(数据服务节点)-->SVC` 与 `MDM(分发)-->SVC`。两条链的差异是实质性的：

- 数据集链（图上承诺）：API 的列语义、行权限、口径继承数据集治理，数据集下线联动；
- DEV 直发链（代码现实）：只要一段过审的 SELECT + 一个数据源 ID，绕过 dataset 的语义层与（若未来存在的）行列管控。

当前直连风险被三层收口压住（SQL 只能来自服务端 Provider、只读单语句、消费侧有 IP/Key/限流/计量），所以它是**受控旁路**而不是失控旁路；但只要平台确认"⑤ 段消费单元=数据集"，本模块就缺一个 DATASET SourceProvider 来回到主轴。对"BI 替代品"之问（本模块语境即"API 是否数据集的门面"）：**现状不是**——是 SQL 任务产出的门面；数据集与 API 目前互不知情（数据集侧 grep 亦无对 data-service 的引用）。

模块自我认知与代码一致：ARCHITECTURE §1 自述"负责固定 SQL + Datasource Runtime Snapshot"，从未自称消费数据集——**偏差在图二与 03 验收路线，不在模块文档**（03 步骤 4"从该数据集发布一个 API"当前无法按字面执行，属文档超前/错位）。

## 7. 现状总结（九项）

1. **一句话定位**：数据服务=主轴⑤的"只读 SQL API 运行时"——发布、鉴权、限流、缓存熔断、计量、文档六件套全部真实闭环，但供给它的不是图上的数据集，而是数据开发与主数据的发布产物。
2. **最扎实的部分**：调用平面安全模型（IP 硬闸→Consumer fail-closed 主模型→legacy 走廊、集群 CAS 限流 fail-closed、参数脱敏落证、XFF 可信代理白名单）+ 五枚架构契约测试，工程与治理文档密度全仓第一梯队。
3. **最大空洞**：`DST-->SVC` 假接线（§5.1）。⑤ 段"消费单元统一走数据集"的叙事在 API 这一路完全不成立；图二、03 验收路线需与代码对表（改图接 Provider，二选一，拍板记录尚无定论——05 清单未列此乱象，**本次盘点新增发现，建议列为 R-9**）。
4. **次级断链**：指标引用（§5.4）、资产/血缘覆盖（§6 P1）、告警（P1）——数据服务是治理横切的盲区模块：它在"卖数据"，但台账不知道它存在。
5. **闸门现状**：管理面有 RBAC+Project 双控与来源拒绝，但**无审批闸**；发布动作的真实权限闸前移到 DEV RELEASE 权限，本模块侧"上线即公网可调"（IP 策略默认姿态待实测，§3.2）。
6. **前后端错位清单**：接口缺页面——Runtime 策略 PUT、openapi 生成、文档保存、通用 publish/republish/sources（且为设计性死路）；页面缺后端——logs 服务端筛选；传闻的"DEV HTTP 节点直发 SVC"证伪（§5.7），HTTP 节点本身是僵尸类型（归数据开发 P1 处置）。
7. **文档与现实的一致性**：模块自身文档（ARCHITECTURE/PROJECT_GOVERNANCE/CLUSTER_RUNTIME）与代码高度一致、甚至预先声明了不做的范围（"不负责血缘/审批/分布式缓存"）；不一致发生在平台层文档——图二画了不存在的边、03 写了跑不通的步骤。**注意 05 清单尚未收录"图二 DST→SVC 假接线"与"MTR→SVC 假接线在 SVC 侧的镜像"，本篇 §5 为第一手证据。**
8. **孤儿/冗余面**：V1 表内 sql_text/data_source_id 的手工时代遗产与"managed 拒绝"逻辑并存（同一张表两种世界观）；legacy key 与 consumer 双鉴权模型；前端 api.ts 六枚零引用封装。低风险但计入维护噪音。
9. **风险提示**：在 P0 拍板前，任何"通过 API 泄露敏感行列"的安全评估都会评估错对象——评估对象应该是 DEV 数据服务节点的 SQL 审发流程，而不是数据集权限；同时"API 无总配额+NONE 模式+IP 默认值未实测"三项叠加是对外暴露面的最薄弱组合，建议优先实测与收口。
