## 1. 模块概览

大屏是主轴⑤"消费与服务"端的**展示型资产模块**：以"模板 + 每组件数据绑定"的方式定义一块可轮询刷新的可视化大屏。后端极简——只管名称/描述/模板 ID/不透明 bindings JSON 的草稿行与发布快照；模板本体、组件语义、查询构建与渲染全部在前端。

- 后端：Maven 模块已接入 reactor（`data-ops-business/pom.xml:31`）并进入 boot 装配（`data-ops-boot/pom.xml:108`）。包结构：application/controller/v1/dao/domain/publication/repository(+codec)/version/config，文件数仅 ~24 个主源码，是同类模块中最薄的。生命周期=**可变草稿（revision 自增）→ 发布时快照成不可变版本 → 支持下线（offline）与回滚（rollback）**。
- 数据：自有 Flyway **仅 1 段迁移、2 张表**（`V1__baseline_digital_screen.sql`：yak_digital_screen（草稿+发布指针+status+revision）、yak_digital_screen_version（发布快照，含 source_revision/published_time）；前缀 `yak_digital_screen*`）。全库再无其它迁移触碰（已 grep 核实）。**无模板表、无资产台账投影、无血缘登记、无审计接线。**
- 前端：路由 4 条（`navigation.ts:77-80`）：`/digital-screen` 列表、`/digital-screen/new` 模板挑选新建、`/digital-screen/:id/edit` 编辑器、`/digital-screen/:id` 预览（viewer）。页面目录内已重构为 `list/ editor/ viewer/ runtime/` 结构化布局，根级 `index/new/editor/viewer.tsx` 是单行 re-export 兼容壳，根级 `components/`、`hooks/` 是 `export *` 转发旧位（如 `hooks/useDigitalScreenViewer.ts`→`viewer/hooks/…`）。渲染协议在 `src/components/screen-engine`（通用、与数据集无关），执行管线在 `pages/…/runtime`（planner→executor→query key/cache/并发→Dataset API→adapter）。
- 定性：**前端重、后端轻**。前端运行时质量高（缓存/并发/失败隔离/30s 轮询均有实现与测试）；后端则把真相让渡给了浏览器——绑定内容不校验、模板不存在于服务端、治理横切（资产/血缘）完全缺席。

## 3. 子功能逐个分析

### 3.1 生命周期：草稿-版本-发布（§2.5/7/8/10）——R-4 的当事件
- **业务含义**：展示墙的"改↔上"节奏需要可回退、可撤下，故草稿可变、发布才留版本，语义成立。
- **实现度**：**必要、机制达标**（锁与幂等都真实）：publish 在 `SELECT … FOR UPDATE`（RepositoryAdapter.lockById:61-66）内做 revision 比对幂等；update/restoreDraft 用 `setSql("revision = revision + 1")` 原子自增；快照记录 `source_revision` 可追溯"哪个草稿修订产生了哪个版本"（SQL:13,33——这个字段设计比仪表盘的版本语义更可审计）。
- **问题**：①**并发编辑无客户端乐观锁**：UpdateDigitalScreenRequest 不带 expectedRevision（DigitalScreenRequests.java:19-23），两人同开编辑器互相覆盖，最后写入者赢，revision 只增不比对；②status 仅 DRAFT/PUBLISHED 两态（DigitalScreenStatus.java），"曾发布现已下线"与"从未发布"在列表上不可分辨；③草稿态无版本：改 20 次没发布，线上还是老版，但草稿的中间态丢了（对比仪表盘：每次保存留版本——**两种相反的取舍**，各对外半截，见 §7）。
- **建议**：update 请求补 expectedRevision 并把冲突透出（平台错误透传 M-2 的规矩）；状态列补 OFFLINE 或在视图层持久化区分。

### 3.2 数据绑定与模板：整条真相链路在前端（§2.3/4/6/13）——本模块最大结构性问题
- **现象（旁路取证）**：后端对 bindings_json 只做 JSON 序列化合法性检查（BindingsCodec:21-27），**不校验其中 datasetId 是否存在、是否属于当前项目、字段是否还在**；digitalscreen 模块的全部 import 只有 framework/core/datasource-config，零业务模块依赖。模板 ID 同样只当字符串存——若前端删掉/改名一个内置模板，已发布大屏的 `resolveScreenTemplateById` 解析失败，页面显示"未知模板"（DigitalScreenEditorView.tsx:222），后端毫无感知。
- **数据流**：绑定的"metrics"是字段级聚合 `{field, aggregation}`（types.ts:6-7；6 种聚合 SUM/AVG/COUNT/COUNT_DISTINCT/MAX/MIN）——**与指标中心无关**；查询经浏览器直发数据集查询 API（runtime/query.ts → services/dataset）。未触及裸 SQL/数据源直连，底线与仪表盘一致。
- **必要性判断**：机制**必要**（大屏本就该轻后端）；当前形态**过渡**——"轻"过了头，项目隔离与引用完整性都失守：bindings 里的 datasetId 可以指向**其它项目**的数据集（后端不知道，前端 viewer 只加载元数据解析成功的那些，跨项目引用是否泄露数据取决于 dataset API 的项目作用域——dataset 控制器有 @ProjectScope，故实际读取仍被项目闸挡住，**但这层防线在别人的模块里，大屏自身没有表达引用关系**）。
- **建议**：至少给 publish 加一道校验（发布时解析 bindings 内 datasetId 并存在性检查，可复用仪表盘 gateway 走廊模式）；模板进库（一张 `yak_digital_screen_template` 表或复用文件资源）是治本项。

### 3.3 运行时管线（§2.12/13）
- **实现度**：**必要、达标**，且有文档有测试（runtime/README.md、4 个 *.test.ts）。query key 含数据集 id/version+完整 payload；同 key 合流（line/bar 共享一次查询）；10s 会话缓存；≤4 并发；AbortController 取消过期请求；失败隔离到组件；Viewer 30s 轮询、后台页签暂停。PR4 明确未做全局筛选/组件联动/下钻（README:44，"PR 5 concerns"）——规划自白清晰。
- **问题**：与仪表盘（经 `components/analysis/query-runtime`）是**两套平行实现**的"查询计划+去重+缓存"，参数与语义各调各的（缓存时长、并发上限不同）；同一张图在看板与大屏上视觉协议也不通用（ECharts 配置两套）。归谁见 §7 合并建议。
- **建议**：下沉为单一查询运行器（含缓存策略注入），两模块只做渲染 adapter。

### 3.4 模板体系（§2.3/4）
- **实现度**：内置 4 模板 + 前端渲染协议（screen-engine：renderer registry + validator + PremiumVisuals 装饰件如 scan/pulse 动效、glass/hud 边框）**较必要**，页面已展示（新建页画廊+模板 preview）。
- **问题**：**自定义模板与模板上下架状态全存 localStorage**（screen-template-service.ts 文件头），意味着：模板无法团队共享、无法随项目迁移、后端 bindings 校验（若未来加）无法对照模板 schema；模板的 draft/published/offline 三态和大屏的两态是**同一词汇的两种方言**。
- **建议**：模板先入库（哪怕 JSON 文档形态），再谈"模板市场"。

### 3.5 画布与布局（§2.5 的另一面）
- **现象**：编辑器没有自由画布——组件位置/层级由模板决定，用户只能绑数据；`ScreenComponent` 模型里位置字段随模板写死（screen-engine/model.ts）。**页面已展示的只有"模板内编辑"**，README 所称"layout…expressed through typed ScreenTemplate documents"即模板定义布局。
- **必要性判断**：对指挥中心类场景**较必要**（模板足够）；对"给已有大屏加一块图"的场景是硬缺口——无添加/删除组件入口，也**不能换模板**（update 不接受 templateId，见 §2.5 备注）。
- **建议**：短期允许换模板或克隆组件；自由画布视 PR5 联动一起做，避免重复造仪表盘的栅格。

### 3.6 前端目录重构遗留（兼容壳）
- 根级 `index/new/editor/viewer.tsx` 4 个单行壳服务路由表注册；根级 `components/*.tsx`、`hooks/*.ts` 共 9 个 `export *` 转发壳指向 `list//editor//viewer/` 子目录。均**冗余（过渡件）**，归 pages 层；路由仍指旧路径，故壳不能即删。建议路由改指新目录后删除（对照 R-1 治理先例：删前三重检查+tsc 基线）。

## 4. 真实功能定位

**大屏=模板驱动的轮询展示墙（kiosk/指挥中心），不是 BI 工作台**。判据：后端零查询执行、零 composition 语义；全部表达能力（组件类型、视觉、绑定协议、查询构建、缓存策略）住在前端；内容供给只有"模板 + 数据集聚合绑定"两样。

**与仪表盘并存是否成立？** **成立，但当前是"一个真需求 + 一个半成品实现"的并存，而不是互替**：
- 场景不重叠：仪表盘=分析型（筛选/联动/下钻/复用分析资产），大屏=展示型（整屏轮询、装饰动效、模板品牌感）；合并页面会同时毁掉两种心智。
- 重复发生在机制层：生命周期双指针 vs 状态机（§7 R-4）、查询运行器两套、图表视觉协议两套。
- **不成立的另一半**：大屏目前缺消费出口（无分享外链，TV 端也得登录）与治理在场（资产台账/血缘/审计全无，见 §2.15）——若不补，它相对仪表盘就只剩"更好看的皮"，存废才真正可议。

## 6. 缺失能力

| 优先级 | 缺失能力 | 现状证据 | 影响 |
|---|---|---|---|
| **P0** | 发布/绑定完整性校验：publish 时校验 bindings 的 datasetId 存在且属当前项目；模板引用可解析 | §3.2：后端不透明直存；"未知模板"仅前端文案兜底 | 断链/坏模板的大屏可正常发布，viewer 才爆炸；治理三件套（血缘/台账/守卫）全部无从谈起 |

## 7. 现状总结（九项）

1. **一句话定位**：大屏=前端模板引擎 + 极薄持久层（草稿行+发布快照）的轮询展示墙；后端只有 CRUD 与发布指针，语义全在浏览器。
2. **最扎实的部分**：发布机制的并发正确性（FOR UPDATE+幂等+source_revision 审计字段）、运行时管线（合流/缓存/并发/取消/失败隔离，有 README 有测试）、前后端 API 封装完整无闲置端点。
3. **最大空洞**：引用完整性与治理在场（P0 两项）。bindings 是"查无对证的自由 JSON"，资产台账/血缘两清皆无——它是⑤段消费出口里唯一不被"一本账"看见的。
4. **方法论未兑现点**：模板体系只在代码常量与 localStorage 里，"平台模板市场"（TemplateView 的管理界面语义）与真相存储脱节。
5. **闸门现状**：发布/下线/回滚均无审批、无审计；对比 05 清单第 15 条审批五类流不含 SCR，与图一致，但作为"上线到墙上"的动作，无闸的正当性需拍板记录（参照指标中心文档同类条目处理）。
6. **前后端错位清单**：前端有、后端无：模板管理、自定义模板状态、绑定 schema；后端有、前端弱：status 两态区分度；接口无页面：无（唯一闲置为 ApplicationService.count()）；页面已展示、真相不在库：模板与草稿并发覆盖（§3.1）。
7. **R-4 核实结论（本盘点主任务，与《仪表盘》§7.5 同文互证）**：**不共享——各写一套，且是两种相反的生命周期设计**：仪表盘=可变指针+不可变草稿版本（保存即版本、发布仅移指针、restore 产生新草稿、无 status/offline）；大屏=可变草稿单行（PUT 原地改+revision++）+发布才产生不可变版本+一等公民 offline/rollback。逐件核对：实现类各自一套（DashboardVersionManager/DashboardPublisher/DashboardVersionReader vs DigitalScreenApplicationService/DigitalScreenPublisher/DigitalScreenVersionReader，无共同基类或接口；全仓 grep 未发现任何发布/draft 公共抽象，common 层仅有与本场景无关的 VersionDigests 与仅 dashboard 实现的 AssetProvider）；表前缀各自独立（yak_dashboard* 6 表规范化 vs yak_digital_screen* 2 表 JSON 文档式）；事务策略不同；前端运行器与视觉协议也各一套。**命名与包结构高度同构（facade/Publisher/VersionReader/codec/controller v1），说明是同一规范下的两次独立施工，不是一次施工的两份拷贝**。合并建议（写进两份文档，口径一致）：①不合并页面与场景（§4）；②把三件同型零件下沉共用——版本快照存储与版本号分配、发布指针/下线/回滚状态转移（语义取两者并集：草稿即版本 or 快照时版本可由资产声明，但 offline/rollback/hasUnpublishedChanges 统一词汇与实现）、前端查询运行器（planner/cache/concurrency 收敛为 analysis 与 digital-screen 共用）；③先补大屏 P0（发布校验+资产/血缘投影，以 dashboard 的 gateway/AssetProvider/LineageSynchronizer 为模板），治理面合流先于代码面合流；④05 清单 R-4 状态可由"待核实"改"已核实：各写一套，建议下沉公共件"。
8. **孤儿/冗余面**：前端 13 个兼容转发壳（重构遗留，路由未迁不能删）；内置模板 4 套中的 simple-dashboard 与仪表盘场景心智重叠（展示需求下它是"穷人版仪表盘"），保留与否随模板入库一并决策。
9. **风险提示**：大屏的"轻后端"极易被误读为"已完成、可演示"；实际是**演示可用、生产三缺**（缺校验、缺台账、缺出口）。在同一支团队先后施工仪表盘与大屏的背景下，若无 R-4 治理动作，后续每加一种发布类资产（报表/报告？），就会第三次分叉生命周期代码——这是 05 清单 §R-4 "改两遍必漏"的完全体版本。
