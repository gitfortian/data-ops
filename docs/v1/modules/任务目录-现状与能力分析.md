## 1. 模块概览

| 项 | 内容 |
|---|---|
| 模块名称 | 任务目录（Task Catalog，`yak-ops-business-task-catalog`，pom 自述"Published task asset catalog shared by authoring domains and workflow discovery"） |
| 主脉位置 | ④编排执行段。图二定位：DEV --发布不可变Revision--> CAT；CAT --锁版本任务--> WFL & QUA & DST（S4/S5 契约） |
| 上游（向货架写入） | 数据开发（`DevelopmentTaskPublisher`、`DevelopmentReleaseService`，source=DATA_DEVELOPMENT）；数据质量（`QualityTaskPublisher`，source=DATA_QUALITY，监控器启停自动上下架）。`TaskAssetSource.DATA_INTEGRATION` 仅枚举占位，**全仓库无生产方** |
| 下游（从货架读取） | 工作流（`WorkflowTaskBindingResolver` 锁版本快照/升级）；数据集（`TaskCatalogDatasetAdapter`→`DatasetPublisher`/血缘/schema/查询执行）。**数据质量不读目录**（详见 §5 边核实）；另有 boot 层迁移回填 `DatasetProjectCompatibilityBackfill` |
| 一句话定位 | 平台已发布任务的**中立索引 + 锁版本解析闸**：只存发现元数据（名称/类型/状态/项目）和"当前线上版本指针"，版本内容永远归源域（append-only 修订表），消费方通过 SPI 回源解析——货架管"哪个版本现在算数"，不管"版本里装了什么" |
| 实现状态 | 核心机制（发布 upsert、锁版本解析、只读发现 API、项目/空间投影、来源对账钩子）**已实现且已被 WFL/DST 真实消费**；不可变内容机制经核实成立（源域修订仓储无 update/delete 口）。存在三处结构性事实：①目录本体无任何写 REST 接口，写全部走进程内 Java 调用；②目录自身无独立页面/菜单，其操作面（发布中心）实现于数据开发模块；③图二 CAT→QUA 边方向与代码现实相反（详见 §5） |
| 主要入口 | REST：仅 `GET /api/v1/task-catalog/assets`、`GET /api/v1/task-catalog/assets/{assetId}`（`TaskCatalogController`，读侧）。用户可见面：工作流画布任务选择器（`task-asset:` 前缀选项）、工作流节点检查器（版本升级按钮）、`/data-development/releases` 发布中心页（上下线/切版本/版本历史） |

## 3. 子功能逐个分析

### 3.1 发布货架（#1 upsertPublished + 恒 ONLINE）
- **名称**：发布/重发布投影
- **业务含义**：源域每次发布任务/启停监控器，把"这个任务存在、当前哪个版本算数"钉到一张中立索引上；S4 契约的执行点。
- **使用角色**：无人直接使用（数据开发"发布"按钮、质量监控器启停是其触发者）。
- **输入**：source+sourceRef+projectId+name+taskType+revisionId+revisionNo。
- **输出**：`yak_task_asset` 一行（唯一键幂等 upsert），返回 TaskAsset。
- **依赖**：无（写入端不校验 revisionId 真属于该 sourceRef——校验推迟到解析时）。
- **交互模块**：DEV、QUA（写方）；WFL/DST（间读）。
- **必要性**：**必要**。全平台"锁版本引用"的落点。
- **理由**：一张表 + 一条 upsert 承载了目录最小真相；内容零复制，无第二真相风险。
- **问题**：指针可被写成任意值（含更小 revisionNo、含别的节点的 revisionId），错误只在 resolve 时爆炸；`publish()` 无单调性守卫。
- **建议**：**保留**，补发布侧轻校验（revisionId 经 provider 可解析且 revisionNo 不劣于当前，除非显式走"切换线上版本"操作）。

### 3.2 锁版本解析（#6 resolveRevision + Provider SPI）
- **名称**：不可变版本回源解析
- **业务含义**：任何消费方给 (assetId, revisionId)，目录负责把它变成源域的不可变定义，并做类型一致、项目一致两道对账。
- **使用角色**：程序（工作流快照/升级、数据集发布/血缘/schema/查询）。
- **输入**：assetId、revisionId（+当前项目上下文）。
- **输出**：`TaskAssetRevision`（asset + source-neutral `TaskSourceRevision`：definition/checksum/revisionNo/sourceProjectId）。
- **依赖**：`TaskAssetRevisionProvider`（DEV/QUA 两实现；provider 缺失抛"来源尚未接入版本解析"）。
- **交互模块**：WFL、DST 强消费；DEV/QUA 供内容。
- **必要性**：**必要**。这是"货架"区别于"清单"的核心：锁住的版本永远解析出同一内容。
- **理由**：不可变性在存储层成立——`DevelopmentTaskRevisionRepository`/`QualityTaskRevisionRepository` 接口只有 insert/find/list，**无任何 update/delete 方法**；工作流快照再做 revisionNo 精确匹配（resolver:69），改版本必须显式升级。
- **问题**：解析失败以 IllegalStateException 冒泡到调用方 HTTP 层，错误文案是否原样到界面未逐一实测；目录不缓存解析结果（数据集查询路径每轮回源，性能可接受但未压测）。
- **建议**：**保留**。

### 3.3 只读发现 API（#4/#5 Controller）
- **名称**：已发布任务发现接口
- **业务含义**：编排器/数据集构建者的"货架目录页"数据源：有哪些任务能挂进 DAG。
- **使用角色**：数据工程师（在工作流画布间接使用）。
- **输入**：source/status/keyword 查询参数（项目上下文自动过滤）。
- **输出**：TaskAsset 列表/详情（currentRevision 指针含 revisionNo）。
- **依赖**：`TaskAssetCatalogReconciler`（list 前触发，当前仅 Quality 注册）。
- **交互模块**：前端 `services/taskCatalog/index.ts`（带内存缓存）；发布中心页经 DEV 模块间接读。
- **必要性**：**必要**。无它则画布任务库、实例名回显都无处安身。
- **理由**：全仓库唯一对外 REST 面；前端只在这条链上消费（workflow 两处），没有任何页面直接展示"任务目录"本身。
- **问题**：接口存在、无目录型页面（判定见 §4）；list 无分页（全量返回，当前量级安全，货架变大后是隐患）。
- **建议**：**保留**，中期补分页。

### 3.4 编排消费面：工作流锁版本与升级（#7）
- **名称**：工作流任务绑定/升级
- **业务含义**：S5 契约主体——DAG 节点钉死 (taskAssetId, taskRevisionId, taskRevisionNo)，源任务改版不影响在跑逻辑，升级是显式动作。
- **使用角色**：数据工程师（画布节点检查器"升级到 vN"按钮）。
- **输入**：节点三元组；升级时读资产当前指针。
- **输出**：执行快照 `TaskVersionSnapshot`（definitionJson+checksum 冻结进运行）；`updateAvailable` 标记回显。
- **依赖**：目录 get/resolveRevision + `TaskRegistry`（legacy SYNC 分支共存）。
- **交互模块**：CAT→WFL 主链；经 WFL 到任务内核执行。
- **必要性**：**必要**。全模块存在的头号理由。
- **理由**：跨项目、下线、类型三道 fail-closed 校验齐备；"先解析后改草稿"防脏指针持久化；离线资产仅拦升级不拦运行（语义自洽）。
- **问题**：JAVA 任务能上架不能编排（目录闸集合≠编排闸集合），对货架用户是一句看不懂的报错；legacy `task-asset:` 前缀散在前端多处字符串协议。
- **建议**：**保留**。

### 3.5 数据集消费面（#8）
- **名称**：数据集锁版本引用
- **业务含义**：数据集把某任务某版本的 SQL 当查询真相源（QUERY_REVISION），血缘/schema 同锚。
- **使用角色**：数据消费者/分析师（数据集页，无感知地受益于锁版本）。
- **输入**：sourceTaskAssetId（+version 行内 revision 三元组）。
- **输出**：数据集版本行、回源 SQL 执行、血缘登记。
- **依赖**：`DatasetTaskCatalogGateway`（目录→数据集私有快照的防腐层）。
- **交互模块**：CAT→DST；DST→分析/服务下游间接受益。
- **必要性**：**必要**。使目录成为"编排段+消费段"共同货架，而不只服务工作流。
- **理由**：防腐层设计干净——数据集不 import 目录 SPI，只经 gateway 转私有类型；表列 `source_task_asset_id/source_task_revision_id/_no` 在 baseline 即固化。
- **问题**：数据集侧无"源已发新版本"提示（前端 grep 无 updateAvailable 类似物，界面仅显示当前 Vn；是否算缺失见 §6）；详情页把资产显示成 `SQL TaskAsset #<id>` 裸 ID 文案，可读性差（该文件属数据集模块）。
- **建议**：**保留**。

### 3.6 上下线生命周期（#3 + DISABLED）
- **名称**：资产状态机（ONLINE/OFFLINE/DISABLED）
- **业务含义**：下线=退出"新编排发现"，保留指针供存量锁定引用继续解析运行。
- **使用角色**：发布运营者（发布中心"下线/重新上线"按钮）。
- **输入**：source+sourceRef（+项目）。
- **输出**：status 列更新。
- **依赖**：无。
- **交互模块**：DEV 发布中心、QUA 启停自动同步、WFL 选择器过滤（前端只拉 ONLINE）。
- **必要性**：**较必要**（ONLINE/OFFLINE 二态已足够支撑语义；DISABLED 第三态是冗余）。
- **理由**：下线不杀存量引用与 §3.2 的不可变承诺一致；质量监控器禁用即自动下架（`QualityTaskPublisher.eligible`）。
- **问题**：`DISABLED` 后端**无任何写路径**（全仓库仅读侧枚举/过滤/报错引用），前端却已做了 DISABLED 徽标与文案——典型的"表先行、壳先行"；下线无引用方影响面提示。
- **建议**：**补齐或裁剪**：要么补禁用流（配审批），要么删枚举+前端死分支。

### 3.7 发布前对账 reconciler（#9）
- **名称**：投影修复钩子
- **业务含义**：发现查询前把源域与货架的对不上的账就地修掉（存量监控器补上架）。
- **使用角色**：程序（Quality 存量数据在版本化上架机制前无需洗数）。
- **输入/输出**：无参 reconcile()→逐监控器重发布；异常仅 warn 吞掉。
- **依赖**：QualityMonitorRepository、QualityTaskPublisher。
- **交互模块**：CAT（钩子定义方）↔ QUA（唯一实现方）。
- **必要性**：**较必要**（对质量存量数据是真实需要；机制通用性已留口）。
- **理由**：30s/项目节流+页 200 分页扫描，实现克制；controller 测试专门覆盖按 source 过滤触发。
- **问题**：每次打开工作流任务库都可能触发全项目监控器扫描（性能税，靠节流兜底）；DEV 无对称实现，历史 legacy 行靠 boot 启动回填兜底，通道不统一。
- **建议**：**保留**，中期把 DEV 投影修复也收进同一钩子。

### 3.8 发布中心运营面（#10，跨模块）
- **名称**：发布中心（DEV 模块所有、目录状态的实际 UI）
- **业务含义**：把"货架当前指针"变成可运营动作：看版本历史、切任意历史版本（回退/前滚）、上下线。
- **使用角色**：数据开发负责人/发布运营。
- **输入**：assetId（+revisionNo）。
- **输出**：指针变更 + ONLINE/OFFLINE/DISABLED 计数、`hasNewerRevision` 提示。
- **依赖**：目录 service 的 list/get/publish/offlineSource + DEV 修订仓储。
- **交互模块**：是 CAT 的 `TaskCatalogService` 除 SPI 外最大的进程内消费方。
- **必要性**：**必要**。这是货架指针唯一被产品化的运营面；没有它，"切换线上版本"要么没有要么只能是后门。
- **理由**：代码明确自认这是"目录指针的合法改写口"（`activate` 注释"Switches the catalog pointer to any immutable historical revision"）；分页在服务端内存做（全量 list 后 sort/slice）。
- **问题**：**它是全平台版本真相的运营面，却物理归属数据开发、只见 DATA_DEVELOPMENT 一个来源**——质量上架的资产无运营 UI（只能靠启停间接控制）；页面命名"发布中心"不含"任务目录"心智，图二 CAT 节点在菜单上无对应物。
- **建议**：**保留 + 边界写明**（在文档/产品口径上承认"发布中心=任务目录的数据开发视图"，质量来源后续并入或补面）。

## 4. 真实功能定位：全平台版本真相源，还是 DEV 的附表？

**裁定：三层拆开看，它三层各是不同东西。**

1. **内容真相**：不在目录。不可变的版本内容在 `yak_dev_task_revision` / `yak_quality_monitor_revision`，源域 append-only（仓储接口无 update/delete，已核实）。目录表只有指针（`current_revision_id/no`）+发现元数据。这层设计**完全兑现了"货架不存货"**。
2. **"哪个版本现在算数"的真相**：在目录，全平台唯一。`yak_task_asset` 是 WFL 锁版本、DST 锁版本共同解析的闸口，任何模块想"按目录引用任务"都必须过它的 provider 校验——这一层它是**真的全平台真相源**，且被三个消费模块 import 级核实（pom 依赖：workflow/dataset/quality/data-development 四模块均引 `yak-ops-business-task-catalog`）。
3. **运营面（谁在看、谁在改指针）**：目前 100% 经数据开发之手。唯一的 UI（发布中心）在 DEV 模块、只看 DATA_DEVELOPMENT；唯一的指针回退口（activate）是 DEV 的功能；目录自身零写接口。**从产品现实看，它今天表现为"DEV 的发布账本 + WFL/DST 的解析依赖"**，"目录"作为独立心智尚未立起来。

**无独立 UI 是否成立**：成立，但有边界条件。货架的三类角色（发布方 DEV/QUA、消费方 WFL/DST、运营方）就当前产品阶段都能在各自场景内完成操作，专门的"目录页"价值有限。但两个前提没做到时"无独立 UI"会持续造成附表观感：①没有跨来源视图（质量的 300 个上架资产在 UI 上不可见，仅工作流选择器混排时以"数据质量"标签一闪而过）；②没有引用方反查（见 §6 P1），运营者对"这个货架被谁依赖"零感知。

**判定一句话**：架构上是版本真相源，产品上暂时是 DEV 的附表——差的是跨来源运营面和反查能力，不是代码质量。

## 6. 缺失能力表

| 优先级 | 缺失能力 | 现状证据 | 影响 |
|---|---|---|---|
| P1 | **引用方反查**：给 assetId（或 revisionId）查"哪些工作流节点/数据集版本锁着我" | 目录仅有按 (source,sourceRef) 与 assetId 的正向查询；全仓库无对 `WorkflowNodeSpec.taskAssetId`/`yak_dataset_version.source_task_asset_id` 的反向索引查询接口 | 发布中心"下线"无影响面提示；任务改名/下线后运营者不知波及谁；§4"无独立 UI"的边界条件之一 |
| P1 | **图与契约修正：CAT→QUA 边摘除/改写** | 见 §5 第三行 | 04/05 文档标 ✅ 是错的——登记册 #6 的"质量"会误导后续按图施工（如在 quality 里找目录消费方而找不到） |
| P2 | **发布指针写入校验**：publish 时 revisionId 可解析性 + revisionNo 单调性（activate 显式豁免） | `TaskCatalogService.publish` 只验 id>0；错指针到 resolveRevision 才抛（§3.1） | 脏指针窗口期内消费方随机报错，定位成本高 |
| P2 | **DISABLED 态闭环** | 后端无写路径（§3.6），前端已有徽标分支；发布中心筛选器也只有 ALL/ONLINE/OFFLINE | 死状态+死代码；若属规划应连工单出处一起写明 |
| P2 | **质量资产的运营面** | 质量资产上架后无任何页面可看其版本历史/指针（发布中心限定 DATA_DEVELOPMENT，`requireDataDevelopmentAsset` 硬闸） | 质量侧"发布"语义完全寄生在监控器启停上，出问题只能读库 |
| P3 | **DATA_INTEGRATION 供给方** | 枚举+前端标签映射"数据同步"已备好，无 provider/publisher；同步任务仍走 legacy `TaskRegistry` 通道进工作流 | 三来源之一的边是预留而非现实，图二上不应有预期 |
| P3 | **发现 API 分页** | `list` 全量返回；发布中心在服务端内存 sort/slice 也是因此 | 货架规模增长后的第一个性能点 |
| P3 | **DEV 投影 reconciler** | 仅 Quality 实现；DEV 历史行靠 boot 回填（一次性）+`claimLegacyProject`（惰性） | 对账通道不统一，跨来源修账各写各的 |
| P3 | **数据集侧升级提示** | 工作流有 updateAvailable+升级按钮；数据集仅有"重新发布取最新指针"的隐式路径，界面是否需显式提示属产品决策（当前无法确认是否刻意省略） | 消费段用户不知道锁的版本已旧 |

## 7. 现状总结

1. **完成度**：核心机制全量落地——发布 upsert、锁版本解析（三道一致性校验）、只读发现 API、上下线、项目投影、来源对账钩子；模块小而完整（11 个主源文件、1 张表、1 个迁移文件），且被 4 个业务模块 pom 级依赖、2 个模块（WFL/DST）真消费。
2. **不可变性判定（本次盘点最重要问题）**：**成立，无后门**。内容层源域 append-only 仓储物理上无 update/delete；解析层 revisionNo 精确匹配；改写"当前指针"的唯一口是发布中心 activate（产品化回退功能，且不影响已锁版本的存量引用）。唯一薄弱处是指针写入缺前置校验（P2）。
3. **页面现实**：任务目录**无独立页面、无菜单项**（navigation.ts 无对应条目，全 UI 无"任务目录"字样）；它出现在三条用户可见链上——工作流画布任务选择器（"已发布 vN"徽标）、工作流节点检查器升级按钮、发布中心页（在数据开发菜单组下，只管 DATA_DEVELOPMENT）。判定：接口存在，页面未展示（目录形态）；运营面存在，挂在别家（发布形态）。
4. **图的偏差**：登记册 #6"任务目录→工作流/质量/数据集"中"质量"是错的——质量是供给方不是消费方（§5）；这是 #5/#6 两条 ✅ 中唯一经代码证伪的部分，需回改 05 文档。
5. **口径旁路**：数据资产台账的 TASK 资产走 DEV 节点直供（含未发布节点），不读货架——同一任务在平台内有两本账（台账看节点、货架看已发布版本），同源不同径，暂无对账。
6. **状态机诚实度**：ONLINE/OFFLINE 语义清晰且被消费端尊重（选择器过滤、快照不拦存量）；DISABLED 是"枚举+前端徽标先行、后端无写方"的空头状态。
7. **项目/空间治理是全模块最严的部分**：PROJECT_OPTIONAL 注解、生成列唯一键、legacy 惰性认领、boot 启动回填且冲突拒绝启动、跨项目访问伪装成"不存在"（防 ID 泄露）——五件套完整，且有 contract test 护航。
8. **测试覆盖**：模块自身仅 2 个测试文件（service 单测 + reconciler 触发测试），量薄但打在关键行为上（发布幂等、类型拒收、过滤归一）；真正的行为验证散布在消费方测试（WorkflowTaskAssetBindingTest、WorkflowQualityTaskAssetBindingTest、DatasetPublisherTest 等）与两个架构边界测试中。
9. **一句话总评**：一个**机制正确、外壳缺席**的模块——"不可变版本货架"的技术承诺全部兑现且干净利落，但它作为④段独立节点的"产品人格"尚未成立：没有自己的页面、没有跨来源视图、没有反查能力，今天它是被三个模块重度依赖的基础设施，和一个躲在发布中心背后的指针。
