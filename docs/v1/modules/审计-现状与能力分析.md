# 审计 · 现状与能力分析

> 盘点日期：2026-09-21；依据：`docs/v1/04-主脉与模块交互图.md` 图二（横切B，DS/SYN/DEV/WFL/QUA -.操作记录.-> AUD）+ 代码走查。后端 `yak-ops-business-audit`（28 个 Java 文件，**无 Controller**），查询 REST 端点在 boot 层，前端视图散在三处。

## 1. 模块概览

- 模块名称：审计（操作记录）
- 在主脉与模块交互图中的位置：横切B 末端收集器；声明入边 5 条（DS/SYN/DEV/WFL/QUA）
- 上游模块：各业务域写入方；下游：boot 查询端点（AuditQueryController）供前端
- 模块一句话定位：设计良好的审计 SDK（事件模型+时间线渲染+JDBC 存储），但**接入面远小于设计面**——声明的 5 条边实测只有 2 条真接
- 当前实现状态：**部分实现**（库完整、埋点稀疏、查询端点存在）
- 主要入口：无独立菜单（判断）；查询经 boot `AuditQueryController`；写入经 `BusinessAuditService`/`AuditTransactions` 由各模块 import

## 3. 子功能逐个分析

**写入 SDK 全套**——业务含义：一次接入即留痕；角色：各模块开发。必要性：**必要**（S 契约无对应条，但属平台问责底座）。问题：SDK 好而埋点少=好锁没门。建议：**保留**。

**查询端点**——必要性：**必要**。问题：boot 层单 Controller 的过滤/导出能力深度当前无法确认。建议：保留。

**已接入埋点（DS/LIF/APR/部分 SVC）**——必要性：**必要**。问题：接入靠各域自觉，无 CI 守卫（语义 SPI 有编译期测试、审计没有）。建议：**补齐**为强制规范（关键动作清单化）。

**未接的三条声明边（DEV/SYN实时/QUA）**——这是本模块的核心乱象：04 图与 05 登记册（#记录为 ✅ 边）与代码相反。业务上：数据开发是变更最频繁的域，其操作无痕=审计最大的洞。必要性：补接是**必要**。建议：**补齐**（DEV 发布/试运行、实时任务生命周期、质检执行三处埋点）。

**system 双页面 + 安全审计页**——三处"审计"视图并存。必要性：operation-logs 与 oplogs 二者**冗余**其一（待路由核实哪个在用）；安全 access 视图**较必要**（语义不同应改名"访问日志"）。建议：**合并/下线**重复页。

## 4. 模块真实功能定位

- 实际角色：**审计基础设施（工具模块）**，尚不是"治理闭环"——写入侧覆盖率低，查询侧无处消费（没有告警联动、没有合规报表）。
- 是否关键节点：声明关键、实际半旁路。
- 被强依赖：workflow 查询其数据、审批页展示其记录——被展示性依赖，非控制性依赖。
- 真实边界：记录+查询，不做分析与告警。
- 职责过载/不清：不清之处在于"谁负责催埋点"没有机制；前端三视图边界混乱。
- 若下线：boot 查询 404、系统日志页空白；各业务运行不受影响——**当前审计缺席不会打断任何流程，这正是问题**。

## 5. 与其他模块的交互关系

- 上游（写）：DS ✅、LIF ✅、APR ✅、SVC 部分 ✅；DEV ✗、RTS ✗、QUA ✗（三条声明边断）。
- 下游（读）：boot Controller → 前端页面；workflow 进程内读。
- 数据流：同步写（业务事务内 AuditTransactions 包裹）；无事件总线；无异步任务。
- 风险点：①声明与现实相反会让管理者以为"核心操作都有痕"；②audit 表增长无保留策略（当前无法确认有清理任务——自身不做生命周期是讽刺点）。

## 7. 模块现状总结

- 已实现核心：完整 SDK + JDBC 存储 + boot 查询端点 + 4 域真实埋点。
- 未闭环：3 条声明边零接入。
- 接口无页面：多数查询参数/过滤能力。
- 任务无界面：无。
- 冗余：system 双 oplog 页；安全 access 页语义混杂。
- 真实定位：审计基建可用、覆盖率不足。
- 最大风险：**图的承诺与代码相反**——04/05 把边标 ✅，读者据此放心，实际核心变更无痕。
- 最该补齐 3 项：①DEV 埋点；②双页合并；③CI 守卫。
- 下一步：先修 05 登记册标注（把 DEV/QUA/RTS 改 ⚠️），再立补埋点票。
