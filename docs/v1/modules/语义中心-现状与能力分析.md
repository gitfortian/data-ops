# 语义中心 · 现状与能力分析

> 盘点日期：2026-09-22。依据：代码现实（`yak-ops-business/yak-ops-business-semantic`、`yak-ops-ui/src/pages/semantic`、Flyway、菜单迁移）＋ 权威架构图 `docs/v1/04-主脉与模块交互图.md`、交互契约 `docs/v1/05-模块交互与乱象清单.md`（S2/S10、乱象 R-5/R-8），并以 01/02 文档交叉验证（有差异处以代码为准）。
> 菜单名提示：模块叫「语义中心」，菜单组在 `V2036__domain_navigation_regroup.sql` 中改名为**「数仓标准体系」**，挂在一级域「标准与建模」（modeling）下——即乱象 R-8（菜单名≠模块名）的代码实证。

## 1. 模块概览

- **定位**：主脉③段最上游，"先立标准→再定指标→再建表→再加工"的第一环。拥有四类真相：**六类数据标准、业务域树、业务过程（含标准字段库与源表绑定）、数仓分层配置**。
- **后端**：`yak-ops-business-semantic`，主代码 94 个 Java 文件、约 7.4k 行；8 个 Controller（controller/v1）、12 个 api 接口（其中 8 个为对外只读 SPI）、私有 Flyway 目录 13 个迁移（V1~V13，11 张 `yak_semantic_*` 表）；12 个测试类（catalog/domain/process/field/preset/capture/recommend/usage/approval 全覆盖）。
- **六类标准**（`StandardKind.java`，同表 `kind` 判别列 + 类别专有可空列）：NAMING 命名、TYPE 类型、CODE 码值、UNIT 单位、CALIBER 口径、SECURITY 安全。六类共享一套 CRUD，全部在「数据标准」一页可见；CODE 类另做"码集聚合"视图（同一 `code_set_code` 的多码值聚合管理）。
- **前端**：`pages/semantic` 5 个路由页 + 1 个隐藏编辑页，约 4.0k 行：`/semantic/standards|domains|processes|processes/:id/edit|fields|layers`（`config/navigation.ts:121-126`）。此外 `services/semantic` 被 modeling、metric、data-asset、mdm 的**外部页面**直接引用——语义是前端跨页消费最广的词表源之一。
- **对外契约**：8 个只读/推送 SPI（StandardQuery/Recommend/Capture/Usage、ProcessApi、LayerConfigApi + 两个反向读取 LayerStdBindingReader/LayerUsageReader，由 modeling 实现、ObjectProvider 松耦合注入）。`DEPENDENCIES.md` 声明"消费方仅经 api 包 SPI、禁止直读表、依赖方向单向 modeling→semantic"。
- **实际被依赖**：modeling（23 处 import，最重）、metric、asset、lifecycle、mdm 共 5 个模块编译期依赖（pom 实证）；security 声明了 optional pom 依赖但**零 Java 引用**；data-development **完全未接线**。（盘点后已补线：缺口单 01=security 经 `std_security_id` 校验引用 SECURITY 标准；缺口单 02=data-development 经 `StandardRecommendApi` 做 SQL 输出字段命名检查，2026-09-22）

## 3. 子功能逐个分析

### 3.1 六类标准目录（共享 CRUD，NAMING/TYPE/CODE/UNIT/CALIBER/SECURITY）
- 业务含义：全平台"标准词表"的唯一属主，六类同表 kind 判别、类别专有列由服务层按 `StandardKind` 强制必填。角色：数据治理专员/建模工程师。输入：kind+编码+名称+类别专有字段（乐观锁 version）。输出：项目内标准记录，供字段库/建模列/指标/MDM 属性引用。依赖：无外部模块。交互模块：modeling/metric/mdm（经 StandardQueryApi/Recommend/Capture）。必要性：**必要**（③段最上游的定义权）。当前问题：①SECURITY 类的 mask_rule 无人消费、与 dsec 分级并行两套（详见 5.4）；②编码不可改但无改名审批闸（见 3.6）。建议：**保留**。

### 3.2 码值标准·码集聚合管理
- 业务含义：把同 `code_set_code` 的多个码值聚成一个"码集"整体管理（新建整集/追加码值/整体启停删），字段库按码集编码（而非单码值）引用整个值域。输入：码集+码值列表。输出：码集详情/版本/选项。依赖：同表存储（无独立码集主表，REQUIREMENTS 32.1 方案 A）。交互模块：modeling（std_code_set_code 松散引用列）。必要性：**必要**（避免逐行管理码值的可用性问题）。当前问题：码集是字符串逻辑分组，跨项目/全局码集无预留；重命名码集编码需逐行改。建议：**保留**，出现跨项目共享码集需求时升级为主表。

### 3.3 标准版本快照
- 业务含义：每次修改前把完整旧状态写入 version 表（payload_json），支撑"标准改过什么"追溯。角色：治理专员/审计。输入：修改动作。输出：版本列表抽屉。依赖：同事务写入。必要性：**较必要**（词表变更影响下游全部引用，须可追溯）。当前问题：**回滚只读**（V3 注释明示本期仅查看）；前端只有查看抽屉、无对比 diff。建议：**保留 + 补齐**（版本 diff，视需要开放回滚）。

### 3.4 预置标准初始化
- 业务含义：平台级模板（类型/命名/码值/单位/口径/安全各有种子数据）一键复制进项目，冷启动即有可用词表。输入：点击"初始化"。输出：批量标准（幂等）。必要性：**较必要**（降低六类标准从零录入成本）。当前问题：初始化后再改模板与项目实例无同步机制（复制式，一次性）。建议：**保留**，属合理取舍。

### 3.5 标准用度统计与反哺（APPLY/BYPASS）
- 业务含义：modeling 在套用/绕过标准的动作点推送事件，语义侧聚合出每条标准的采纳/绕过数，绕过≥采纳且≥3 判"可疑"反哺标准修订。角色：治理专员。依赖：`StandardUsageApi`（fail-open，不阻断建模流程）。交互模块：modeling（编辑器/反推导入/推荐套用三个场景位，scene=EDITOR/REVERSE_IMPORT/RECOMMEND）。必要性：**必要**——这是语义从"死词表"变成"有反馈回路的标准"的关键机制，05 清单 S2 的活性证明。当前问题：无定时汇总/报表页（仅单标准详情抽屉查看），可疑标准无治理动作承接。建议：**保留 + 补齐**（可疑标准清单视图）。

### 3.6 标准发布审批（后端完整、前端已接入口）
- 业务含义：标准从 DISABLED 生效为 ENABLED 走 STANDARD_PUBLISH 审批流，批准即启用（同事务，决策 D5）。后端：`POST /{id}/publish-approval` + `StandardPublishApprovalHandler`（注册进审批中心 flowCode）。前端：**全仓库 semantic 页面无任何调用**（仅数据资产有自己的 publish-approval 按钮）。**判定：接口与审批回调存在，页面未展示（发起入口缺失）**。必要性：**较必要**（05 清单第 15 条"语义变更审批"标 ✅，指机制存在；从用户视角发布闸不可用）。当前问题：实际发布=直接改状态端点绕过审批，与"发布无闸"的防护意图相悖。建议：**补齐界面**（数据标准页加"提交发布"按钮+状态机区分待审批态）。
- **已落地（2026-09-22，缺口单 03）**：数据标准页/详情抽屉照 modeling 先例接"存量代码+开关"三件套（`listFlows` 探开关、`findByBiz` 在途快照、15s 轮询终态并提示驳回原因）；开闸后非 CODE 行"启用"替换为"提交发布"（不留直发按钮，停用不拦），在途冻结行操作并出"审批单"跳转；后端补 `submit` 前置校验 `PUBLISH_ALREADY_ENABLED(42023)`。CODE 码集整组与 `/status` 端点级在途拦截为遗留边界，见 03 单。

### 3.7 业务域树
- 业务含义：按主题分层的业务域（交易域/订单子域），是全平台"域"一词的唯一定义源（S10）。输入：编码/名称/父级/负责人。输出：树；被过程挂靠、指标/建模表单消费。依赖：删除时校验过程引用。交互模块：metric、modeling（domain_id 列+表单树选择）、asset（目录树维度）。必要性：**必要**。当前问题：R-5 一词二义的历史包袱（详见第 7 节，代码侧已基本修复）。建议：**保留**。

### 3.8 业务过程管理（含粒度/FACT-DIM 类型）
- 业务含义：域锚定的业务动作（下单/支付），带分析粒度与事实/维度类型，是指标（原子指标=过程+度量）与建模派生的语义锚点。输入：编码/名称/所属域/grain/bizType。输出：过程记录+字段数统计。依赖：业务域。交互模块：metric（process_id 必填于原子指标）、modeling（44 派生读过程字段集）、asset（目录）。必要性：**必要**（③段"标准→指标→建模"链条的中枢概念）。当前问题：无。建议：**保留**。

### 3.9 过程字段集与源表绑定
- 业务含义：过程挂标准字段（引用不复制）+ 绑定物理源表（MAIN/DETAIL/DIM+关联条件），为建模派生提供"该过程该有哪些字段、从哪张表来"。输入：fieldId/isRequired、datasourceId+sourceTable。输出：过程装配上下文。依赖：datasource 模块（连通性校验、表搜索下拉）。交互模块：modeling `ModelDeriveService`/`ReverseImportService` 经 ProcessApi 消费（含 `listProcessSources` 按角色继承字段）。必要性：**必要**（语义到物理的唯一接合点）。当前问题：编辑页混排 modeling 主线视图，页面归属心智略混。建议：**保留**。

### 3.10 标准字段库（五类标准引用的载体）
- 业务含义：项目全局字段字典，role=过程标识/维度/度量，每个字段可引用类型/单位/口径/码集/安全五类标准——**这是"列的语义"的中央登记处**。输入：编码/名称/角色/std_* 引用。输出：字段记录（data_type 为类型标准快照服务端同步）。依赖：六类标准。交互模块：过程字段集、modeling（StdFieldMatcher/派生落列）、mdm。必要性：**必要**——若没有这层，六类标准只是孤立词表；字段库把标准组装成可复用列定义。当前问题：类型快照同步（引用标准变更后字段 data_type 是否即时刷新——未在同步路径上找到批量重刷机制，**当前无法确认**存量一致性）。建议：**保留 + 核实快照同步**。

### 3.11 数仓分层配置（含定标强制与落标率）

## 4. 模块真实功能定位

**它是全平台词表真源，不是又一套 CRUD** —— 证据：

1. **被编译期强依赖 5 个模块**：modeling（23 处 import：查询/推荐/沉淀/用度/过程/分层全套 SPI + 反向实现两个读取器）、metric（域/过程/口径/单位解析，`MetricReferenceResolver` 仅经 SPI）、asset（目录树按层/域/过程组织）、lifecycle（TTL 按层取默认）、mdm（属性 std_* 引用校验经 StandardQueryApi）。消费方全部**只存松散 ID/编码**（modeling V8 六列、mdm V3 四列、metric V1/V2 四列），无一复制标准内容——S2 契约在数据层成立。
2. **前端消费广度**：`services/semantic` 被 modeling（4 页）、metric 表单、asset 目录/注册、mdm 属性页直接 import；域树/标准下拉是跨模块表单组件。
3. **反馈回路存在**：用度统计（APPLY/BYPASS→可疑判定）使词表有活性数据，这在一般"标准管理"型 CRUD 中不常见。
4. **反向依赖存在**：semantic 的分层页展示建模侧实时算出的落标率/引用数（反向 SPI+ObjectProvider，无编译反向依赖）——它是少数"双向都真"的交互。

**强依赖的例外（定位的反面证据）**：六类标准中的 SECURITY 是"名义真源"——security 模块有自己的 `yak_dsec_security_level`/掩敏体系且对 semantic 零 Java 引用，安全标准目前只被字段库/建模列引用，管不住数据安全页。口径标准同理风险低（CALIBER 无平行系统）。结论：**真源地位成立，但覆盖度是"六类中五类真、一类平行"**。
