# 告警 · 现状与能力分析

> 盘点日期：2026-09-21；依据：`docs/v1/04-主脉与模块交互图.md` 图二（横切B，WFL/QUA -.失败通知.-> ALR）+ 05 #16 + 代码走查。后端 `yak-ops-business-alert`（15 个 Java 文件）+ 插件 `yak-ops-plugin-alert`（api + dingtalk），前端 `yak-ops-ui/src/pages/alarm`。

## 1. 模块概览

- 模块名称：告警（通知渠道）
- 在主脉与模块交互图中的位置：横切B 末端；声明入边：WFL、QUA 失败事件
- 上游模块：工作流、数据质量（触发方）；下游：外部渠道（钉钉 webhook）
- 模块一句话定位：渠道插件化的通知发送器——**钉钉一条通道真实可发**，质量侧通道（EMAIL/WEBHOOK）只落 PENDING 不投递
- 当前实现状态：**部分实现**（渠道管理/规则/记录三件套页面 + DingTalk 真投递；事件路由与订阅机制薄）
- 主要入口：前端 `/alarm`（渠道/规则/记录三 Tab）；后端 AlertController；SPI：`AlertNotificationSink`、`AlertPlugin`

## 3. 子功能逐个分析

**渠道管理（含测试/启停）**——业务含义：告诉运维"出事发到哪"；角色：平台管理员/运维。输入：webhook 配置；输出：可发送渠道。依赖：插件。必要性：**必要**。问题：渠道类型仅钉钉一种实装，下拉里若出现未实装类型即误导（EMAIL/WEBHOOK 质量侧 PENDING 已是先例）。建议：**保留 + 收敛**（未实装类型下架或标注"未启用"）。

**钉钉插件投递**——真实代码链（WebhookClient+单测）。必要性：**必要**（本模块存在价值的实证）。问题：无重试/退避与投递回执追踪（当前无法确认）。建议：保留补可靠性。

**规则 Tab**——业务含义：定"什么事告"。必要性：**必要**（否则渠道空转）。问题：规则与触发源（workflow/quality 事件）的绑定链路未证实闭环——05 #16 称工作流失败通知✅，工作流盘点实测只到站内信，说明规则引擎可能**有壳无流**。建议：**补齐**（把 WFL 失败事件接进规则评估）。

**记录 Tab**——可观测。必要性：**较必要**。建议：保留。

**站内信双轨**——system/messages 与 alert 并存。必要性：站内信**较必要**；问题：双轨无路由规则。建议：**合并**（站内信作为一个内置 channel 纳入规则路由）。

## 4. 模块真实功能定位

- 实际角色：**一个配置完整的发送器 + 一条没接上的事件线**。通知体系真正在跑的是站内信（寄生在 system 域），告警模块离"失败自动钉钉"差最后一段路由。
- 关键节点：否（当前无人依赖它保命——半夜跑失败确实没人知道，05 #16 担心的场景未解除）。
- 被强依赖：无。
- 类型：工具模块（通知网关）。
- 边界：管发送与渠道，不管事件产生；但"规则"页让它看起来管订阅——职责展示大于实质。
- 下线影响：钉钉通知（若有手工使用）消失；其余无感。

## 5. 与其他模块的交互关系

- 上游：WFL→ALR ⚠️（半接线：站内信真、渠道规则未证实）；QUA→ALR ⚠️（PENDING 无投递）。项目记忆亦曾载"调度告警在内存、无 UI"——现已有 UI，但**事件流未闭环，属于"页面已展示但后端未完成"的变体**。
- 下游：外部钉钉 webhook（唯一出网口）。
- 数据流：记录表写入；控制流：toggle/send 同步调用；异步：无；共享存储：无。
- 风险点：①"有渠道页≠有通知"的错觉（与安全模块同型的展示性风险）；②webhook secret 存 configJson 的加密口径当前无法确认。

## 7. 模块现状总结

- 已实现核心：渠道 CRUD/测试/启停、钉钉真投递、规则与记录页。
- 未闭环：失败事件→规则→投递主链（模块存在的理由）。
- 接口无页面：send/sendAuto API。
- 任务无界面：无。
- 冗余：与 system/messages 双轨。
- 真实定位：待接线的发送器。
- 最大风险：**承诺已通知、实际只有站内信**——05 #16 需降级标注。
- 最该补齐 3 项：①事件闭环；②假渠道处置；③投递可靠性。
- 下一步：一条竖线打通（workflow 失败→规则→钉钉），比再加渠道值钱。
