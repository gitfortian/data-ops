| 当前实现状态 | **已实现**（SQL_QUERY 来源端到端闭环：DEV 工作台建→草稿→发布版本→上线→下游查询；查询运行时、诊断、血缘、资产投影齐备）；**半实现**（QUERY_REVISION 锁版本路径：后端机制完整、有测试，但前端无创建入口，初始发布接口 `POST /api/v1/datasets` 页面未展示）；**占位**（TABLE/VIEW 枚举值存在但无 query adapter、无创建路径） |
| 主要入口 | 前端菜单「消费与服务→数据集」`/dataset`（列表）、`/dataset/:id`（详情），`yak-ops-ui/src/config/navigation.ts:73-74`；DEV 工作台 Dataset 节点编辑器 `pages/development/data-development/components/dataset/DatasetNodeEditor.tsx`；API 前缀 `/api/v1/datasets`（`DatasetController.java:38`）与 `/api/v1/data-development/nodes/{nodeId}/dataset*`；Flyway：`db/migration/yak-dataset/V1__baseline_dataset.sql`（5 张表，单一基线，无后续增量）；模块内无定时任务；随 boot 构建（`yak-ops-boot/pom.xml:93`） |

特别说明：图二承诺的"一本消费账"在当前代码里是**三本半**——ANA/AGT/DBH/SCR 的前端取数都走 dataset 查询运行时（账在），但 **SVC 完全旁路 dataset 自建第二份 SQL 真相**（`data-service/.../V1__baseline_data_service.sql:9-10` 自带 `data_source_id + sql_text`），且 **Dashboard/大屏的取数是浏览器直连 dataset query API**，后端消费侧没有统一收口。详见第 4、5 节。

## 3. 子功能逐个分析

### 分组 A：管理与详情（功能 1–5、17）

**A1 列表 + 上下线 + 详情六页签**
- 业务含义：消费层资产的登记簿——谁能看、什么状态、哪个版本、字段契约是什么。
- 使用角色：数据消费者（分析师/运营）看契约与预览；管理员上下线闸口。
- 输入：无参列表 + 前端筛选；datasetId。输出：`DatasetVO/DatasetDetailVO`。
- 依赖：`DatasetReader`（同模块）、security 项目上下文。
- 交互模块：下线动作冲击所有下游（前端文案自认"下线后 Analysis、仪表盘和大屏无法查询"，`detail/index.tsx:762`）。
- 必要性：**必要**。这是"消费账"的账本本体。
- 当前问题：①列表一次全量拉取+前端过滤分页（`index.tsx:59` 调 `listDatasetsForManagement()` 无分页参数），数据集体量变大后必然劣化；②无删除能力（误建只能永久下线）；③"空态引导去发布中心发布数据集"是假引导（发布中心无此功能，见功能 3/9）。
- 建议：**保留 + 补齐**（后端分页、删除/归档守卫、修正空态文案）。

**A2 权限模型（功能 17）**
- 业务含义：项目间隔离靠 `@ProjectScope`；菜单码只控制入口显隐。
- 必要性：**必要**（现状半成品）。
- 当前问题：DatasetController/节点 dataset API 均无 `@RequiresPermission`，与同仓 DEV 节点控制器（写/发布/执行分权限，`DevelopmentDatasetNodeController.java:47,65,82`）标准不一；"谁能改数据集定义/上下线"与"谁能查数"完全没有区分。
- 建议：**补齐**（read/manage 两档权限码）。

### 分组 B：创建与版本化（功能 6–9）

**B1 Dataset 节点（SQL_QUERY 路径，功能 6–7）——当前唯一有 UI 的创建路径**
- 业务含义：数据开发工作台里一种独立节点类型，用户直接选数据源、写只读 SQL、冻结成版本化的消费契约；不产出调度任务。
- 使用角色：数据开发/分析师。
- 输入：nodeId + dataSourceId + SQL(≤200000 字符) + 可选字段覆写；输出：草稿（即时保存）或新 `DatasetVersion`（发布）。
- 依赖：`DevelopmentDatasetFacade`（dataset 模块稳定边界）、`DatasetSchemaDiscovery`（经 datasource SPI 真执行取列+取样）、任务目录（仅用于校验节点合法性上下文）。
- 交互模块：DEV 树/编辑器注册（`editors/registry.tsx:125 type==='DATASET'`）、`DevelopmentNodeType.DATASET`。
- 必要性：**必要**。这是⑤段入口的进水口，且"Dataset 节点＝直连消费定义、SQL 任务＝调度产出"的边界在代码注释里说得清楚（Controller 类注释）。
- 当前问题：①图一把进水口画成"发布任务→锁版本→数据集"，现实主流路径却是 Dataset 节点直连 SQL——**图与码的主路径不同**；②`yak_dataset.development_node_id` 唯一键意味着数据集与节点 1:1，节点删除时数据集的存续/联动策略在 dataset 模块侧未见守卫（DEV 侧如何处理属数据开发盘点范围，**当前无法确认**是否有级联）；③编辑器的 SQL 安全校验是正则黑名单（`DatasetSqlSafety`），能拦常见写操作但非语法级验证。
- 建议：**保留**；主脉图应改画或将 QUERY_REVISION 路径真正接上（见 B2）。

**B2 TaskAsset 锁版本路径（QUERY_REVISION，功能 8–9）——图二 CAT→DST 边的本体**
- 业务含义：把任务目录中 ONLINE SQL TaskAsset 的**当前不可变 Revision** 冻结为 DatasetVersion，任务升级不显式发布新版本则下游查询逻辑恒定（登记册第 6 条 S5 规矩的 dataset 侧执行）。
- 使用角色：设计上是数据开发（发布任务后转数据集）；**现实中无人可点**。
- 输入：`sourceTaskAssetId`；依赖：`TaskCatalogDatasetAdapter.get/resolveRevision`（含项目 fail-closed）。
- 查询时行为：每次查询按版本内 `sourceTaskAssetId+revisionId` 回源任务目录取 SQL 内容再编译执行，并校验 revision 快照一致（`QueryRevisionDatasetSourceAdapter.java:57-67`）——冻结的是**引用+revision 号**，SQL 文本不在 dataset 库中。
- 必要性判定：**较必要，但当前是断头路**。机制+测试完整（`DatasetPublisherTest` 覆盖 publishFromRelease 幂等/追版/字段稳定 ID），前端却只接了"发布新版本"按钮（且仅对已存在的 task 来源数据集生效），**首次发布 `POST /api/v1/datasets` 与幂等入口 `publishFromRelease` 均无生产调用方**。结论：该路径现存数据集中预计为零或极少（无法查运行库确认，**当前无法确认**存量）。
- 建议：二选一——(a) 在发布中心/任务详情补"发布为数据集"动作，把图二 CAT→DST 边接通；(b) 承认 Dataset 节点是唯一进水口，将 publish/publishFromRelease 端点标记 legacy 并同步改图。悬挂现状最差。

**B3 TABLE/VIEW 占位（功能 12）**
- 业务含义：枚举预留"直读物理表/视图"来源。
- 必要性判定：**过渡**。前端列表标签与详情页已为其写了防御文案（`SOURCE_TYPE_LABELS`、"尚未接入"提示），但无 adapter、无创建端点、版本表 `source_task_asset_id NOT NULL` 暗示当初只设计了 task 来源。
- 建议：明确排期接入或删除枚举值；前端展示两个永远选不到的标签属于噪音。

### 分组 C：查询运行时（功能 10–11）

**C1 语义查询编译与下推**
- 业务含义：⑤段所有消费形态的执行引擎——把"维度+聚合指标+过滤+排序"编译为单层包装 SQL，经平台唯一 `SqlExecutionRuntime`（caller=DATASET 策略强制只读、虚拟线程可取消、超时/maxRows 受控）推到源库执行；**无本地引擎、无物化快照、结果不落库**。
- 使用角色：分析前端（仪表盘图表）、大屏运行时、问数后端、Playground。
- 输入：`QueryDatasetRequest`（dimensions/metrics/filters/sorts/limit≤1000/timeoutSeconds≤120/versionNo）；输出：列绑定+行集+truncated+耗时。
- 依赖：core `SqlExecutionRuntime`（实现驻 datasource 模块）、`DatasetSourceQueryRegistry`（按 sourceType 精确路由）、字段契约（过滤/维度引用 fieldId 而非物理列，防注入面收敛到 `SAFE_IDENTIFIER` 校验）。
- 交互模块：见功能 10。
- 必要性：**必要**，全模块价值之锚。
- 当前问题：①每次查询实时穿透源库，**无任何服务端结果缓存/物化层**（前端仅有 1.5s 的同参共享缓存，`components/analysis/query-runtime.ts`），大屏轮询与重看板直接砸源库；②limit 硬上限 1000，导出/明细场景无出路；③无异步/流式查询（>120s 的重查询不支持）；④聚合下推依赖方言通用函数（`DatasetQueryCompiler` 的 metricExpression），26 种数据源方言兼容性只能靠运行时试错——**当前无法确认**在非 MySQL 系源上的实测覆盖面。
- 建议：**保留**；缓存/物化与异步查询是 P1 演进方向（第 6 节）。

**C2 查询诊断（功能 13）**
- 业务含义：每次 attempt 唯一 queryId + 四段耗时（wait/prepare/execute/transfer）+ SQL 脱敏指纹落库，异常也落 REJECTED/FAILED 终态。
- 必要性：**较必要**（消费层"谁能查、查多慢、查挂在哪"的账本）。
- 当前问题：证据链已闭环且被仪表盘性能弹窗复用，是全仓观测做得最实的一块；仅诊断数据无保留期清理策略（表只进不出）。
- 建议：**保留 + 补齐**（TTL 清理）。

### 分组 D：治理外围（功能 14–16）

**D1 资产投影 / 血缘派生 / 首页供数**
- 业务含义：数据集作为资产进台账（DATASET 类型）；从当前版本 SQL 解析表/列级血缘（`EVIDENCE_SOURCE_TYPE=DATASET_SOURCE_PARSE`）；首页消费 overview 快照。
- 依赖：asset/lineage 模块 gateway；AFTER_COMMIT 事件 + REQUIRES_NEW 投影事务，主流程不被拖垮。
- 必要性：**必要**（对齐登记册第 10、血缘承诺 `DST -.-> LIN`）。
- 当前问题：血缘方向只登记"上游表→数据集"，消费方（哪些仪表盘/大屏引用了本数据集）的反向边由 dashboard 侧登记（`DashboardLineageSynchronizer` 存在），dataset 本身不重复记——分工正确；`lineage/DatasetLineageSnapshotReader` 是否有页面消费未逐一核对——**当前无法确认**。
- 建议：**保留**。

## 4. 真实功能定位

**问题：数据集是⑤段消费层的唯一入口，还是旁路横生？**

结论：**"唯一入口"是设计意图，当前现实是"准入口 + 两处旁路 + 一处取数越层"**：

1. **入口地位真实成立的部分**：分析（绑定校验+全部取数）、智能问数（后端全量经 `DatasetQueryService`，且只读 dataset——连 05 清单 R-6 都承认其唯一声明依赖是 dataset）、仪表盘/大屏的前端图表取数（全部调 `/api/v1/datasets/{id}/query`）——⑤段四种消费形态里有三种半确实吃这一本账。
2. **旁路一（真旁路）：数据服务 API**。后端 pom 只依赖 datasource（`yak-ops-business-data-service/pom.xml`），表结构自带 `data_source_id + sql_text`（V1 基线:9-10），Java 源码 grep dataset 零命中。图二 `DST --> SVC` 边**不成立**，SVC 是⑤段里自己开闸取数的第二真相。这不是"引用了不同东西"，而是同一件事（对外供数契约）两套模型。
3. **旁路二（取数越层）：仪表盘与大屏的数据面在浏览器**。两模块后端只 import dataset 做**存在性校验**（`DatasetDashboardAdapter.requireExists`），真实数据由前端直连 dataset query API。这使"消费账"在审计/限流/缓存层面缺一层服务端收口——平台不知道"哪个仪表盘查了哪个数据集多少次"（只有 dataset 侧 query-performance 知道 queryId 级事实，无消费方归因）。
4. **入口的进水口也被换过**：图一/图二的主叙述是"DEV 发布任务→CAT 锁版本→DST"，代码现实是"DEV 工作台 Dataset 节点直写 SQL_QUERY 草稿→发布版本"，锁版本路径（QUERY_REVISION）无 UI 首发生成入口（功能 9）。**接口存在，页面未展示**。
5. 数据集兼任"⑤段唯一语义引擎"（聚合下推/字段契约/版本可回溯），这个职责在分析、大屏、问数之间没有第二份实现——引擎层是干净的。

一句话：**数据集已经是分析/问数/看板取数的真账本，但"一本消费账"要成立还差两刀——数据服务收编（或正式豁免并改图）、消费侧取数从浏览器直连改为服务端归因（或接受现状并在文档层正名）。**

## 6. 缺失能力表

| 优先级 | 缺口 | 现状证据 | 影响 | 建议动作 |
|---|---|---|---|---|
| P0 | 锁版本首发链路无 UI（CAT→DST 边断头） | `DatasetController.publish`/`DatasetService.publishFromRelease` 零调用方；`releases/index.tsx` 无 dataset 动作 | 图二承诺与代码现实背离；QUERY_REVISION 能力（含查询期回源校验、字段稳定 ID）整体闲置 | 发布中心加"发布为数据集"，或正式退役该来源并改图（决策级） |
| P0 | 数据服务旁路无处置 | 第 4 节第 2 点 | "一本消费账"假象；API 面与 BI 面同一 SQL 两处维护 | 并入 05 乱象清单：要么 SVC 增加 dataset 来源模式，要么 04 图改画 `DS→SVC` 并明文豁免 |
| P1 | API 无权限码，仅项目隔离 | `DatasetController` 无 `@RequiresPermission`（对比 DEV 节点控制器） | 同项目内任意用户可上下线/发布版本 | 补 read/manage 两档权限并接入菜单码 `dataset-management` 体系 |
| P1 | 无服务端缓存/物化，消费侧无归因 | 查询即穿透源库；前端仅 1.5s 去重（`query-runtime.ts`）；大屏轮询直连 | 源库压力与"谁在查"不可答 | 查询侧加 TTL 缓存/物化选项（与 TABLE/VIEW 来源合并规划）；query-performance 增加 caller 维度（DASHBOARD/SCREEN/AGENT） |
| P2 | TABLE/VIEW 枚举占位 | 功能 12 | 前端展示两个不可用标签，用户误解为可选来源 | 排期接入或删枚举 |
| P2 | 列表全量拉取无后端分页 | 功能 1 | 规模化后列表劣化 | page 化（与 overview 的 listLimit 机制已有，可复用） |
| P2 | 数据集不可删除/归档，DEV 节点删除联动未证实 | 无 DELETE 端点；节点级联**当前无法确认** | 垃圾数据集永久驻留 | 补归档态 + 下游引用守卫（analysis/dashboard/widget 引用计数） |
| P3 | 诊断表无 TTL 清理；导出/大数据量场景（limit≤1000）无出路 | `yak_dataset_query_performance` 无清理；`MAX_LIMIT` | 存储缓涨；明细下载需求外溢 | 定期清理任务 + 异步导出通道 |

## 7. 现状总结

1. **实现完成度：高（查询运行时与 SQL_QUERY 主链）/ 中（版本化双轨的另一轨）**。Dataset 节点→草稿→发布→上线→下游查询端到端有码有页有测试；QUERY_REVISION 锁版本轨后端完备但 UI 断头。
2. **与图二一致性：11 条相关边里 8 条成立、1 条半成立（CAT→DST）、1 条不成立（DST→SVC）、1 条图外新增（DST→HOM）**；最重的偏差是 SVC 旁路与"消费账取数在浏览器"两处。
3. **前后端对称性：好中带一暗**。页面能力全部有后端；反向缺口两个——`POST /api/v1/datasets`（接口存在页面未展示）与 `publishFromRelease`（接口存在且无调用方）。TABLE/VIEW 是唯一"前端有标签、后端无实现"位。
4. **数据模型：干净**。5 张表职责分明（身份/不可变版本/版本字段/草稿字段/查询诊断），draft 列与 version 表分离正是"预览契约≠持久契约"硬规则的落库表达；`source_task_asset_id NOT NULL` 暴露了版本表最初只为 task 来源设计、SQL_QUERY 靠 0 值兼容的演进痕迹。
5. **代码健康度：高**。分层（definition/publication/query/schema/lineage/observability/gateway）+ 依赖边界测试（analysis 侧 `AnalysisDependencyBoundaryTest` 同款机制）+ 模块自述文档（README/DOMAIN/ARCHITECTURE）三件套齐；错误语义中文可读、事务边界明确。
6. **职责过载信号：轻度**。兼任了资产投影、血缘取证、首页供数三个外围，但全部走 gateway/provider 模式不存第二真相，属健康扩展而非膨胀。
7. **治理接入：全**。血缘、资产台账、项目空间 fail-closed、SQL 只读策略（消费方 caller 由 core 强制）四项都在线；审计未接（上下线/发布无操作审计记录）——同仓 DEV 已显式接 `BusinessAuditService`，dataset 未接，属偏科。
8. **对相邻模块的真实依赖（代码事实）**：core（SqlExecution SPI/ProjectScope）、common（权限/枚举）、datasource（经 SPI adapter）、task-catalog（adapter）、lineage/asset（gateway/provider）；前端消费方 analysis/dashboard/digital-screen/agent 全部经 `/api/v1/datasets` HTTP 面，后端跨模块依赖方仅 analysis（binding）、dashboard（exists）、agent（catalog+query）、home（overview）、data-development（facade）五家。
9. **综合判断：保留，定位需一次"账务清算"**。数据集作为⑤段语义引擎的地位是真实的、代码质量是全仓上乘；P0 两件事都不是写代码，而是**拍板**：锁版本首发链路接上还是退役改图、SVC 收编还是豁免改图。P1 权限与消费归因是"入口"之名兑现的最低补票。

## 8. 掌握度自检

| 问题 | 掌握度 | 说明 |
|---|---|---|
| 两种可运行来源与创建路径 | 高 | Facade/Manager/Publisher/Writer 全链读码 + 前端 DatasetNodeEditor/use-dashboard 交叉；TABLE/VIEW 无 adapter 以 Registry 抛错逻辑确证 |
