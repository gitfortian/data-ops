## 1. 模块概览

- **一句话定位**：全平台统一的「资产节点 + 有类型有向边」图谱底座（`yak_metadata_asset` / `yak_metadata_relation`），自身**不解析 SQL、不生产边**——解析与登记全部由各源域模块经进程内 facade 完成；lineage 只提供图模型、幂等 upsert、证据域替换、有界遍历与查询 API。
- **公开契约**（`ARCHITECTURE.md` 公共 API 边界）：`analysis.sql.SqlProjectionLineageAnalyzer`（source-neutral 解析接口，实现在 data-development）、`domain.*`、`query.LineageQueryService`、`registration.LineageRegistrationService`、`maintenance.LineageMaintenanceService`；调用方经各自 Gateway/Adapter 隔离（dataset/analysis/dashboard 均有 `gateway/lineage/*Adapter`）。
- **HTTP API**（`/api/v1/lineage`）：注册资产/关系（POST）、资产搜索/按 ID/按 assetKey 查询、upstream/downstream/graph（depth 后端上限 **10**，方向 BOTH/UPSTREAM/DOWNSTREAM）。**无 DELETE 端点；overview（首页统计）不对外走 HTTP，仅进程内消费；controller 无 `@RequiresPermission` 注解**（仅 `@ProjectScope(PROJECT_OPTIONAL)`）。
- **存储**：自有 Flyway 仅 2 段迁移（V1 建两表；V2 把 `yak_metadata_asset` **就地扩为统一实体目录**，列 steward 契约：lineage 拥有 asset_key/asset_type/parent_asset_id/properties，metadata 拥有目录列含 `gone_at`）。图遍历与搜索按当前项目过滤（`LineageDaoImpl` 每查询 `eq(projectId)`），唯一键 `uk(project_scope_id, asset_key)`，边唯一键含证据与版本。
- **登记方（8 个来源，逐模块 grep 核实）**：DEV（SQL 解析）、MOD（引导式手工）、MTR（依赖快照 afterCommit）、DST（版本 SQL 解析 afterCommit）、ANA（图表绑定 afterCommit）、DBH（生效快照 afterCommit）、MDM（手动同步，走 `PhysicalTableAssetKey`）、METADATA（采集/登记通道直写共表**只供节点不登边**）。
- **缺席方（grep 零命中，全模块无 lineage 引用）**：SCR 大屏（核实「无血缘投影」成立）、SEC 数据安全、SYN 离线/实时同步、SVC 数据服务、AGT 智能问数、WFL/JOB/CAT/QUA/RES/SEM/DS（数据源本体）。
- **04/05 口径校验**：图二登记边只画 `MOD & MTR & DEV & DST`，**实际 ANA、DBH、MDM 也在登记**（《分析》《仪表盘》两盘点已各自记为「图外补全」，本盘点复核为真）；#8 模型血缘、#9 指标血缘 🔧（M-3 已修并实测）与代码一致——M-3 修复痕迹在 `pages/metric/lineage/index.tsx:60-89`（虚拟上游合成）与 `ModelingLineageController.graph` 未登记时自动登记。R-8（菜单名/路由）属实。

## 3. 子功能逐个分析

### 3.1 全局血缘工作台（§2.1–2.7）
- **必要性：必要**。模块的门面页，也是 M2-3 深链枢纽（指标/数据集/资产详情都往这里跳）。搜索→选根→方向/深度/类型过滤→详情/证据/回链，闭环完整；双击重设中心代替「逐层展开」。
- **理由**：这是全平台唯一能看见跨域合流图的地方；「视图筛选前端裁图、影响计数前端计算」说明后端未提供过滤/聚合语义，但页面可用。
- **建议**：保留；补「按类型过滤后向 graph 请求传参」与节点数上限提示（见 §6）。

### 3.2 域内血缘页/Tab（指标/模型/数据集/MDM/资产 1 跳）
- **必要性：必要**。域内视角=带业务上下文的图（指标页有依赖表对照、模型页有登记动作、MDM 有同步按钮）。
- **理由**：五处嵌图共享 `features/lineage`（LineageNode/graph-layout/visual），一份渲染协议，非重复建设。
- **问题**：指标图 API `/metrics/{id}/graph` 前端实际改用通用 lineage 端点+依赖表合成（M-3），`/{id}/graph` 与 `/modeling .../asset-id` 等端点部分无页面调用方——接口冗余苗头，量小。
- **建议**：保留；把 M-3 的「虚拟上游合成」口径下沉到后端登记侧（根治裂节点后删除前端补偿）。

### 3.3 影响分析两页（/metric/impact、/modeling/impact）
- **必要性：较必要**。是真需求（口径变更前排雷），但两者都不走血缘图，分别比对 `yak_metric_dependency` 快照与 43 分层映射。
- **理由**：血缘模块自身**没有影响分析 API**；图侧只有 1 跳下游边数（资产运行/健康用）。三套「影响」词汇各说各话。
- **建议**：短期保留；中期以图 downstream 遍历统一「下游影响清单」，两页消费同一底座，映射/快照只作补充属性。

### 3.4 DEV SQL 发布解析登记（outbox+worker）
- **必要性：必要**。全链路唯一的表级+列级自动血缘生产者，工程最扎实：解析在事务外（prepare）、写在独立事务（worker 恢复项目空间）、revision 护栏防旧图新、evidence 替换回收孤儿资产、解析失败如实落 parseStatus=FAILED/PARTIAL/UNRESOLVED 属性。
- **建议**：保留，作为其余登记方的对齐模板。

### 3.5 SQL 血缘预览
- **必要性：较必要**。编辑期可见「这条 SQL 将产生什么血缘」，降低登记后知后觉；不落库、纯解析复用同一引擎，无第二真相。
- **建议**：保留。

### 3.6 模型引导登记
- **必要性：必要**（MTR 的 CONSUMES 边依赖模型 TABLE 节点先存在）。但登记为「用户确认后/graph 触发」而非发布即登记（《模型工作台》P3 已记）；键 `modeling:model:{id}` 与物理表键**不是同一节点**（见 §6 P1-2）。
- **建议**：保留并升级为发布钩子；补模型↔物理表缝边。

### 3.7 指标/数据集/分析/仪表盘 afterCommit 投影登记
- **必要性：必要**。治理在场的兑现：删除时 evidence 清理（指标 removeMetric、分析 clear、仪表盘 clear），更新时整域替换，fail-open 不拖垮业务 CRUD。
- **问题**：dataset 侧表/列资产键**未走 `PhysicalTableAssetKey`**（见 §6 P0-2）；仪表盘只按「生效快照」登记，草稿态图中不可见（设计使然，已在《仪表盘》记）。
- **建议**：保留；修键口径。

### 3.8 MDM 三段登记
- **必要性：较必要**。横切模块主动进图的孤例，且是唯一全程使用 `PhysicalTableAssetKey` 的登记方（键口径正确）。手动触发是合理交互（同步动作可重放、幂等）。
- **建议**：保留。

### 3.9 HTTP 通用注册 API
- **必要性：过渡**。设计上是给「未来平台来源/外部登记」留的口子，全仓 grep 无任何调用方（前端、其它模块都不用它）。且**无权限注解**，POST 即写共享目录表。
- **建议**：要么声明消费契约并补鉴权，要么从对外契约降级（当前无法确认有外部消费者）。

### 3.10 维护三件（evidence 替换 / revision 护栏 / GONE 撤销）
- **evidence 替换+孤儿清理：必要**，撤销/更新的唯一机制（无 HTTP DELETE 的补偿设计）。
- **revision 护栏：必要**，防乱序回写。
- **GONE→撤销：必要但当前是断口**——端口 `CatalogGraphRevocation` 在 metadata 侧已定义并被 `MetadataPresenceService` 在确认 GONE 后经 `ObjectProvider` 调用，**全仓无实现类**；lineage 查询侧也不按 `gone_at` 过滤。「图上挂着不存在的表」是被注释点名的坏形态且正是现实。
- **建议**：lineage 侧补撤销实现（复用 evidence 机制按 assetKey 摘节点摘边），或最低限度读侧过滤 `gone_at IS NOT NULL`。

### 3.11 首页总览/资产运行/健康/元数据抽屉消费
- **必要性：必要**（血缘作为「能不能放心用」的输入之一进状态机与健康分）；首页 overview 有界（≤20 边），成本可控。
- **建议**：保留。

## 4. 真实功能定位

## 7. 现状总结

1. **完成度**：图底座（模型/存储/遍历/登记契约/维护机制）+ 8 个登记方 + 5 处消费方全部真实在线，前端工作台与 5 处嵌图齐备；是同类盘点里接线最广的横切模块之一。
2. **架构纪律**：高。公共 API 边界有架构测试守卫（`LineagePublicApiBoundaryTest` 等 5 个）、facade/role 事务边界收敛、调用方一律 Gateway 隔离、边带证据可整体替换——「不存第二真相」在 lineage 侧成立。
3. **最大空洞**：撤销闭环整体缺失（P0-1+无 HTTP DELETE，删除全赖登记方自觉 evidence 清理；GONE 断链是元数据盘点与本盘点双重指认）。
4. **键口径**：`PhysicalTableAssetKey` 下沉共用是好设计，但执行有漏网——dataset 直拼（P0-2）、模型键自成体系导致主链中段断链（P1-1）；MDM/采集侧正确。
5. **与 04/05 一致性**：#8/#9 🔧✅ 属实；但图二「血缘登记」边漏 ANA/DBH/MDM 三对真边，登记方名单已膨胀到 8 家，图需修订；R-8 菜单名/路由不一致属实（菜单归 data-asset 组、路径却在 `/data-analysis/lineage`，两套坐标并存）。
6. **SQL 解析定位**：解析器（JSqlParser）归 dev 模块所有，lineage 只持 source-neutral 接口供 dataset 复用——「血缘模块自己会解析 SQL」是误读；列级解析依赖数据源 catalog 取 schema，方言二段名做了容错（`DevelopmentSqlLineageService.loadSchemaColumns`）。
7. **异步策略分档**：DEV=outbox+轮询（最重，可恢复）、MTR/DST/ANA/DBH=AFTER_COMMIT+fail-open（轻，失败只留日志——「图可能悄悄缺」是共同代价）、MOD/MDM=手动或查询触发（引导式）。
8. **影响分析真相**：用户可见的两个「影响分析」页面都不消费血缘图；血缘模块对外只有通用图查询；「上游变更→下游清单」的平台叙事当前靠各模块私有台账拼。
9. **定性判断**：不是局部拼图——它已经是溯源底座的**承重墙**，但三道接缝（GONE 撤销、dataset 裂键、模型↔物理表缝合）未合拢；合拢前「一条链追到底」在真实 SQL 书写习惯下会中段断，且断得无声无息。
