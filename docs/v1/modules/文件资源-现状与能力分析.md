## 3. 子功能逐个分析

**1 创建目录 / 2 资源树 / 3 目录列表 / 4 详情（命名空间骨架）**
- 业务含义：给文件提供目录树组织与检索空间，按项目隔离（`@ProjectScope(PROJECT_REQUIRED)` + project_id 列）。
- 使用角色：数据开发工程师、平台管理员。输入：名称/父目录/关键字。输出：树/列表/详情 VO。
- 依赖：`yak_ops_resource` 表；存储插件目录操作（LOCAL 才真正 mkdir）。
- 交互模块：前端资源页、开发编辑器选择器、首页总览。
- 必要性：**必要**。没有命名空间就没有"资源货架"。
- 理由：是 17（运行时供给）和 20（开发引用）的定位前提。
- 当前问题：`/tree` 全表加载内存建树，无深度/规模上限；错误文案与权限粒度尚可。
- 建议：**保留**（树接口补懒加载或上限，列入第 6 节）。

**5 分页条件查询**
- 业务含义：服务端分页检索资源，与"树"互补。角色：潜在列表页消费者。
- 输入：`ResourceQueryDTO`（页码/关键字/节点类型）；输出：分页 VO。
- 依赖：`ResourceDao.selectPage`。交互模块：无（前端 service 封装了 `fetchResourcePage` 但没有任何页面调用）。
- 必要性：**过渡**。当前唯一实际消费场景（目录浏览）已由 3 覆盖。
- 理由：接口存在、页面未展示，属"备而未用"；但契约测试覆盖它（`ResourcesControllerContractTest`），删除有成本。
- 当前问题：与树/列表并存易让新人误以为有第二套浏览 UI。
- 建议：**合并**——未来做全局资源搜索/大列表页时启用，或在 DEPENDENCIES.md 标注"仅 API 消费"。

**6 重命名 / 7 移动**
- 业务含义：维护资源路径。输入：新名/目标目录；输出：更新后的节点（子孙 full_path 级联改，物理文件 move）。
- 依赖：`ResourceStorageGateway.move`；同名冲突校验（唯一键 `uk_project_parent_name`）。
- 交互模块：被 20 间接影响——任务 configJson 存的是 resourceId 而非路径，所以改名不破坏任务引用（设计正确）。
- 必要性：**必要**。文件系统基本能力。
- 问题：**改名/移动也递增 version**（`bumpNamespaceRevision`，`ResourceNamespaceManager.java:198`），会让仅改了路径的 Java 任务在版本校验处误判失败——版本号语义混用了"内容版本"与"任何变更"。
- 建议：**保留 + 重构**（version 只在内容替换时递增；命名空间变更用 update_time 表达即可）。

**8 递归删除**
- 业务含义：删目录连同子孙，物理文件事务提交后异步清理。
- 输入：资源 id；输出：布尔。依赖：`findDescendants`（按 full_path 前缀）、`ResourceStorageLifecycle.deleteAfterCommit`。
- 交互模块：**理论上应被任务引用检查拦截，实际无任何引用校验**——删除仍被 Java/Python/Shell 任务引用的文件，只会让后续运行时报错。
- 必要性：**必要**（生命周期闭环）。
- 问题：无软删除/回收站；物理删除在 afterCommit 执行，进程崩溃会留孤儿字节；无审计事件（audit 模块虽有 resource_type 列，但本模块零埋点）。
- 建议：**保留 + 补齐**（删除前引用扫描 + 审计埋点，第 6 节 P1/P2）。

**9 上传 / 11 替换文件**
- 业务含义：文件进入平台的两个物理入口；替换=原地覆盖 + version+1 + checksum 更新。
- 输入：multipart 文件（≤100MB）；输出：资源 VO。依赖：`StorageOperator.upload`、`ResourceChecksum`（SHA-256）。
- 交互模块：产物即 17 的被解析对象（JAR/脚本）。
- 必要性：**必要**（模块立身之本）。
- 问题：替换无历史，11 与"版本管理"的宣传（02 文档"改文件产生新版本"）不符——**新产生的只是"版本号"，不是"可回滚的版本"**；上传无后缀白名单/恶意文件策略。
- 建议：**保留**；对"版本"能力做二选一处置（实现历史存储或修正宣传口径，见第 6/7 节）。

**10 在线创建 / 12 在线编辑 / 13 分页预览**
- 业务含义：不走文件系统即可产出/维护脚本类文本资源，服务"脚本供给"主链路。
- 输入：名称+内容（18 种可编辑后缀内、≤2MB）；输出：内容 VO。依赖：`ResourceContentPolicy`。
- 交互模块：直接被 20 的开发者使用。
- 必要性：**较必要**。上传已可覆盖创建场景，但在线编辑脚本是任务开发的高频轻量动作，值得独立入口。
- 问题：无并发编辑冲突检测（后写覆盖，乐观锁字段 version 未参与编辑校验）。
- 建议：**保留**（编辑时携带 baseVersion 做围栏校验）。

**14 下载**
- 业务含义：把平台文件带回本地。角色：开发者/管理员。依赖：`resource:download` 权限码。
- 必要性：**必要**（治理诉求下，下载是审计最该盯的出口）。
- 问题：下载零审计。建议：**保留 + 补齐**审计。

**15 存储插件体系（LOCAL/MINIO/HDFS + 查询接口）**
- 业务含义：物理字节与元数据分离，可切换对象存储/分布式文件系统；`/storage-plugins` 让页面显示可用后端。
- 输入：`yak.resource.storage.type` 配置；输出：插件列表 VO。
- 依赖：`StorageOperator` SPI（`data-ops-plugin-storage-api`）、boot 打包 `data-ops-plugin-storage-all`。
- 交互模块：仅本模块 storage 包可见 `StorageOperator`（`ResourceStorageRegistry` 封装，架构测试守边）。
- 必要性：**必要**。这是"通往外部的门"的门轴，也让 HDFS/MinIO 部署可行。
- 问题：存储类型由**父目录继承**决定（`ResourceParentResolver.Parent.storageType()`），跨存储移动被禁——大版本切换存储（LOCAL→MINIO）时无迁移工具，文档也未见规划。
- 建议：**保留**（补存储迁移预案，第 6 节 P3）。

**16 围栏版本机制**
- 业务含义：任务定义可选绑定 `resourceVersion`，运行时版本与当前不符即失败，防止"发布后文件被悄悄换掉"。
- 输入：resolve(id, version)；输出：内容或异常。依赖：`yak_ops_resource.version/checksum`。
- 交互模块：17 的校验分支；Python/Shell 默认不锁版本（PythonEditor 显式 `resourceVersion: undefined`），仅 Java 在选择时记录当前版本。
- 必要性：**必要**（这是当前唯一能兑现的"版本"语义，且方向正确）。
- 问题：三处语义漂移——①"版本"名不副实（不可取历史内容）；②改名/移动递增版本造成误伤（见 6/7）；③前端无"选择历史版本"交互（也没有可选项）。
- 建议：**重构**为真版本（内容快照表）或如实降级宣传为"内容变更防护号"。

**17 运行时解析（脚本/JAR 供给任务内核，图二声明边）**
- 业务含义：任务执行前把资源物化为本地临时文件并校验 checksum，供 Java 起 `java -jar`、Shell/Python 读取脚本文本。
- 链路（全证据）：`AbstractTaskExecutorAdapter.java:77-78`（job 注入 capability）→ `Shell/Python/JavaTaskExecutorAdapter.java` → 插件 `ScriptTaskSupport.resolveScriptContent`（api 模块:135-152）、`JavaTaskExecutor.resolveAllResources`（多 JAR 到共享临时目录）→ `ResourceResolverAdapter` → `ResourceDownloadProviderAdapter` → 存储流。
- 必要性：**必要**。这是本模块在主轴上的存在理由，链路经 `data-ops-spi` 解耦、job 模块 pom 不依赖 business-resource，边界干净。
- 问题：任务发布（task-catalog 不可变 Revision）时不冻结资源版本——configJson 里锁不锁版本取决于编辑器当时行为（Java 锁、Python/Shell 不锁），同为"发布"语义却不一致；不锁的任务每天跑的是"当前"文件，工作流可重复性破口。
- 建议：**保留 + 补齐**（发布时统一固化 resourceVersion，配合 16 的真版本能力才有完整意义）。

**18 变更传播 / git 同步死端**
- 业务含义：预留"资源变更同步到外部系统（疑似 git 仓库）"的扩展点。
- 现状：`ResourceChangeDispatcher` 遍历 `List<ResourceFileSyncProvider>`，全仓无实现类，providers 恒空（代码里 `providers.isEmpty()` 短路）；`git_sync_status` 列/PO/VO 全链携带但唯一写入值是 'NONE'。
- 必要性：**过渡/冗余（当前）**。无任何消费方。
- 问题：死扩展点 + 恒空字段进表结构、进 VO、进前端类型，制造"有 git 同步"的错觉，是典型 AI 生成-未收口痕迹。
- 建议：**下线或降级**：保留 `ResourceChangeDispatcher`（发布钩子成本极低），但删除 `git_sync_status` 列的对外暴露（VO/前端类型），并在 ARCHITECTURE.md 明确"同步提供者未实现"。

**19 首页文件资源总览**
- 业务含义：首页"资源中心"卡片展示文件数/目录数/总字节/近 7 天动态。
- 输入：无；输出：OverviewResponse。依赖：`ResourceTreeReader`（又一次全表）。
- 交互模块：business-home 直接依赖 business-resource（pom + import 领域类），**不走 SPI**。
- 必要性：**较必要**（首页只读总览是产品设定），但实现方式不合规。
- 问题：跨模块直连 Java 类破坏"模块间只经 SPI"的治理方向；且图二无 RES→HOME 边（图漂移）。
- 建议：**保留能力、重构接线**（改走 SPI 或在图二补边）。

**20 开发编辑器资源选择器**
- 业务含义：让 Python/Shell/Java 节点以"引用"方式使用文件资源而非粘贴副本。
- 现状：完整可用（`ResourcePicker.tsx`，按后缀过滤、目录导航、显示所选文件）。
- 必要性：**必要**（无它则 17 无人触发）。

## 4. 模块真实功能定位

- **实际角色**：文件仓库 + 任务运行时的脚本/JAR 供给方。与图二声明一致，没有职责膨胀，也没有偏离主轴的"顺手做"的功能（区别于平台上多数乱象模块）。
- **是否关键节点**：是——对 Java 任务（只能经资源引用运行，`JavaTaskExecutorAdapter.java:43-54` 明确 resource-only 无内联内容）是**硬依赖**；对 Shell/Python 是软依赖（可内联脚本，引用是可选增强）。SQL 任务完全不经过它。
- **被谁强依赖**：后端仅 `data-ops-business-job` 经 `ResourceResolver` SPI（能力可缺席，`ObjectProvider` 判空注入）；前端 data-development 编辑器、home 总览直接消费。离线同步、质量、数据集、指标等模块均不依赖它（已全仓 grep `io.yak.ops.business.resource` 与 `ResourceResolver` 确认）。
- **类型归类**：基础设施型支撑模块（存储 + 命名空间 + 解析），非业务流程节点。
- **真实边界**：命名空间/内容/存储路由/运行时解析/变更传播五个包，架构测试（`ResourceDependencyBoundaryTest`、`ResourceLayeringConventionTest`、`ResourceRoleConventionTest`、`ResourceFlywayContractTest`）+ 模块 README 五件套（REQUIREMENTS/DOMAIN/ARCHITECTURE/DEPENDENCIES/REVIEW.md）守着——是平台上治理最规整的模块之一。⚠️ 但 `ARCHITECTURE.md` 包图写的是 `controller/v1/mapper/ResourceRequestMapper`，实际代码是 `controller/v1/converter/ResourceRequestConverter`——文档与代码已漂移，"最规整"也没躲过。
- **职责过载或不清**：无过载。唯一不清处是"版本"这个词在本模块内的真实语义（围栏号）与产品宣传（02 文档"版本管理"）、与任务目录的"不可变版本"三者不同义，是潜在吵架点。
- **明天下线的影响**：Java 任务全灭、Shell/Python 引用模式任务全灭、首页资源卡片降级为"不可用"（`HomeResourceCenterReader` 已有 ObjectProvider 判空优雅降级）、资源页 404。影响面集中且真实——**该模块有存在价值，不是乱象**。

## 5. 与其他模块交互

| 维度 | 事实 |
|---|---|
| 上游依赖（谁调用文件资源） | ①任务内核（job）经 SPI `ResourceResolver`（`AbstractTaskExecutorAdapter` 按任务是否含 resourceId 条件注入）；②任务插件 shell/python/java 经 capability 机制取用；③首页（home）直接 Java 类依赖读树；④数据开发前端直接调 `/list`、`/tree` API（仅 UI 层） |
| 下游输出（文件资源调用谁） | 存储插件（`data-ops-plugin-storage-{local,minio,hdfs}`）经 `StorageOperator` SPI 落字节；数据源模块仅借用其 `BusinessDatabaseConfiguration`（配置类复用，非运行时耦合）；boot 的 `ResourceProjectCompatibilityBackfill` 启动回填 project_id |
| 数据流 | 上传/编辑 → 元数据行 + 物理字节（同一 storagePath 覆盖写）；执行 → 读流 → 临时文件 + SHA-256 核对 → 进程消费。**单向、拉取式，任务执行不回写资源** |
| 控制流 | 权限闸门 `@RequiresPermission(resource:view/create/update/download/delete)`（码表在 security 目录 SQL `V1000/V2006`，菜单在 `V2036` 导航重组）；项目隔离 `@ProjectScope(PROJECT_REQUIRED)` |
| 事件 | 仅事务提交后的 `ResourceChangeDispatcher`（进程内、同步、异常吞掉只 warn），**无外部实现、无 MQ、无 Spring 事件** |
| 同步调用 | job→resource 的 resolve/download 为进程内同步调用（同 JVM）；无跨服务 RPC |
| 异步任务 | 无定时任务；删除的物理清理由 afterCommit 回调（非异步线程） |
| 共享存储 | 与全平台共库 `yakBusinessDataSource`（默认 yak_security 库），本模块独占 `yak_ops_resource` + `yak_resource_schema_history`；LOCAL 存储默认 `./data/resources`（容器内路径，见 compose） |
| 风险点 | ①版本围栏依赖"资源当前行"，而资源行可被改名/移动/编辑不断 bump——发布即执行快照的"不可变"语义在这条边上不完整；②home 直连领域类是图二外的私搭线，SPI 治理的例外；③任务→资源引用藏在 configJson 字符串里，删除资源无护栏；④`ResourceRepositoryAdapter.findById` 存在"projectId 为空则无过滤查询"的运行时走廊（代码自注 temporary，`:41-45`），是租户隔离的已知豁口 |

| 缺失能力 | 为什么需要 | 影响的业务场景 | 优先级 | 建议实现方式 | 依赖模块 |
|---|---|---|---|---|---|

## 7. 模块现状总结

- **核心能力已闭环**：目录树命名空间、上传/在线创建/编辑/预览/下载/移动/重命名/递归删除、LOCAL/MINIO/HDFS 可插拔存储、SHA-256 完整性校验、项目隔离与五档权限码——页面与后端逐一对应，无"前端有页面没后端"项。
- **图二唯一声明出边（脚本/JAR→任务内核）真实接线**：前端资源选择器 → configJson resourceId → job capability 注入 → SPI 解析物化 → 三类任务插件消费，端到端证据链完整（第 5 节）。这是全平台少见的"声明=实现"的边。
- **未闭环能力**：①"版本"只有围栏号没有历史内容（宣传与现实的头号偏差，P0）；②发布不统一固化资源版本；③删除无引用护栏；④操作无审计。
- **接口存在、页面未展示**：`POST /api/v1/resources/page`（service 层已封装 `fetchResourcePage`，零页面调用）。
- **死代码/冗余**：`ResourceFileSyncProvider` 零实现 + `git_sync_status` 恒 'NONE'；`pages/resources/resource-management/service.ts` 仅为 @deprecated 转发壳。
- **真实定位**：基础设施型供给模块，被 Java 任务强依赖、Shell/Python 软依赖；治理水准（架构测试五件套 + 模块文档）全平台领先，但 ARCHITECTURE.md 包图已与代码漂移（mapper vs converter）。
- **最大风险**：版本语义三分歧（资源围栏号 / 任务目录不可变 Revision / 02 文档"版本管理"）叠加"内容不可回溯"，会让工作流的可重复性在文件这条腿上始终是软的。
- **最该补的 3 项**：①历史版本存储与按版本取内容（P0）；②发布时统一固化 resourceVersion（P1）；③删除/替换前引用检查（P1）。
- **下一步**：先拍板"版本"一词在本模块的定义（围栏号 or 快照），据拍板实施第 6 节 P0/P1；顺手修 ARCHITECTURE.md 漂移与 git_sync_status 噪音；在图二评审时决定是否补 RES→首页 投影边、把 home 直连改为 SPI。

## 8. 掌握度自检

本模块我可以较有信心地判定"已实现且接线真实"，因为核心链路每一跳都有文件级证据，且模块体量小、边界由架构测试固化。不能完全掌握的有三点：①任务运行时（job 执行进程/workflow 调度器）在**运行时**是否真的把 resourceVersion 传入 `resolve(id,version)` 的全部实际组合，我只核实到代码路径与编辑器行为（Java 写版本、Python 显式不写），未跑端到端实例验证线上任务的 configJson 分布；②MinIO/HDFS 插件的连通性配置与生产使用情况（test-jar 目录与 compose 存在，但无法从代码判断现网启用了哪种存储）；③`yak_ops_resource` 的存量数据规模（决定 `/tree` 全表加载是理论风险还是现实风险）。如需补，用 03 号文档的端到端验收路线跑一次"上传 JAR→建 Java 任务→发布→改文件→再跑"即可闭环第①点。
