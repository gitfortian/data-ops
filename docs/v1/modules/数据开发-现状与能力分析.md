## 1. 模块概览

数据开发是主脉③段末端的「加工任务生产线」：提供以资源树 + 多标签 Monaco 编辑器为核心的 IDE 工作台（路由 `/data-development`），对 SQL / Shell / Python / Java / HTTP 五类可执行节点做「草稿 → 试运行 → 发布不可变 Revision → 投影任务目录」的完整生命周期（`DevelopmentTaskService` → `DevelopmentTaskPublisher` → `TaskCatalogService.publish`），并额外承载两类输出节点（Dataset 节点→数据集、Data Service 节点→数据服务运行时）。表结构共 9 张 `yak_dev_*` 业务表 + 1 张借住的 `yak_system_env_var`（Flyway 基线 `V1__baseline_data_development.sql`，开发期迁移已压缩为单一基线，发布后不可变）。

链路质量总体较高：草稿乐观锁冲突检测（`DevelopmentDraftConflictException`）、发布校验委托 Task Plugin（`DevelopmentTaskValidator`）、checksum 去重的不可变版本（`yak_dev_task_revision`）、SQL 发布经 outbox 异步登记血缘（`yak_dev_lineage_outbox` + `DevelopmentLineageWorker`）、编辑器运行走共享任务内核且持久化执行历史（`yak_dev_task_execution` + `DevelopmentTaskExecutionReconciler`，见模块内 `EXECUTION_CONTROL_PLANE.md`）。

但对照架构图有两条上游承诺边（SEM→DEV、MOD→DEV）在代码中零落地，一条下游治理边（DEV-."操作记录".->AUD）未接入，一条回边（WFL--每天定时跑-->DEV）实际不存在对 DEV 的运行时回调；且模块内混入了与任务生命周期并行的第二套草稿/版本机制（Data Service 节点）和一个前后端三不管的 HTTP 类型，职责过载迹象明确。

## 3. 子功能逐个分析

### 3.1 目录树与节点管理
- 名称：开发资源组织（目录 + 节点）
- 业务含义：为③段加工任务提供项目内的文件树式收纳，节点即"任务/输出资源"的身份证。
- 使用角色：数据开发工程师（编辑权）、项目管理员（删除权）。
- 输入：名称、类型、所在目录；输出：`yak_dev_node` 记录（含 `configured`、`updated_by`）。
- 依赖：`TaskCatalogService`（重命名同步投影元数据 `updateSourceMetadata`、删除联动 `offlineSource`）。
- 交互模块：任务目录（CAT）。
- 必要性：必要。
- 理由：是 IDE 工作台与后续发布链的寻址基础；删除即下线目录投影，联动语义正确。
- 问题：节点类型在 Controller 层用字符串传递后 `DevelopmentNodeType.require` 校验，创建接口可建出前端无法编辑的 HTTP 节点（见 3.10）；`configured` 标志只在发布时置真，树上是唯一状态信号，缺"草稿已改未发布"的脏标记透出（前端靠本地 dirty 状态）。
- 建议：创建接口按"编辑器已就绪"的类型白名单收口；树上透出 已发布/有未发布改动 两态。

### 3.2 SQL 编辑器与草稿保存
- 名称：SQL 编写工作台（Monaco）
- 业务含义：数据加工逻辑的唯一创作面，替代直连数据库改脚本。
- 使用角色：数据开发工程师。
- 输入：SQL 文本 + configJson（含方言/数据源选择）+ baseRevision；输出：`yak_dev_task_draft` 行（乐观锁 revision 递增）。
- 依赖：前端 `editors/sql/`（completion/hover/signature/format/diagnostics/metadata/lineage 子目录）；元数据补全经数据源目录 API；保存经 `DevelopmentTaskDefinitionNormalizer` 归一化。
- 交互模块：数据源（DS，真依赖）；语义（SEM）自 2026-09-22 语义缺口单 02 起接命名标准检查（optional 依赖，非阻断提示）；模型（MOD）未接。
- 必要性：必要。
- 理由：主脉③的核心生产力入口，完成度高（多方言 profile、片段补全、血缘预览、草稿冲突弹窗）。
- 问题：语法检查只有前端结构扫描（括号/引号配对，Warning 级），后端无独立"语法校验"接口——发布时 plugin.validate 是唯一的强校验点，试运行前错误只能靠运行时抛出；`getDraft` 对 SQL 有读取时归一化副作用路径（读接口内含 normalize）。
- 建议：若要做"编辑器内真校验"，应暴露发布校验（plugin.validate）为独立预检接口，而非新增第二套校验逻辑。

### 3.3 试运行（编辑器运行）
- 名称：手动运行（提交-轮询-取消-重试）
- 业务含义：发布前在开发态验证 SQL/脚本正确性，是"草稿→版本"之间的质量闸。
- 使用角色：数据开发工程师。
- 输入：编辑器当前定义（未保存亦可运行，快照 `development:{nodeId}`）；输出：`yak_dev_task_execution` 持久历史 + 运行结果（output_json，上限 2MB 截断）。
- 依赖：job 模块 `TaskExecutionGateway`（插件式 runtime：sql/shell/python/java 四个 plugin 存在，`yak-ops-plugins/yak-ops-plugin-task/`）；无对应 plugin 时 `requireRuntime` 明确报"未安装 Task Runtime"。
- 交互模块：任务内核（JOB）、数据源（DS，经 SQL runtime）。
- 必要性：必要。
- 理由：控制面设计成熟——HTTP 提交不等待终态、durable id 为客户端身份、对账器收敛丢失状态、重试保留 retry_of_execution_id 链路（`EXECUTION_CONTROL_PLANE.md`）。
- 问题：运行历史页未见取消/重试按钮（能力只在工作台暴露）；运行中的编辑器复用需 `GET /executions/active` 重挂，页面切换丢标签页状态时依赖该机制，未在文档中向用户说明。
- 建议：运行记录页补取消/重试入口即可闭环，不必新增能力。

### 3.4 发布不可变 Revision 并投影任务目录
- 名称：任务发布（S4 契约实现）
- 业务含义：③→④的转换器主接口——把可变草稿凝固为带 checksum、可被工作流/质量/数据集锁版本引用的交付物。
- 使用角色：数据开发工程师（publish 权限）。
- 输入：nodeId + draftRevision；输出：`yak_dev_task_revision`（revisionNo 递增、`source_draft_revision` 溯源、checksum 判重复用）+ task_catalog 的 TaskAsset 投影 + （SQL）血缘 outbox 任务。
- 依赖：`DevelopmentTaskValidator`（未装 plugin 拒发）、`TaskCatalogService.publish`、`DevelopmentLineageOutbox.enqueue`。
- 交互模块：任务目录（CAT）、血缘（LIN，异步）。
- 必要性：必要。
- 理由：这是全模块存在的架构理由；`DataDevelopmentTaskRevisionProvider` 反向为 CAT 消费方解析版本正文，形成"目录持指针、DEV 持正文"的干净协议；目录侧 `requirePublishableTaskType` 挡输出节点，边界清晰。
- 问题：发布是同步事务、血缘是异步最终一致，发布成功页面不提示血缘稍后可见；同 checksum 复用时 revisionNo 不递增，用户可能困惑"点了发布版本号没变"（行为正确但表达缺失）。
- 建议：发布成功 toast 补"血缘登记排队中"提示；复用版本时明示"内容未变化，沿用 vX"。

### 3.5 发布中心（releases 页）
- 名称：发布中心（任务上下线与版本切换）
- 业务含义：以任务目录投影为账本的"已交付货架"操作台：看 ONLINE/OFFLINE/DISABLED、切任意历史不可变版本、重上线。
- 使用角色：数据开发负责人 / 项目管理员（release 权限）。
- 输入：状态/类型/关键字过滤；输出：上下线、activate 后的最新目录状态。
- 依赖：`TaskCatalogService`（list/get/offlineSource/publish）；禁用态任务拒绝直接上线（fail-closed）。
- 交互模块：任务目录（CAT）。
- 必要性：较必要。
- 理由：与任务目录的"目录治理"职责有重叠之嫌，但当前实现是纯门面（无第二份存储），且提供了 DEV 视角的批量盘点，价值成立。
- 问题：`DevelopmentReleaseService.page` 先全量拉三种状态再内存过滤分页（仅适合当前量级）；DATASET/DATA_SERVICE 输出节点的发布不在此页展示，"发布中心"实际只覆盖任务类资产，命名略大于实际。
- 建议：量级增长后下沉为目录侧统一查询；或明确页面范围文案。

### 3.6 血缘预览与登记
- 名称：SQL 血缘（预览 + 发布后登记）
- 业务含义：让 DEV 成为血缘证据的生产者之一（图中 DEV-."血缘登记".->LIN）。
- 使用角色：数据开发工程师（预览）；系统自动（登记）。
- 输入：SQL 文本 / 已发布 Revision；输出：编辑器内表/列级预览图；`LineageRegistrationService` 登记记录（TASK 资产与列血缘，含 DerivedAware 处理派生列）。
- 依赖：数据源目录（解析表身份，`TableIdentityResolver` + `DataSourceCatalogReader`）、血缘模块。
- 交互模块：血缘（LIN）、数据源（DS）。
- 必要性：必要。
- 理由：outbox + 轮询 + 项目上下文恢复（`DevelopmentLineageWorker`）+ 仅最新版本写入（`writeIfLatest`）的写法健壮，且与资产投影 asset_key 同源（D6）。
- 问题：仅 SQL 类型有血缘；解析器存在同域多套（module 内三个 parser + 复用 lineage 模块 `SqlProjectionLineageAnalyzer`），长期有语义漂移风险。
- 建议：收敛为血缘模块提供的单一分析器，DEV 侧只做证据提交。

### 3.7 Dataset 节点
- 名称：Dataset 产出节点（③→⑤直通边）
- 业务含义：在开发态把一段 SQL 冻结为数据集资产（数据源+SQL+字段契约），供分析/服务/问数消费。
- 使用角色：数据开发工程师、下游消费者间接受益。
- 输入：编辑器中的定义与 preview 推断字段；输出：dataset 模块的 NodeDataset 资产 + 发布版本。
- 依赖：dataset 模块 `DevelopmentDatasetFacade`；发布前置=源任务已上线（校验 `taskCatalogService.list("DATA_DEVELOPMENT","ONLINE")`）。
- 交互模块：数据集（DST）、任务目录（CAT，只读校验）。
- 必要性：较必要。
- 理由：架构图明确画了 DEV--Dataset节点产出-->DST，实现与图一致。
- 问题：它是第三套"编辑-预览-发布"微机制（复用 task draft？还是 facade 内冻结契约？两条路径并存的心智负担）；与数据集模块自有管理页的职责切分需要产品确认（当前看 DEV 侧是生产、数据集侧是消费，成立但文档未写）。
- 建议：保留，但把"节点→资产"契约文档化，避免数据集模块旁路直改。

### 3.8 Data Service 节点
- 名称：数据服务开发节点
- 业务含义：在开发工作台直接编写查询 SQL 并把 API 发布到数据服务运行时（上线/下线/状态）。
- 使用角色：数据开发工程师 / API 提供方。
- 输入：definition_json（SQL+参数+响应契约草稿）；输出：`yak_dev_data_service_revision` 不可变版本 + data-service 运行时发布状态（SOURCE_TYPE=`DATA_DEVELOPMENT_DATA_SERVICE`）。
- 依赖：data-service 模块 `DataServicePublisher`/`DataServiceManager`/`DataServiceViewFactory`；`DevelopmentDataServiceNodeSourceProvider` 以 SPI 反向注册进 data-service 的发布源。
- 交互模块：数据服务（SVC）。
- 必要性：较必要（存在理由成立，但位置错误风险高）。
- 理由：图二并无 DEV→SVC 边（只有 DST→SVC），这是代码超出架构图的第四类产出物；且模块内同时存在 draft/revision 双版本表和两个包的 `DevelopmentDataServiceSqlCompiler`（service 包一份标 deprecated 的装配壳），是最新长出来的一块，机制与任务链并行。
- 问题：职责过载的主要来源；数据服务模块自身页面若也可创建 API，则出现双入口（数据服务模块侧现状本文不展开，标注：**当前无法确认其与本页面是否构成重复入口，需数据服务模块盘点时核对**）。
- 建议：短期冻结新能力进入该子域；中期评估迁回数据服务模块、DEV 只保留"从任务派生 API"的薄入口。

### 3.9 编辑器设置
- 名称：用户级编辑器设置
- 业务含义：主题/字体等偏好持久化，跨设备一致。
- 输入/输出：`yak_dev_editor_setting`（user_key→JSON）。
- 必要性：过渡（锦上添花，成本极低，无害）。
- 问题：设置面板同时挂在系统设置页（`pages/settings`），入口双份。
- 建议：保留，收敛为一个入口。

### 3.10 HTTP 节点
- 名称：HTTP 节点类型（占位）
- 业务含义：设计中"调用外部 HTTP"的加工节点。
- 现状：后端枚举有（且被 `supportsTaskLifecycle=true` 放行、任务目录与编排白名单都接受），但 `yak-ops-plugins/yak-ops-plugin-task/` 下无 http 插件（试运行/发布校验都会报"未安装 Task Runtime/Plugin"），前端 registry 无编辑器（`UnsupportedEditor`）、创建菜单无入口。
- 必要性：冗余（当前形态）。
- 理由：一条三头不一致的空类型：目录/编排侧为它开口，运行与编辑侧都没有它；留着会诱导 API 用户经 `/nodes` 直接建出不可用的 HTTP 节点。
- 建议：删除枚举项与白名单痕迹，或补插件+编辑器后一起启用——二选一，不要维持现状。

### 3.11 资产投影（TaskAssetProvider）
- 名称：TASK 资产供给器
- 业务含义：把 SQL 节点投影进数据资产目录（asset ticket 97），asset_key 与血缘登记键同源。
- 使用角色：治理角色（在资产侧看到）。
- 必要性：较必要。理由：图二未画 DEV-.->AST 独立边（资产模块声明为"全模块 Provider 投影"），实现方式符合治理框架。
- 问题：仅 SQL 类型入资产，Shell/Python/Java 节点不在资产账上，口径需在资产盘点中确认是否有意为之（当前无法确认）。

## 4. 真实功能定位

**结论：数据开发首先是、也应当是"主脉③→④的转换器"，而不只是又一个任务编辑器；但当前它正在向"加工任务+数据资产+服务 API"三合一生产工作台漂移，存在职责过载。**

1. 转换器身份成立且质量高：draft→immutable Revision→Task Catalog 投影这条链有显式的作者边界声明（`DevelopmentNodeType.supportsTaskLifecycle()` 注释明言"Do not derive this from PROCESSING/OUTPUT"）、有 checksum 幂等、有反查 SPI、有目录侧 fail-closed 闸（输出节点不得入目录）。05 清单 S4 标 ✅ 与代码一致。
2. "又一个任务编辑器"的嫌疑主要在输出节点侧：Dataset 节点（产出⑤资产）与 Data Service 节点（产出 API 并直连其运行时）各自内嵌了编辑、预览、草稿、版本、发布的全套小机制，其中 Data Service 的 draft/revision 表是独立于任务链的第二套版本系统。这些能力单独看都有理由（图上 Dataset→DST 边已画），叠加看则让 DEV 从"SQL 等加工任务"扩展为"所有可编排产物的 IDE"，与主脉图对 ③ 段的职责声明不符。
3. 与 workflow 前端的职责切分清晰、无侵蚀：DEV 前端 = 单节点的生产闭环（树/编辑器/运行/发布/发布中心/运行记录，`menuGroup: 'development'` 三条路由）；workflow 前端 = 锁版本任务的 DAG 编排、调度与实例（`menuGroup: 'workflow'`：definitions/schedules/instances）。`registry.tsx` 中注释明确"Scheduling belongs to Workflow"，DEV 编辑器刻意未挂调度面板；工作流绑定 DEV 任务只经 `taskAssetId + revision`（`WorkflowTaskBindingResolver`），不回读 DEV 草稿。切分成立，应写为契约固化。
4. "每天定时跑"回边的真相（详见第 5 节）：是逻辑回边而非运行时回调——DEV 不提供执行 SPI 给 job/workflow；调度运行时执行的是 CAT 锁定的 Revision 快照，经 job 内核直接跑。这意味着 DEV 模块下线草稿区不影响已发布任务的定时运行，边界比图上画的更干净，应在文档层面把该回边注释为"执行的是发布到目录的版本，DEV 本身不在运行链路上"。

## 7. 现状总结

1. **实现完成度：高（任务主链）/ 中（输出节点）**。草稿-运行-发布-版本-回切-血缘的③→④主链每一环都有实现、有测试（模块测试目录含 20+ 测试类与 4 个架构约束测试）、有前端页面。
2. **与架构图一致性：主干边全部兑现（DS、CAT、DST、LIN），承诺边 SEM 已按语义缺口单 02 部分接线（命名符合度提示，2026-09-22），MOD、AUD 仍缺失，回边语义与图不符（无 WFL→DEV 回调），另有一张图外超纲边（DEV→SVC）**。
3. **前后端对称性：好**。`services/data-development/api.ts` 与 10 个 Controller 的端点一一对应，未发现"前端有按钮无后端"；反向缺口为 HTTP 类型（有后端无页面）与运行记录页操作列（能力在工作台未同步到列表页）。
4. **数据模型：小而稳**。9 张业务表职责单一、乐观锁/checksum/outbox 三处关键并发设计齐备；唯一杂质是 `yak_system_env_var` 借住。
5. **代码健康度：中上**。分层（controller/task/draft/revision/publisher/outbox/worker）清晰且有显式边界注释与架构测试；瑕疵在包迁移未完成留下的一批 deprecated 壳与双份命名（两个 `DevelopmentDataServiceSqlCompiler`、两个 `DevelopmentTaskValidationException`）。
6. **职责过载信号：明确存在**。模块承载了任务生产、血缘取证、资产投影、数据集冻结、API 开发+发布共五种职责；其中 Data Service 子域自建第二套草稿/版本机制，是最可能演化为乱象源（与数据服务模块双入口）的一块，建议进入 05 清单观察项。
7. **治理接入：偏科**。血缘（异步 outbox）接入良好；审计完全未接；任务目录联动（改名/删除/禁用）处理到位。
8. **对相邻模块的真实依赖（代码事实）**：datasource、job、task-catalog、lineage、asset、dataset、data-service 七个业务/插件模块（pom），semantic 为 optional 依赖（仅命名检查提示，2026-09-22 起），无 modeling/metadata 依赖。
9. **综合判断：保留并巩固"③→④转换器"定位；对输出节点做迁出评估；P0 三项中语义挂接已落地短期提示（语义缺口单 02），模型挂接、审计仍待做**。该模块不是重灾区，反而是全仓少见的"图与码基本对得上"的样板，问题集中在欠账边而非乱码。
