## 1. 模块概览

| 项 | 内容 |
|---|---|
| 模块名称 | 数据源（Datasource） |
| 在主脉与交互图中的位置 | ①接入段，「通往外部的门」：连接·目录·SQL执行（04 图一 S1 / 图二 DS 节点） |
| 上游模块 | 无（模块边界即平台边界，面向外部数据库/搜索引擎/文档库）；横切引用方：元数据采集（目录读取）、审计（操作记录） |
| 下游模块 | 离线同步、实时同步、数据开发（含 SQL 任务执行）、数据质量（04 图二 `DS -->①连接--> SYN & RTS & DEV & QUA`）；此外还被数据集、数据服务、生命周期、主数据、建模、语义、首页直接读取（详见第 5 节，超出图二箭头范围，属登记册第 1 条「全模块 → 数据源」的合法引用） |
| 一句话定位 | 平台对外部数据系统的唯一连接真相：管连接串、管目录读取、管 SQL 执行入口，别的模块只准引用 ID，不准私存连接（05 清单 S1） |
| 当前实现状态 | **已实现**（连接管理 / 目录读取 / SQL 执行运行时三条主链均有后端闭环）；子功能层面有毛刺：驱动上传前端展示后端缺失、SQL 执行审计接口存在页面未展示、插件 install 为空语义过渡接口 |
| 主要入口 | 前端路由 `/data-source`（菜单：数据接入→资源管理组下「数据源管理」，`data-ops-ui/src/config/navigation.ts:68`）；API 前缀 `/api/v1/data-source`、`/api/v1/data-source/catalog`、`/api/v1/data-source/plugin/config`、`/api/v1/sql-executions`；配置开关 `yak.datasource.enabled`（默认 true，`config/ConditionalOnDataSourceEnabled.java`）；模块内**无任何定时任务** |

特别说明（结构性事实）：本模块还**持有平台元数据库本体**——`BusinessDatabaseConfiguration` 定义了 `opsDataSource`（平台自身 MySQL/MariaDB）与事务管理器，全仓 47 个业务文件 import `ConditionalOnDataSourceEnabled`、多个模块的持久化配置 import `BusinessDatabaseConfiguration`。数据源模块因此兼任了「平台基础设施」角色，这超出图二 DS 节点的表达，是第 4 节「职责是否过载」的直接证据。

## 3. 子功能逐个分析

### 分组 A：连接管理（功能 1–10）

**A1 数据源 CRUD + 分页查询 + 总览统计（功能 1–6、9）**
- 业务含义：登记外部库连接信息（类型/JDBC URL/参数/环境/备注），作为全平台唯一连接登记簿。
- 使用角色：平台管理员（建源）、数据开发（下拉选源）、其余模块只读。
- 输入：`DataSourceDTO`（name/dbType/connectionJson/environment/remark）；输出：脱敏后的 `DataSourceVO`/统计。
- 依赖：`DataSourcePluginRegistry`（参数校验规范化）、`BusinessAuditService`、`DataSourceRepository`。
- 交互模块：所有下游选源场景（同步/开发/质量/建模/语义/主数据/数据服务/数据集）+ 首页总览。
- 存在必要性：**必要**。这是「门」的本体，无替代。
- 理由：04 图二除文件资源外①段仅此一个入口节点；05 登记册第 1 条以它为 S1 规矩的守门方。
- 当前问题：①删除无引用校验（`DataSourceManager.delete` 直接物理删，同步任务/模型绑定的 data_source_id 会变悬空引用）；②project 隔离靠 `@ProjectScope(PROJECT_REQUIRED)`，但 `/all`、`/option` 返回 `findAll(null)`，跨项目可见性语义含糊。
- 建议：**保留**，删除链路**补齐**引用守卫。

**A2 连接测试（功能 7–8）**
- 业务含义：验证参数可达性，回写 `conn_status`。
- 角色：平台管理员、数据开发。输入：已存 ID 或临时参数；输出：boolean + 状态回写。
- 依赖：插件 `testConnection`、超时配置 `yak.datasource.connection-test.timeout-seconds=5`。
- 交互：状态被 summary 卡、首页 cockpit、各模块选源提示消费。
- 必要性：**必要**。理由：门的第一职责是「连得上」。
- 当前问题：只有手动触发；`conn_status` 无定时巡检，页面显示的"已连通/断开"会随时间失真。
- 建议：**保留 + 补齐**（周期探活）。

**A3 敏感参数脱敏与回填合并（功能 10）**
- 业务含义：密码/token 私钥不出前端，编辑提交时旧密文合并回填。
- 角色：全角色透明受益；安全底线。
- 依赖：`DataSourceSecretCodec`、`SensitiveTextMasker`、插件 descriptor 声明 secretKeys。
- 必要性：**必要**。
- 当前问题：脱敏只发生在**传输/展示层**，`connection_params` LONGTEXT 在平台库中为明文 JSON；平台库泄露=全部外部凭证泄露。
- 建议：**保留 + 补齐**（静态加密）。

### 分组 B：目录（功能 11–16）

**B1 库/Schema/表/字段浏览与搜索（11、12）**
- 业务含义：穿透读外部库 information_schema，给所有「选表」场景供数。
- 角色：数据开发（同步映射、建模反向导入、质量规则、语义绑定、MDM 采集）。
- 输入：dsId + database/schema/keyword；输出：`CatalogTableVO/CatalogColumnVO`。
- 依赖：插件 `DataSourceCatalog` SPI、`CatalogReadPolicy`、`DataSourceCatalogMatcher`、缓存。
- 交互模块：离线同步 `OfflineIncrementalPlanner`、质量 `DataSourceQualityCatalogAdapter`、数据集 `DataSourceDatasetCatalogAdapter`、元数据 `DataSourceCatalogHarvestSource`、建模 `ReverseImportService` 等。
- 必要性：**必要**。理由：图二 MET、SYN、QUA 三条线都从 DS 取目录；无它则各模块自带 JDBC 代码，违反 S1。
- 当前问题：本模块自身**没有目录浏览页面**（能力存在但平台内无「看这个数据源里有什么表」的直达界面，目录浏览寄生在其他模块表单里）；元数据采集页面的目录已并入资产目录（R-2 拍板），DS 页面不承担此职责，边界需在文档层说清。
- 建议：**保留**；是否给 DS 页加目录树属产品决策（P2），不补也成立。

**B2 预览前 20 行 / count / SQL 模板 / resolve-sql（13、14）**
- 业务含义：选表时的轻量数据确认 + SQL 拼装辅助。
- 角色：数据开发（配置同步时的数据核对）。
- 依赖：catalog 读策略 + queryTimeout 15s。
- 必要性：**较必要**。预览与模板构建是同步/开发配置体验的关键支撑，且已按只读策略执行。
- 当前问题：入口全部在其他模块，DS 页面自身不可预览，用户想"看看这个源"要绕路。
- 建议：**保留**。

**B3 Catalog 诊断 + 元数据缓存 + 失效事件（15、16）**
- 业务含义：目录读取可观测（慢操作阈值）与性能缓存；数据源变更后 AFTER_COMMIT 清缓存。
- 角色：运维/开发排障。
- 必要性：**较必要**（缓存必要，诊断接口当前无人消费）。
- 当前问题：`/catalog/diagnostics` 前端零调用（接口存在，页面未展示）；`DataSourceChangedEvent` 只有模块内监听器，下游（元数据、同步）若另有缓存/快照，收不到变更通知。
- 建议：**保留缓存与事件**；诊断接口**下线或并入 SQL 执行观测页**二选一；事件对外发布列入观察。

### 分组 C：插件与驱动（功能 17–21）

**C1 插件注册与 26 类型支持（17、18）**
- 业务含义：ServiceLoader 启动期发现插件，descriptor 携带能力集（6 类 Capability）与表单 schema，前端动态渲染连接表单。
- 角色：平台管理员（选类型填表）、平台开发（扩展类型）。
- 必要性：**必要**。这是「门」可扩展性的本体，26 种类型（22 种 JDBC + Doris + ES7/8 + MongoDB）中覆盖国产化（达梦/人大金仓/GBase/OceanBase/openGauss/虚竹/崖山/HighGo 等），符合医疗 HIS 场景。
- 当前问题：DuckDB（单机文件库）、IRIS/HANA 等类型是否真有落地场景无法从代码确认——**当前无法确认**哪些类型在生产被实际使用（无使用统计）。
- 建议：**保留**；新增类型走准入（避免插件目录膨胀成 R-4 类重复）。

**C2 插件 install（19）**
- 业务含义：历史上「安装插件」的遗留端点，现为纯可用性检查。
- 必要性：**过渡**。代码注释自认 legacy。
- 当前问题：前端仍在调（`installDataSourcePlugin`），给用户"安装了什么"的错觉。
- 建议：**下线**（前后端同批移除），或改名「插件可用性检查」并去按钮化。

**C3 驱动上传（20）**
- 业务含义：JDBC 自定义驱动包上传（表单 customField 触发 DriverManager 组件）。
- 现状：前端组件、service、API 常量齐全；**后端端点不存在**（全仓无 `plugin/driver/upload` Controller）。
- 必要性：**必要**（国产化/私有库常需外置驱动，且当前所有驱动编译期打包进插件）。
- 当前问题：用户上传动作必然 404/失败，属断链功能；驱动若必须靠重新构建镜像解决，违背「门要能开」的定位。
- 建议：**补齐后端**（含存储路径、类加载隔离——`ElasticsearchSdkIsolationTest` 表明仓内已有 SDK 类隔离先例可复用），或将该字段从表单 schema 中摘除（不推荐，能力本身必要）。

**C4 SSH 隧道（21）**
- 业务含义：经跳板机连内网库，参数内嵌在连接 JSON，由 JDBC 插件在建连时生效。
- 必要性：**必要**（医院内网场景几乎必然）。
- 当前问题：仅 JDBC 系插件支持；ES/Mongo 无隧道能力声明（capability 检查会拒）。
- 建议：**保留**。

### 分组 D：SQL 执行运行时与审计（功能 22、23）

**D1 SqlExecutionRuntime（平台级）**
- 业务含义：全平台唯一的 SQL 执行入口：接口定义在 core（`data-ops-core/.../SqlExecutionRuntime.java`），实现却在数据源模块（Default + Observable@Primary 门面，虚拟线程跟踪、可 cancel/await、事务模式由 runtime 拥有并拒绝用户 SQL 夹带事务控制语句）。消费方：SQL 任务插件（caller=SQL_TASK，经 job 模块 `SqlTaskExecutorAdapter`）、数据集（DATASET）、数据服务（DATA_SERVICE）；策略层强制消费 caller 只读。
- 使用角色：间接服务数据开发（任务运行）、数据分析（数据集查询）、外部调用方（数据服务 API）。
- 输入：`SqlExecutionRequest/Plan`（dsId、SQL/语句列表、maxRows、超时、transactionMode）；输出：结果集/影响行数/快照。
- 存在必要性：**必要**。理由：04 图二把"SQL执行"写进 DS 的副标题（连接·目录·SQL执行），且它是 S1「不许各模块私存连接」能成立的执行侧保证——所有模块经它触库。
- 当前问题：①CONSOLE、ANALYSIS 两个 caller 枚举后端零使用（无 SQL 控制台产品化，属预留）；②运行时接口在 core、实现在 business-datasource，`data-ops-plugin-task-sql` 同时 import 两者，层次耦合值得留意但方向正确；③生命周期模块绕过 runtime 直接用 `DataSourceExecutionProvider` SPI（`DataSourceTtlSqlGateway`），执行审计表**记不到 TTL DDL**，属第二执行通道。
- 建议：**保留 + 重构**（把 ExecutionProvider 直连路径收编进 runtime 或至少在策略/审计层对齐）。

**D2 SQL 执行审计（23）**
- 业务含义：每次执行落 `yak_ops_sql_execution` 聚合 + `yak_ops_sql_statement_execution` 语句明细（SQL 字面量脱敏 SHA-256 指纹、预览、耗时、截断标记），API 可分页/详情/汇总。
- 角色：运维、安全审计（应然）；当前实际无人。
- 必要性：**必要**（「门」的日志面；05 登记册 DS→AUD 的机器可查部分）。
- 当前问题：接口存在、页面未展示；数据在持续写入但没人看，观测价值为零。
- 建议：**补齐前端**（P1 级补齐，成本极低：三个只读接口已有 VO）。

### 分组 E：审计与权限联动（24、25）

**E1 操作审计接入（24）**：必要（04 图 `DS -.-> AUD` 已兑现，且事务提交后才盖章，语义正确）。建议保留。
**E2 RBAC（25）**：较必要。问题：READ 用新编码 `resource:data-source:read`，写操作用旧编码 `datasource:create/update/delete/test`，V1000 目录同时存在新旧两套；SQL 执行观测又是第三个命名域 `resource:sql-execution:read`。同一模块三种命名风格，授权页易漏配。建议**重构**（统一到 `resource:data-source:*`，走一次 V2006 式对账迁移）。

## 4. 模块真实功能定位

**实际承担的角色**：比图二写的还多——①「通往外部的门」（连接登记+目录+SQL 执行，符合设计）；②**平台元数据库的持有者**（`BusinessDatabaseConfiguration` 定义 opsDataSource 与事务管理器，47 个文件的持久化条件装配挂靠在 `ConditionalOnDataSourceEnabled` 上）；③平台 SQL 执行机制的供给方（core 定接口、本模块给主实现）。

**是否主脉关键节点**：是。①接入段唯一结构化数据入口；②段（同步/采集）、③段（开发/建模）、④段（SQL 任务）、⑤段（数据集/数据服务查询）全部穿过它。它宕了不是「数据源页面打不开」，是全平台停止触库（包括平台自身元数据库）。

**是否被其他模块强依赖**：是，全仓最强依赖（见第 5 节 import 统计：14 个业务模块 + 2 个插件模块有功能级依赖，另有约 47 处仅基础设施级依赖）。

**更像哪类**：入口 + 执行。不是配置、不是展示、不是治理——它是带执行内核的入口网关。

**真实边界**：应含「连接登记、目录读取、SQL 执行、凭证治理、插件扩展」；实际还含「平台自身 DB 配置」（不该在业务模块里长期持有）与「SQL 执行审计存储」（合理但需观测面配套）。

**职责是否过载/不清**：轻度过载。两个混入点：(a) 平台元数据库配置作为其他模块开关被反向依赖，数据源 disable 会连锁瘫痪——这是隐式耦合，不是显式契约；(b) 目录/执行大量能力无自有界面，全靠寄生在下游模块表单中，「模块的页面」≠「模块的能力」，盘点时极易误判。

**若明天下线**：离线/实时同步无法定义源表目标表、元数据采集断源、数据质量规则选不了表、SQL 任务全部执行失败、数据集与数据服务 API 全部 500、建模反向导入/映射失效、MDM 采集断链、首页与数据源页空白——主脉①即断，②③⑤段全部停摆。它是可下线性最低、故障爆炸半径最大的模块之一。

- **数据流**：外部库 → 插件（JDBC/HTTP/Mongo driver）→ 目录/结果集 → 各模块；凭证加解密只在本模块边界内完成（展示层）。
- **控制流**：各模块仅持 data_source_id 引用（S1 契约，抽样未见私存连接串——mdm/modeling 表存的是 `source_id` 列，如 `V4__create_mdm_source.sql`），✅ 契约被遵守。
- **事件/异步**：仅模块内 `DataSourceChangedEvent`（清缓存，AFTER_COMMIT）；**无对外的"数据源已变更/已删除"事件**，下游持有者无感知。SQL 执行审计经虚拟线程异步落库。
- **共享存储**：本模块私有 3 表（见文末）；下游表以 `data_source_id` 弱引用，**无外键、无删除守卫**，悬空引用是结构性风险。
- **交互风险点**：(1) delete 无引用校验（最大）；(2) ExecutionProvider 旁路 runtime 造成第二执行通道、审计不全；(3) 47 处 `ConditionalOnDataSourceEnabled` 使"关数据源=关全平台"；(4) 前端目录/预览能力全部寄生在别的模块，DS 自身页面看不到自己管的门后有什么。

## 7. 模块现状总结

- **已实现核心能力**：连接登记 CRUD/测试/统计（含项目隔离与 RBAC）、26 类型插件 SPI 体系（能力声明+动态表单）、目录穿透读取（缓存/搜索/预览/诊断）、平台级 SQL 执行运行时（策略化只读、事务托管、可取消、审计落库）、审计联动、SSH 隧道。三条主链（连接·目录·SQL执行）与 04 图二承诺一致，S1 契约在代码层被普遍遵守。
- **页面已展示但未闭环**：JDBC 驱动上传（后端 404 级断链）；插件「安装」（空语义过渡）。
- **接口存在但无页面**：`/api/v1/sql-executions`（执行审计三接口）、`/catalog/diagnostics`（目录诊断）。
- **任务存在但无界面**：无定时任务（这本身是缺失——探活不存在）；catalog 缓存失效事件仅模块内。
- **冗余或重复建设**：权限编码新旧并存三套命名；生命周期/数据集 schema 经 `DataSourceExecutionProvider` 旁路 runtime 形成第二执行通道（不复制连接，但绕策略与审计）；`/all` 与 `/option` 语义高度重叠。总体冗余度低，远好于消费段模块。
- **真实业务定位**：带执行内核的入口网关 + 事实上的平台元数据库持有者（后者应显式化为基础设施，而不是隐式耦合）。
- **最大风险**：**删除零守卫 + 明文凭证**的组合——前者让误删一次即可静默打断主脉②③④⑤多段链路，后者让一次平台库泄露变成全量外部库沦陷。
- **最该补齐的 3 个能力**：①引用守卫与删除保护（P0）；②驱动上传后端 + 连接探活 + 执行审计页（P1 三件套）；③凭证静态加密（P1）。
- **建议下一步动作**：本周内出「数据源引用登记表」技术方案（各下游模块注册引用查询，delete 前置校验）；把驱动上传排进下个迭代（前后端配对或删除前端假按钮）；给 `/api/v1/sql-executions` 配一个最小只读页；开一次凭证加密专项（含存量洗数迁移脚本）。
- **与 05 清单的偏差记录**：登记册第 1 条现状标 ✅，本次盘点确认「不私存连接」成立，但发现其未覆盖的两个结构问题：删除无守卫、变更无对外通知，建议作为 R-9 候补入册。
