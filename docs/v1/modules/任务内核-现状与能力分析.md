## 1. 模块概览

| 项 | 内容 |
|---|---|
| 模块名称 | 任务内核（后端 `data-ops-business-job`，辅以 `data-ops-plugins/data-ops-plugin-task/*` 四执行插件与 `data-ops-core .../plugin/task/TaskPluginRegistry`） |
| 主脉位置 | ④ 编排执行段："执行机制"——上承任务目录锁版本产物与文件资源脚本/JAR，下为工作流/质量/同步提供统一执行入口 |
| 上游（入边） | 图二声明：RES--脚本/JAR-->JOB（**已核实真实接线**，与文件资源盘点结论一致，见第 5 节）。代码实际还有图二未画的入边：工作流（节点派发）、数据开发（试运行/运行记录/重试）、质量与同步（反向注册 Executor/Provider） |
| 下游（出边） | 图二声明：JOB--执行-->WFL & QUA & SYN。**逐边核实**：三条边的真实语义各不相同——WFL 是"被内核执行"（工作流节点经 Gateway 路由），QUA/SYN 是"内核路由到域自有执行器"（QUALITY/SYNC Executor 由质量/同步模块实现并注册进 Gateway，内核只按类型分发）；此外有图二未画的 SQL 执行真正落地在数据源模块 `SqlExecutionRuntime`（见第 4 节） |
| 一句话定位 | 业务无关的**任务发现聚合 + 不可变快照契约 + 按类型执行路由 + 插件类任务共享运行时装配**（虚拟线程、幂等、状态、取消）；它不做调度、不存执行事实、SQL 类任务连执行引擎都不在自身进程内——是"路由与生命周期壳"，不是"引擎全家桶" |
| 实现状态 | **核心闭环已实现**：四类插件任务（SQL/Python/Shell/Java）+ 两类域执行器（SYNC/QUALITY）共 6 种类型经统一 Gateway 执行，dev 试运行与工作流调度两条调用链均真实走通；但存在结构性缺口——插件任务运行态**纯内存无持久化**（重启即失联）、执行记录表内核为零张、无日志体系、Java 任务被排除在工作流编排白名单外、HTTP 类型四处置名却无任何实现——详见第 6/7 节 |
| 主要入口 | 后端 REST 仅两个：`TaskController`（`GET /api/v1/tasks`，工作流可见任务列表）、`SystemEnvVarController`（`/api/v1/system/env-vars` GET/PUT/DELETE，设置页环境变量）。其余能力**只对内不对外**：`io.yak.ops.business.job.task` 包 Java 契约（TaskProvider/TaskExecutor/TaskExecutionGateway），无跨服务 RPC、无对外执行 REST。数据库：内核自有表 **0 张**（唯一业务表 `yak_system_env_var` 的建表 DDL 却住在数据开发模块的 Flyway 基线里，见第 2 节附注） |
| 开关与装配 | 无独立 `yak.job.enabled` 开关（boot 无条件打包）；插件经 Java SPI（`META-INF/services/io.yak.ops.plugin.task.api.TaskPlugin`，恰好 4 个：sql/python/shell/java）由 `TaskPluginRegistry.load()` 装配；**该 Registry Bean 的定义点异常地落在数据开发模块**（`DataDevelopmentTaskPluginConfiguration`，@ConditionalOnMissingBean）——内核自身不装配自己的插件注册表 |

## 3. 子功能逐个分析

**1-2 任务发现（/api/v1/tasks + Provider 聚合）**
- 业务含义：给工作流一张"当前可执行"的任务清单，业务域经 TaskProvider 反向注册，内核不认识任何业务表。
- 角色/输入/输出：工作流编辑器/实例页；taskId→descriptor+snapshot。
- 依赖：`OfflineSyncTaskProvider`（唯一 Provider，每次 list 全量扫同步定义）。
- 必要性：**必要**。这是 S7"执行入口不许各写各的"的发现半边（执行半边见 3）。
- 当前问题：①接口语义名不副实——名叫 tasks 却只有 SYNC 任务（dev/质量任务走 task-catalog 资产投影，前端 `instances.ts:181-206` 手工合并三个来源），"一个清单"实际是两个真相源拼的；②每次调用全量 refresh 无缓存；③`TaskRegistry.get/snapshot` 的 legacy 通道被工作流限定仅 SYNC（`WorkflowTaskBindingResolver:53-57`）。
- 建议：**保留**。把"目录资产为主、Registry 为辅（legacy）"的现实写进接口文档，或让 Registry 聚合目录投影实现单一清单。

**3 执行路由 Gateway**
- 业务含义：全平台任务执行的唯一闸口：start/status/cancel 三动作按类型分发，重复注册启动即拒。
- 必要性：**必要**（模块立身之本；S7 ✅ 的直接兑现者）。
- 理由：三条真实调用链（WFL 节点派发、DEV 试运行/重试、经它路由到 QUA/SYN 域执行器）全部经它，grep 无旁路 Executor 直调生产代码。
- 当前问题：Gateway 无鉴权概念（纯进程内），触发人/操作者信息不进 TaskExecution——审计只能在调用方；`TaskExecutionTrigger.SCHEDULE` 枚举值生产代码零使用（工作流定时跑仍标 WORKFLOW），触发来源统计失真。
- 建议：**保留**；补 SCHEDULE 语义接线或删除枚举值。

**4 插件运行时（共享生命周期）**
- 业务含义：幂等、异步、状态机、取消、结果转换一套实现，四个类型 Adapter 只贡献 Capability（硬规则 7/8）。
- 必要性：**必要**。这是内核区别于"各写各的"的核心价值，代码质量高（原子状态转换、幂等 owner 等待、fatal 透传）。
- 当前问题（内核最重的一处）：**运行态纯内存且永不回收**——`executions`/`idempotencyIndex` 无任何 remove；进程重启全部在途执行失联（workflow poll 收 "not found" 即 failNode，插件任务**不可恢复**，SYNC/QUALITY 因执行器自存 DB 可续，插件类不行）；`@PreDestroy shutdownNow` 直接杀进程不等待；LOST 状态定义了无人产出（`TaskExecution.terminal()` 认它，全仓无生产者）。
- 建议：**保留 + 重构**（执行态落库或至少终态 TTL 清理 + 恢复期 LOST 判定，见第 6 节 P0）。

**5 上下文工厂 / 项目上下文传播**
- 必要性：**必要**。虚拟线程丢 ThreadLocal 是经典事故点，`captureProjectContext`（`:66-73`）正确解决。
- 问题：projectContext 为 null 时静默裸跑（`:71` return action）——异步任务可能无项目上下文执行。建议：**保留**，null 分支改 fail-fast 或告警。

**6 SQL 任务执行**
- 链路：Gateway→Adapter→plugin-sql→**数据源模块 SqlExecutionRuntime**（core 接口/DS 实现/caller 只读策略/执行审计，详见数据源盘点 D1 节）。
- 必要性：**必要**（平台最高频任务类型）。
- 理由：复用平台级 SQL 运行时带来统一超时/取消/审计；方向正确（job 依赖 datasource capability 是 DEPENDENCIES.md 显式允许的外部走廊）。
- 当前问题：SQL 的"执行引擎"物理上不在任务内核——内核出的是壳（幂等/线程/状态），引擎、连接、凭证、审计全在数据源模块；多语句脚本只回传最后一个结果集（`SqlTaskExecutor:115-151`），中间 SELECT 丢内容留 affectedRows 汇总，宽结果场景截断。
- 建议：**保留**，但定位表述上如实写"SQL 执行=内核路由 + 数据源运行时"（第 4 节）。

**7-8 Python / Shell 任务执行**
- 必要性：**必要**（图二 RES→JOB 边的两类脚本消费者；`ScriptTaskSupport.resolveScriptContent:135-152` 支持内联与资源双模，资源模式即文件资源解析链）。
- 当前问题：①**运行时供给不锁版本在这两类是软的**——资源模式按 configJson 是否带 resourceVersion 决定 `resolve(id,version)` 或 `resolve(id)`，而 dev 编辑器 Python 明确不写版本（文件资源盘点已证），发布后每天跑"当前"文件；②宿主机进程模型：无容器/无隔离，python/bash 需在 PATH，长任务占应用进程所在机器资源；③stdout/stderr 一次性读尽截断 50k，无流式、无中间进度。
- 建议：**保留**；锁版本问题随文件资源 P0（真版本）一并解，本模块配合发布时固化 resourceVersion。

**9 Java 任务执行**
- 必要性：**必要**（JAR 型任务的唯一执行通道；resource-only 设计正确——二进制内容不可能内联）。
- 当前问题（本次盘点最重要的发现之一）：**Java 执行链全通但调度断链**——`WorkflowTaskEligibilityPolicy` 白名单 {SQL,SHELL,HTTP,PYTHON} 无 JAVA，前端任务选择器同集合（`instances.ts:179`），Java 任务发布进目录后**进不了工作流**，只能手动试运行。四类执行里唯一在 job 侧"能做不能排"的类型。
- 建议：**保留 + 补边**（白名单加 JAVA；配合发布时资源版本固化，否则调度化后会把"不锁版本"缺陷放大到每日定时场景）。

**10 HTTP 类型占位**
- 业务含义：无。四处置名是历史设计残留（推测原规划 HTTP 调用节点）。
- 必要性：**冗余**。发布/试运行两道闸已天然拦截，但白名单与枚举留着会持续误导（新人以为有 HTTP 节点；图二评审时也被问过）。
- 建议：**下线或立项二选一**——短期从 workflow/dev 白名单与 node-model 移除 HTTP（后端发布闸保留兜底）；若产品确需 HTTP 节点，按插件契约新增 `data-ops-plugin-task-http`（有验收标准再开工），不做"接口存在页面未展示"式半成品。

**11 SYNC 路由**
- 必要性：**必要**（图二 JOB→SYN 边）。
- 理由：离线批任务以工作流节点形态被调度，全靠这套契约；且同步是唯一 TaskProvider，发现+执行两边都吃内核。
- 当前问题：snapshot version≤0 的兼容通道允许回读"当前定义"执行（`OfflineSyncTaskExecutor:41-44`→`execute(taskId)`），与硬规则 3"禁止运行时回读当前配置"存在一条明示的例外走廊；数据面在外部引擎（18080），内核、同步模块、外部引擎三处状态一致性靠 idempotencyKey+对账维护。
- 建议：**保留**；兼容走廊排期收敛（目录锁版本全面接管后删除 version≤0 分支）。

**12 QUALITY 路由**
- 必要性：**必要**（图二 JOB→QUA 边；质检监控发布为 QUALITY 任务资产进目录，工作流定时跑质检由此触发）。
- 当前问题：质检规则 SQL 的执行**旁路了平台 SQL 运行时**——经 `QualityDataCatalogGateway.preview`→`DataSourceCatalogReader`（且 quality 直接 import datasource 模块内部类，非 SPI），意味着质检 SQL 不进 `yak_ops_sql_execution` 审计面；"检查未通过=任务 FAILED"的语义让工作流失败告警兼作质量告警通道（与 05 清单第 16 条一致，可接受但要在文档里写明）。
- 建议：**保留 + 接线整改**（quality SQL 改走 SqlExecutionRuntime caller 枚举，纳入统一审计——与数据源盘点"第二执行通道"问题合并治理）。

**13-14 环境变量**
- 业务含义：给脚本/JAR 任务注入全局配置（凭证、PATH 类变量），设置页可视化维护。
- 必要性：**较必要**。执行链注入（14）必要；管理面（13）当前是唯一有独立页面的内核能力。
- 当前问题：①安全面——GET 返回 OS 全量环境变量（常含 DB 密码、token），接口无权限码、出参不脱敏，登录用户即可读；②无项目隔离（多项目共享一套，改了互相影响）；③无变更审计；④写生效即时但**无逐 key 版本/回滚**。
- 建议：**保留 + 立即治理**（OS 变量不返回值只列 key，或至少脱敏；补权限码与审计，见第 6 节 P1）。

**15 稳定契约与架构测试**
- 必要性：**必要**。8 类契约 + 四支架构测试 + 五件套文档，是"执行入口不许各写各的"能长期成立的制度保障（与文件资源并列全平台治理最规整模块）。
- 当前问题：**文档漂移两处**——①DOMAIN.md/DEPENDENCIES.md/ARCHITECTURE.md 均称"deprecated SYNC corridor（SyncTaskRunner 等三类）暂时保留"，实际生产源码已删净，架构测试 `legacySyncTaskCompatibilityBoundaryCannotReturn` 反向断言其**不得出现**（文档比代码旧）；②`additional-spring-configuration-metadata.json` 声明 `yak.job.schedule.*` 四属性，全仓 Java/yml 零引用（真实配置是 boot 的 `yak.schedule.*`，归框架调度桥），属认知噪音。
- 建议：**保留**，顺手修两文档一 json。

**16 执行记录与日志（内核侧缺失面）**
- 业务含义：回答"任务内核有没有自己的运行实例页/日志页"：**没有，且按设计不该有**（执行事实归业务域）。
- 现状核对：运行实例列表=工作流实例页（`/workflow/instances`，含节点/attempt 时间线/重试按钮）与 dev 运行记录页；日志查看=节点详情 Node Output JSON 块（`WorkflowInstanceDetail.tsx:470`）与 dev 执行详情 output pre（`executions/index.tsx:469-471`）——展示的是**结果 JSON 里的 stdout/stderr 字符串**，全平台无执行日志文件/流式日志/日志页面。
- 必要性：**必要（作为缺失能力补）**。插件任务重启失联后，attempt 表里只有 error_message，内核侧无任何运行簿可溯源。
- 建议：见第 6 节 P1"执行日志落地"。

## 4. 模块真实功能定位

**它是平台唯一执行引擎吗？——不是；它是唯一执行入口吗？——在"任务"这个概念上，是的，且这条约束目前是真实的。**

- **准确角色：路由 + 契约 + 一类半执行器。** 内核物理拥有的执行机制只有"插件类共享运行时"（虚拟线程起进程/委托）这一套壳；六种类型的真实执行引擎分布：SQL→数据源模块 `SqlExecutionRuntime`（事务/取消/审计都在 DS）；Python/Shell/Java→宿主机子进程（这部分算内核引擎）；SYNC→外部批集成引擎（18080）；QUALITY→质量自有执行器+数据源目录预览。README 第一句"通用任务运行中枢"成立，但"执行机制"四个字在图二里不能读成"所有计算都发生在内核"。
- **S7"执行入口不许各写各的"✅ 成立且已验证**：生产代码中不存在 Gateway 之外的任务执行入口（TaskExecutor 直调 grep 零命中；`/api/v1/tasks` 只读）。但要区分两类旁路：①**合法复用**——dataset/data-service 直调 `SqlExecutionRuntime` 属"即席查询"不是"任务执行"，不在 S7 射程；②**真旁路**——生命周期 TTL DDL 走 `DataSourceExecutionProvider` 绕开 runtime（数据源盘点已记）、质量规则 SQL 走 catalog preview 绕开 runtime，两处不复制"任务"但绕开了统一 SQL 审计与策略，是数据源盘点"第二执行通道"问题在内核视角的投影。
- **它是关键单点**：工作流每一次节点派发、dev 每一次试运行/重试都过 Gateway；SQL/Python/Shell/JAVA/QUALITY/SYNC 六类任务的幂等、状态词表、取消语义由内核一处定义。明天拔除内核=平台所有调度与运行能力同时瘫痪，且无第二实现可切换——区别于多数"可以下线也不心疼"的治理对象模块。
- **边界纪律**：`job.* -> business` 依赖方向被架构测试锁死（唯一例外 pom 直依赖 `data-ops-business-datasource`——名义用途是复用 `BusinessDatabaseConfiguration` 数据源配置类，实际顺带获得了对 DS 内部类的编译期可见性，JobDependencyBoundaryTest 允许了这条走廊）；不注册 Cron、不持有调度状态（Schedule 归工作流域，quartz 引擎归框架桥）；不存执行事实。职责收敛度全平台最高。
- **归类**：基础设施型执行中枢（介于内核与运行时之间），不是业务流程节点。
- **真实能力半径与图二的偏差**：图二 JOB 的三个出边里，WFL 方向画反了语义——实际是 WFL 调 JOB（派发），JOB 不回指 WFL；QUA/SYN 两条边准确（内核路由到域执行器）。图二未画入边 DEV→JOB（试运行是内核第二大流量来源）。
- **单实例属性**：内核运行态在内存（第 3 节 4），叠加工作流的 MySQL 命名锁单主守卫（`WorkflowRuntimeSingleMasterGuard`），当前架构只允许多实例中一个驱动执行——内核是**嵌入式单进程运行时**，不是分布式执行层（无 worker/无远程派发/无队列持久化）。

## 7. 模块现状总结

1. **核心能力已闭环且入口纪律真实**：六类型（SQL/Python/Shell/JAVA/SYNC/QUALITY）统一经 `TaskExecutionGateway` start/status/cancel，工作流派发与 dev 试运行两条链逐跳有代码证据；grep 未发现任何绕过 Gateway 的任务执行入口——05 清单第 7 条 ✅ 维持，且本次把"✅"的依据从印象升级为文件级证据。
2. **图二三条出边全部接线但语义需加注**：WFL 边方向实为"被调用"；QUA/SYN 边是"路由到域自有执行器"（触发而非代跑）；RES→JOB 入边真实，但版本围栏在 Python/Shell 上不锁的缺陷经此边传入内核，内核侧无兜底校验。
3. **头号结构性缺口**：插件任务运行态纯内存——重启失联、无恢复、无清理、LOST 死语义，叠加单主锁，坐实"嵌入式单进程运行时"属性；这与"数据平台执行内核"的产品预期之间要不要升级，需在 01 层面拍板。
4. **最刺眼的断链**：Java 任务执行链全通却进不了工作流（白名单/前端选择器无 JAVA），而白名单里放行的 HTTP 是零实现占位——一收一放之间恰好放错。
5. **接口存在、页面未展示/无页面**：内核 REST 面本就极小（2 个 controller），无"接口存在页面未展示"欠账；反向欠账是**页面无内核宿主**——运行实例、日志、重试等观感全部寄生 workflow/dev 页面，内核自身唯一露脸页面是设置页环境变量 Tab（且 settings 菜单 hidden）。
6. **死代码/噪音清单**：HTTP 四处占名；`TaskExecutionTrigger.SCHEDULE` 零使用；LOST 状态零生产者；`yak.job.schedule.*` 配置元数据无对应实现；`TaskRegistry.get` legacy 通道仅 SYNC 可用；文档三处"corridor 保留"滞后于已删代码。体量小、全部可一次收口。
7. **安全/治理债集中于环境变量**：OS env 全量出参、无权限码、无项目隔离、无审计——内核唯一"对内不对外"纪律失效的敞口（它对前端开着写接口）。
8. **最大风险**：不在内核自身，而在"执行"这个词的叙事——平台对外说"任务内核统一执行"，物理现实是"统一路由 + 引擎四方分居（DS/宿主机/外部引擎/质量）+ 两条 SQL 旁路"；不写清楚，未来每个新执行类型（HTTP、Spark…）都会在这里长出第二个真相。
9. **最该补的 3 项与下一步**：①Java 接入工作流（P0 白名单一行+联调）；②执行态 TTL/LOST 收口与日志落地（P0/P1 配对做）；③HTTP 处置+环境变量安全收口（P1 决策类）。下一步：先随 03 验收路线跑一次"上传 JAR→发布→（补白名单后）工作流定时跑→改文件→再跑"端到端，验证 RES→JOB→WFL 全链与版本围栏，再启动第 6 节修复序。

## 8. 掌握度自检

本模块我可以较有信心判定"契约与路由层已实现且接线真实"：从 Gateway 到插件到进程/引擎的每一跳、以及四个调用方（WFL/DEV/QUA/SYN）的接入点都有文件行级证据，且模块自带文档同构测试防漂移。不能完全掌握的三点：①**运行时行为未实测**——虚拟线程并发下幂等/取消、Python 子进程僵死（destroyForcibly 失败）等边界只读码未压测；插件任务执行在**现网**的并发与存活分布（内存 map 是否已在漏）需运行观测佐证，当前无法确认；②**外部批集成引擎（18080）** 是黑盒（test-jar/compose 有痕迹，引擎侧实现不在本仓），SYNC 边数据面行为以其为准无法核验；③工作流引擎 `io.yak.framework.workflow.engine` 为外部构件（仅 `output/decompiled-remote` 有反编译参考），重试/状态机在引擎层的完整语义以仓内工作流盘点为准。如需闭环第①点，用 03 号文档验收路线加一个"重启应用时节点 RUNNING"用例即可定性。
