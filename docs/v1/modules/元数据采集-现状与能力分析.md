## 3. 子功能逐个分析

### 3.1 采集任务管理 + dry-run + 手工运行 + 运行历史（清单 #1~#4）
- **名称**：采集/对账任务页
- **业务含义**：定义"采哪个源、哪个库/schema、表名模式、是否到列级"，先预演再生效，运行结果四类计数透明。
- **使用角色**：数据工程师/平台管理员（权限码 `data-metadata:create/update/delete`）。
- **输入**：数据源 id、作用域、cron、熔断阈值（collapse_threshold_pct）、缺席轮数（missing_rounds）。
- **输出**：`yak_md_collect_job`/`yak_md_collect_run` 行；采集落共表目录行。
- **依赖**：数据源模块（凭据与目录读取都在对方，本模块只交 id，见 `DataSourceCatalogHarvestSource` 注释）；Quartz 调度框架（可缺位）。
- **交互模块**：datasource（同步读）、asset/lineage（共享存储）、前端采集页。
- **必要性判断**：**必要**。
- **理由**：这是"②段采集执行器"的实体操作面；启用闸门（dry-run 前置）+ 手工触发通道的取舍有明确论证（`MetadataCollectJobController` javadoc）。
- **问题**：页面上可选 providerType=REGISTERED 建任务，但执行体未落地（见 3.7）——用户可创建永远跑不了的任务。
- **建议**：**保留**；短期在任务表单对 REGISTERED 通道加"执行体未交付"提示或暂时禁选。

### 3.2 物理采集引擎（#5）
- **名称**：`MetadataHarvestService`
- **业务含义**：一轮采集把数据源的 服务→库→表→列 四层事实投影进统一目录，是全模块存在的理由。
- **使用角色**：系统（用户经任务页触发）。
- **输入**：任务行 + 数据源目录 SPI（`DataSourceTable/DataSourceColumn`）。
- **输出**：共表 upsert 行（指纹 `content_hash` 判增量）、`yak_md_change` 流水、四计数。
- **依赖**：datasource 插件（JDBC：`GenericJdbcCatalog` 走 `DatabaseMetaData.getTables/getColumns`；Doris 继承之；ES/Mongo 各有 `DataSourceCatalog` 实现）；`HarvestSystemDatabases` 过滤引擎库。
- **交互模块**：datasource（读）；lineage/asset（经共表间接）。
- **必要性判断**：**必要**。
- **理由**：一次采集落四层不是冗余——`parent_asset_id` 只在首次 INSERT 写，层级错过即永久为平（代码注释明确）。
- **问题**：分批只能"按作用域 + 内存 50 表一组 + 落库 500 行一批"，源侧 `listTables` 无游标，超大单库作用域没有解（端口注释如实声明）；非 JDBC 插件列读取失败按 PARTIAL 处理是正确姿态，但等于列级目录对 ES/Mongo 不保证。
- **建议**：**保留**。

### 3.3 缺席判定与熔断（#6）
- **名称**：`MetadataPresenceService` + `CatalogGraphRevocation`
- **业务含义**：把"这轮没见到"与"确实不存在"分开：四道闸拦误删，坍塌比例熔断整轮判 SUSPECT。
- **输入**：本轮 seen 集 + 上一有效轮时刻。**输出**：`gone_at` 软删行 + GONE 流水。
- **依赖**：仅本模块。**交互模块**：血缘撤销（端口已定义，**无实现方**——ticket 113 至今未提供 lineage.api 撤销入口，缺席时只记日志）。
- **必要性判断**：**必要**。
- **理由**：采集唯一不可逆损失点就是误删；"证据不足就什么都不做"的形状是对的。
- **问题**：GONE 后血缘图上的节点撤销实际不会发生（`revoke` 无装配者），"图上挂着一张不存在的表"这个被注释点名的坏形态正是当前现实。
- **建议**：**补齐**（lineage 侧提供撤销实现，接上现有端口）。

### 3.4 定时调度（#7）
- **名称**：`MetadataScheduleEngineBridge`/`MetadataCollectScheduleHandler`
- **业务含义**：启用任务的 cron 闹钟；重启后从任务表补齐登记。
- **必要性判断**：**较必要**。
- **理由**：形态沿用 lifecycle 模板，有调度则省心；无调度时手工触发是明示的降级通道而非事故。
- **问题**：Quartz 内存存储不补跑，调度器缺位平台是常态——定时承诺要打折；调度线程项目上下文恢复已有专门处理（handler 第一件事是 `ProjectContextScope`）。
- **建议**：**保留**。

### 3.5 统一搜索 + 目录浏览 + 实体详情（#9~#11）
- **名称**：`/api/v1/metadata/search`、`/entities/{id}` 与资产目录内嵌视图
- **业务含义**：物理表/列 + 模型/标准字段/域/指标一次查询混合返回，类型是 facet；详情按元模型出块、块级容错。
- **使用角色**：全部找数用户（经资产目录页）。
- **输入/输出**：q/筛选/排序 → 混合命中（列命中聚合成"命中 N 列"下钻）；详情返回目录事实 + 统计/子级/历史/标签/血缘入口/源域实时块。
- **依赖**：MySQL FULLTEXT ngram（唯一检索实现 `MysqlMetadataSearchBackend`）；modeling 的 `modelEntityProvider`（源域实时块，按 `type_def.provider_bean` 寻址）。
- **必要性判断**：**必要**。
- **理由**：菜单并入资产是 IA 决策（M2-2），检索核与详情核的实现仍在且只此一份——`data-asset/catalog/index.tsx` 直接 import `@/pages/data-metadata/components/AssetExplorer`，"目录只有一本"在代码层成立。
- **问题**：①组件物理归属仍在 `pages/data-metadata` 而消费在 `pages/data-asset`，跨页 import 是维护隐患（盘点口径问题，非乱象）；②`pageEntityChanges` 封装了但页面没挂"更多"按钮，完整时间线不可达；③投影实体（dataModel/metric 等）目录里的投影行本身怎么进来尚无通道（见 3.7）。
- **建议**：**保留**；补齐详情时间线翻页入口。

### 3.6 元模型（#12~#13）
- **名称**：`yak_md_type_def`/`yak_md_field_def` + 自省/配置 API
- **业务含义**："类型与字段是行，不是代码"：新增一类可采集/可检索实体=插一行；前端类型面、详情构成、搜索权重、血缘类型映射全部由它驱动。
- **输入/输出**：`GET /types` 供前端；写侧 CRUD + 槽位校验（`MetamodelValidationService`：searchable/facetable 必须有落点，7 个生成列槽是硬容量）。
- **必要性判断**：**必要**。
- **理由**：这是本模块区别于"一张采集表"的结构性资产；8 类实体种子 + `lineage_asset_type` 映射（V3 补齐）是共表两套语义能共存的前提。
- **问题**：写侧 API 无任何界面（接口存在，页面未展示）——现实里改元模型只能直改库，校验逻辑形同虚设；`LEGACY_GLOBAL` 与 `PROJECT_REQUIRED` 同前缀混布有踩坑面（注释已自我说明）。
- **建议**：**补齐**界面（ticket 132 UI 侧）或将写侧接口收敛为运维专用并在文档钉死。

### 3.7 登记 push + 投影对账（#14~#15）
- **名称**：`MetadataRegistrationApi` + `RegisterRetryWorker` + ticket 135 对账通道
- **业务含义**：modeling/semantic/metric 的实体在保存时投影进目录（push），定时对账兜底。
- **输入/输出**：`RegisterCommand` → 共表 REGISTERED 行；失败落 outbox 每秒重放。
- **必要性判断**：**较必要**（方向正确、当前是半成品）。
- **理由与问题**：outbox、永不拖垮源域保存、键前缀硬校验等设计全部落地且有测试；**但 grep 全仓库无任何业务模块调用 `MetadataRegistrationApi`**（唯一跨模块引用是 modeling 实现 `EntityProvider`，那是详情实时读，不是登记）。即 push 挂钩（131）未接、对账执行体（135）未落地、`CollectRunService.execute` 明言 REGISTERED"暂不可触发"。V2 注释"现网 11 行认领"指的是把 lineage 存量行按 key_prefix 认领为投影行，这些行此后如何保鲜——**当前无法确认**（没有通道会更新它们）。目录里非物理类的四类实体实际处于"有壳无源"状态。
- **建议**：**补齐**（131+135 是登记通道成对的两半，缺一即目录漂移无解）；在补齐前把采集页 REGISTERED 任务入口降级为不可建。

### 3.8 标签与治理待办（#16~#17）
- **名称**：`yak_md_label`/`yak_md_task`
- **业务现状**：标签只有读路径（详情块），写侧工单 124 未做——页面上"标签"块对现网数据基本恒空；`yak_md_task` 表和 mapper 存在但主代码无引用，认证过期/待办办结（125）未落地。
- **必要性判断**：**较必要**（变更流水已证明"元数据可度量"，标签/待办是其下一步；当前属规划先行建表）。
- **问题**：表先行、代码后补的形态容易被误读为"已有治理功能"。
- **建议**：**补齐**或明确标记为预留（00 总表口径：只写已实现）。

### 3.9 资产供数 MetadataTableAssetProvider（#18）
- **名称**：METADATA 资产供给
- **业务含义**：采集到的物理表以 `AssetSourceType.METADATA` 进资产台账，让状态机"已发现"对真实表成立。
- **输入/输出**：共表 table 行 → `AssetDescriptor`（assetKey 逐字符直通、sourceId 用行主键、owner/domain 留空的降级口径有注释论证）。
- **必要性判断**：**必要**。
- **理由**：这是 M2-2"目录并入资产"能成立的物理供数边——并入的是入口，供数仍然由本模块做。

## 4. 真实功能定位：目录入口并入资产后，本模块还剩什么？

**结论：本模块是采集执行器与目录真相源，不是薄壳——但它是"只剩引擎、供数半边没接线"的引擎。**

拆开看，并入资产的只是**两个菜单入口**（目录浏览、统一搜索，V2037），而以下四样东西全部仍在本模块、且资产页在直接消费它们：

1. **采集执行内核**：任务模型、四层落行、指纹增量、在场性熔断、变更流水（`harvest/` 包全部）。
2. **目录真相源**：`yak_metadata_asset` 的目录列（display_name/md_attributes/entity_status/gone_at/provider_type/槽位列…）由本模块读写（steward 契约：血缘列不碰，`SharedTableWritePathContractTest` 守界）。
3. **检索与详情核**：`/search`、`/entities/{id}`、`/types` 是元数据实体视图的全部数据来源，资产台账视图里的 TABLE 行也靠本模块 provider 供数。
4. **元模型**：8 类实体、7 槽位、类型→血缘枚举映射，全局配置仅此一家。

但"还剩什么"的另一面是**兑现程度打折**：目录的价值在消费，而当前已接线的消费方只有资产台账（投影供数）与前端检索（人看）；规划中价值最高的 modeling 符合性对账没有做，REGISTERED 投影通道"能建任务不能跑、能定义类型没有 push"。**主脉链"采集→目录→建模"实测断在最后一跳**：物理采集→共表目录这一跳真实通畅（含熔断保护），目录→建模一跳只有接口实现（`MetadataQueryApi`）而无消费代码。

定性建议口径：对技术负责人而言，本模块应表述为**"②段采集执行器 + 目录供数 SPI，M2-2 后转型为无独立目录页的后台内核 + 一个采集运维页"**，而不是"已并入资产的剩余壳"。

## 7. 现状总结

1. **完成度分层明确**：采集执行链（任务→dry-run→执行→在场性→流水→检索→详情→资产供数）后端+前端双全且有测试矩阵（模块内 25 个测试文件，含架构守卫测试）；登记/对账、治理侧、概览三块是"表先行、壳先行"。
2. **页面现实**：`data-metadata` 目录下现存 4 组页面/组件；可达路由仅 `/overview`（占位）与 `/collect`（完整）；目录与搜索能力经 redirect 在 `/data-asset/catalog?view=entity` 呈现，实体视图副标题已标注"数据由元数据模块采集提供"（R-2 收尾项）。
3. **采集覆盖面**：支持的数据源=平台数据源插件全集（generic JDBC、Doris、ES、Mongo），列级抽取对 JDBC 系为真 introspection（`DatabaseMetaData.getTables/getColumns`）；统计增强仅 MySQL；ES/Mongo 列读取失败按 PARTIAL 如实降级。
4. **供数方式两种、兑现一种**：物理表经 `AssetProvider` 进资产台账（已接线）；投影实体（模型/标准字段/域/指标）设计为"源域写时登记+对账"，两半均未落地——当前这四类目录行只读存量与源域实时块，无增量保鲜。
5. **与资产目录的边界**（本盘点最重要的口径问题）：并入的是**入口与心智**（目录只有一本），**没有易主的是真相与执行**——共表目录列的写方、检索核、采集调度、元模型全在本模块；资产页的"元数据实体"视图实为本模块组件跨目录 import。边界风险在反向：若未来有人把 `AssetExplorer` 迁进 `pages/data-asset`，本模块前端残余将只剩采集页，届时模块定性需同步改写。
6. **主脉接线判定**：MET→AST 虚线（目录并入资产）已兑现；datasource→MET 兑现；**MET→MOD 实线未兑现**（有接口无消费），主脉②→③段经由本模块的一跳目前靠人眼看目录间接完成，不构成系统闭环。
7. **可靠性姿态好、承诺要打折**：熔断、空集不判删、PARTIAL 不静默、GONE 软删、账没对齐宁可 SUSPECT——误删防线是全模块最扎实的部分；打折项是"定时"：Quartz 内存存储不补跑，代码自认手工触发是主路径，生产级周期保鲜承诺实际偏弱。
8. **文档-代码一致性**：`docs/data-metadata/plan.md`+issues 与实际落地偏差可控（未落地项均如实留注释指回工单号，如 `CollectRunService:124`），无"文档说完成代码没有"的反向谎言；唯一易误读处是 V2 种子注释"现网 N 行认领"暗示投影在更新，实际保鲜通道未建。
9. **一句话总评**：一个**引擎沉、外壳轻、消费面半成品**的模块——采集执行与目录真相的价值真实存在，但它兑现的是"找得到"，还没兑现"用得上"（对建模/质量）；下一步价值全部押在 ticket 120/131/135 三张票上。
