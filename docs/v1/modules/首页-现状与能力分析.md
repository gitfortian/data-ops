## 3. 子功能逐个分析

**1 头部摘要（cockpit）**
- 业务含义：一眼看清"接了多少源、此刻有多少在跑"。角色：全体登录用户。输入：无；输出：两个数。依赖：datasource/sync-offline/workflow/quality 四域读模型。
- 必要性：**必要**。⑤段"只读总览"的题眼。
- 问题：①"运行中"= 三域 runningCount 简单求和，近 7 天窗口——口径（叫"运行中"却含 7 天窗口）只在 home 代码里定义，任何其它页面查不到这个数；②降级写 0 混淆"没有"与"不可用"（REQUIREMENTS.md 自己承认是历史契约）。
- 建议：**保留 + 补口径文档**（指标定义进各域或产品词典，首页只引用；降级语义向 quality 的 `available:false` 模式看齐）。

**2 快速创建卡 / 16 快捷导航**
- 业务含义：把高频"进门动作"前置。纯跳转，零数据。
- 必要性：**较必要**（导航价值真实；4+4 个入口均有对应路由且可达）。
- 问题：#16 的"查看更多"按钮和临时 SVG 图标是明示过的半成品；两组入口（快速创建/快捷导航）语义有重叠感但分工尚可（创建 vs 消费）。
- 建议：**保留**（#16 占位按钮要么删要么随统一入口页启用）。

**3-7 数据中心（最新任务/指标/趋势/近期任务/调度摘要）**
- 业务含义：平台"发动机舱"——三域运行事实合并视图 + 环比 + 趋势。角色：数据工程师/值班人。依赖：三域 ExecutionOverviewReader 家族。
- 必要性：**必要**。图二 WFL--运行事实-->HOM 声明边的主要兑现物，也是首页区别于"入口页"的核心价值。
- 问题：①各域在 home 里合并成"一个成功数/一个耗时"，**跨域聚合语义（processedRecords 三域相加、avgDuration 加权）是首页发明的指标**，任何业务模块页面没有对应口径；②#7 调度摘要不含质量域、#15 日历含质量域，同一页两个"调度"数字口径不一致；③"查看更多"按钮无 onClick（死按钮）；④detailPath 坏链（第 5 节）。
- 建议：**保留 + 收敛口径**（要么各域提供官方合并口径、首页只搬运；要么在 01/02 文档登记"运行总量"归首页所有）。

**8 审批待办 / 14 通知中心**
- 业务含义：把"等我办的事"顶到门面。角色：审批人/接收人。
- 必要性：**必要**（待办与消息是首页作为工作台的刚需）。
- 问题：**完全绕开 home 后端**，前端直连 approval/security API；#14 的 `markMessageRead` 使首页存在写动作（虽然语义上是 security 的合法命令）。home 架构文档宣称"首页读模型都经 /api/v1/home/**"在此不成立。
- 建议：**保留能力、归位接线**——要么并入 home 后端聚合端点，要么在图二正式登记 APR/SEC→HOM 边并承认"前端聚合也是首页的一部分"。

**9 质量告警面板 / 10 数据质量面板**
- 业务含义：图二 QUA-."质检结论".->HOM 虚线的兑现：健康度雷达 + 待处理问题 + 近 24h 告警。
- 必要性：**必要**（声明边，且"质量结论上首页"是治理闭环的展示端）。
- 问题：同一"质量"域走**两条不同通道**（#10 经 home Reader、#9 前端直连 quality），风格分裂；#10 有权限码保护而 #9（告警明细同样敏感）无对应权限边界校验（仅登录态）。
- 建议：**保留 + 并轨**（告警总览收进 home quality Reader 或同等权限门）。

**11-13 数据资产区（数据集/仪表盘/大屏/数据服务）**
- 业务含义：" produced 了什么"的货架预览。角色：数据消费者。
- 必要性：**较必要**（⑤段消费入口清单是首页合理职责）。
- 问题：仅数据集一列经 home 后端，仪表盘/大屏/服务三列全部前端直连各模块 API；大屏与服务是**全量列表拉到前端排序截 5**（接口无 limit 参数），数据量增长后首页加载先劣化在这里；home 后端为血缘/资产计数做的一切聚合无人消费（#18）。
- 建议：**保留 + 补服务端 top-N**（各模块 overview 端点带 limit，或收进 home 聚合）。

**15 调度中心日历**
- 业务含义："本月有哪些定时任务会跑"。角色：值班/运营。依赖：ScheduleManager 统一快照 + Quartz 重算。
- 必要性：**必要**（跨三域的统一调度视图在任何业务模块页都没有，唯首页提供——真正的增量价值）。
- 问题：①触发点由首页**自行用 cron 表达式重算**，不读调度器实际 next-fire——若任务暂停未同步 status、或触发窗口受 endTime 等运行时修正，日历会与真实调度漂移（代码已处理 startTime/endTime 元数据，但无法确认覆盖所有运行时状态，属"第二推算源"苗头）；②工作流条目点击跳 `/workflow/schedules`——**该路由不存在，必然 404**；③无"过去某月"数据边界（历史月 cron 照常重算显示，非事实回放）。
- 建议：**保留 + 改造**（取 ScheduleManager 的 next/previous fire 实际值替代重算；修坏链）。

**17 资源中心卡**
- 业务含义：文件仓库存量与活跃度。
- 必要性：**较必要**（①接入段的门面投影，权限门做得最完整：后端权限码+前端权限钩子+双端 unavailable 语义）。
- 问题：实现方式即已知线索所记私搭线；且 `tree()` 全表内存建树——首页每次加载为省一个聚合 SQL 而拖起对方全表。
- 建议：**保留能力、重构接线**（与《文件资源》文档结论一致：改 SPI/聚合 SQL 或图二补边）。

**18 血缘总览死载荷 / 19 Welcome 孤儿页**
- 必要性：**冗余（当前形态）**。#18 每次首页加载都真实查询 lineage 今日数据并拼装图结构，然后被前端丢弃——纯烧算力；#19 是脚手架残留，与 home 并存的第二个"欢迎页"概念。
- 建议：**二选一**——#18 要么前端把血缘微图卡渲染出来（数据已具备），要么后端删掉该块；#19 删除（R-1 先例：三重检查 + tsc 基线核对）。

## 4. 模块真实功能定位

- **实际角色**：两层组合投影——后端 Reader 聚合（8 端点）+ 前端直连聚合（6 个外域 API）。首页的真实"聚合面"比 home 后端大得多：**页面上 12 个数据板块里只有 6 个走 /api/v1/home/**。**
- **"只读总览"成立吗？后端层面成立**：零表、零写、零定时任务、GET-only、无 DAO 穿透（各域查询仍封装在各自 Repository 后面，home 未直接查别人的表——与 ARCHITECTURE.md 承诺一致，逐 Reader 核实）。**整体层面有例外**：通知卡片"点击即标已读"是经 security 接口的合法写动作；首页因此不是严格只读页（建议按"读为主、写经他域"如实登记）。
- **是否第二真相源？未存储性越界，但有两条"推算越界"苗头**：①调度日历自算 cron 未来触发点（真相属调度运行时）；②跨域合并指标（运行总量/平均耗时/环比）的口径定义权实际落在首页代码里。均未产生持久化副本，风险级别"中"，但放任会长。
- **是否越权聚合写入？** 无任何写端点、无命令方法（公共角色全为 Reader，`HomeArchitectureTest` 锁定）；不存在越权写入。
- **类型归类**：消费投影层（无自有领域）。
- **真实边界**：controller/v1 + 6 个 Reader 包；`HomeArchitectureTest` 只锁"角色注解+路由+ProjectScope+两个权限码"，**不锁依赖包白名单**——第 5 节的私搭线在测试上是漏网之鱼；模块三件套文档（ARCHITECTURE/DEPENDENCIES/REQUIREMENTS）均未收录 resource 包与 `/home/resources` 端点（文档漂移，后补的卡片没回文档）。
- **被谁依赖**：仅 boot 装配。职责无外溢。
- **明天下线的影响**：12 个板块全部消失但**零业务功能损失**（各板块数据源和跳转目标都在自己模块页存在）——首页是典型的"低耦合高体验"模块，下线风险 = 导航与值班效率下降，不是数据断裂。

### 5.3 交互风险与图外私搭线

1. **图二对首页的描述严重失真**：声明 2 条入边，实际后端 8 条 + 前端 6 条。首页是全平台**入边最多**的节点，却是文档上最"干净"的节点——这正是"图外私搭线"的温床。RES→HOME 只是已被发现的那一条。
2. **无 SPI 化、但边界质量不一**：home 自身纪律好（不碰 DAO、Reader 命名、ObjectProvider 全可缺席降级、有架构测试）；问题在治理框架没给它 SPI 通道——各模块只暴露 Spring Bean 形式的读侧，任何进程内消费者都要 pom 直依赖。**判据结论：首页不是第二"存储"真相源，但是最大的"编译期耦合"真相消费方**（7 个模块任一重构内部包结构，home 直接编译失败；`WorkflowExecutionOverviewReader.java:3` 式的类名耦合）。
3. **detailPath 坏链（已核实）**：后端 `HomeScheduleCenterReader.java:244`、`HomeDataCenterReader.java:476` 硬编码 `/workflow/schedules`，`navigation.ts:117` 实际路径是 `/workflow/definition/:id/schedule` 与 `/workflow/instances`——**工作流条目点击必进 404 页**。`/data-quality/execution/{executionId}` 传的是 id 而路由参数语义是 executionNo（前端 #10 用 executionNo），**是否错跳当前无法确认**，需运行时验证。
4. 口径分裂：数据中心"调度"（#7 两域）vs 调度中心日历（#15 三域）；质量数据双通道（#9 直连 vs #10 经 home）。
5. 权限不对称：cockpit/datacenter 把 quality **运行事实**（失败数/告警计数源）合并进总数展示，而该数据在 quality 模块自家页面受 `quality:execution:read` 门控——无此权限的用户在首页仍能看到含质量域的"运行中/失败"合计（**越权读取当前无法确认到具体数字级，但通道不对称是代码事实**）。

## 7. 模块现状总结

- **核心能力已闭环**：8 个只读端点 ↔ 12 个页面板块全部接真实数据，无 mock、无"前端有页面没后端"、无"接口存在页面未展示"的悬浮端点（唯一致死载荷是 assets 的 lineage 块，属"后端算了前端不要"的反向缺口）。定时任务与缓存：**皆无**。
- **图二声明边的兑现度**：WFL→HOM、QUA→HOM 两条声明边都真实存在且有页面消费；但真实交互面是声明面的 7 倍，前端还有一整张图二完全无法表达的直连网。
- **未闭环能力**：①调度日历用 cron 重算替代调度器事实；②跨域指标口径无归属登记；③坏链（/workflow/schedules）；④权限不对称；⑤home 三件套文档落后于 resource 卡片的加入（文档漂移）。
- **死代码/冗余**：Welcome.tsx 孤儿页；assets/overview 的 lineage 响应块（后端算+前端类型定义+零消费）；三个无 onClick 的"查看更多"按钮。
- **真实定位**：组合投影层/工作台首页，不是第二真相源（零存储），但有两条"推算/口径"越权苗头；下线只伤体验不伤数据。
- **实现质量画像**：防御式降级（ObjectProvider + try-warn-空值）全模块一致，6 个 Reader 均有单测、路由与权限有架构测试——是平台上"结构纪律"较好的模块，问题集中在**治理登记**（边、口径、文档）而非代码质量。
- **最大风险**：编译期直连依赖 7 个模块内部包 + 前端直连 6 个模块 API，全部未入图；下一次任意模块"内部重构"都会先撞碎首页，而按图评审根本查不到这条边。
- **最该补的 3 项**：①坏链修复 + 血缘死载荷收口（P0）；②取数边全量登记上图 + import 白名单测试（P1）；③调度日历改读实际触发时间 + 指标口径登记（P1）。
- **下一步**：把首页作为"图二维护纪律"的样板战役打：先登记（第 5 节表原样入 05 清单）、再拍板"前端直连是否算首页合法形态"、后做 SPI 化（可与各模块读侧收口合并推进）；顺手删 Welcome.tsx、修 detailPath。
