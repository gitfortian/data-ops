# 主数据 · 现状与能力分析

> 盘点日期：2026-09-21；依据：`docs/v1/04-主脉与模块交互图.md` 图二（横切B）+ 05 R-7 + 代码走查。后端 `yak-ops-business-mdm`（**130 个 Java 文件**，横切段最大），前端 `yak-ops-ui/src/pages/mdm`。

## 1. 模块概览

- 模块名称：主数据（MDM）
- 在主脉与模块交互图中的位置：横切B 治理段；声明边：SEM-.标准.->MDM、MDM-.变更审批.->APR、MDM-."复用同步搬运".->SYN；R-7 定性：真相=主数据档案（归B），采集借同步的道（②编排者）
- 上游模块：语义中心（标准）、数据源（经 sync 采集）；下游：审批中心（MDM_CHANGE）、消费方（自建分发/API）
- 模块一句话定位：**一个自带全套子系统（采集/清洗/质量/分发/API/审批）的垂直业务应用**，而不是挂在平台上的治理件
- 当前实现状态：**已实现（自成闭环）**——12 个 Controller、前端 10+ 页面、审批真接；同时是**平台复用契约的最大违例者**（直连 sync 内部 Service）
- 主要入口：前端 `/mdm/{overview,modeling,identification,cleansing,quality?,distribution,service,approval,source?...}`；后端 Mdm{Entity,Attribute,Record,Source,Collect,Clean,Quality,Distribution,Service,Governance,Approval,Overview}Controller

## 3. 子功能逐个分析

**实体/属性建模 + 识别规则**——MDM 的地基，角色：主数据管理员。必要性：**必要**（模块成立的前提）。问题：模型与语义中心六类标准的挂接深度未证实（风险同安全平行词表）。建议：保留 + 核实标准引用。

**记录 CRUD/清洗**——日常运营主面。必要性：**必要**。建议：保留。

**采集（借 sync）**——业务含义：从源系统定期抽主数据；角色：管理员。必要性：**必要**（R-7 认可的"编排在②"）。问题：**实现方式违例**——不走 SPI 直连 sync 内部 Service，sync 重构即波及；且采集对账失败时**无通知**（sync 盘点：实时/离线通知缺口波及 MDM 编排）。建议：**重构**（经 sync 对外 SPI 或 job 内核发布任务，锁版本）。

**自建质量**——业务含义：主数据完整性/唯一性校验。必要性判断：**冗余（形态）/较必要（需求）**——需求真实，但该走平台 quality 的四元组契约，而不是再造一套。建议：**合并**（迁到 quality 规则集，保留入口）。

**变更审批（MDM_CHANGE）**——必要性：**必要**；这是全平台唯一"发起入口+回调+业务页"三件套齐的流，反而证明审批中心其他四流没接完（样板价值）。建议：保留，输出为接入范式。

**分发 + 自建 API 服务**——业务含义：主数据推/拉到目标系统。必要性：分发**必要**；自建 Service API **冗余**——数据服务平台已具备 API 定义/发布/鉴权/限流/计量，MDM 再养一个对外接口层=两份鉴权两份台账（且不在资产账内，同大屏"查无此资产"路径）。建议：**合并**（分发目标走数据服务或 sync 落地）。

**驾驶舱**——必要性：**较必要**；建议保留。

## 4. 模块真实功能定位

- 实际角色：**独立主数据产品嵌在平台里**。它垂直自给（采集→质量→审批→分发→API），对平台横向能力只真用了审批一件。
- 关键节点：对主数据域内是关键；对平台主脉（数据旅程）是**旁挂**——不在①~⑤任何必经链上。
- 被强依赖：无（只有 sync 被它反向调用）。
- 类型：治理 + 执行 + 入口（自带对外 API）复合——**入口那一层是越界的**。
- 边界问题：与 quality、data-service、sync 三处重叠/越界（本盘点单模块最多）。
- 若下线：主数据业务消失，平台其余模块零感知——健康解耦的反证：它谁也没真用。

## 5. 与其他模块的交互关系

- 上游：SEM→MDM 当前无法确认实接（无 import 证据）⚠️；DS→MDM 经 sync ⚠️（越界直连）。
- 下游：MDM→APR ✅（唯一全闭环）；MDM→SYN ✅但违例；MDM→外部系统（自建 API）。
- 数据流：采集落 mdm 表→清洗→审批→分发；控制流：审批回调 MdmChangeApprovalHandler；事件/异步：采集复用 sync 批次机制；共享存储：**读 sync 内部实现**（最大风险点）。
- 其他：MDM 不在 AssetProvider 名单（台账缺席）；MDM 未接 lineage（主数据→消费方血缘断）。
- 风险点：①sync 内部类绑定=最脆弱依赖；②双质量/双 API 让"平台能力"与"域内能力"对不上账；③项目记忆提示其历史迁移曾卡 Flyway（V14 清遗留列），变更纪律要盯。

## 7. 模块现状总结

- 已实现核心：模型/识别/采集/记录/清洗/审批/分发/接口/总览全链可用。
- 未闭环：标准引用、通知。
- 接口无页面：部分内部服务。
- 任务无界面：采集批次借 sync（可接受）。
- 冗余/重复：**自建质量、自建对外 API** 两处；越界直连 sync 一处。
- 真实业务定位：垂直主数据应用，平台化程度低。
- 最大风险：**它是"平台能力不用、域内重复建设"的模板案例**——若不纠偏，下一个域模块会照抄这个姿势。
- 最该补齐 3 项：①sync 依赖合规化；②质量/接口并入平台件；③入账入血缘。
- 下一步：给 MDM 立"平台化改造"专票（P0 一项 + P1 三项），其余功能冻结扩张。
