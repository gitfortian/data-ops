## 与实时同步共用后端包的边界说明

`data-ops-business-sync` 是一个 **Maven 聚合父包**（`data-ops-business/data-ops-business-sync/pom.xml`），仅做打包聚合，本身不含代码。其下两个子模块：

- `data-ops-business-sync-offline`（本文档）
- `data-ops-business-sync-realtime`（见《实时同步-现状与能力分析.md》）

**边界判定**：两子模块 Java 包路径完全独立（`...sync.offline.*` vs `...sync.realtime.*`），经全量 import 扫描**不存在任何互相引用**；两者各自持有独立的 Controller、DAO、Flyway 目录与引擎网关。所谓"共用后端包"只发生在 Maven 聚合层与命名层，**代码层不共用任何类**。唯一交集是二者都依赖 `data-ops-business-datasource`（读连接/目录）。因此离线同步的能力与实时同步的能力可各自独立评估、独立下线，互不影响。

## 3. 子功能逐个分析

### 3.1 任务定义（草稿/单表/多表/上下线）
- 业务含义：用户配置"从哪个源表搬到哪个目标表、怎么映射列、失败怎么办"。角色：数据工程师。输入：源/目标数据源 ID、表、列映射、通道参数、重试策略。输出：`yak_offline_job_definition` 记录 + 编译后的 Link-Up `job_spec_json`。依赖：数据源目录（`DataSourceCatalogReader`/`DataSourceDao`）。交互模块：数据源、Link-Up 引擎、执行。必要性：**必要**——这是整个模块的入口对象。当前问题：单表/多表两套 saveOrUpdate 端点，脚本配置为死路由。建议：**保留**（脚本路由可**下线**）。

### 3.2 Link-Up 引擎对接（`LinkUpClient` + `LinkUpJobSpecFactory`）
- 业务含义：把逻辑 JobSpec 提交到外部 Link-Up 批量执行引擎并拉取状态/日志/指标。输入：`externalExecutionId`、`idempotencyKey`、`definitionVersion`、`jobSpec`。输出：`LinkUpJobResponse`（状态、metrics、commitSummary、transitions）。依赖：`yak.sync.offline.engine.base-url`。必要性：**必要**（这是"搬运"真正发生的地方）。当前问题：① Link-Up 服务端不在本仓库（本仓库仅 REST 客户端），平台能否跑批完全取决于外部引擎是否部署可达；② `OfflineSyncProperties.Engine.baseUrl` 默认 `http://127.0.0.1:18080`，本地占位。建议：**保留 + 补齐**（把 Link-Up 部署契约/健康检查/降级提示产品化；见第 6 节）。

### 3.3 Connector 能力发现与适配器
- 业务含义：按数据源类型动态生成配置表单/校验。角色：数据工程师。依赖：数据源插件、Link-Up connector discovery。必要性：**必要**。当前问题：适配器含 ClickHouse/Doris/StarRocks/ES/Mongo/JDBC/Passthrough，覆盖面依赖 Link-Up 端是否都实现——**当前无法确认**运行端是否支持全部。建议：**保留**，补齐端到端能力探测。

### 3.4 执行与重试（execute/cancel/retry/batch）
- 业务含义：一键/批量搬运一次，失败按策略重试。输入：`jobDefineId`、幂等键。输出：`batch_execution`→`job_execution`(attempt)。依赖：Link-Up。必要性：**必要**。建议：**保留**。

### 3.5 游标增量同步（`OfflineIncrementalPlanner`/`Cursor`）
- 业务含义：用已提交游标只搬增量，成功才推进，失败复用原上界（见前端 `SingleTableConfigSection:401` 文案）。数据存储：`yak_offline_sync_cursor`（CAS `state_version`）。必要性：**必要**（离线增量的核心价值，区别于全量重灌）。当前问题：仅覆盖单表向导文案，多表/分区场景增量边界需核实。建议：**保留 + 补齐**（增量在多表模式的可观测性）。

### 3.6 批次对账（`OfflineExecutionReconciler`）
- 业务含义：图二"对账"——核对 Link-Up 上报与本地状态、发现 lost/超时。必要性：**必要**（异步执行的最终一致性保障）。当前问题：后端能力，无独立"对账结果"界面。建议：**保留**。

### 3.7 调度（`OfflineScheduleHandler`）
- 业务含义：给任务挂 cron 定时自跑。依赖：框架 `data-schedule-api`。输入：cron/时区/启用位。输出：到点提交批次。必要性：**必要**。当前问题：与工作流调度是两条独立线（本模块任务级调度 vs 工作流编排调度），用户心智需区分。建议：**保留**。

### 3.8 补数 Backfill（后端有/前端无界面）
- 业务含义：对历史时间窗/分区批量回填。后端：`OfflineBackfillController` + `OfflineBackfillPlanner(300 行)` + Dispatcher，批次 `trigger_type=BACKFILL`。前端：batch-link-up 目录内 grep 无任何 backfill 调用（唯一"补数"UI 在 `pages/workflow/schedules/BackfillDrawer`，属工作流模块）。**判定：任务/接口存在，无界面**。必要性：**较必要**（离线场景常用）。建议：**补齐界面**或明确并入工作流补数、下线独立控制器。

### 3.9 失败通知
- 业务含义：最终失败/重试耗尽时通知用户。依赖：core `NotificationRouter`。必要性：**较必要**。建议：**保留**。

### 3.10 作为 SYNC 任务被任务目录/工作流复用（`OfflineSyncTaskProvider`/`Executor`）
- 业务含义：让离线同步任务像普通开发任务一样进 DAG。输入：`TaskVersionSnapshot`。输出：`TaskExecution`。必要性：**必要**（图二 JOB→SYN 契约的实现）。当前问题：仅"上线且未自带调度"的任务可被发现（`isWorkflowEligible`）。建议：**保留**。

### 3.11 审计（`OfflineAuditBridge`）
- 业务含义：操作/执行记录进审计域（图二 SYN→AUD）。必要性：**必要**（合规）。建议：**保留**。

### 3.12 主数据复用搬运（MDM 直连 offline 服务）
- 业务含义：MDM 采集借离线同步"这条道"搬主数据（图二 MDM-.复用.->SYN）。当前问题：MDM **直接 import** `OfflineJobDefinitionService`/`OfflineJobExecutionService`（`MdmCollectService.java:19-20`、`MdmProcessingTaskService`、`MdmQualityService`），是强编译期耦合而非 SPI 契约，违 S1/解耦精神。必要性：复用本身**较必要**；实现方式**需重构**（建议经 common 层契约）。

## 4. 模块真实功能定位

- **实际角色**：②段"批量搬运"的完整执行子系统，且是④段的"可被编排任务类型"、是主数据的"搬运复用底座"。
- **是否关键节点**：**是**。被任务内核/工作流、主数据、审计三处强引用；被前端两个隐藏路由（工作流/MDM 间接）依赖。
- **被强依赖点**：MDM 编译期直连；`TaskProvider`/`TaskExecutor` SPI；`OfflineSyncViewMapper` 相关 VO 位于 `data-ops-common`。
- **类型归类**：核心业务模块（非过渡、非冗余）。
- **真实边界**：真相域 = 离线同步任务定义 + 批次/尝试/游标/事件生命周期；不拥有连接（数据源）、不拥有编排（工作流）、不拥有审计存储（审计域）。
- **职责问题**：① backfill 有后端无前端，职责悬空；② MDM 直连其内部服务，边界被穿透；③ 脚本配置死路由。
- **下线影响**：整体下线将切断 MDM 采集、工作流 SYNC 任务类型、批量搬运能力——**不可轻易下线**。

## 5. 交互关系

- 上游：数据源（`DataSourceDao`/`DataSourceCatalogReader` 读连接与目录，`OfflineJobDefinitionRepositoryAdapter.java:5`、`OfflineIncrementalPlanner.java`）；任务内核（`io.yak.ops.business.job.task.*` SPI，`OfflineSyncTaskProvider`/`OfflineSyncTaskExecutor`）；主数据（`MdmCollectService.java:19-20`）。
- 下游（概念）：模型工作台——**代码层无对 modeling/lineage/asset 的直接依赖**；"落地表"通过写入目标数据源的物理表实现，模型侧收录属另一条线（当前无法确认是否自动登记为模型）。
- 横切：审计（`OfflineAuditBridge`，business-audit）；通知（core `NotificationRouter`）。
- 数据流：定义 → JobSpec 编译 → Link-Up 提交 → 引擎执行 → 状态/日志/指标回流 → 批次/尝试落库 → 游标推进。
- 控制流：调度框架 `ScheduleHandler`、工作流 TaskExecutor、手动 execute、MDM 复用四路触发同一执行内核。
- 同步/异步：提交同步、执行异步，靠 reconciler + event 收敛。
- 共享存储：自有 5 张 `yak_offline_*` 表 + 私有 Flyway 目录 `db/migration/yak-offline-sync`（V1~V5）。
- 风险：强依赖外部 Link-Up HTTP 服务；MDM 编译期穿透；异步对账窗口内状态不一致。

## 7. 现状总结（9 项）

1. 完成度：**高**（后端 ~16.5k 行、前端全套页面 + 执行/调度/增量/对账/重试/通知/审计）。
2. 与图二对齐：搬运、对账、JOB→SYN、审计、MDM 复用均有代码实证。
3. 最大风险：执行引擎 Link-Up 在仓库之外，可达性决定可用性。
4. 页面-接口一致性：绝大多数一致；backfill 接口有页面无（任务/接口存在无界面）；script 路由有页面无后端（已废弃跳转）。
5. 遗留/孤儿：前端 `definition-legacy.ts`/`task-legacy.ts` 引用了 `/api/v1/task-definition`、`/api/v1/copilot/ai`、`/api/v1/devops/client/*` 等端点，且经 `pages/.../api.ts`（标 `@deprecated`）再导出——属遗留兼容层，当前 batch-link-up 主流程走新 `services/batch-link-up/api.ts`。
6. 耦合越界：MDM 直接 import 本模块内部 Service（非契约）。
