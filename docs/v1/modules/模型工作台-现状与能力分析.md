## 1. 模块概览

模型工作台是数仓物理模型的**设计台账与治理工作台**：在项目空间内维护"模型主数据（目录/标签/业务域/分层/业务过程绑定）→ 表结构设计（列/主键/索引/分区/表属性）→ 标准治理（推荐/沉淀/映射）→ 版本发布（快照/回滚）→ 血缘登记/TTL 绑定"的完整元数据链路。

关键事实（均经代码核实）：

- **平台不执行任何建表**。`DdlService` 注释明确"Rendering only — the platform never executes the script (decision D3)"，Controller 文案亦标"仅生成，不在平台内执行"；全模块无任何对外部数据源的 DDL 执行通道（仅经 `DataSourceCatalogReader` 做只读 introspection）。
- **DDL 生成覆盖 6 种方言**（MySQL/PostgreSQL/Oracle/Doris/ClickHouse/StarRocks），commit `645b5705e` 标题写"骨架"，实际完成度高于"骨架"：每方言有独立渲染器 + 独立单测 + 类型目录，详见 3.6。
- **分层配置真身在语义中心**：预置模板 ODS/DWD/DWS/ADS 四层（`yak_semantic_layer_template`），项目可在语义中心自定义增删启停；modeling 只通过 `LayerConfigApi`（只读 SPI）消费。"分层可配置·预置四层"与代码一致。
- **模型生命周期状态为 DRAFT/PUBLISHED/DISABLED** 三态（`ModelStatus`），无独立"审批中"状态；审批通过回调直接执行发布。
- 与指标中心双向解耦成立（05 文档 S3 ✅）：metric 侧经 `ModelQueryApi` 消费模型；modeling 侧经 common 层 `io.yak.ops.common.api.metric.MetricQueryApi` 反推指标，`ObjectProvider` 优雅降级，编译期无反向依赖。

## 3. 子功能逐个分析

### 3.1 模型台账（CRUD/目录/标签/回收站）
- **业务含义**：数仓物理模型的唯一登记簿，挂目录、打标签、按分层/过程/域检索。
- **使用角色**：数据工程师（建模人）、数据架构师（审阅）。
- **输入**：名称/编码/方言/分层/业务过程/业务域/目录/描述。**输出**：模型卡片与列表。**依赖**：语义 SPI（过程/分层/域名称解析）、项目空间。**交互模块**：SEM（读）、MET（被投影）、APR/LIN/LIF（按模型 ID）。
- **必要性**：必要。模块一切能力的宿主实体。
- **问题**：新建向导方言硬编码 `MYSQL`（`ModelCreateWizardDrawer.tsx` handleNext），其余 5 种方言只能在详情"编辑"里改，与 ModelDialect 六方言能力宣称不完全对齐。
- **建议**：向导内开放方言选择或与逆向导入的数据源 dbType 联动（`constants.ts` 已有 `dialectOfDbType`）。

### 3.2 表结构编辑器（列/主键/索引/分区/表属性）
- **业务含义**：设计目标物理表结构，平台内真相源。
- **输入/输出**：全量字段清单 JSON→持久化列/索引表+结构 JSON。**依赖**：`StructureDialectCatalog`（类型约束）、语义标准字段（绑定时带出类型长度）。
- **必要性**：必要，工作台核心。
- **问题**：保存为全量替换、乐观无冲突检测（并发编辑互踩风险当前无法确认）；主键/分区/表属性持久化在 model 表列（V7），列扩展靠 ALTER 追加（V8/V12/V13/V17），列表已 10+ 扩展列，趋于肥大。
- **建议**：并发编辑加版本戳校验；列元数据考虑收敛为结构 JSON + 少量查询列。

### 3.3 逆向导入
- **业务含义**：把已存在的数据源表（含 SYN/RTS 落地表）纳入模型台账。
- **输入**：数据源 ID+表名列表；**输出**：模型+列+来源绑定+标准匹配；**依赖**：datasource `DataSourceCatalogReader`（JDBC 直读）+ 语义标准匹配（`StandardFieldMatcher`）。
- **必要性**：必要，是 04 图 "SYN/RTS→MOD 落地表"边当前**唯一**的实际通道（人工发起）。
- **问题**：无同步任务完成→自动建议建模的联动；每表独立事务但无失败重跑入口（前端按次操作）。
- **建议**：与 sync 落地事件做订阅式衔接（列入缺失能力 P2）。

### 3.4 派生建模（按业务过程）+ 3.5 指标反推草稿
- **业务含义**：ODS→DWD/DIM 继承、DWS 聚合、ADS 应用反推；DWS/ADS 支持选指标自动生成度量/维度候选并入结构。
- **使用角色**：数据工程师。**输入**：业务过程+目标分层（+统计周期/SCD/应用绑定/指标 ID）。**输出**：结构草稿+自动映射+血缘登记。**依赖**：SEM `LayerConfigApi/ProcessApi`、common `MetricQueryApi`（S3 解耦）、上游模型。
- **必要性**：必要，是"分层可配置"落地的证明；`DeriveLayerPolicy` 对自定义分层按不支持处理，保守正确。
- **问题**：反推草稿是"并入建议"而非可追溯的生成物（指标变更不会回流刷新已并入字段，仅靠 source-diff/impact 人工排查，且 source-diff 无界面）；ADS 应用绑定 app_code/app_name 为松散文本（V13），无目录约束。
- **建议**：优先给 source-diff 补界面（能力已在，见 3.12）。

### 3.6 DDL 多方言生成（重点核实对象，commit `645b5705e`）
- **业务含义**：按模型结构渲染目标方言 CREATE TABLE 脚本，供 DBA/开发手工执行。
- **逐方言完成度判定**（结论：**六个方言全部达到"可渲染完整建表脚本"级，不是只到接口层**；均有独立单测）：
  - **MySQL**（`MysqlDdlGenerator`，121 行）：内联列注释、UNIQUE/普通索引、ENGINE/CHARSET 表选项、HASH/KEY 分区直出、RANGE/LIST 提示补分区定义。✅完整。
  - **PostgreSQL**（107 行）：注释拆 `COMMENT ON` 后置语句、`CREATE INDEX`（支持 USING 类型）、RANGE/LIST 分区+子分区提示+分区键须含于主键的提示。✅完整。
  - **Oracle**（90 行）：表/列注释后置语句、索引独立语句、RANGE/LIST、双引号大小写折叠提示。✅完整。
  - **ClickHouse**（151 行）：`Nullable(T)` 表达可空、固定 `ENGINE = MergeTree`、ORDER BY 取主键、表达式分区、可空分区键/主键告警、data-skipping 索引跳过并提示。✅完整（引擎不代挑是明确取舍）。
  - **Doris/StarRocks**（各 18 行 + `AbstractOlapDdlGenerator` 121 行共用）：UNIQUE KEY / PRIMARY KEY 键模型、`DISTRIBUTED BY HASH`（桶数/副本数注释提示不编默认）、二级索引跳过提示、KEY 列序提示。✅完整（两兄弟同模板合理）。
  - 共性收敛件：`AbstractDdlGenerator`（引号/默认值/转义/hints）、`DdlTypeResolver`（跨方言类型偏好链换算，消灭 `BIGINT(20)` 在 PG 这类非法写法）。
- **仍属"生成器"而非"落地器"的边界**：仅覆盖 CREATE TABLE，无 ALTER/增量脚本；分区明细、桶数、副本数、CH 引擎、OLAP 二级索引均以注释提示交人补；`DdlService` 找不到模板方言会抛 `INVALID_DIALECT`（当前 6 枚举全覆盖，实际不触发）。
- **必要性**：必要。**问题**：无"结构变更→ALTER 脚本"能力；DDL 弹窗无 diff 对比。**建议**：后续版本发布联动生成 ALTER。

### 3.7 来源映射 + 分层字段映射
- **业务含义**：字段级血缘/影响分析的数据基础（19/43/45 票）。**输入**：目标列←来源表.列+转换表达式；标准字段在各层落地关系。**输出**：映射清单、by-field 反查。**依赖**：语义标准字段、模型结构。
- **必要性**：必要（impact、lineage、TTL 均间接受益）。
- **问题**：`TransformExpressionValidator` 只做语法校验，表达式不生成可执行 SQL，与"加工任务"占位一致——映射目前是**登记性数据**，不驱动执行。
- **建议**：与 DEV 打通前保持现状即可，勿造第二套 SQL 真相。

### 3.8 标准推荐/沉淀/使用上报
- **业务含义**：建模现场消费六类标准并把好设计反哺标准库。**依赖**：semantic 五个 SPI。**必要性**：必要（③段"标准→建模"顺序的落地）。
- **问题**：推荐"仅提示不阻断"，治理率提升靠自觉；主线视图（3.9）已提供覆盖度观测，闭环基本成立。

### 3.9 主线视图与影响分析
- **业务含义**：按业务过程看 ODS→ADS 各层覆盖；按标准字段/来源列查改动波及面。
- **必要性**：较必要（治理运营工具）。
- **问题**：**影响分析页面已上线但全站无入口**（路由 hidden、无任何跳转代码），主线视图有入口（列表页 Segmented）；影响分析实际处于"页面存在，入口缺失"状态。
- **建议**：P1 低成本修复——在主线视图过程节点、表结构编辑器标准字段列加跳转链接。

### 3.10 版本管理与发布
- **业务含义**：结构快照（列数/checksum/发布人），发布后结构只读、可回滚。
- **必要性**：必要。**问题**：版本仅存列清单（V16 `yak_modeling_model_version`），索引/分区是否完整入快照当前无法确认（`ModelVersionService` 未见独立 DDL 字段扩展）；发布**不做任何物理动作**，"PUBLISHED"语义=元数据盖章。
- **建议**：文档与 UI 文案持续明示"发布≠建表"，防止用户误解（详情页 DDL 弹窗已做）。

### 3.11 发布审批（MOD→APR）
- **业务含义**：MODEL_PUBLISH 审批流，批准回调同事务自动发布（`ModelPublishApprovalHandler.onApproved`），在途单唯一由审批中心 uk 保证。
- **必要性**：必要（05 文档"发布无闸"乱象的对治）。
- **问题**：**后端闭环完整、前端零入口**——`services/modeling/api.ts` 无 publish-approval 调用，`detail.tsx` 只有直发按钮；05 表#15 对建模审批标 ✅ 属"后端已实现"口径，页面链路未通。且常规编辑保存不经审批（仅发布可审批）。

- **必要性**：较必要。**问题**：注意 04 图箭头 "MET--数据目录-->MOD" 与代码方向相反（实为 MOD 供给 MET）；架构图应修订（列入第 6 节）。

## 4. 真实功能定位

**结论：模型工作台是"表结构设计台账 + 治理工作台"，不是"设计→物理化闭环"。**

判定依据：① DDL 明确"仅生成不执行"（决策 D3，`DdlService.java:14`、`ModelingModelController.java:137`）；② 发布=版本快照落库，无任何数据源写入代码；③ 平台不感知建表是否成功、无落地状态回写字段（`ModelStatus` 无 LANDED 类状态）；④ 与数据开发（物理化的自然承接方）的"加工任务"仅为 COMING_SOON 占位（`unified/index.tsx` L22，ticket 21/22）。

这不是缺陷而是当前定位：**元数据真相 + 标准治理 + 变更可追溯**的执行由人/DBA 完成。风险在于用户可能把"已发布"误读为"表已建好"。若未来要升级为物理化闭环，正确路径是打通 DEV（用来源映射生成 SQL 任务），而非在 modeling 内嵌执行器。
