# 数据安全 · 现状与能力分析

> 盘点日期：2026-09-21；依据：`docs/v1/04-主脉与模块交互图.md` 图二（横切A 质量与安全）+ 代码走查。后端 `yak-ops-business-security`（48 个 Java 文件），前端 `yak-ops-ui/src/pages/data-security`。

## 1. 模块概览

- 模块名称：数据安全
- 在主脉与模块交互图中的位置：横切A；声明边：SEC-."分级打标盖章".->AST、SEM-.标准.->SEC、SEC-."变更审批".->APR
- 上游模块：语义中心（标准——**实测断边**）；下游：数据资产（分级事实供数）、审批中心（ACCESS_GRANT 流）
- 模块一句话定位：分级分类 + 脱敏策略 + 访问授权的**配置与台账模块**（策略不落入任何执行链路）
- 当前实现状态：**部分实现**——页面与 CRUD 后端齐，但"安全执行"（脱敏/拦截在消费链路生效）未落地
- 主要入口：前端 `/data-security/overview|classification|masking|access|compliance|audit`；后端 10 个 Controller：SecurityLevel、DataCategory、Classification、Discovery、Masking、AccessPolicy、AccessDecision、AccessLog、Compliance、Overview

## 3. 子功能逐个分析

**安全等级+分类目录+打标**——业务含义：给数据定密级归类；角色：安全管理员。输入：人工选择；输出：分级标签事实。依赖：无外部；交互：资产（供数）。必要性：**必要**（盖章事实源）。问题：分类目录与语义 SECURITY 标准构成一词二义（本应有源）；打标对象覆盖范围（是否含数据集/API 列级）当前无法确认。建议：**保留 + 补齐**（改引语义标准）。

**自动发现（Discovery）**——按敏感特征扫描识别；角色：安全管理员。必要性：**较必要**（人工打标不可规模化）。问题：接线与深度当前无法确认。建议：保留观察。

**脱敏规则配置**——业务含义：定义列级脱敏算法；角色：安全管理员。输出：策略 JSON。依赖/交互：**无任何消费方**——查询链路（dataset/analysis）、API 发布（data-service）、问数（agent）都不读它。必要性判断：**冗余（以当前形态）**——一个不改变任何数据输出的脱敏模块只是安慰剂；它是"应必要而未闭环"。建议：**补齐执行点**（在 dataset 查询运行时与 data-service 响应渲染处挂脱敏 SPI），限期不补则页面降级标注"策略登记，暂不生效"。

**授权策略+ACCESS_GRANT 审批+访问日志**——业务含义：谁能访问什么的闭环申请制；角色：安全管理员、审批人、申请人。输入：申请单；输出：授权记录+日志。必要性：**必要**（平台权限叙事核心）。问题：授权决策是否被真实执行链路查询未证实（AccessDecision 无消费方证据）——即"批了也没人查"；另平台还有 system/permissions 权限体系，**两套权限并存**，边界未说明。建议：补齐（接入执行点）+ 与系统权限做职责裁决。

**合规检查/安全概览**——展示与自评；必要性：**较必要**；问题：概览若含 mock/恒零指标会误导（当前无法确认逐项真实性）。建议：保留，指标须来自真实计数。

**data-security/audit 页面**——又一处审计视图，与 system/operation-logs、system/oplogs 并存三处。必要性：**过渡**（入口整合前形态）。建议：**合并**入统一审计中心页。

## 4. 模块真实功能定位

- 实际角色：**分级标签台账 + 授权申请受理**；不是执行引擎。图二"SEC-.分级打标盖章.->AST"这条边是它目前唯一的横切实效。
- 关键节点判定：半关键——资产状态条依赖其供数，除此之外无人依赖。
- 类型归类：配置模块 + 治理模块。
- 真实边界：管标签、策略、申请单；**不管**任何数据读写路径。
- 职责过载/不清：与 system 权限体系职责重叠不清；"安全"名号大于实效（脱敏不落链路），易给管理者虚假安全感——这是本模块最大的定性问题。
- 若下线：资产状态条少一格事实；授权申请无处受理；其余无影响——反证其未进入控制链路。

## 5. 与其他模块的交互关系

- 上游：语义中心→SEC：**断边**（模块内 grep `import io.yak.ops.business` 除自身外零命中，自建类目树成立平行词表，04 图该虚线应标 ⚠️）。
- 下游：SEC→AST：✅（SecurityClassificationQueryApi，资产是唯一消费方）；SEC→APR：✅（AccessGrantApprovalHandler）。
- 数据流：只出标签事实；控制流：授权申请→审批→落策略表→（无人执行的）决策查询；事件：无；异步：无；共享存储：无。
- 风险点：①脱敏零执行=合规假象；②AccessDecision 与系统权限双轨；③平行词表随标准体系扩大会持续放大 R-5 类混乱。

## 6. 缺失能力分析

| 缺失能力 | 为什么需要 | 影响的业务场景 | 优先级 | 建议实现方式 | 依赖模块 |
|---|---|---|---|---|---|
| 脱敏在 dataset 查询运行时执行 | 否则脱敏页=假象 | 敏感列被任何消费者明文读取 | P0 | 查询结果渲染前挂 MaskingExecutor SPI | 数据集 |
| 脱敏/授权在 data-service 响应链路执行 | 对外 API 是泄露面最大出口 | 外部系统集成 | P0 | 网关响应过滤器 | 数据服务 |
| 接入语义 SECURITY 标准（弃自建类目） | 一词一义（S10） | 跨模块对账 | P1 | 改引 semantic 只读 SPI | 语义中心 |
| AccessDecision 执行点接入（消费链路鉴权） | 授权批了要真拦得住 | 行级/列级管控 | P1 | dataset/service 调用前决策查询 | 审批中心 |
| 自动发现扫描接线核实与补全 | 规模化打标前提 | 存量表 | P2 | 元数据遍历+规则识别 | 元数据 |
| 与 system 权限体系职责声明 | 双轨并存是治理债 | 沟通/审计 | P2 | 文档裁决：功能权限归 system，数据权限归 security | — |

## 7. 模块现状总结

- 已实现核心：分级/分类/打标 CRUD、ACCESS_GRANT 审批闭环、资产供数、访问日志。
- 未闭环：脱敏执行、访问决策执行、自动发现。
- 接口无页面：AccessDecision 查询 API、部分 Discovery 能力。
- 任务无界面：无。
- 冗余/重复：与语义 SECURITY 标准的平行词表；与 system 权限双轨；audit 页三处并存之一。
- 真实业务定位：标签台账 + 受理台，未进控制链路。
- 最大风险：**"安全已就位"的错觉**——10 个 Controller、6 个页面给人一种体系完备感，实际零拦截。
- 最该补齐 3 项：①dataset 脱敏执行点；②data-service 鉴权+脱敏；③接语义标准。
- 下一步：以"执行点清单"立项，每个策略页标注"是否生效中"。

## 8. 掌握度自检

本文档足以回答：安全模块的入口/表/Controller 全貌、三条声明边的真假（SEM 断、AST/APR 通）、脱敏零执行的定性。无法确认：打标对象覆盖面、AccessDecision 是否有 boot 层调用、合规页指标真实性、自动发现完成度。
