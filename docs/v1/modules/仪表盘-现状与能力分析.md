## 1. 模块概览

仪表盘是主轴⑤"消费与服务"端的**组合与发布层**：把分析（Analysis）产出的图表按栅格布局拼装成 Dashboard，附带全局筛选器、联动交互与主题，并以"追加式不可变版本 + 双指针（草稿/已发布）"的方式管理资产生命周期。它**不执行任何数据查询**（REQUIREMENTS 明示非目标），运行时由浏览器直连数据集查询接口取数。

- 后端：Maven 模块已接入 reactor（`data-ops-business/pom.xml:30`）并进入 boot 装配（`data-ops-boot/pom.xml:103`）。包结构：definition/read/change/version/publication/composition/gateway(analysis|dataset|lineage)/reference/lineage/repository(+codec)/dao/domain/controller/v1/config，分层由 `architecture/` 下 6 个架构测试守护（DashboardArchitectureDocumentationTest 等）。
- 数据：自有 Flyway **仅 1 段迁移、6 张表**（`V1__baseline_dashboard.sql`：yak_dashboard、yak_dashboard_version、yak_dashboard_widget、yak_dashboard_filter、yak_dashboard_filter_binding、yak_dashboard_interaction；前缀 `yak_dashboard*`）。全库再无其它迁移触碰这些表（已 grep 核实，仅 V1 两个文件命中，另一处为 target 编译产物）。
- 前端：路由 **4 条**（`navigation.ts:69-72`）：`/dashboard` 列表、`/dashboard/new`、`/dashboard/:id/edit` 编辑器、`/dashboard/:id` 查看（实为重定向到 `edit?preview=1`，`viewer.tsx`）；另有隐藏旧路由 `/data-analysis/chart-analysis` 重定向 `/dashboard`（navigation.ts:81 + `chart-analysis-redirect.tsx`）。页面约 57 个文件（主目录合计 ~8.8k 行，editor.tsx/use-dashboard.ts 两件套 655+753 行），与分析模块共享 `src/components/analysis`（查询模型/图表配置/运行器）。
- 定性：**"编辑-版本-发布"闭环真实且工程纪律高**（append-only 快照、XOR 绑定校验、项目空间隔离、血缘/资产投影）；**消费端出口弱**（无分享/外链/行级权限，跨筛选与下钻等前端能力存在"前端私有、后端不校验"的旁路地带）；与大屏的 R-4 核实见 §7。

## 3. 子功能逐个分析

### 3.1 版本-发布闭环（§2.3/10/11）——模块脊梁
- **业务含义**：把"看板改版"变成可回溯事实：每次保存产生不可变版本，编辑永不影响线上快照。
- **输入/输出**：输入完整 composition（widgets/filters/interactions/theme/activeDatasetId）；输出新版本行 + 指针移动 + `DashboardChangedEvent`（触发血缘重算）。
- **实现度**：**必要，达标**。机制三件套清晰：append（DashboardVersionAppender）、发布移指针（DashboardPublisher.java:40-58，等值时 no-op）、恢复=复制历史快照 append 新版本（DashboardVersionManager.restoreVersion:56-58）。`currentVersionId`/`publishedVersionId` 双指针独立是本模块明示的设计决策（README:99）。
- **问题**：①**无下线态**——发布后无法收回（对比大屏有 offline）；②无回滚为"直接发布历史版"的路径，只能 restore→publish 两步（可用但语义绕）；③每次保存即 append 版本，编辑器高频保存会让版本表无界增长，无保留/清理策略；④并发保存无乐观锁（nextVersionNo 竞争下依赖 DB 唯一键 uk_version_no 报错兜底，用户看到的是保存失败，**当前无法确认**是否有重试体验）。
- **建议**：与大屏统一"发布语义"时一并处理（见 §7 合并建议）；给版本历史加保留策略或压缩。

### 3.2 组件绑定：引用分析 XOR 内联分析（§2.5）
- **业务含义**：一条边支持两种消费姿势——复用 Analysis 资产（改分析全体看板跟随）或内联快照（看板自带图表定义，不被外部改动波及）。
- **实现度**：**必要、达标**。XOR 强校验真实（DashboardWidgetPolicy.java:52-57：linked==inline 即抛错）；两侧存在性校验走 Dashboard 自有 gateway（AnalysisDashboardAdapter→AnalysisReferenceService.requireExists；DatasetDashboardAdapter→DatasetReader.require），依赖走廊受架构测试保护（DEPENDENCIES 走廊：只准 gateway 触碰外模块）。
- **问题**：①linked 组件是"引用不锁版本"（README:49 明示 freeze reference not copy），Analysis 被改后已发布看板渲染随之改变，与"已发布快照不可变"的口径存在语义裂缝（快照冻结的是引用键，不是查询结果定义）；②**只挡 Analysis 删除、不挡 Dataset 删除**：inline 组件的 datasetId 与 analysis 自己的 dataset_id 断链后，看板运行时才报错（dataset 模块无任何反向守卫，grep 核实）。
- **建议**：为 dataset 删除补对 dashboard/analysis 的引用检查（对称化 DeletionGuard SPI）；评估 linked 组件是否需要"锁分析版本"选项。

### 3.3 内联分析与旁路（§2.6/8 的 inline 面）——本模块最大旁路
- **现象**：inlineAnalysis 是自由 JSON（≤64KB），后端只校验"对象形状+datasetId 若存在须真实"（WidgetPolicy:88-95），**不校验 chartType/querySpec/dashboardBehavior**。前端图表类型有 11 种（含 stackedBar/area/scatter/radar/funnel/treemap），后端 AnalysisChartType 只认 5 种且带基数规则（AnalysisChartBindingPolicy:10-31）——走 `/api/v1/analyses` 的引用路径受管，走内联路径的 6 种高级图表与跨筛选/下钻/点击跳转配置（direct-link-editor.tsx、model.ts 的 dashboardBehavior）**完全游离于后端契约之外**。
- **必要性判断**：内联模式本身**必要**（看板自带的临时图表是 BI 常识）；但校验不对称属**过渡**形态。
- **影响**：血缘提取器按"尽力解析、失败标 UNRESOLVED/PARTIAL"设计（DashboardInlineLineageExtractor:23-48），说明作者已预期脏数据；下游（血缘/资产指纹）对内联图表的口径只能尽力而为。
- **建议**：把 chartType 白名单与"metrics 必须 field+aggregation"两条最低限度校验加到 inline JSON 策略（不必复制整个 analysis 校验器）；长期考虑内联图表升格为"看板私有的不可见 Analysis"。

### 3.4 全局筛选与联动（§2.7/8）
- **实现度**：**较必要、达标**（对 5 种基础图而言）。筛选器/交互已规范化进独立表（filter/binding/interaction），版本快照完整；运行态筛选、SELECT 联动在前端真实工作（use-dashboard.ts:303-319 URL 预置、interaction-runtime.ts）。
- **问题**：两套联动语义并存——表结构的 Interaction（仅 SELECT→filter）与 inline JSON 里的 dashboardBehavior（crossFilters/clickAction/下钻）互不相干，前者受后端策略管、后者不受；且交互的 sourceField 只取"第一个主维度"（direct-link-editor.tsx:43-44 注释自认）。
- **建议**：合并为一套模型并补后端策略，否则 Interaction 三张表会被前端行为配置架空。

### 3.5 查看/消费出口（§2.11–13）
- **实现度**：**必要但薄弱**。查看口只有登录态项目内路由（/dashboard/:id→preview 模式，读 published 快照）；数据靠浏览器直查 dataset API。**无分享、无外链、无匿名访问、无行级权限、无导出**（后端零实现、前端零入口；grep 分享/share/embed 无功能命中）。`?df=&dv=` 只是筛选预填，不是分享机制。
- **建议**：作为⑤段消费门面，只读分享链接（token 化、项目内、可过期）是仪表盘区别于分析/大屏的最优先补强项。

### 3.6 血缘与资产投影（§2.15/16）
- **实现度**：**必要、达标**，且是同类模块中做得最全的：不仅投影 DASHBOARD 资产，还把每个组件合成 CHART 资产（linked 复用 `chart:analysis:{id}` 键、inline 造 `chart:dashboard:{id}:widget:{k}` 私有键），inline 再向上接 DATASET/DATASET_FIELD CONSUMES 边（DashboardLineageSynchronizer.java:41-86,160-276）。afterCommit+REQUIRES_NEW+fail-open，asset_key 与资产台账同源（:340）。
- **问题**：血缘按"生效快照"（published 优先）登记，草稿态在图中不可见——设计使然但需在读图侧周知；内联字段解析 best-effort，UNRESOLVED 时图面缺边是预期行为。

### 3.7 前端工程现状
- 编辑器（editor.tsx/use-dashboard.ts）承载 12/19 个子功能，单文件 655+753 行，配套 finebi-chart-builder/sheet-bar/config-* 等；`services/dashboard`（api/document/overview/performance/theme/types）与后端 DTO 一一对应，wire 层做了 long-id→string、操作符映射、normalizeDashboardDocument 容错——前后端契约质量高。
- **重复/遗留件**：`pages/data-analysis/dashboard/dashboard-service.ts` 是 `@deprecated` 转发壳（指向 `@/services/dashboard`）；`api.ts` 内每个函数保留 `fetchXxx` 兼容别名；`viewer.tsx` 只剩重定向。均**冗余（过渡件）**，归前端 services 层，建议下个迭代删除别名。
- **localStorage 私有态**：sheet 备注/隐藏（sheet-bar.tsx）、编辑器草稿暂存（use-dashboard.ts STORAGE_KEY）、旧主题缓存——服务端模型没有这些字段，属"页面已展示但真相不在库"的账实不符项。

## 4. 真实功能定位

**仪表盘=已发布组合快照的 BI 工作台**，这个定位成立且落地扎实：它拥有自己的真相（composition 与版本指针）、不复制上游真相（分析归 analysis、数据归 dataset）、投影治理事实（血缘/资产）也守规矩（同源键、fail-open）。

**与大屏并存是否成立？** **当前成立，但理由不是 R-4 猜的"两者重复"，而是两者实际做的是不同的事**：
- 仪表盘：后端强契约（6 表规范化 composition + XOR 校验 + gateway 走廊）× 分析资产复用 × 交互分析（筛选/联动/下钻），面向**分析师日常查看**；
- 大屏：后端弱契约（一坨前端私有 bindings_json）× 前端模板引擎 × 轮询监控运行时，面向**展示墙/指挥中心**（详见《大屏-现状与能力分析》§4）。
两模块在**机制层**（发布生命周期）各写一套且语义相反（§7 R-4），在**运行层**（查询执行、缓存、去重）也各写一套（components/analysis/query-runtime vs pages/digital-screen/runtime）；但在**场景层**互不替代。并存的代价不在功能重复，而在机制重复——治理动作应是下沉共用零件，而不是合并页面。

## 7. 现状总结（九项）

1. **一句话定位**：仪表盘=主轴⑤的组合与双指针发布工作台——composition/版本/血缘/资产四件事都是实的，查询执行按设计外包给数据集前端直查。
2. **最扎实的部分**：版本-发布机制语义（append-only+双指针+restore 即新版本）、XOR 绑定校验与 gateway 依赖走廊（含架构测试守护）、血缘投影（三级资产+同源 asset_key）、前后端 wire 契约质量。
3. **最大空洞**：消费出口（P0 之一）。发布做得很正式，但发布之后没有"给谁看"的答案——无分享/外链/权限/导出，查看仍要进编辑器预览态。
4. **旁路取证结论**：存在两条旁路——inlineAnalysis 直绑数据集（后端不校验查询内容，§3.3）与前端私有联动配置（dashboardBehavior 不进后端模型，§3.4）；但均**未触及裸 SQL/数据源直连**，所有取数仍必须经数据集查询 API，"数据真相归 dataset"底线未破。
5. **R-4 核实结论（与《大屏》文档同一结论，互为印证）**：**机制各写一套，且不是同一套语义的重复，而是方向相反的两种设计**——逐文件比对：仪表盘"草稿即不可变版本（每次保存 append，发布只移指针），无状态列，无 offline/rollback"（`DashboardVersionManager.java`/`DashboardPublisher.java`/`V1__baseline_dashboard.sql:8-11`）；大屏"草稿即可变单行（PUT 原地更新+revision 自增+status 列），发布才生成不可变版本快照，另有一等公民 offline 与 rollback"（`DigitalScreenApplicationService.java:67-78`/`DigitalScreenPublisher.java:24-73`/`V1__baseline_digital_screen.sql:10-15`）。共用性检查全部落空：①无公共基类/service（全仓 grep publish/draft/version 抽象仅命中 asset 的 `AssetProvider` 接口——且只有 dashboard 实现，digitalscreen 无任何跨模块 import）；②各自 Flyway（`yak_dashboard*` vs `yak_digital_screen*`，互不引用）；③表结构形状不同（6 表规范化 vs 2 表 JSON 文档）；④发布事务策略不同（`@Transactional("yakBusinessTransactionManager")` vs 默认事务+`FOR UPDATE` 行锁）。**合并建议**：不要为"合并"而合并页面（场景不同，§4）；把可下沉的公共零件限定为三件——版本号分配+不可变快照落库（两模块的 VersionRepository 逻辑同型）、发布指针/下线态转移（统一"offline/rollback"语义词汇表）、前端查询运行器（analysis/query-runtime 与 digital-screen/runtime 的 planner/cache/concurrency 收敛为一件）；若平台先给大屏补资产台账/血缘投影（其 P0），仪表盘作为该公共契约的现成参照，两边合流成本最低。
6. **闸门现状**：发布无审批（图上亦无 DBH→APR 边，自洽）；项目空间隔离+权限码（menu code `dashboard`）是唯一防线。
7. **前后端错位清单**：后端有、前端弱：versions 无保留策略下的抽屉性能；前端有、后端无：sheet 元数据、编辑器暂存、dashboardBehavior 联动、高级图表 6 型（**页面已展示、服务端不保管/不校验**——账实不符主清单）；已 deprecated 未下线：activate 端点、dashboard-service.ts、fetchXxx 别名。
8. **孤儿/冗余面**：与大屏的重复主要在前端运行层与发布件（§5 之 5.7 交叉引用）；模块自身冗余为兼容壳，低风险。
9. **风险提示**：README/REQUIREMENTS/DOMAIN 与代码高度一致（罕见的自曝式文档，non-goals 清单可直接当治理基线用）；引用本模块时注意其"生效快照=已发布优先否则草稿"的回落语义（EffectiveSnapshotReader），血缘与预览看到的可能是不同版本。
