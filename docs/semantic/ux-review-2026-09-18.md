# 语义中心页面交互体验改进清单

时间：2026-09-18 深夜 ｜ 环境：`http://localhost:8000`，项目空间「默认空间」，root 账号
背景：借这次给默认空间灌 27 个业务域 / 23 个业务过程 / 148 个标准字段的机会，逐页走了一遍语义中心的五个入口（数据标准、业务域、业务过程、标准字段、数仓分层），记录实际卡点。
标注：**[实测]** = 在页面上复现到；**[代码]** = 页面无法操作（浏览器画布被隐藏）时从源码确认。

优先级口径：P0 影响数据正确性或让人无法继续；P1 明显增加成本；P2 打磨项。

---

## A. 会让人拿到错数据的（P0）

### A1. [实测] 业务过程「引用标准字段」的**是否必填永远显示「可选」**

- 现象：`/semantic/processes/1/edit` → 引用标准字段 Tab，`order_id`、`cust_id` 等 12 个字段全部渲染成「可选」。
- 证据：接口 `GET /api/v1/semantic/processes/1/fields` 明确返回 `"required": true`。
- 根因：`yak-ops-ui/src/pages/semantic/processes/edit.tsx:576` 读的是 `record.isRequired`，后端 VO 字段名是 `required`；本地类型 `edit.tsx:76` 与 `services/semantic/types.ts:165` 也跟着写成了 `isRequired`。
- 影响：用户在这个页面**无法判断哪些字段是主键/必填**，会误以为之前配的必填没生效，进而重复编辑、或干脆不信这个列表。
- 建议：列渲染改 `record.required ?? record.isRequired`，类型统一为 `required`。绑定弹窗表单项 `name="isRequired"`（`edit.tsx:657`）是提交用的，可保留，但要确认后端接收名一致。

### A2. [已修复] 业务过程「关联源表」的数据源名退化成 `数据源 #2`

> 2026-09-19 复查更正：本条原结论把 999 归因于前后端，**是错的**。真实根因在本次灌数脚本自己写坏的数据。

- 现象（当时）：Tab 内三行绑定都显示 `数据源 #2`，而不是「订单库」。
- 真实根因：`harness_semantics.py` 克隆 dws/ads 数据源时把 `conn_status` 写成 `'SUCCESS'`，而 `DataSourceConnStatus` 只有 `UNKNOWN/CONNECTED/DISCONNECTED` 三个常量（`yak-ops-common/.../enums/datasource/DataSourceConnStatus.java:11-15`），`parse()` 直接 `valueOf` → `IllegalArgumentException`。`environment='DEV'` 侥幸能过（`DataSourceEnvironment.parse` 有 DEV→DEVELOP 别名），`jdbc_url` 则是 `replace("/dwd?", …)` 对无查询串的 URL 是空操作。
- 影响半径比预想的大：这一行脏数据不只让自身不可用，而是让 **`POST /api/v1/data-source/page` 整个列表接口返回 999**（PO→VO 逐行转换，任一行抛异常即整体失败）。前端 `edit.tsx:150` 又把这个失败 `.catch` 成空数组，于是所有数据源名统一退化成裸 ID。
- 已做：① 数据修正 16/17 的 `conn_status='CONNECTED'`、`environment='DEVELOP'`、`jdbc_url` 指向 `dws`/`ads`；② 脚本改为以 `connection_params` JSON 为唯一来源重建连接配置（不再用字符串 replace），并把枚举真名写死 + 注释说明踩坑原因（`harness_semantics.py:468-471`）。
- 实测（2026-09-19）：`/api/v1/data-source/page` → `code=200`、14 条；`/semantic/processes/2/edit` 的「关联源表」Tab 正确显示 `订单库 / trade_order / 主表`、`订单库 / trade_order_detail / 明细表`、`商品库 / item_item / 维表`。

**本条留下来的两个真问题**（这才是要改的，降级为 P2）：

- **前端静默吞错**：`edit.tsx:150` 的 `.catch(() => setDatasources([]))` 把任何失败变成空数组，界面既不报错也不给重试入口，兜底文案 `数据源 #${id}` 对用户零信息量。建议改为 `数据源未加载 · 重试` + `message.warning`。
- **后端整表被单行脏数据拖死**：列表转换没有按行隔离，一条不合法的枚举值能让 14 条数据全部查不出来、且只回一句"操作失败请稍后重试"。建议转换失败按行降级（该行标记异常态）而非整页 500，同时 999 要带可定位的原因。

### A3. [实测] 项目空间错位时页面不给任何提示，看起来像"数据丢了"

- 现象：默认工作空间是「测试项目空间」(project_id=2)，业务域页只有 1 个根域、数据源列表为空；切到「默认空间」(project_id=1) 后才是 12 个根域、12 个数据源。
- 影响：语义中心、建模、数据源三个模块的数据都按项目空间隔离，但页面标题区只显示空间名，空态文案是「还没有业务域 / 点击右上角新建根域」——**把人往"重新录一遍"的方向带**。
- 建议：空态区分两种情况：当前空间确实无数据 vs 其他空间有数据。后者文案给「切换到有 N 条数据的『默认空间』」的直达入口。

### A4. [代码] 业务域拖拽落到"节点间隙"会被静默改成根域

- `domains/index.tsx:163-166`：`dropToGap` 分支弹的是「已按同级处理；如需微调排序，请在编辑表单中修改排序值」，但紧接着执行 `moveSemanticDomain(dragId, undefined)` —— 传 `undefined` 父级即**移动到根层级**，不是"保持同父"。
- 影响：想调个顺序，结果把「订单」从「交易域」下面拽成了根域，提示语还说没事。树层级是建模主线的骨架，这种静默改层级最难被发现。
- 建议：间隙落点应解析出目标父节点与插入位置，或干脆先禁用间隙拖拽（只允许 drop 到节点上），排序仍走表单。

## B. 明显增加操作成本的（P1）

### B1. [实测] 业务域树 `defaultExpandAll` 对异步数据无效

- 现象：27 个域，页面只渲染 13 个节点（12 个根 + 1 个隐藏无障碍节点），子域全部折叠。
- 根因：`domains/index.tsx:210` 用 `defaultExpandAll`，而数据是 `useEffect` 异步 `loadTree()` 之后才进 `treeData`，antd 只在首次挂载时读这个属性。
- 建议：改成受控 `expandedKeys`，首次加载完成后展开所有"有子节点"的域；并加搜索框（27 个域已经开始需要滚动查找了）。

### B2. [实测] 业务过程列表没有关键字搜索，23 条已经开始翻页

- 现状：只有「全部业务域」「全部类型」两个下拉，列里有 编码/名称/描述，却没有搜索框；分页固定 10 条/页。
- 影响：语义体系铺开后（本次 23 个过程，按 9 个业务域继续铺开很快上百），找一个过程要点 3-4 页。
- 建议：加编码/名称模糊搜索 + 分页可切换。标准字段页 148 条同理，且更需要。

### B3. [代码] 标准字段页有「启用/停用」状态列，但没有对应操作

- `fields/index.tsx:282-285` 渲染了 启用/停用 Tag，但行操作里没有切换状态的按钮，`status` 只能靠接口改。
- 影响：字段口径作废时无法在页面上停用，只能删（删会被引用关系挡住）或走接口。
- 建议：行操作补「停用 / 启用」，并在停用二次确认里显示被多少业务过程引用。

### B4. [代码] 「初始化预置标准」按钮一旦有数据就再也进不来

- `standards/index.tsx:114` 注释写明：只在"空列表且未筛选"时才查初始化状态并展示按钮。
- 影响：预置标准分 6 类（命名/类型/码值/口径/安全），用户先手工建了 1 条类型标准，就再也无法一键补齐其余骨架。本次灌数时码表缺 `settle_cycle`、`order_channel`，就没法增量补预置。
- 建议：按钮常驻（放在「新建标准」旁边），文案区分"首次初始化"与"补齐缺失分类"，并做幂等（已存在的 std_code 跳过）。

### B5. [实测] 数仓分层初始化后 DWS/ADS 没有数据源与库名，页面不提示"未配置"

- 现状：ODS/DWD/DIM 建好即带 `datasource_id`，DWS/ADS 两行是 `null`；我在库里补了 dws/ads 数据源并回填后，建模的 DWS/ADS 才有落库位置。
- 影响：用户在建模工作台选 DWS 建模型，走到保存/发布才可能报错，而报错点离配置点很远。
- 建议：分层列表对 `datasource_id` 或 `database_name` 为空的行加醒目「未配置」标记 + 行内直达配置；预置分层时若同名数据源不存在，给"去创建"而不是留空。

### B6. [实测] 已绑定的关联条件只能看自由文本，改不动

- 现象：`关联源表` Tab 里 `d.order_id = t.order_id` 以纯文本展示，只有「解绑」。
- 但 `edit.tsx:434-475` 已经实现了「关联表 / 本表字段 / 目标字段」三段选择器——只在新增时用。
- 建议：已绑定行走同一套选择器做行内编辑，避免"改条件 = 解绑 + 重新绑一遍"。

## C. 反馈与文案（P2）

### C1. [实测] 错误提示用猜测掩盖真因

- `domains/index.tsx:124`：`message.error('保存失败（编码可能已存在），请检查后重试')` —— 任何异常（网络、500、校验）都归因到"编码可能已存在"。
- 建议：透出后端 `message`，只在业务码明确是重复时才提示冲突。

### C2. [代码] 服务端对 `std_unit_id` / `std_security_id` 不做存在性与类别校验

- 灌数时必须自己先比对 `yak_semantic_standard` 的 `kind` 才能保证引用正确；接口层没有这道保护。
- 风险：单位挂成"重量"、安全分级挂成"类型标准"这类脏引用可以静默写库，而下游 DWS 口径推导会直接错。
- 建议：保存时校验 `std_*_id` 存在、`project_id` 一致、`kind` 匹配（TYPE/UNIT/CALIBER/SECURITY 各归各位）。

### C3. [实测] 业务域详情面板信息太薄

- 现状：右侧只给 名称/编码/描述/负责人 + 编辑删除。
- 建议：补「本域下业务过程数」「关联标准字段数」「关联模型数」三个可点击计数，点开直接筛出对应列表——业务域是建模主线入口，现在要自己去业务过程页按域过滤。

### C4. [实测] 刷新页面会掉登录

- 现象：在 `/semantic/domains` 做一次带 `ignoreCache` 的 reload，直接跳 `/login?returnTo=/semantic/domains`，需要重登。
- 影响：调试期间高频刷新时反复登录。`returnTo` 处理是对的。
- 说明：未能确认是 idle-timeout 还是 token 存储位置问题，留待跟进。

## D. 建议处理顺序

1. A1（必填显示错误）——一处前端改动，收益最直接。
2. A4（拖拽静默改层级）——数据破坏型，且用户无感知。
3. A3 + B1 + B2（空间提示、树展开、搜索）——语义体系铺开后最先痛。
4. B3/B4/B5/B6 —— 补齐"页面能做完闭环"的缺口。
5. C 类随手带上。
6. A2 残留两问（前端静默吞错、后端单行脏数据拖垮整表）—— P2，但"一行坏数据让 14 条全查不出来"值得顺手加固。

> 2026-09-19：A2 主体已闭环（灌数脚本脏数据修复 + 脚本防复发），不计入待办。
