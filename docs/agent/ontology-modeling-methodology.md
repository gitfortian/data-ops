> 日期：2026-09-04 | 状态：方法论 v2（grilling 讨论定案后修订）

## 一、为什么需要这份方法论

建模实操复盘确认的三个病根：

1. **四套建模传统混用而无主线**：Kimball 维度建模（事件/粒度/角色）、DDD 本体论（实体/类型/标识）、语义层指标理论（原子-派生-复合）、Agent 工程（aiContext/use_rule）——层次不可见；
2. **表单驱动而非问题驱动**：起点"要回答什么业务问题"从未出现；
3. **字段的消费者不可见**：aiContext 给 AI、粒度给编译器、场景分类给 Agent 路由——界面从未说明。

v2 的解法 = 一条主线（事件优先）+ 一个换轨点 + 三条贯穿线 + **三层表达规范**（新增，回答"交互过程与结果怎么表达"）。

## 二、总框架

```text
━━ 上半场 · 概念层（白板/纸面为主）━━
定边界 → 【抽事件 → 抽实体】(并列两小步,事件在前) → 定类型(确认粒度) → 建层级 → 抽关系
                                                                    （验证① 概念一致性）
         ★换轨点:定类型把名词二分为「事实(事件)」和「实体」
                  事件 → 走分析线(绑定业务实例);实体 → 走主数据线

━━ 换轨:业务问题清单（每个问题 = 事件 × 度量 × 维度 × 时间）━━

━━ 下半场 · 分析层（问题驱动,按优先级落地）━━
事件绑定业务实例(数据集) → 字段翻译(角色+字段说明) → 原子指标 → 派生/复合
→ 旅程登记(把事件串成用户故事,Flow 承载)
                                                （验证② 问题回放 + 对数）

━━ 能力层 · AI 能做什么 ━━
术语（黑话→口径）· 场景分类 · 函数（只读计算）· 动作（写语义:AI 推荐+人工审核）
```

三条**贯穿线**叠在主线上：**例外**（算什么不算什么）、**动作**（动态世界）、**验收标准**（怎么算做完）。

## 三、主线（六步，v2 事件优先）

### 1. 定边界

- **产出**：业务域范围说明、与相邻域分工。**落点**：业务域。**消费者**：Agent 检索范围、权限。
- **判据**：任意业务名词能唯一归入一个域。**常见错误**：按组织架构划域；边界重叠。

### 2. 抽事件 → 抽实体（v2 调整：事件在前）

- **抽事件**：列出"这个域里会发生哪些事"——发券、领券、浏览、加购、下单、支付……每个事件将落为一个事实。**为什么在前**：分析建模的全部纪律从事件出发（Kimball 第一原则）——**事件决定粒度，粒度决定一切**；实体清单可以从事件和问题反推。
- **抽实体**：列出"被谈论的东西"——用户、商品、券……伴随两问："它身上会发生什么动作？"（补事件）"它有哪些例外规则？"（补贯穿线一）。
- **动词归并判据（v2 新增）**：动词要不要独立成事件，**看它是否独立成行出现在数据里**——一行数据承载多个动词时（如"发放记录+核销时间"同行），后到的动词是**状态**不是事件，不单独立。例：领券并入发放（同一行）、支付并入下单（订单状态区分）。
- **常见错误**：一个动词一个对象（数据集粒度被撕碎）；把动作挂成实体。

### 3. 定类型（★换轨点）

- **产出**：事件确认粒度（**一行数据 = 一件什么事**）；名词二分为事实（PROCESS）/ 实体（ENTITY）/ 值对象（VALUE）。
- **判据口诀**："这一行是不是一件发生的事、且要算数？"是 → 事实。
- **常见错误**：为挂指标硬造无业务含义的事件；把事实当主数据建。

### 4. 建层级

- **产出**：维度层级（类目一级→二级、省→市、会员等级序）。**消费者**：上卷查询。**现状**：产品无 UI（G-5，批次 2），先写进相关属性的 aiContext。

### 5. 抽关系

- **产出**：静态归属路径（含基数、join 条件），**含自引用形态**（用户—用户邀请关系，v2 案例新增）。
- **边界澄清（v2 强调）**：**交互（动词）是事实本体，不是关系**；关系是让事件和实体能连起来查询的静态路径。
- **判据**：关系能被业务语言复述（"订单属于用户"）；两侧字段已锚定再抽（ANCH-1 命中率）。

### 6. 验证① 概念一致性

- **产出**：实体可标识、关系可复述、边界不重叠、类型过口诀、例外清单收全、**动作清单收全**（贯穿线二）。纸面走查。

## 四、贯穿线一 · 例外（口径与规则）

未显式化的例外 = 口径事故。三级落点：

| 层级 | 含义 | 落点 | 现状 |
| --- | --- | --- | --- |
| 指标口径例外 | 算什么不算什么 | businessFilterJson | 后端有、UI 无（G-3） |
| 属性取值域约束 | 字段合法值 | requires_json | 后端有、UI 无（G-4） |
| 数据级例外 | 脏数据/爬虫/去重 | 质量模块，本体侧记入字段说明 | — |

纪律：抽事件/实体时同步收集（"什么情况下不算数？"）；例外必须在指标定义处显式化。

## 五、贯穿线二 · 动作（动态世界）

- 动作与事件孪生：**动作产生事件**（推券动作产生券发放记录与埋点事件）；动作清单反向校验实体完整性。
- **执行模式（v2 定案）**：**AI 推荐 + 人工审核**。Agent 基于模型生成动作建议（推谁/推什么/走什么渠道 + 理由 + 其他选项），人工确认后执行；全自动白名单（LOW 风险+预算限额）留待治理三件套里程碑。
- 落点：ACT-1 登记（参数/效果/风险级）；执行被拒（ACTION_NOT_EXECUTABLE）在治理上线前是预期行为。

## 六、贯穿线三 · 验收标准（怎么算做完）

| 产物 | 验收条款（可判定） |
| --- | --- |
| 对象 | 属性全锚 + 标识唯一定位 + 样例回放 |
| 指标 | 对数标准（误差阈值）+ 口径例外清单完备 |
| 旅程 | 旅程步骤与状态流转经业务方确认 |
| 域 | 问题清单逐条回放可答 |
| Agent 端 | 盲评通过率（D3 口径） |

**追溯性门禁**：产物与问题双向可追溯，答不出归属 = 过度建模，进裁剪清单。
**建模完成的唯一定义**：问题回放全绿 + 对数通过。

## 七、三层表达规范（v2 新增 · 交互过程与结果怎么表达）

> 回答的问题：**"用户领券了就是能查到可用券、用户支付了就是订单状态变 paid——这些怎么让 AI 理解？"**
> 原则：不加新建模对象，三层各有载体，用**大白话写作规范**约束质量。

| 层 | 表达什么 | 载体 | 写作规范 |
| --- | --- | --- | --- |
| ① 事件层 | 发生了什么 | 事实对象（动词） | 按数据集归并（见主线第 2 步判据）；粒度=一行是什么事 |
| ② 状态层 | 现在怎样 | 实体状态字段 + **状态机说明**（aiContext） | **三问模板**：这个字段有哪些状态？什么动作会让它变？变成什么？→ 拼成一段话。例："订单状态：待支付→已支付→已发货→已完成；用户付款后从待支付变成已支付" |
| ③ 旅程层 | 整条链怎么串 | 业务流程（Flow）：步骤=事件对象有序排列 | 每步 note 模板："本步发生什么事件 → 哪些对象状态如何变化"。例："用户付款：订单 待支付→已支付，券 未使用→已核销" |

**小王的故事（贯穿示例）**：8月1日平台给小王发 10 元券（券发放明细 +1 行）→ 公众号点开（埋点 +1：点击/公众号）→ 领券（可用券 +1）→ 8月3日浏览加购（埋点 +2）→ 8月5日下单支付 100 元用券（订单明细 +1：实付 90 优惠 10；发放行补核销时间；订单状态=已支付）。**交互过程 = 明细表按时间多出来的行；交互结果 = 状态字段的值变了**。建模人只在三处各写一句大白话，查询与推理 AI 自行完成。

**产品承载**：状态层"预拟+确认"（批次 1 设计：StatusGuideForm）；旅程层用现有 Flow 登记（零开发）。

### 交互宪法（易用性五则 · 2026-09-04 产品主定调，约束一切建模界面）

> 前提：使用者业务能力强、**技术零基础**；语义素材的最终读者是 AI。据此五则，按序裁决每一个输入项：

1. **可推断的，绝不问**——编码自动生成、角色按字段类型预判、主键按 id/单号模式自动识别、时间按日期类型自动处理；
2. **能选的，不填**——枚举类一律选择器，选项必须是业务词；
3. **需叙述的，"预拟 + 确认"**——系统先拟一段大白话，人只改；描述比表单灵活，因为语义本来就是给 AI 的话，表单是给人填的格子；
4. **零术语**——角色/主键/粒度/锚定/事实/实体等枚举与术语永不出现于界面，只活在 tooltip 与系统内部；
5. **语义素材 AI 起草、人做审核**——人最贵的动作是"判断对不对"，不是"填空"；批次 1 规则预拟，批次 2 LLM 预拟（交互不变，质量质变）。

**裁决示例**：角色（可推断→自动+卡片化确认）、编码（可推断→自动生成隐藏）、状态说明（需叙述→预拟+确认，G-9 已按此重设计）、字段锚（向导路径自动成立，零输入）。

## 八、换轨后的分析层（绑定业务实例）

- **"锚定"对外一律表述为"绑定业务实例"（v2 定案）**：对象=概念，数据集行=实例，**粒度=一行是什么实例**（"这个表的一行代表一件什么事？"）。
- **明细表纪律（v2 定案）**：所有分析基于明细表，不做预聚合场景；锚定粒度默认"明细"，汇总粒度语句并入数据集用途描述。
- 序列：事件绑定实例 → 字段翻译（角色+字段说明）→ 原子指标（口径唯一源头）→ 派生/复合 → **旅程登记（Flow）**。
- 实体落地纪律不变：概念层全抽（白板），系统落地按问题清单优先级；"抽了暂不建"的实体记入问题清单文档（问题→实体→落地状态[已落地/缓建/裁剪]）。

## 九、术语表（v2 新增 · 消歧）

| 术语 | 定义 | 对应产物 |
| --- | --- | --- |
| **业务事件** | 一次发生的事，一行数据承载一次发生；分析的最小单位 | 事实对象（PROCESS） |
| **业务流程** | 事件按业务顺序串成的步骤链（叙事，不是数据） | Flow（GOV-4） |
| **实体** | 被描述、被关联的东西，一行=一个 | ENTITY 对象 |
| **值对象** | 可枚举小分类 | 维度 |
| **绑定业务实例** | 把对象绑定到数据集：数据集的行 = 对象的实例 | 锚定（anchor） |
| **角色** | 字段的分析角色（度量/维度/描述），与物理类型无关 | role |
