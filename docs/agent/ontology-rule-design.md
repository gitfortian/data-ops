# 业务规矩(规则)· 设计(规则先行批次)

> 日期:2026-09-05 | 视角:**产品与交互设计**——只描述用户看到什么、做什么、得到什么。
> 上位文档:`ontology-metric-registration-design.md`(数的三件套)、方法论蒸馏参照:sharptoolbox/Onto-DataAnalyse(M3 规则模型)。
> 产品决策(产品主确认):吸收其"规则是一等公民"思想——**口径例外从指标说明里的一句话,升级为有名字、可引用的独立规矩**;后续"值域映射、场景"批次依次跟进。

---

## 一、一句话定位

> 规矩回答"**为什么这么算**"。它挂在记录上、有名字、有条件;数(指标)引用规矩,而不是把例外埋在说明里。

## 二、用户看到什么

### 时刻一 · 立规矩(在检查器/节点菜单里)

- **入口**:检查器新增"这个记录的规矩"分区;节点 ⋮ 菜单新增"规矩"分类。
- **一条规矩三个要素**:
  - **名字**:"退款单不算""只下单未付款不算"
  - **条件**(可选,能选就不填):字段 + 怎么比(等于/不等于/大于/小于/至少/至多)+ 值,可多行;系统自动检查字段是不是这条记录身上登记过的
  - **一句说明**:人话补充,给 AI 和后来的人看
- 立完即生效,没有上线流程——规矩是业务事实的陈述,不是需要审批的变更。

### 时刻二 · 引用(登记一个数时)

- "什么情况不算进来"一问变成两部分:
  - **引用哪条规矩**(多选,列的就是这条记录身上已立的规矩)——首选,点了就引用;
  - **或直接写一句**(临时例外,没有名字)——兜底,适合一次性口头规矩。
- 数的卡片上显示它引用的规矩名,口径出处一目了然。

### 时刻三 · 查看

- 检查器"规矩"分区列出全部规矩(名字+条件人话+说明),可增删改;
- 家底抽屉的数卡片同样显示引用的规矩名。

## 三、文案对照

| 不出现 | 取而代之 |
| --- | --- |
| 规则 / RULE / 业务限定 | 规矩 |
| ruleType: VALIDATION/CALCULATION/… | (内部各司其职,本批界面不出现) |
| filter 条件 / expression | 怎么比:等于 / 不等于 / 大于 / 小于 / 至少 / 至多 |
| 引用规则 rule_refs | 引用哪条规矩 |

## 四、这一批明确不做的(及去向)

- **规矩的类型区分**(效力/算法/推断/对照):后端留类型字段,界面本批不暴露,值域映射批次用"对照"类型承载;
- **规矩变更加版本**:规矩改了不影响已上线的数(它们引用的是规矩本体,展示随最新);版本化随治理规划后续批次;
- **规矩的执行**(算数时真的把退款单滤掉):随确定性查询链路批次落地——本批先让规矩"被记录、被引用、被看见";
- **值域映射**(5=已退款):下一批,复用规矩的"对照"类型。
