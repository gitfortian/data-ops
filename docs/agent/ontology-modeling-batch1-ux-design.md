## 一、产品定位

建模这件事，过去是"把表单填对"，现在要变成"把业务讲清楚"。

我们的用户是**业务能力强、完全不懂技术的人**。他们脑子里有的是业务问题（"哪些沉睡用户该发券了"）和业务常识（"退款单不该算进销售额"），缺的是把问题翻译成数据的路子。所以批次 1 的产品主张只有一句话：

> **用户负责讲业务，系统负责做建模。**

为此提供两个入口，服务两种时刻：

| 入口 | 给谁用 | 什么时刻 | 一句话定位 |
| --- | --- | --- | --- |
| **建模向导** | 业务分析师 | "我有一个问题，想让数据回答" | 从问题出发，一路确认，走到能查数 |
| **资产视图 + 对象详情** | 建模维护者 | "我要看看/改改已经建好的东西" | 浏览家底、精修细节、变更受控 |

两个入口不是二选一：向导负责"从 0 到 1 可答"，详情负责"从 1 到 N 精修"，产物之间互相跳转、上下文不丢。

贯穿所有界面的铁律（交互宪法）：**能自动生成的绝不让人填；能给选项的绝不让人写；必须写的话，系统先拟草稿、人只改；界面上不出现任何技术词。**

## 二、两个用户的故事（先看全貌，再看逐屏设计）

**小雅，业务分析师。** 老板问她："沉睡的用户能不能用券拉回来？"她打开建模向导，输入这句话。系统问她几个业务问题（这件事发生在哪份数据里？要算的数是什么？按什么分类？），她逐一确认——大部分答案系统已经帮她选好了，她只是点头。十分钟后，一份"沉睡用户消费分析"的模型上线，可以查数了。她没写过一行代码，没见过一个术语。

**老周，数据工程师。** 一个月后，运营说订单状态多了个"已退款"要补进说明。老周打开资产视图，点开"下单记录"的详情，在订单状态那栏看到系统之前拟好的说明，补上"已退款：不计入销售额"，提交变更。系统自动列出了哪些分析会受影响，他确认后生效——没有打断任何人。

下面按这两个故事展开逐屏设计。

## 三、入口 A · 建模向导（逐屏交互设计）

> 向导有五步。设计基调：**每一屏只问一个业务问题，答案优先给默认，用户的手指最多点两下。**

### 第 0 屏 · "你想回答什么问题？"

- **用户看到**：一个大输入框，占位文案是一句业务话："例如：哪些沉睡用户适合发券拉活？"；下方一个安静的次级入口："我还不确定问题，先从数据开始"。
- **用户做什么**：把老板的问题原样打进来（或直接跳过）。
- **系统在做什么（幕后）**：记住这句话——它将成为这份模型的名字来源、指标命名建议的来源、以及日后"问题回放验收"的登记项。
- **离开时得到**：一个有了主心骨的建模会话。

### 第 1 屏 · "这件事发生在哪份数据里？"

- **用户看到**：已上线数据集的列表（带业务名），以及三个接续的业务问句——"要算的数是什么？"（数值字段单选，已按类型预选）"按什么分类看？"（字段多选，文本/日期类已预选）"这个问题还涉及哪些东西？"（候选实体勾选：用户/商品/券……来自数据集与既有对象）。
- **用户做什么**：选一张表，扫一眼两三个预选答案，勾一勾涉及的东西。
- **系统在做什么（幕后）**：确定分析的事件与归属；勾选的实体进入"本问题支撑清单"，没勾但值得建的被默默记进问题清单（缓建/裁剪），不会丢。
- **离开时得到**：问题的骨架——在哪里算、算什么、按什么看、涉及谁。
- **本屏的克制**：如果数据集里没有数值字段，只说一句"这份明细里没有能加总的数，换一份试试？"——不解释原因，不堆术语。

### 第 2 屏 · "这个表的一行，代表一件什么事？"

- **用户看到**：已选数据集 + 一个**填空式确认**："这个表的一行代表一件什么事？"（占位示例：*一笔订单 / 一次券发放*）；再加一句开放引导："这份数据主要帮谁回答什么？"
- **用户做什么**：用一句业务话回答（比如"一次券发放"）。就这一句。
- **系统在做什么（幕后）**：这句话就是"实例粒度"的声明——它决定了以后每一个数能不能相加、怎么相加；同时登记为数据用途，供 AI 按场景取用。
- **离开时得到**：业务与物理数据之间的第一根线，而且是用用户自己的话系的。

### 第 3 屏 · 字段含义确认（本向导的重头戏）

- **用户看到**：一摞**字段卡片**，每张卡是一句业务话，而不是一个术语下拉：
  - "金额 —— 用来**累加的数**"
  - "券种 —— 用来**分类**的"
  - "订单号 —— 每行数据的**身份证**"（系统自动认出的，不需要用户做任何事）
  - "下单时间 —— 记录**什么时候发生的**"（日期字段自动处理，不出现勾选框）
- **用户做什么**：从头到尾翻一遍卡片。绝大多数卡片直接点头；个别不对的，点卡片换一个说法（"用来累加的数"↔"用来分类的"）。
- **系统在做什么（幕后）**：把每张卡片翻译成内部的角色标记；遇到**状态类的字段**（取值就那几种的文本），自动拟好一段大白话说明——"订单状态：待支付→已支付→已发货→已完成；用户付款后，从待支付变成已支付"——用户觉得哪里不对，直接改字；同时为每个字段预拟一句"给 AI 的话"，用户扫一眼确认。
- **离开时得到**：一份每个字段都有业务含义的清单，以及一批已经写好的 AI 理解材料。
- **本屏的克制**：用户全程见不到"角色""主键""度量""维度"这些词——它们在系统内部各司其职；用户也永远不面对空表单，所有说明都是"拟好了等你改"。

### 第 4 屏 · "这个数怎么算？"

- **用户看到**：指标名称已从问题预填（可改）；"**怎么算？**"三个业务选项：**求和（默认）/ 数个数 / 平均**；一个开放引导："**什么情况不算进来？**（比如：退款单算不算？只下单没付款算不算？）"
- **用户做什么**：选一个算法，把老板嘴里"不算数"的规矩写一句。
- **系统在做什么（幕后）**：生成指标（编码自动生成、隐藏）；那句"不算进来"被登记为口径例外——它是日后每一次算数的规矩，也是 AI 回答"为什么这个数和报表不一样"时的依据。
- **离开时得到**：一个口径清楚、可以直接被提问的指标。

### 第 5 屏 · 产出与上线

- **用户看到**：一张"这次建模做了什么"的清单卡（一种记录 + 它的字段含义 + 绑定的数据 + 一个指标），和一个醒目的"**上线**"按钮。
- **用户做什么**：点上线。
- **系统在做什么（幕后）**：先做一遍**上线自查**，把发现的问题翻译成人话逐条列出——"有 2 个字段还没说明它对应哪里的数据（去补）""这个记录还没有能当身份证的字段（去指定）"——每条都带"去修复"的跳转；全部通过才真正上线。
- **离开时得到**："查看详情"（进入对象详情精修）与"再回答一个问题"（向导重开）两条路。问题从这一刻起可以被真实回答了。

## 四、入口 B · 资产视图与对象详情

### 4.1 资产视图（现有三栏的转型）

保留三栏作为"家底浏览"：左边业务域、中间记录列表、右边概要。交互变化：

- 点击记录**进入详情页**（原来挤在右栏 tabs 的内容全部迁入详情）；
- 右栏新增"**业务黑话**"页签：维护术语表——"沉睡用户""爱占便宜用户"这类黑话，各对应一段"怎么算"的说明，让 AI 听得懂人话；
- 属性面板常驻"**新增一条字段说明**"快捷入口（打开即多一行，不再让人找按钮）；
- 列表带搜索与分页；
- 新增"**用户旅程**"的登记入口：把"发券→点开→领券→逛→下单"像讲故事一样排成步骤，每一步写一句"发生了什么、什么变了"——这是 AI 理解业务来龙去脉的材料。

### 4.2 对象详情（双入口共用的"精修台"）

**进入方式**：资产视图点记录、向导产物"查看详情"、搜索直达（链接可收藏可分享，刷新不丢）。

**顶部：建模进度条**。一句话回答"这个东西齐不齐"——"字段说明 6/8 · 已绑定数据 · 可以上线，但建议先补 2 个字段说明"。每一项可点击跳到对应位置修。

**详情分六个区，从上到下就是维护频率从高到低**：

| 分区 | 用户在这里做什么 | 交互要点 |
| --- | --- | --- |
| 基本信息 | 改名称、负责人、适用场景 | 与向导同一套表单，术语零暴露 |
| 字段含义 | 逐字段看/改业务含义与"给 AI 的话" | 卡片式，同向导第 3 屏；字段对应的物理位置用下拉选择，不再手抄编号 |
| 数据绑定 | 换绑数据集、写用途 | 状态异常（比如数据变了导致对不上）时红字提示并给"去修复" |
| 关联关系 | 看"它和谁有关系"，登记新关系 | 出边/入边分开列；登记时系统自动试连两侧数据并告知"能不能连上、命中率如何" |
| 指标 | 看哪些指标建在它上面，登记新指标 | 指标卡片点开能看到口径例外原文 |
| 变更单 | 已上线的记录要改，从这里发起 | 改完不直接生效——生成一张"变更单"，逐字段对照新旧，写明影响哪些分析，确认后才生效 |

**发布/上线的体验**（资产视图与详情一致）：点"上线"→ 弹出**上线自查清单**（人话逐条："未绑定数据，去绑定""没有能当身份证的字段，去指定"）→ 有问题就地修 → 全绿才放行。**事后报错在这个产品里不存在。**

## 五、贯穿体验的文案原则（文案业务化）

所有界面文案按"业务问句"重写，原则：**说人话、说业务话、术语进气泡**。对照示例：

| 界面上不再出现 | 取而代之 |
| --- | --- |
| 锚定数据集（SEC-4 一致性校验） | 绑定数据（系统会自动检查字段类型对不对） |
| 锚定粒度 | 这个表的一行代表一件什么事？ |
| 字段说明（PIL-1 唯一编辑入口） | 给 AI 的话：这个字段表示什么 |
| 登记变更（GOV-6） | 变更单（改了什么、影响谁，确认后生效） |
| DRAFT / PUBLISHED / DEPRECATED | 草稿 / 已上线 / 已下线 |
| 场景分类（SCEN-1） | 适用场景 |
| MEASURE / DIMENSION / 主键 | 用来累加的数 / 用来分类的 / 每行数据的身份证 |

走查标准：界面上 grep 不到任何治理代号与技术枚举（气泡提示与代码注释除外）。

## 六、分阶段上线节奏

按用户价值的先后（先让"改东西"顺手，再开"新动线"），每阶段以一个用户故事收口：

1. **第一阶段 · 对象详情与上线自查**——上线后，老周的故事成立：维护者有了专属的精修台，发布不再靠撞运气；
2. **第二阶段 · 资产视图升级 + 业务黑话 + 用户旅程**——上线后，家底可浏览、黑话可积累、业务的来龙去脉可登记；
3. **第三阶段 · 建模向导**——上线后，小雅的故事成立：业务人员第一次可以独立完成建模；
4. **第四阶段 · 文案业务化走查**——贯穿各阶段交付，收尾时全界面零术语。

（整体节奏与工作量估算见 `ontology-workbench-ux-evolution-plan.md`；工程拆解见文末备注。）

## 七、这一批明确不做的体验（及去向）

- **AI 起草全部内容**：本批由规则预拟（字段说明、指标命名），界面已按"预拟+确认"设计，下一批换 AI 起草，用户无感升级；
- **维度层级**（省→市、类目树的结构化管理）：本批以文字说明承载，后续随可视化一并做；
- **口径例外的结构化编辑**：本批用一句引导描述承载，后续做结构化规则；
- **派生/复合指标**：本批仍在资产视图登记（它们依赖已上线的原子指标），向导暂只产出"一个能直接回答问题的数"。

## 八、落地备注（给开发，不影响上文产品语义）

- **前置施工**：`pages/ontology/index.tsx` 拆分为 `workbench/`（资产视图）、`object-detail/`（详情）、`wizard/`（向导）、`shared/`（表单/卡片/预检/选择器/字段说明预拟等组件）——机械搬移不改行为，拆完手工冒烟三栏全流程；
- **新增关键组件**：字段含义卡片（含内部角色映射）、字段说明预拟器（内部三问拼装）、上线自查清单、变更单字段对照表、旅程步骤编辑器；
- **URL 约定**：`/ontology`（资产）、`/ontology/records/:id`（详情）、`/ontology/wizard`（向导）；域与记录进 URL；
- **质量门槛**：每阶段交付 tsc/biome 零告警；文案走查 grep 零术语；每阶段以对应"用户故事"做手工验收。
