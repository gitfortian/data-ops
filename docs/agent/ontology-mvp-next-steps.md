# 本体语义 MVP 验证通过后 · 下一步开发规划

> 日期：2026-08-27
> 定位：**MVP（订单域最小闭环）验收通过后的后续路线**。上游依据：`knowledge-docs/ontology/06-design-v1`（分期路线）、`07-mvp-v1`（验收/backlog 机制）、`docs/agent/data-agent-development-plan.md` v1.2（统一排期 Phase 5/6）、`docs/agent/pending-issues.md`（遗留跟踪）。
> 前置门槛：**只有 MVP 测试真正通过（D1~D5 出数）才启动二期**——避免在未证明价值的语义层上提前堆自动化。

---

## 〇、先定义"测试通过"（避免自欺）

MVP 验收不是"能跑了"，是五个可证伪指标全部出数（07 方案 §1.3）：

| # | 指标 | 门槛 | 产出物 |
| --- | --- | --- | --- |
| D1 | 编译正确率 | 30 条 dry-run SQL 全数工程师评审通过 | SQL 快照评审记录 |
| D2 | 数值一致性 | 语义查询结果 vs 手写黄金 SQL 100% 一致 | 自动比对脚本输出 |
| D3 | 问答通过率 | 语义层 ≥ 基线（Dataset 直答），目标相对提升 ≥ +15% | 25 问盲评（业务1+技术2，评分≥2.5 计过） |
| D4 | Token/推理步数 | 平均下降 ≥ 30%（Schema 预加载效应，bkn 实测 -47.9% 参照） | 冒烟日志 `KIND_LLM_CALL` 计量统计 |
| D5 | 资产完备 | 3 对象/2 关系/5 指标/12 术语全 PUBLISHED + Ossie YAML 过 schema 校验 | 资产清单 + 导出校验 |

**同时完成失败归因分类**（D3 中被拒/答错的题逐条归类）：

```text
建模缺失 / 编译缺陷 / Agent 行为 / 口径争议
```

这四类归因**直接就是二期 backlog 的来源**——分类出的失败题优先进入二期任务，而不是拍脑袋列要做什么。

> 若 D3/D4 不达标（语义层没比 Dataset 直答更准更省）：**停下，不进入二期**。先回查 Schema 预加载是否真正注入（SemanticPromptContributor 装配）、工具切换是否有退化、种子口径是否与业务方核对过。MVP 的失败实验本身也是二期规划输入（归因→立项）。

## 一、阶段总览（对齐 design-v1 四期与 plan v1.2 Phase 5/6）

```text
MVP 验收通过（D1~D5 + 归因分类）
   │
   ▼
二期「自动化」  Catalog 采集落库 · 血缘推荐映射 · LLM 补描述(护栏) · 口径冲突检测   （≈4 周）
   │
   ▼
三期「治理」    指标审批流 · 口径变更影响分析 · 术语运营 · 行级权限注入              （≈6 周）
   │
   ▼
四期「开放」    SEMANTIC API 类型 · 语义 MCP Server · 派生/复合指标 · INDIRECT 关系  （按需）
```

排序原则：二期解决"建模太慢、全靠手工"（产能）；三期解决"口径没人管、不敢信"（可信）；四期解决"能力封闭、接不出去"（开放）。二期是后两期的地基——**Catalog 采集是推荐映射的原料，推荐映射是治理的对象**。

## 二、二期 · 自动化（MVP 通过后立即启动，≈4 周）

| # | 任务 | 为什么做（公理/来源） | 前置 | DoD（可证伪） | 工作量 |
| --- | --- | --- | --- | --- | --- |
| E1 | **Catalog 定时采集落库**（改造 datasource 模块） | 语义承诺来自物理能力（A2）；血缘是本体存储现成底座（06 §1.2） | 无 | Quartz 任务按时执行；`yak_metadata_asset` 出现 TABLE/COLUMN 资产；变更检测（字段增删）触发本体验证 | 2 PD |
| E2 | **血缘推荐映射工作台** | INFERRED 永不直接生效（A6）；SqlColumnLineageParser 801 行是现成引擎 | E1 | 对每个待建模属性产出候选物理列（含 confidence）；确认后才 MANUAL 落库；INFERRED 绝不直接生效 | 3 PD |
| E3 | **LLM 辅助补描述（带护栏）** | AI 生产元数据必须有护栏（A5） | E2 | 默认 dry_run；confidence ≥0.75 且 fill_empty 模式才落库；业务 display_name 不可覆盖；全程留痕 | 2 PD |
| E4 | **多源同名字段口径冲突检测** | 冲突先检测后合并（A6） | E1 | 两个数据源同名字段/同义术语 → 显式告警（复用 alert 插件钉钉通道），不静默覆盖 | 1.5 PD |

**二期验收**：建模一个真实业务域的产能（人日/对象）至少减半；所有 INFERRED 推荐 100% 经人工确认后才生效；冲突检测在双数据源场景实测命中。

## 三、三期 · 治理（≈6 周）

| # | 任务 | 为什么做 | 前置 | DoD | 工作量 |
| --- | --- | --- | --- | --- | --- |
| G1 | **指标版本审批流**（IN_REVIEW 状态 + 通知） | 治理失位是最高风险（06 §8：口径没人定→建成第二套口径） | 二期完成 | DRAFT→IN_REVIEW→PUBLISHED→DEPRECATED 全流转；审批人签名后 PUBLISHED | 3 PD |
| G2 | **口径变更影响分析产品化** | 血缘 upstream/downstream 现成能力包装；改字段必须知道影响哪些看板/API/Agent | E1+血缘 | 指标/属性变更 → 输出受影响清单（看板/API/Agent/指标）| 2.5 PD |
| G3 | **术语表运营界面** | Glossary 是语义检索与 Agent 意图匹配的素材 | 无 | 术语 CRUD + 同义词批量导入 + ai_context 三字段维护 | 2 PD |
| G4 | **行级权限配置与注入** | 权限在查询翻译时刻生效（A3）——`RowPolicyProvider` Hook 已在 MVP 留空（Noop） | G1 | 配置行级规则 → 语义查询编译时注入 WHERE；越权行被过滤；配置界面 | 3 PD |

**三期验收**：一个指标从定义到发布全程走审批流且留痕；改一个字段能列出受影响物清单；行级权限规则注入的 SQL 快照测试通过。

## 五、与 Agent 主线（可观测性）的协同

本体语义后续阶段与 agent 模块**共享同一可观测性底座**，两线并行不冲突：

- **调用级计量（KIND_LLM_CALL）**：二期 E3（LLM 补描述）的 token 成本、三期 G1 的影响分析都需要它出数；
- **反问挂起帧可投递（PI-101-B 修复）**：HITL 是 E3 补描述人工确认的重要交互形态，MVP 反问链路已闭环，二期直接复用；
- **semantic_ref 溯源**（已落 V6）：E2/E4 的推荐与冲突告警经语义查询再次反查数据时，证据链能串起来。

**gate 纪律**：四期 O 系列不做进二期/三期排期；二期/三期每期结束以 DoD 勾选 + 影响分析回写 `pending-issues.md` 收尾。

## 六、执行建议（给项目组的落地序）

1. **先跑 MVP 验收**（D1~D5，约 2.5 PD）——这是"下一步"的**起点**，不是可选项；
2. 验收报告产出后，**把失败归因四分类表转成二期 backlog**（E1~E4 的具体任务）；
3. 二期开工第一件事是 E1（Catalog 采集）——因为 E2 推荐、E4 冲突都吃它的料；
4. 三期 G4（行级权限）依赖编译器 RowPolicyProvider Hook（MVP 已留空），是四期发布多部门共享前的安全前置；
5. 每期结束，把实际 PD、偏差、归因写进 `pending-issues.md` 完成登记（沿用现机制）。
