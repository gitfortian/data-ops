## 1. 为什么需要决策

真实订单案例从 MySQL 订单源采集到已发布 ODS 模型，却仍出现来源字段映射未填、模型与已确认下单过程未关联、业务标准字段库为空、血缘只有模型包含字段、DataDev 入口只提供技术节点；专业功能分别存在，却没有一条可以把业务需求变成真实可消费数据的用户旅程。原逻辑模型的实体/属性/关系、版本、逻辑→物理映射数据结构在 Modeling 主分支存在，但独立 CRUD / 生成 API / 前端作者工作区缺位；旧 FR-06 认为逻辑模型不必关联 Semantic，已经与现有 PD-003 的事实所有权背景不相称。

用户：业务负责人、兼任数据建设的实施者、标准治理人、数据架构师、数据开发工程师。  
用户目标：从“已有来源数据”或“要回答的业务问题”出发，理解来源与业务、建立标准、确认逻辑设计、落地物理设计并交接运行，最终交付一项真实经过验证的数据结果。  
适用旅程：J1、J2、J3；质量、安全、血缘与影响贯穿其中。

## 2. 待批准的产品选择

### D1. 双入口，同一组权威事实，不创建第二套建设后台

- 入口 A：从业务目标/业务过程开始 → 发现和确认可用数据。
- 入口 B：从已有数据源、元数据、资产或已发布来源模型开始 → 发现/确认业务含义。
- 两条路径都复用稳定的 Datasource、Metadata、Asset、Semantic、Modeling、DataDev、Metric、Dataset / Data Service 事实引用。
- 可以存在跨页面任务上下文或进度投影，但不可将其当成第二个业务模型/标准库/任务定义真相，不得自动创建一份“影子实体”。

### D2. 区分业务语义、逻辑设计、物理设计

- Semantic：业务域、业务过程、数据标准、标准字段（标准字段身份与生效/引用）。
- Modeling Logical：逻辑实体、逻辑属性、实体关系、标识、事实粒度、逻辑版本及到物理模型的设计映射；引用 Semantic 正式对象，不能另起一套业务过程和标准定义。
- Modeling Physical：分层、目标方言、表列、主键、分区、技术类型及物理版本；可引用逻辑设计，不强制每个已有来源表都对应独立逻辑实体。
- DataDev / Workflow：加工任务、SQL/同步定义、真实执行与运行证据；不由 Modeling 替代运行引擎。
- Metric、Dataset / Data Service、Consumption：按 PD-003/PD-002 各自持有指标定义、受治理消费定义与实际使用证据。

### D3. 逻辑建模是非 ODS 业务目标设计的默认桥梁，ODS 贴源镜像为明确例外

- 正向：过程/业务问题、标准字段 → 逻辑实体与关系审阅 → 标准化 DWD/DIM 等物理目标设计。
- 逆向：已授权物理来源 → 可直接设计 ODS 来源镜像 → 由其证据生成逻辑实体与关系候选 → 人工确认 → 标准化物理目标。
- 不强迫首次 ODS 导入前建立全量标准字段、逻辑模型、Doris 连接；逻辑层也不得因名称相似自动确认业务主键、Join 基数或指标口径。
- 复杂聚合、SCD、跨表 Join 是否在逻辑画布定义约束还是在可运行加工计划完成，需要进一步产品/架构评审。逻辑模型不直接保证可执行 SQL。

### D4. 非 ODS 标准治理是真实发布合同（具体门禁阶段待冻结）

- 业务字段必须引用合法、启用、当前项目可用的标准字段身份，角色所需的类型/单位/码值/口径等数据标准由 Semantic 校验；只有类型标准 ID 不代表通过“标准字段库”约束。
- ODS 允许保留原始类型、脏值以及未绑标准字段的源列，不得无声明地标准化原始数据。
- 系统技术列（处理时间/追踪列）是否例外、草稿阶段宽限、标准失效后的依赖状态，必须作为单独门禁表评审；不能在当前代码中自行推断阻断全部保存。
- 所有新建路径（手工、逆向、逻辑转物理、过程派生、从现有模型复制、Agent 候选采纳）必须复用同一领域校验契约，不能选择一个入口就绕过正式有效化。

### D5. 正式交接基于精确引用，设计版本不冒充部署与执行

- 来源引用：项目范围、数据源/Schema/表列稳定身份、采集时点/来源指纹、权限状态和覆盖范围。
- 逻辑引用：逻辑模型/版本、实体/属性、业务过程 ID、标准字段 ID 与适用的标准版本/有效性。
- 物理引用：物理模型/版本、目标分层、环境/方言、逻辑→物理、来源→物理列映射以及待确认转换规则。
- DataDev 交接必须显式确认执行目标环境、权限、SQL / Task 与运行方式；不把“生成 DDL”当成“已建表”，不把“设计版本已发布”当成“数据已入仓”。
- 同一体验可以聚合三类进度：设计就绪、部署就绪、数据运行就绪；各事实由 owning domain 提供，不能新建跨域大状态机。

### D6. 渐进式体验，不以技术模块数量定义流程

- 不新增顶级导航域；首先复用现有业务语义、模型工作台和数据开发专业入口，通过上下文动作、预览/确认和稳定回链衔接。
- 首页/引导面表达“当前目标、已完成成果、阻断项与下一步”。专业用户保留独立作者工作台和精细配置。
- 系统建议/Agent 只作为待确认方案，展示证据、来源覆盖、漂移/冲突；不擅自保存、发布、执行。
- 模型列表里的“已发布”明确限定为设计版本，运行进度不覆盖它。

## 3. 备选方案及取舍

| 方案 | 取舍 | 建议 |
|---|---|---|
| A. 继续修补各模块既有 CRUD | 代价小，但故事无跨域衔接；重复录入不消失 | 不建议 |
| B. 新建通用“数据建设”一等领域并接管对象 | 看似统一，但将出现第二业务真相与迁移负担 | 不建议 |
| C. 任务化体验 + 原域事实 + 逻辑设计桥梁 | 跨域体验改善大，需明确引用/版本和用户决策 | **建议采纳（待 Owner 批准）** |
| D. 每张源表先生成逻辑模型再进入 ODS | 操作线性，但重复技术结构、阻碍贴源和脏数据保真 | 不建议 |

## 4. Truth Owner、生产和消费关系

| 正式事实 | Owner | 上下游仅允许 |
|---|---|---|
| 数据源身份/采集证据 | DataSource / Metadata | 授权、有界读取与稳定 Ref |
| 业务域/过程/数据标准/标准字段 | Semantic | Model/Agent 引用，经原域校验 |
| 逻辑与物理模型、设计映射、模型版本 | Modeling | 上游证据引用/下游只读版本合同 |
| 任务、运行、调度与 SQL/同步定义 | DataDev / Workflow / 对应 Runtime | 只读运行回执和受权任务交接 |
| 指标定义、指标版本/验证/发布 | Metric | PD-003 的正式版本依赖 |
| Dataset / Data Service 与使用证据 | 相应业务域及 Consumption | PD-002 的访问、查询与 Usage Evidence |
| Lineage、Asset 治理事实 | 原域 | 可组合呈现，不由引导流程重写 |

## 5. 用户可见导航与迁移

1. 保留现有专业导航和已保存资产不变；优先在已有入口增加“从业务目标”“从已有数据继续”的推荐路径与上下文回链。
2. 来源镜像创建进入 ODS 后，自动显示同名直通**候选**及待确认来源覆盖，不能替用户暗中确认加工。
3. 业务域/业务过程详情可进入逻辑模型候选审阅；逻辑模型编辑展示实体/属性/关系及引用、版本/发布，但与标准字段 Authoring 相互跳转而非复制。
4. 从确定逻辑版本预览物理生成或关联**已有** DWD/DIM；显式确认差异后写入，生成不自动发布/部署。
5. 从物理设计中明确前往 DataDev 原工作区，重查模型版本、来源、目标环境和权限；保持明确的“任务待创建/待配置/执行失败/已成功”回执。
6. 灰度与迁移期间旧物理模型、旧来源映射和标准绑定继续存在；不凭猜测回填逻辑模型或自动发布旧模型。

## 6. 风险和未决阻断项（本 PD 未 ACCEPTED）

1. **默认跨域路径**：业务目标优先还是数据源优先，是否在现有模型工作台内部同时开放，Owner 如何验证首期最佳方案？
2. **逻辑↔Semantic**：逻辑属性必须/可选引用 StandardField 的边界、业务概念与过程对应关系、合法的孤立草稿、变更/停用后版本健康度。
3. **逻辑↔物理映射**：一对多、多对一、单库单方言历史限制，如何处理现有已发布物理模型、幂等、历史版本和冲突。
4. **非 ODS 门禁**：标准字段强制的生效操作点（保存/发布/派生/生成）与系统技术字段例外。
5. **映射一致性**：ODS 来源身份、列映射、版本、源端漂移在同一次确认中如何事务性落地/回滚。
6. **DataDev 交接**：与现有 F-002 Data Development Hub 的任务定义边界、可达 API、实际目标数据库授权及真实部署证据。
7. **PD 依赖**：PD-009 为 PROPOSED，来源语义智能初始化不可预设为已获产品批准；本案只定义未来引用/接受候选的方向。
8. **首个业务口径**：订单量统计的时区、下单/支付时间、取消订单、去重键由业务确认，不能擅定。

## 7. 产品结果及验收证据

首个黄金故事：订单库 → 元数据采集与 ODS 保真 → 下单业务过程/标准字段 → 逻辑订单实体及版本 → DWD 物理模型与准确字段引用 → DataDev 真执行 → 质量/权限/血缘 → 一项已确认 Metric → Dataset 查询与 Usage Evidence。

至少提供四类证据：
- **设计**：标准字段合法引用、逻辑/物理模型精确版本、来源表/列映射回读。
- **工程**：目标环境连接/权限、任务/SQL 定义、真实执行结果和失败恢复。
- **业务**：口径确认、字段转换异常处理、数据质量/安全验证报告。
- **消费**：受治理 Dataset / Data Service 真实成功查询、访问裁决、使用证据与影响回链。

反向场景必须验证：ODS 可不先有逻辑模型和标准字段，非 ODS 无标准字段不能变成正式有效版本，权限撤销/元数据漂移不能继续以旧候选静默提交，逻辑版本变化不静默覆盖已发布物理结构，Provider UNAVAILABLE 不当作 EMPTY/FAILED。
