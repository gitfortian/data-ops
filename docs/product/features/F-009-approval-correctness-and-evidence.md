# F-009 — 既有审批闭环正确性与依据可理解性

负责人：Product / Approval / Security / Modeling
创建日期：2026-10-05

> 修复既有审批旅程中的可见性、送审事实一致性和故障留痕问题。不新增审批状态、导航入口、事实 Owner 或流程类型。

## 1. 用户问题与结果

**用户：** 业务申请人、指定审批人、流程管理员。
**问题：** 审批人需要确认送审依据与实际获批内容一致；无关人员不能读取申请依据；失败后有可重试结果与操作证据。部分源域目前允许在途修改策略/模型。
**能力：** 复用 Approval 的实例、审批人快照、同步 SPI 回调和审计，以及源域已有版本与变更事实。
**结果：** 当事人可读取依据；批准只作用于与送审依据一致的源域事实；handler 缺失/失败不形成虚假终态；查询有界。

## 2. 旅程与事实归属

申请人提交源域变更 → 指定审批人在既有“我的待办”核对冻结依据 → 通过或拒绝 → handler 校验并更新源域事实 → 回到源域核对版本/状态和审批记录。

Approval 拥有流程、审批单、审批人快照、决定和审批轨迹；MDM、Security、Modeling 等源域拥有各自业务对象、版本及生效事实。复用 ApprovalApi / ApprovalFlowHandler、CurrentProject、RBAC、BusinessAuditService、源域持久化和版本服务。payload 是源域生成的只读解释材料，不是业务真相。

## 3. 范围

- by-biz REST 查询按详情相同的当事人 / manage 规则保护依据。
- 终态处理前要求 handler 可用；不可用时保留原在途状态。
- Access Policy 与 Model Publish 校验送审快照/版本；事实变化不得按旧单生效。
- callback 失败留下审批动作失败证据。
- 分页参数限制正数和最大页大小；流程列表使用分页。
- 最大长度 flowCode 可删除并释放唯一键。
- 详情能读取撤销原因；依据可理解且可回链源域。

## 4. 非目标

不增加会签、分支、转交、委托、通知、SLA、表单引擎、菜单、强制审批门禁或新状态机。不改变资产直上架双轨、F-007 旅程、F-008 工作入口。#285 的其他增强建议需要另行决策。

## 5. 验收与成功信号

| 信号 | 目标 | 证据 |
|---|---|---|
| 依据访问 | 非当事人通过 by-biz/detail 都不能读 payload | API 权限测试 |
| 送审一致性 | 送审后源域或并发修改不能使旧依据批准新内容 | Security / Modeling 持久化旅程 |
| 回调失败 | 审批、步骤和源域整体回滚且记录失败操作 | 真实事务集成测试 |
| 有界查询 | 负值/超大页参数不能绕过分页 | DTO 与分页契约测试 |
| 依据可理解 | 审批人能辨识改动并回源域核对 | 登录态详情、深链走查 |

E2E：提交 → 指定审批人待办 → 核对依据 → 批准生效/拒绝无生效 → 源域版本及审批/审计可回看。另覆盖撤销、handler 缺失、callback 失败、跨项目和非参与者拒绝。

Mock 单测不代表 DB 并发/事务证据。合并后需 CI 与真实 E2E 证据；未验收不得标记 SHIPPED。若实施需引入新跨域状态或事实，回到产品治理流程。
