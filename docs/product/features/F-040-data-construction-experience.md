## 1. 用户、目标与价值

**主要用户**：首次建立数仓的数据实施人员；业务负责人；数据治理与建模工程师。  
**用户问题**：用户已有数据源和业务需求，但当前需要在 DataSource、Semantic、标准字段库、物理建模、字段映射、模型发布、DataDev 各自操作，反复选择同一数据源/过程/字段；逻辑模型业务设计环节缺位，非 ODS 标准规则在入口间不一致；“模型已发布”与“物理表已部署 / 数据已运行”混淆。  
**期望结果**：用户基于已连接数据或业务目标，都能沿一条**可返回、可解释、可人工确认**的路径，从来源证据到业务语义、标准字段、逻辑模型、物理模型、数据加工与消费；专业模式保留原页面，不牺牲细粒度控制。  
**为什么现在做**：真实订单 0→1 巡检 (#512) 和故事地图 (#513) 已明确证明不是单一按钮缺失，而是产品主线断裂。低层模型时代的专业后台不应倒逼用户理解 Maven/数据库技术模块。

**本次不追求统一所有内部状态机**：Model / ModelVersion、Dev Draft / Revision / Execution、Metric / Validation / Publication、Dataset Consumption 属不同 Domain，交互只能聚合这些事实。

## 3. 用户活动与边界

以 #513 的 US-00～US-22、A4L、US-11L/US-11P 为唯一故事地图索引，覆盖 J1（外部数据到可信对象）、J2（业务定义到 Metric）和 J3（生产到受治理消费）。

### 场景 1：已有来源数据

连接订单库 → 采集 trade_order/trade_order_detail → 资产/业务过程候选审阅 → ODS 保真模型（来源直通候选、统一确认与保存）→ 标准字段治理 → 业务逻辑模型（实体/属性/关系/粒度）→ DWD/DIM 物理设计 → DataDev 任务/SQL/执行 → 质量/安全/血缘 → Metric → Dataset / Data Service。

### 场景 2：业务目标先行

输入“我要统计每天订单量” → 确认指标问题（时间口径、状态过滤、主键去重） → 确认业务域/业务过程 → 发现来源或明确来源缺失 → 标准字段候选/审阅 → 逻辑模型设计 → 与已有 ODS / DWD 关联或完成缺口 → 合流数据开发与消费。

**ODS 例外**：来源镜像可以跳过逻辑模型和标准字段的先行创建，仍需稳定来源身份；**非 ODS 正式模型不能跳过标准字段引用**。如果业务目标尚不能确认，允许只读探索或保存待确认的逻辑草稿，但不能自动发布正式业务口径。

## 4. 范围划分

### Slice A：完成可信设计基础（本规格第一纵向切片）

- 数据源/Metadata/业务过程上下文传递的 UX 规范与稳定引用校验。
- ODS 从来源导入后展示来源表、技术列、主键、字段覆盖及列来源的批量候选/确认；保存时准确区分编辑态、模型来源绑定和列映射。可保留原始脏类型与注释。
- 标准初始化/标准字段库的“已有匹配 / 待确认新建 / 冲突 / 停用 / 不应标准化”分类，并支持返回原业务过程。
- 逻辑模型 MVP：关联过程/标准字段/来源证据的实体、属性、逻辑主标识、关系与业务粒度草稿；审阅和版本回读；与当前 ODS 保真模型区分。
- 物理模型工作台状态/下一步真实、来源血缘不将 CONTAINS 当业务下游。

### Slice B：第一次真正的跨域数据交付

- 从逻辑版本预览/确认 DWD/DIM 物理模型或对齐既有物理设计；类型适配、标准字段引用门禁、模型版本的逻辑→物理关联和审计。
- 精确模型/版本交给 DataDev/离线集成现有拥有者，目标环境/发布/执行全程显式权限与回执；不自研新的任务执行引擎。
- 运行级质量、安全、数据标准与真实血缘的负向检查。
- 一项经业务确认的“每日下单订单量”候选指标（实际口径待确认）经 Metric 正式验证发布，再通过既有 Dataset/受治理消费契约完成真实查询。

### 明确不做

- 不新增顶级“数据建设”模块、第二套语义定义、第二标准字段库、第二模型版本库或运行引擎。
- 不用逻辑模型生成 ODS 源镜像作为强制门槛；不自动推断订单明细=新业务过程。
- 不在 Product Decision 未批准前推翻现有已发布模型、不进行批量历史自动迁移。
- 不用一个字段弹窗承担多表 Join / SCD / 完整 SQL/调度工作流。
- 不让 Agent 未经业务用户确认新建正式标准、确认模型关系、发布或执行。
- 不把 F-039（PD-009 PROPOSED）中的 Agent 来源语义初始化能力视为产品上已授权的前置依赖。

## 5. 真相归属、复用及接口意图

| 环节 | 唯一 Owner | 复用及必须验证的引用 |
|---|---|---|
| 来源物理证据 | DataSource / Metadata | datasourceId、database/schema、table/column、采集批次/时点/指纹、授权范围 |

## 6. 核心交互合同

### 6.1 “继续建设”上下文

推荐的最小上下文：用户本次选择的 sourceRef、processRef、logicalModelRef、physicalModelRef、targetLayer、metricIntent（仅草稿上下文）。客户端可以保存短暂恢复信息，但最终数据都从 owning domain 读取。没有匹配/已失效/权限撤销时必须显示“不能确认”及回到来源页，而不能静默清空或用同名对象猜测。

### 6.2 逻辑模型设计

初始展示业务对象清单及关系，而不是技术分区/方言表单；属性可引用已启用 StandardField，允许显示“该字段尚未在标准字段库定义”的**待确认**条目。保存独立逻辑草稿；确认逻辑版本再交接物理方案。关系来源、基数及主标识必须附业务确认/证据，不依赖物理外键推断。

### 6.3 非 ODS 标准字段硬校验

- 创建字段时优先从标准字段库选择，不应默认开放任意自定义业务字段后只给弱警告；
- 可将未标准化候选加入“待治理逻辑草稿/问题清单”，但正式物理设计发布前由服务端按 model layer 与 role 验证 stdFieldId；
- 对“技术列是否例外、草稿保存是否阻断”保留阻断评审，未达成决策前不能擅自编码；
- 物理类型/长度、方言类型转换与逻辑类型/标准类型应分层展示，不能因强制标准就静默把 ODS 金额 VARCHAR 当 DECIMAL。

### 6.4 设计、部署、运行、消费彼此独立

设计模型 Published ≠ Doris 目标已建表；目标配置/DDL 审阅 ≠ SQL 已执行；DataDev Task Published ≠ 实际执行成功；Metric Published ≠ Dataset 查询成功。可展示基于原事实的横向进度说明，不写第二个全局 businessStatus。

## 8. 完整错误态/权限/加载/跨域回链

- 来源：未采集、部分采集、连接失败、实时表列变化、来源权限撤销、跨项目对象。
- 标准：库为空、标准停用、同名异义、类型标准有但 stdFieldId 缺失、强制口径不明确、无权引用。
- 逻辑：业务过程缺失、粒度待确认、关系基数未知、物理已有同名/同业务模型、并发逻辑版本变化。
- 物理：目标 Doris 方言不支持原源类型、保存失败、来源映射未覆盖、已发布设计与未部署状态差异。
- 开发：目标环境不存在/无权限、任务未保存、SQL 语法或数据转换失败、运行态丢失。
- 消费：指标定义/版本未通过验证、发布与数据可用状态不一致、受治理访问禁止、provider unavailable、空数据应与未知分离。
- Agent：候选来源不完整、预算耗尽、需人工提问、响应超时或证据过期，不自动执行后续步骤。

每个状态给出用户可用的“查看原因 / 修复来源 / 重新审阅 / 返回原对象”动作；写入、发布、运行必须重新验证权限与最新版本。

## 11. 风险、兼容与回退

- 旧物理模型保持有效；缺少逻辑版本的历史模型标记“无逻辑关系/legacy”，不可自动回填猜测实体或标准。
- 迁移以新增精确引用和展示差异为主，任何影响旧发布版本的改写需显式迁移计划及历史审计。
- Agent/推荐关闭或不可用时仍可由用户完成手动流程；没有 AI 不应阻断专业建模。
- 已保存设计版本不可因新逻辑版本生成自动覆盖；生成冲突时保留已有版本并提供明确审阅/退出操作。
