# 从业务需求到第一次可信数据交付：用户故事驱动的交互蓝图 V1

Status: DRAFT（交互提案，待产品评审）  
Date: 2026-10-10  
Parent: #513 用户故事地图；Evidence: #512；Decision: PD-010（PROPOSED）；Feature: F-040（DRAFT）

> 这是一份真正按用户故事组织的“下一版产品应如何交互”的蓝图，不是把旧低级模型页面平移到新菜单。页面文字/布局为待评审提案，不代表已实现。任何默认跨域路径或长期规则变化须等 PD-010 ACCEPTED；不能直接当代码实施清单。

## 1. 设计原则与场景范围

**核心用户目标**：从业务问题或已连接的订单库出发，最终能够查询到一次经过确认、运行、质量/安全验证的真实订单业务结果。

**页面设计不以内部模块和数据库表名为主角**，而以“这一步要做什么、需要用户决定什么、做完得到什么、下一步去哪里”为主角。

对每个设计画面都统一回答：
1. 我正在完成哪个用户故事？
2. 系统已知道哪些正式事实、证据来自哪里、哪些只是候选？
3. 哪一项需要业务人员/工程师确认，默认选择是否安全？
4. 点击后究竟“仅预览、暂存草稿、提交正式定义、发布设计、部署、执行”哪一种效果？
5. 成功后去哪里，失败/无权/数据漂移时怎样回到事实 Owner？

**首个黄金样例**：交易 / 下单 order_create；MySQL 订单库 trade_db；trade_order 订单头、trade_order_detail 商品明细；已发布设计 ods_orders；Doris 是目标方言，不可自动推断目标库已连接；标准字段库初始为空。订单金额/时间/status 等脏值需要治理，不得按列名猜类型和清洗规则。业务指标“每日下单订单量”只是候选口径，时区、取消订单/去重仍需业务确认。

## 2. 建议的信息架构：任务引导 + 专业工作台，不新增一级菜单

现有业务域、数据标准、标准字段、模型工作台、数据开发工作台全部保留权威编辑位置。

建议在现有建模/业务语义相邻入口提供 **“继续数据建设”** 的可发现入口（具体位于模型工作台首屏还是业务过程详情需评审），启动时给两种卡片：

- **我有业务目标**：我想分析订单量/销售额 → 明确业务过程/时间粒度 → 搜寻数据和规则缺口；
- **我已有业务数据**：从数据源/资产/源表选择 → 查看证据 → ODS 镜像/逻辑实体候选。

这是一种**任务上下文视图**而不是新的数据建设对象。会话中的当前 sourceRef、processRef、logicalModelRef、modelRef 和下一步建议是受控导航投影，不保存第二份业务 Domain Truth。所有对象写入仍回源域，由目标页重新检查项目、权限、版本和指纹。

### 2.1 任务进度的视觉语义

推荐顶端采用紧凑、可返回的任务步骤条，专业页面可隐藏：

~~~text
业务目标 / 数据范围  →  业务与标准  →  逻辑设计  →  物理设计  →  开发运行  →  数据结果
           [可从来源进入 ODS 原样镜像，不强制先经过逻辑设计]
~~~

步骤状态严格区分：
- **已具备来源事实**：已有稳定 ID/版本，可打开详情；
- **有建议待确认**：可预览，不等于保存；
- **已保存设计**：保存草稿，不等于正式发布；
- **条件未满足**：说明具体缺什么，提供修复去处；
- **下游已完成**：仅有原域可核验的发布/部署/运行/消费回执才显示对应完成。

禁止汇总显示一个笼统“100% 建设完成”，除非每项指标来源可复原。权限缺失为 FORBIDDEN、接口不可用为 UNAVAILABLE，不把它们展示成“0 个对象”。

### 2.2 页面层级（用户心智）

- 第一层：**我正在完成的目标 / 当前成果 / 待解决问题 / 下一步**。
- 第二层：**领域设计对象**（业务过程、标准字段、逻辑模型、物理模型）。
- 第三层：**专业实现参数**（数据源、真实 schema、方言、主键/索引/分区、SQL、调度、存储 TTL），在需要时才出现。
- 随时能展开“来源证据 / 版本 / 规则解释”，高级用户仍可直达专业编辑。

## 3. 故事板 A：从已有订单源表开始

### S-01 来源发现完成：用户先看到能做什么

**入口**：Metadata 中 trade_order 表详情 / Asset 来源资产 / DataSource 已连接库表。  
**主标题**：已发现订单主表。  
**摘要**：来源数据库、采集批次、列数、真实数据访问范围、主键/外键信息（未知则标未知）、备注异常线索；显示关联的已有 ODS 模型 ods_orders（如真实 Ref 可解析）。  
**主要动作**：①「构建 ODS 来源模型」②「理解业务含义」；如果已有 ODS 则动作变「查看/补全现有 ODS 模型」，不再次创建同名模型。  
**次要动作**：浏览原始元数据 / 采集历史与漂移 / 授权请求。

操作前不要求用户填写目标方言、命名标准和业务过程。这里技术事实与业务解释分离，只有元数据已知事实可以直接带入。

异常：来源连接失败、采集不完整、旧快照被替换/权限撤销时不允许静默使用最新表结构覆盖旧模型；给出精确覆盖与变更差异。

### S-02 ODS 贴源建模：合并“导入字段”和“重复逐列映射”

**建议画面**：

~~~text
创建/补全来源模型         ODS · 订单主表（草稿）
来源：订单库 / trade_db.trade_order   [查看本次采集证据]
目标：ods_orders ；目标分层：ODS     [高级设置]
-----------------------------------------------------------
结构覆盖：已选 17 个源字段   直通候选 17   冲突/未知 0（示例）
  目标字段       来源字段                    类型保真   处理
  order_id       trade_order.order_id        VARCHAR    原样直通
  order_time     trade_order.order_time      VARCHAR    原样直通；格式待治理
  order_amount   trade_order.order_amount    VARCHAR    原样直通；金额异常线索
  ...            ...                         ...        ...
-----------------------------------------------------------
[保存 ODS 草稿并确认来源]   [返回/暂不保存]
~~~

这里的 17 是按早前已采集样本示意，实际 UI 以当前授权采集快照为准。技术列 process_time/event_time 与业务列分组展示，另标识技术列的来源、含义与生成规则，**不能将来源 17 列和目标 19 列混成“导入一致”**。

保存交互必须明说：是否只保存模型结构、是否正式保存 SourceRef、是否将“同名直通候选”确认为受治理 Mapping、是否是一个一致提交。源列来源凭证、覆盖、变更风险和冲突必须先预览；没有持久化的列映射不能显示“已映射”。

保留专业页面手动添加列、从模型导入、高级分区；“重新导入”需差异预览（新增/删除/类型变化/人工编辑冲突/标准引用风险）和明确覆盖确认，不再直接无提示清空人工成果。

### S-03 理解订单业务：业务过程和粒度不被混淆

从 ODS 源证据可到「交易业务域 / 下单过程」。推荐展示：
- 经确认的业务过程 order_create；
- 关联来源：订单主表 MAIN、订单商品明细 DETAIL；
- **过程事实与模型粒度分开**：下单是业务事件，订单头模型是一笔订单，明细模型是一条订单商品记录；
- “购买商品 buy”如存在，作为待核对是否真是独立业务事件，而非因有明细表默认另建过程。

下一步应是「查看/准备标准字段」或「设计订单逻辑模型」；不让用户从过程列表直接面对 Doris 目标方言。

### S-04 标准字段建设：优先审阅建议，不让用户逐列复制

**建议画面**：

~~~text
为「下单」准备标准字段      已有标准字段 0（示例）
类型标准 / 单位 / 码值 / 口径 / 安全   [查看正式标准目录]
候选               标准字段状态            需要决定
订单编号           待创建：order_no         复用/合并/新建
订单金额           待创建：order_amount     类型、单位、业务含义待确认
下单时间           待创建：order_time       逻辑时间类型与来源异常规则
订单状态           待确认码值               2024/2025 混用，不自动定标
...
[确认选中的候选并提交给 Semantic]   [稍后再做]
~~~

“已有标准库为空”和“当前还未加载到标准列表/无权限”必须不同。点击批量确认之前，逐字段给出正式标准 ID、引用类别、重复冲突与角色合法性预检。业务含义、单位、码值/口径未经确认的候选不能自动启用。实际事务、审批仍由 Semantic 原服务处理，逐项返回成功/复用/待审批/冲突/未知回执。

## 4. 故事板 B：业务逻辑模型工作区（这次的核心新设计）

逻辑模型不应以“选择目标方言、库名、索引”开始。建议落在 Modeling 的**业务逻辑设计**视图，与**物理模型设计**并列，但不新增全平台顶级导航域。

### S-05 逻辑设计初屏

~~~text
交易 > 下单 > 逻辑模型：订单交易模型      [草稿] [版本/影响]
目标：定义下单涉及的业务对象和业务关系，供后续物理设计复用
----------------------------------------------------------------
左侧：业务对象            中央：关系概览       右侧：属性与治理
[订单 Order]              客户 1 --- N 订单   选中「订单」
[订单明细 OrderItem]       订单 1 --- N 明细   粒度：每笔订单
[客户 Customer]           [关系待确认]         业务标识：订单ID
[+ 新建/引入对象]                                属性：
                                                 订单编号→标准字段
                                                 下单时间→标准字段
                                                 金额→标准字段
                                                 ...
----------------------------------------------------------------
[保存逻辑草稿] [审阅差异/确认版本] [预览物理设计]
~~~

**布局是交互草案**，并不要求首期就实现复杂可拖拽 ER 画布；MVP 可以用“实体清单 + 属性面板 + 关系清单/小型图”，关系边有详情。面向业务语言和确认任务，不强迫普通用户理解主外键、方言和物理表分区。

#### 逻辑实体与属性的最小属性面板

- Entity：中文名、稳定编码、业务定义、归属业务域/过程引用、业务实体类型/粒度（按实际能力定制）、责任人、版本。
- Attribute：名称、逻辑数据类型、是否业务主标识、业务含义、StandardField Ref、来源发现证据（可选）、规则/状态（已确认/待核对）。
- Relation：两端逻辑实体、业务定义、基数、属性配对、确认人及来源证据；未知基数显示“待确认”，不能单凭相同字段名自动保存事实。
- LogicalVersion：精确版本、与最近已确认版本差异、关联/影响的物理模型，变更不会静默改写已发布物理模型。

若当前标准字段库为空，允许新建逻辑概念草稿并清晰显示“目标层标准治理尚未满足”，但**不能在逻辑→正式非 ODS 物理发布时绕过必需 StandardField**。

#### 原逻辑模型骨架复用判断

已经有 LogicalModel / LogicalEntity / LogicalAttribute / EntityRelation 及逻辑→物理表列 Mapping 的领域/Mapper/SQL 基础。重设计前须核对 Project/RBAC、CRUD、版本、跨域引用、正式映射身份与复杂关系的适配性。不能因为表存在就断言 API/编辑器已可用，更不能为跑通 UI 直接把业务标准写进逻辑属性的独立标准字段库。

### S-06 逻辑→物理生成 / 对齐审阅

从**已确认逻辑版本**进入：

~~~text
选择目标：DWD（明细层） / Doris（从合法目标环境推导）
来源逻辑版本：OrderTrade v1   已引用标准字段：12/12（示例）
方案：
  Order → dwd_order（新建草稿/对齐已有）
  OrderItem → dwd_order_item（新建草稿/对齐已有）
  Customer → dim_customer（建议，需确认是否本次范围）
校验：
  数据标准           可用 / 缺失引用
  数据粒度与业务键   已确认 / 存疑
  源头 ODS 版本      已选 / 需要建立
  字段类型转换       需处理 VARCHAR 时间、金额
  目标方言与环境     方言已选择 / 运行环境待配置
[预览表结构与映射差异] → [确认生成物理模型草稿]
~~~

预览中每个物理列应可追踪逻辑属性、标准字段、原始 ODS 列、适用目标方言转换建议。遇到已存在同名/同业务物理模型，必须选择“关联现有模型/生成新草稿/取消”，不能自动复制第二张影子模型。历史“单库单方言、一实体一表”可作为首期生成约束**候选**，是否扩展一对多/多对一映射、版本化如何处理需要评审批准，不能代码层默默假定。

确认只是写草稿设计和关联，**不执行 Doris DDL、不自动发布模型、不为 AI 创建可运行 SQL**。

## 5. 故事板 C：物理设计、开发与真实交付

### S-07 物理模型详情重新以“成果与下一步”组织

顶部从“九个专业 Tab 全部展开”改为摘要 + 按阶段展开：

~~~text
订单明细事实模型 · DWD / Doris
设计：草稿 / 版本 vN（精确）
来源：ODS ods_orders vN（已确认/未确认）
业务：交易 / 下单 · 逻辑模型 OrderTrade vN
标准：12/12 合规（示例） | 映射：待审 2 | 目标环境：未配置
------------------------------------------------------
[继续完善字段与映射]  [审阅并发布设计]  [交接数据开发（需预检）]
↓ 专业能力：结构 | 来源与转换 | 逻辑关联 | 版本差异 | 血缘 | 生命周期
~~~

具体 Tab 保留/合并要以已有实现和阶段需求裁定；业务过程“预留”不可再伪装为真实可用维度，DataDev 未实现的内嵌任务能力不能继续显示一页“尚未开放”却没有去专业工作区的动作。

模型状态必须分栏：结构设计发布、目标环境可用性、实际部署状态、运行状态、下游消费状态。每项都有准确来源，不造一个万能“已就绪”大枚举。

### S-08 发布设计的“人能理解的差异”

首次发布建议展示：本次模型含多少业务字段/技术字段、主标识、来源覆盖、逻辑属性引用、标准字段治理、尚存的未确认转换、环境缺口；技术 JSON diff 收在“查看详细差异”。不得显示“删除 / 旧 null”这种对用户毫无价值的伪操作。发布确认清晰告知**只固化设计版本**。

### S-09 从模型到 DataDev 的正式交接

点击「创建加工任务」前，先展示“交接预检”：

- 要加工的**目标物理模型精确版本**（不能默认最新可变草稿）；
- 源端/上游模型精确版本及来源身份、已确认的字段映射/转换规则；
- 目标 Doris 实例、目标数据库/schema、可连接/可写权限；
- 数据源 MySQL 与目标 Doris 类型兼容提示；
- 作业类型：全量/增量/编排方式必须由用户确认，不能从表名猜；
- 如果缺目标环境，显示“模型设计就绪，但不可执行”，允许返回部署配置。

成功交接后打开**现有 DataDev 的正式 Node/Task 编辑器**，展示可审核的初始 SQL/同步配置候选、源逻辑版本追溯和返回模型的精确链接。新建 Task、保存 Draft、发布 Revision、运行、调度仍由原 DataDev/Integration/Workflow 控制，必须分开操作并显示真实执行/失败回执。

### S-10 业务结果闭环

运行成功不等于口径正确。允许业务 Owner 在订单量确认页看到：统计时间、订单排除规则、去重依据、异常订单数、指标精确版本以及实际质量验证报告。然后进入已有 Metric Validation/Publication → Dataset/Data Service 受治理消费；最终展示一条真实查询/调用成功的证据，才称作“第一次可信业务结果”。

## 6. 现有页面逐一裁定初稿（最终依交互评审决定）

| 当前页面/能力 | 建议类别 | 应保留 | 应改变 |
|---|---|---|---|
| DataSource/元数据 | 跨域交互优化 | 连接、采集、历史/差异能力 | 加入有权限的“从来源继续建设”，保留采集时点 |
| Asset | 小调整 | 资产身份/治理状态 | 现有模型与 Semantic 的受控回链 |
| Semantic 业务域/过程 | 流程优化 | 正式 Domain/Process/引用 | 从过程直接进“标准准备/逻辑设计”，不要跳物理方言 |
| 数据标准 | 基本保留 | 六类正式标准、版本、启停、预置补齐 | 根据标准字段缺口提示可回溯的创建上下文 |
| 标准字段库 | 流程重构 | 角色约束、Standard Ref、过程引用 | 批量候选/冲突复核/复用/待审批，避免逐列搬运 |
| 逻辑模型 | 新设计、补完整实现 | 现有领域/SQL 骨架可评估复用 | 建立业务实体/属性/关系/粒度/逻辑版本作者体验 |
| 模型列表 | 信息架构重排 | 原物理 CRUD、标签、目录与权限 | 清晰区分逻辑/物理视图、设计与运行事实 |
| 表结构 | 局部与流程混合 | 高级物理列配置、主键/索引/分区 | 按 ODS/非 ODS 不同需求渐进显示 |
| 来源映射 | 强流程重构 | Mapping 存储/验证/表达式安全边界 | ODS 候选与批量确认、身份/版本一致；DWD 引用逻辑和 ODS |
| 分层映射 | 归属重审 | Semantic 标准到层字段的真实记录 | 避免与来源映射/逻辑→物理映射重复制真相 |
| 模型血缘 | 语义重构 | 可授权图查询 | 把 CONTAINS 当“自身字段”计数，不冒充真实上下游 |
| 生命周期/版本 | 渐进展示 | 已有 TTL/版本/回滚能力 | ODS 初次建模不要求先填 TTL；发布确认人类可读 |

## 8. 交互高风险门禁（必须体现在页面与服务端）

1. **ODS 保真**：可不绑定标准字段；不静默转换 MySQL 来源数据；来源 ref 与真正列映射要分开识别。
2. **非 ODS 字段强制标准化**：每个业务物理列要求有效 stdFieldId 及角色相关 Standard Ref；仅有 stdTypeId 不能冒充合规。何时在保存/发布阻断、哪些技术列例外，需先由 Product/Semantic/Modeling 确认。
3. **逻辑模型确认**：同名列、业务关系、订单粒度、模型复用、版本更新必须可审阅/确认，不把 AI 推断提升为权威事实。
4. **源表漂移**：已采集证据与当前 JDBC 结构不同必须明确“旧/新”，不能自动以新结果覆盖已发布模型。
5. **目标连接**：Doris 目标方言只表示生成技术能力，不是实际实例/库/表存在。
6. **真实运行**：对来源读取/目标写入/任务运行的新风险分别做权限和审计；Modeling 的确认不构成执行授权。
7. **失效与权限**：FORBIDDEN、UNAVAILABLE、EMPTY、STALE、FAILED 不能合并；必须提供适当回退。
8. **可恢复**：页面刷新、用户取消、并发模型改动，必须从权威存储恢复当前状态；不得靠不可验证的前端缓存虚构成功。

## 9. 优先级与验收路径

- **第一批设计收敛：Slice A** — 首屏与两入口、业务过程/标准字段准备、逻辑设计 MVP、ODS 来源导入/映射闭环。做一条静态/交互走查（不造后端成功回执）。
- **第二批完整 E2E：Slice B** — 逻辑→非 ODS 物理、强标准门禁、设计发布与 DataDev 精确引用、真实运行/质量/消费。
- **第三批延展：Slice C** — 订单明细、SCD/DIM、DWS/ADS、多逻辑实体与多物理目标的映射复杂度。
- **第四批运营：Slice D** — 逻辑/标准/来源变化的 Impact、版本修复、重跑、监控、治理运营。

交互蓝图评审 DoD：业务用户能沿两条起点找到同一可信事实；订单逻辑模型可以解释实体/关系/粒度；非 ODS 强标准门禁无歧义；旧页面裁定有原因和回退；关键动作都能明确“预览/保存/发布/运行/消费”；没有实测的接口/状态仍标未知。签字后才更新 Feature 的 APPROVED 和准备集中工程 PR。
