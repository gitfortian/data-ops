## 0. 设计动机与决策边界

用户新增两条设计判断：

1. 逻辑模型不能在 DWD/DIM 的一行说明中带过：作为业务语义到物理结构的**核心可操作桥梁**，必须真正展示实体/业务属性/实体关系/标识/粒度/逻辑版本，以及从逻辑属性到物理列的精确关系。
2. 旧首页完全不适合目前的用户故事，应依新体系整体规划：同一个项目既有需求协作、真实建设路径和待确认动作，也需要专业五域的真实规模/运行概况、异常、继续草稿等入口。

本版参考此前仓库 `PD-010-guided-business-to-data-journey.md` **PROPOSED** 思路：ODS 直接贴源是明确例外；非 ODS 业务物理设计建议经逻辑模型，但**不得将原型的“先冻结再映射”判定直接当作已批准的生产发布强门禁**。其余原域真相遵守 Semantic/Modeling/Metric/DataDev/Asset/Metadata Owner 边界。

## 1. 新首页的信息架构（取代旧首页）

首页角色是 **“从项目事实与当前职责找到下一步行动”**，不是五域所有列表的拼接，也不是一个没有可操作入口的数据大屏。

| 优先级 | 区块 | 回答的问题 / 交互 | 信息归属或证据边界 |
| --- | --- | --- | --- |
| P0 | 项目/业务主题与主要动作 | 当前工作项目、从需求发起/逻辑模型/已发现来源继续 | 项目上下文；样例为订单分析 |
| P0 | 我的待推进与待反馈 | 我当前职责要做什么、哪个事项/版本、下一步归谁；点击进入**精确协作记录** | 协作记录；协作 RBAC 与专业写权限分离 |
| P0 | 来源到可信交付的业务建设路径 | 来源核验→业务语义→逻辑模型→物理分层→指标/消费交付，每步有行动入口 | 不建第二个“跨域完成状态”真相；阶段条只是设计示意 |
| P1 | 异常/阻塞与待确认 | 来源漂移、指标边界争议、等待业务复核；可定位治理或口径确认 | 真正完成判定应回读对应领域证据 |
| P1 | 继续工作 | 已有逻辑草稿版本、物理编辑草稿及来源层级，恢复具体原型上下文 | 当前浏览会话模拟，**非持久化** |
| P1 | 五域快捷进入 | 接入、定义、开发运行、治理、消费，各回到专业入口 | 不取代专业导航/权限 |
| P2 | 真实项目规模与运行概况 | 数据源、物理模型、正式指标、资产、运行异常、数据消费 | 设计期显示“— / 待连接 Owner”；**不伪造实时值或趋势** |
| P2 | 就绪状态说明 | 设计已保存、环境/任务待部署、实际数据运行/消费必须分别有证据 | 不能以模型保存推导已执行/已发布 |

用户上传的《IA-550 数据协作闭环实施方案 v1.0》要求：保留项目概况与运行情况，增加待受理/待确认/待验收、我提交的需求、工作阻塞和继续草稿；首页提供业务主题级交付进度。这些内容在 v0.7 通过**行动/故事入口+带 Owner 标识的真实统计待接入模块**体现，并未创建新的统计规则引擎。

### 首页默认信息及交互约束

- 当前原型是**订单分析**单项目示例，不推断当前登录用户实际项目或其他项目的数据。
- 默认直接显示待推进事项和具体负责人，可切换**协作职责**，筛选与排序只影响本地演示 UI，不修改现有专业 RBAC。
- 从首页进入需求、问题、模型、来源、治理、Metric、数据消费，可返回专业原路径；点击任务应定位同一个协作对象，而不是泛跳空列表。
- 快捷“逻辑模型”默认进入业务逻辑设计，不先弹所有层的技术字段表；“来源”仍是接入域原入口。
- 旧首页占位页不再与新首页并列展示；PC/小屏有响应式 CSS，主内容与侧信息按宽度重新排布。
- 四个会话指标**仅反映本地演示记录**；六个真实项目规模/运行位都显示待连接而非编造数字。真正实现需设计授权范围、时间窗口、错误/空态与跨域数据来源，且不以被隐藏对象推测权限外总数。

## 2. 建模工作台：逻辑和物理两个一等工作区

**建议的顺序**：

- 业务需求/语义过程 `processId`、Semantic 正式标准字段 `stdFieldId`；
- **逻辑设计**：选择或新建逻辑模型，填写业务模型名称、引用正式业务过程、明确业务粒度、属性/角色/标准字段、实体关系及基数。结构只能建议，不凭名称自动确认业务主键/关系基数；
- **逻辑设计版本**：独立冻结可追溯的逻辑快照（此处仅本地演示），新草稿修改需要新版本，旧版本快照不得变动；
- **非 ODS 分层物理设计**：DWD/DIM/DWS/ADS 选择目标层级、显式复用**某个逻辑模型身份与冻结版本**，再选择上游模型版本、批量载入列，完善业务粒度、清洗、维度、汇总或消费投影规则；
- **逻辑↔物理映射**：一次性展示全表物理列、上游来源列与逻辑属性候选，人工确认精确属性 ID；逻辑或物理当前草稿变化则失效，必须重新审阅；
- **校验/保存/交接**：保存**物理设计版本**并关联逻辑映射快照；DataDev 仍负责加工任务、部署、真实运行。

**ODS 例外**：直接从已采集物理源表开始，源列批量镜像 + 处理时间/分区技术列 + 来源列映射。ODS 可以后续用于逻辑候选提取，但首次 ODS 设计不能强制建立全量逻辑模型或 Semantic 标准字段。

### v0.7 原型已演示的操作

- 打开模型工作台默认进入逻辑设计，当前示例 LM-016 订单支付事实、LM-019 会员实体、LM-026 支付分析主题视图。
- 新建空白业务逻辑模型，填写姓名/业务过程/粒度，添加并编辑逻辑属性、Semantic 引用、实体关系与基数。空白实体不可冻结。
- 冻结逻辑草稿版本，旧快照不可被本次修改覆盖；当前草稿修改后之前的映射审阅失效。
- 从逻辑模型选择 DWD/DIM/DWS/ADS 物理方向，支持已有逻辑版本复用，DWS/ADS 不要求每张物理表复制一个新逻辑实体。
- 在逻辑→物理映射表中显式切换引用的逻辑模型，按物理来源字段提供候选映射并经人工确认；没有冻结版本或来源字段、映射过期时拒绝原型级确认。
- ODS 无逻辑版本仍可进行来源表批量结构编辑、原型检查和设计保存。
- 保留上一轮 v0.6 的依赖字段批量加载、DWD 多依赖冲突决策、DWS 指标反推、ADS 消费投影；保留标准字段→旧精确目标映射的路径作为历史对照。

**重要缺口（正式开发前另评审）**：当前逻辑/物理映射仅演示 ID+版本审阅与小规模示例数据，不是生产的多实体ER图设计器或真实模型生产 API；真实模型版本、逐列来源、Join规则/SQL、语义有效性、SCD、权限、Schema drift、变更影响均须经原 Owner 批准、持久化并真实环境验收。数据标准仍由 Semantic 正式持有，不能让逻辑编辑器制造第二套标准主数据。

## 3. 本版与既有三条协作故事如何衔接

- **需求到交付**：首页受理“订单经营日报”→明确业务目标/范围→逻辑模型设计→DWD/DWS/ADS/Metric 专业任务→技术验证→业务验收→正式交付。协作中心只引用专业版本与结果，不冒充真实执行。
- **数据问题到复核**：首页可定位示例售后表来源漂移、指标分歧；问题单由技术/治理核实处置，业务原场景复核/重开；不把质量规则报警和用户反馈混为一谈。
- **指标口径共识**：MET-026 使用分析样例和精确口径版本确认，实质变更须重新确认；业务确认不能代替有发布职责的 Metric 发布。

## 4. 建议验收清单

| 入口 | 路径 | 通过条件 |
| --- | --- | --- |
| 首页主入口 | `#home` | 展示项目、优先行动、业务路径、风险、续接、五域入口、规模/运行待连接槽位；旧空占位不出现 |
| 首页职责切换 | 协作角色切换 | 高亮当前职责相关事项、不修改 Modeling 专业权限 |
| 首页精确恢复 | 从事项/草稿继续 | 进入相同协作 ID、逻辑模型 ID 或物理分层及编辑草稿 |
| 首页真实性 | 所有项目计数及状态 | 无真实服务数据则明确示例或“—待连接”，不造运行成功率 |
| 逻辑模型从零创建 | Semantic 业务过程→新逻辑 | 空白模型、角色属性、基数可编辑；空属性不可冻结 |
| 逻辑版本 | 草稿→冻结→再编辑 | 老版本不变，新修改使映射待复核 |
| DWD | 逻辑 LM-016→ODS PM-701 | 依赖字段批量加载、逻辑属性对照、精确来源字段映射、审阅后允许原型级设计保存 |
| DIM | 逻辑 LM-019→ODS客户 | 维度属性/SCD 与订单事实不同 |
| DWS/ADS | 分别复用分析逻辑 | 指标/消费合同形成目标字段，可复用逻辑版本；不是所有物理模型都需新逻辑对象 |
| ODS | 已采集业务表→ODS | 允许跳过逻辑，字段及技术列保真，资产写权限不作为前置 |
| 数据协作 | 需求/问题/口径各一条 | 原已测试流保留，确认、验证、运行结果各不相同 |
| 响应式 | 1366 / 1024 / 768 / 390 px + 长字段 | 主内容取得宽度、摘要/辅助区落后；**需要真实浏览器测量和截图，当前仅静态 CSS/JS 检查** |

## 5. 后续开发阶段（仅规划，不自动启动）

1. **UX GATE**：人工完整走查 3 个逻辑模型、五个物理层、三条协作流和新版首页；真实浏览器大/中/窄窗口、键盘及复杂字段值的可访问性验收。
2. **Owner 契约与数据校验**：确认 Semantic→Logical→Physical 的稳定版本和映射 ID、变更影响/权限、源列证据；PD-010 是否接受、草稿阶段/正式发布门禁如何执行由 Product 决策。
3. **实施切片**（需下一次明确批准）：逻辑与物理组合入口→映射/变更审查→新版首页读取真实待办/项目事件→跨域协作与专业结果回读。每片有正常/异常/权限/E2E 测试，保持旧 URL 和功能不丢失。
