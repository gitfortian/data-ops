## 1. 为什么从 v0.5.1 迭代

v0.5.1 的四项有边界收尾、标准目录/标准字段库已记录为历史成果。新提出的**分层建模**及独立上传的**业务到研发的数据协作闭环**是下一阶段新设计需求，不能直接把历史 IA-550 的四项验收覆盖成新需求已签收。

此次新原型在现有五域导航之上增加一个工作入口「需求与协作」，保留首页、我的待办、数据源、业务语义/标准/指标、资产/治理及其它专业入口；模型工作台默认以分层路径呈现，原逐对象映射仍留作对照，已从标准字段进来的目标模型确认由原链路处理。新版本继续沿用项目红白黑品牌方向，不修改正式组件或颜色 Token。

## 2. 分层建模：一个工作台，五条不同默认路径

| 层级 | 先明确 | 来源字段怎么来 | 交互中要补充 |
| --- | --- | --- | --- |
| ODS | 已采集源表、来源结构批次/版本 | 批量保真镜像源字段，显示物理源列；可勾选处理时间和分区列 | 核实类型/来源、技术列语义；不要求 Asset Write 和全量逻辑设计 |
| DWD | 业务过程/逻辑粒度、ODS 依赖和模型版本 | 批量继承一至多张 ODS 字段，来源冲突时人工选择 | 清洗、主键/去重、Join 基数、标准字段引用 |
| DIM | 业务实体/属性、ODS 依赖 | 批量生成维度属性候选 | 业务键、代理键及 SCD 历史策略 |
| DWS | 指标需求和统计周期、DWD/DIM 依赖 | 反推统计日期与汇总度量候选；不是整表直接复制 | 聚合/去重、时间窗口、指标版本、无重复计量 |
| ADS | 报表、API 或数据集的输出合同 | 从 DWS 或直接 DWD 投影目标字段 | 消费权限、输出口径与刷新；不强制 DWS 前置 |

每层都有**依赖 → 全部字段 → 层级规则 → 校验/版本**的实际可操作原型。切换已有依赖或重新加载有本地差异确认；多上游同名列需要显式解决；设计保存与 DataDev 部署/运行分开。

注意：来源表、模型、版本及变换均为**演示样例**，不代表已取得数据源实时结构或与真实 Modeling Owner 形成持久映射。现有生产代码 `detail.tsx` 支持从源表、模型、过程导入和 DWS/ADS 指标反推，但多源血缘、字段级版本映射、运行交接仍是未来实施核对项。

## 3. 数据协作闭环：严格遵循上传方案的三条主线

设计依据：需求方提交的《IA-550 数据协作闭环实施方案 v1.0》。

### A. 数据需求 → 研发受理 → 业务验收 → 交付

试点“订单经营日报”，从业务描述进入待受理；协调人受理、提交方案/范围与验收基准；业务确认；技术负责人按需要拆专业任务、链接成果与版本，提交验证；业务单独验收，最后才能进入交付。期望时间与研发计划独立显示；本地模拟交付不声称实际 API 已上线或 SQL 已执行。

### B. 数据问题 → 研发核实 → 治理/研发处置 → 业务复核

从指标、资产、数据集或分析入口发起反馈，带入当前对象与版本，记录实际与预期差异。可分类为质量问题、运行延迟、口径分歧、访问/产品问题或证据不足。专业处理的进度不等于问题单关闭；业务可确认或重开，记录全部历史。

### C. 指标口径诉求 → 业务与分析对同一版本确认 → 技术验证 → 发布交接

使用 MET-026「支付订单数」试点：业务说明口径，分析复核已支付、未支付、支付后退款、重复回传样例；业务口径负责人确认精确草稿版本；技术复核、指标中心进行专业发布。评论和要求样例不等于确认，公式/时间/粒度实质变更成为新草稿，需要重新确认。**协作页不会直接产生 Metric 域的发布版本或真实运行回执。**

## 4. 责任与证据边界

- 工作入口下新增「需求与协作」，内部只有**数据需求/数据问题/口径确认**三个主视图；「我的待办」提供继续入口，首页有当前事项摘要，不将原专业模型、质量、运行入口搬到协作域。
- 同一个用户可以兼任业务、协调、技术、治理、分析、口径负责人；每条记录显示当前负责人/下一步行动人。协作职责与现有专业操作 RBAC 独立，因此专业只读身份仍可提交业务需求或验收。
- 记录展示范围、状态、任务、成果、精确版本、讨论引用/决策时间线、退回理由；转交先待接收，原负责人留在事项中，接收后才成为新负责人，拒接需说明原因。
- 从协作 → Model/Metric/Governance 并返回，恢复原协作记录与视图，不在协作域复制物理列/指标定义的权威事实。
- 需求验收不等于实际交付，专业设计保存不等于开发任务已执行、指标已发布或数据已生产；所有跨域结果需未来通过 Owner 的**真实版本与回执**验证。

## 5. v0.6 可执行场景与本轮审核重点

[自动化测试](../../scripts/architecture/ia550-v06-prototype.test.mjs) 覆盖：

1. ODS 源表先选、字段批量加载、时间/分区技术列可调整。
2. DWD 依赖候选批量继承；已编辑列不被来源变更/重复导入静默覆盖。
3. 两 ODS 同名字段必须处理后再校验；取消依赖变更保留当前草稿。
4. DIM 独立维度/SCD 路径。
5. DWS 指标反推维度与度量；切指标先确认旧草稿。
6. ADS 能以 DWD 为上游，不强迫全部走 DWS。
7. 校验、设计版本和 DataDev 交接区分。
8. 需求受理/范围确认/专业任务/业务验收/实际交付阶段区分。
9. 数据问题明确核实、处置、复核、重开，原证据不抹除。
10. 指标 v1.2 样例与业务确认分开；v1.3 实质变化重新确认。
11. 协作权限独立于专业只读；跨域返回恢复原事项。
12. 转交待接收、拒接留原因、讨论引用不视为业务确认。

**尚未完成的正式产品要求**：真实浏览器五档宽度/键盘焦点/交互实屏，业务对象/审批与版本回读，来源元数据 Schema 漂移证据，模型持久化、多上游列映射的真实后端实现，实际 ETL/任务、通知与验收 API。上述需要**单独具体设计、Owner 合同评审和开发 PR**，不由此 Draft PR 直接开工。协作阶段二/三的多团队排期、提醒升级、统计仍是后续计划，不在本期做全功能。

## 6. 签收策略

先评审**两个新增设计专题**：分层建模向导（五层各至少一条完整路径）和业务协作闭环（三类代表事项、身份与版本边界）。既有 v0.5.1 的四项小修可单独关闭，但 v0.6 没有获得用户审阅与真实浏览器检验前，**不能称整体 IA-550 签收**。

PR #553 继续 Draft，仅设计 HTML、评审文档与模拟 DOM 回归；不自动合并，不进入生产代码开发。
