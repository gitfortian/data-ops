# IA-550 模型工作台分层建模与依赖字段前置设计复核

Status: **PROPOSED / 需要单独的建模 UX 审核，不能视为 v0.5.1 已签收范围**  
Date: 2026-10-13  
Scope: 只检讨 IA 原型的建模交互，暂不修改任何正式代码、物理模型、路由、权限或领域发布规则。v0.5.1 四项有边界整改独立保留。

## 1. 产品负责人提出的核心问题

现有 v0.5.1 原型按统一的「业务关联→字段设计→来源映射→校验→版本」呈现一张模型只映射一个目标属性。这颠倒了真实建设流程：ODS 首先来自有授权的源表结构；DWD/DIM 一般以现有 ODS 与业务过程/逻辑模型为依据；DWS 从主题/指标需求确定粒度，再找 DWD 上游；ADS 从具体服务/报表/消费需求出发，可能使用 DWS、DWD 或其它获准数据集。**旧的“选择依赖模型→批量加载字段→按差异修改”必须保留为核心步骤，不得藏到“字段设计”之后。**

### 定位：一个模型工作台，按层选择的不同默认向导

| 目标层 | 第一问题 | 先选择什么 | 初始字段从哪里来 | 重点人工确认 |
| --- | --- | --- | --- | --- |
| ODS | 从哪张物理业务表保真进入数仓？ | 物理数据源 + Schema/表 + 采集结构版本；也可从 Metadata 来源表直接进入 | 直接镜像来源列；明确技术时间列、来源追踪列、分区规则的可选追加（均需要目标引擎校验，不默认写入业务值） | 贴源保真、增量键/CDC、源列身份、时间与分区语义、来源漂移 |
| DWD（以及 DIM 独立分支） | 哪一个业务事件/实体，粒度是什么？ | 业务过程/逻辑实体及版本；选择一至多张已保存 ODS/合规上游物理模型和其版本 | 批量导入所选上游字段作为**候选**；按逻辑属性和有效标准字段调整名称/类型/角色 | 主键、粒度、去重、关联基数、标准字段、清洗/转换/多源冲突；DIM 的主数据键、历史拉链/SCD 另处理 |
| DWS | 需要什么统计主题、指标和聚合粒度？ | 业务主题/指标需求、时间周期/维度；确认依赖的 DWD/DIM 模型及版本 | 根据指标候选反推维度与度量列，并从实际依赖模型批量加载列形成可追溯候选 | 分组键、时间粒度、窗口、汇总函数、非加性/半加性指标、去重、指标版本；非全部 DWD 列无条件复制 |
| ADS | 面向哪个受治理消费场景？ | 数据产品/看板/接口或查询需求及输出合同，选已发布的 DWS/DWD 等依赖 | 根据消费字段合同和目标上游结构预装结果列；可组合维度/度量 | 消费字段、过滤/排序、刷新 SLA、授权与脱敏、物化或视图策略、变更影响 |

*以上是建议的 **默认 UX**，不是把“ODS 必须来自业务表 / DWS 必须有指标 / ADS 必须来自 DWS”写成不可绕过的技术限定。允许已有模型编辑、复制、业务驱动、源表逆向、经过确认的自定义路径。*

## 2. 交互流程（必须前置“来源依赖及批量字段”）

模型工作台主页：可用模型树/集合筛选 **ODS / DWD / DIM / DWS / ADS**，以及独立的「逻辑设计」。新建时先选 **目标分层 → 建模依据与依赖 → 自动生成字段草稿 → 修改字段/规则 → 校验影响 → 保存设计版本 → 交接 DataDev**。已存在的模型则直接打开当前依赖/字段草稿，不强迫走向导。

**ODS：** 元数据已发现表 → 选择或确认源表、Schema/结构版本 → 预览全部源列并将其填入目标表 → 同屏追加业务要求的技术时间/分区字段 → 核对源列到目标列一对一关系及非 1:1 异常 → 保存模型结构+逐列来源映射快照 → 返回来源。没有 Asset Write 权限不阻断 ODS 设计。设计保存不是目标 DDL 部署，也不是数据同步完成。

**DWD/DIM：** 选业务过程、逻辑实体/版本和目标粒度 → 选一到多张 ODS 模型版本（可按来源约束筛选）→ 一键加载上游字段清单，**不替换当前已编辑字段**，通过差异选择新增/合并/跳过 → 调整清洗字段、映射标准字段 ID、主键/粒度/关联 Join → 提示待确认表达式和依赖字段版本 → 保存模型设计版本。字段自动带入是提效，物理来源的稳定列 ID 和版本必须仍可查。

**DWS：** 选业务指标/分析主题及其精确版本 → 反推建议的统计周期、维度、度量、业务过程及候选 DWD/DIM → 选择实际依赖模型及冻结版本 → 从这些模型加载候选字段 → 形成分组粒度/汇总表达式 → 明确非加性、重复计量、多指标冲突 → 保存。不能仅因为把 DWD 列复制过来就宣称已完成 DWS 汇总设计。

**ADS：** 选消费用途（看板/服务/数据集）和输出字段 → 选 DWS 或直接 DWD 等真实依赖 → 自动显示可选字段、引用的指标或口径 → 按输出合同筛选/关联/投影并审阅刷新、权限和消费影响 → 保存。这里不能要求每张 ADS 都先建立新的逻辑实体，也不能把设计保存当作公开发布。

## 3. 页面信息结构建议

同一模型页以 **“依赖及来源”作为创建时的前置主步骤**，不是仅在字段设计后放一个“来源映射” Tab。基本信息/业务关系可伴随上下文呈现，而非所有层必须先完成。详细模型页可保留以下功能视图：

- **依赖与来源（首要）**：模型版本/物理 Schema/指标版本、来源身份、快照、权限与漂移；选择后显示“加载字段”按钮和可用字段列表。
- **字段与结构（主工作区）**：字段表一次显示全部列，含来源列、目标列、类型、主键、角色、stdFieldId、转换表达式、分组/分区；可批量选择、重命名、追加技术列。
- **处理规则**：DWD 关联/清洗、DIM 拉链、DWS 汇总/窗口、ADS 输出投影，各层启用相关表单，不显示不适用的空控件。
- **校验、版本与交接**：本次结构差异、标准覆盖、来源漂移、精确上游版本、影响范围、保存设计和进入 DataDev。

**字段自动载入绝不等于无条件绑定**：系统只填充有证据的候选，用户确认目标字段/引用/表达式。切换依赖表后先显示新增/删除/类型变化差异并提供保持草稿/合并/放弃，不静默丢弃手工调整。来源表与模型来源记录分清；选择上游模型并不需要直接重新选数据库连接，除非 ODS/逆向源表或需要真实运行目标配置。

## 4. 已有代码能力（与当前原型差距）

- `data-ops-ui/src/pages/modeling/detail.tsx` 已有「从源表导入」「从模型导入」「从业务过程导入」并支持批量导入字段，模型导入会取得 `getModelingStructure`，按重名过滤并尝试继承标准字段、主键。
- 该页已有 DWS/ADS「按指标反推」：`getModelingMetricDraft` → `previewModelingDerive`，ADS 可选上游 DWS/DWD；其返回的是**建议字段草稿**，并入当前编辑器。
- `OdsSourceJourney.tsx` 已从物理表核对、预览来源字段，并在保存时提交结构、来源身份、逐列映射；只在收到核验成功回执时声称保存成功。
- `logical.tsx` 已有独立逻辑模型作者工作区，逻辑实体/属性/关系应继续保留，不把“逻辑模型”合并为所有分层都必须填写的普通字段表。
- **不应过度承诺**：现有“从模型导入”主要是列复制/合并，来源血缘存在 best-effort 的 `assignImportLineage(...).catch(() => undefined)`；这尚不足以证明多源、逐列映射、SQL/加工任务和冻结依赖已完整持久化。正式实现仍需领域/真实环境验证。

## 5. 与现有产品合同的一致性

按 [PD-010](../decisions/PD-010-guided-business-to-data-journey.md) 的 **PROPOSED / NOT_STARTED** 设计思想，ODS 可直接贴源保真，无须先建立逻辑模型或标准字段；非 ODS 默认经业务过程/逻辑设计桥梁，但不能把未获批准的标准强制发布门禁当成现行生产规则。标准字段仍由 Semantic 持有，物理模型引用其稳定 ID；模型版本、来源/逻辑映射由 Modeling 持有；加工 SQL、实际执行和调度由 DataDev/Workflow 持有。

## 6. 必须补的设计验收

1. 从订单物理表建 ODS：进入页面时已有全部源列（可增加采集时间/分区）；来源→目标列证据保留，回来源无需 Asset Write。
2. 从 2 张 ODS 建 DWD：依赖选择在字段编辑前，字段自动加载，重复列有显式冲突决策；更换依赖表不丢手改字段，未核对的 Join 不会被标成通过。
3. 从业务过程/逻辑草稿建 DWD/DIM：按粒度/角色标准建议，引用真实 `stdFieldId`，不重建一份业务标准目录。
4. 从多个指标需求建 DWS：能够选择指标版本和 DWD，生成维度、汇总度量及时间周期的**待确认**草稿，不能将普通列拷贝冒充已生成聚合。
5. 从看板/数据服务目标建 ADS：允许 DWS 或 DWD 上游，先确定输出合同和消费字段。
6. 修改上游模型/Schema 后：旧字段映射/转换校验失效，出现差异比较与复核；已有版本、历史回执不被覆盖。
7. 设计已保存仍明确区分：DDL 部署、数据同步/加工、调度、质量校验和消费发布的真实状态。
8. ODS 的特殊列与非 ODS 的标准约束在界面中明确区分；不得以最新原型的单字段映射代替整个模型表字段设计。

**结论：当前 v0.5.1 的建模交互不能签收。** 在不扩张其它领域的条件下，应将模型工作台单独做“分层向导和依赖字段批量加载”的 vNext 评审稿，再继续正式 UI 重构。此文件只记录拟议交互，并未自动启动新一轮生产实现。
