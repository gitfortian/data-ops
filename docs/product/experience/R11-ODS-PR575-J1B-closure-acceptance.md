# R11 / PR #575 — ODS 物理核验到离线同步的 J1-B 收口与验收

> 状态：验收合同，**不是**实测通过报告。版本：2026-10-16。唯一交付 PR：#575（Draft）。
> 产品优先级：人工建模完整可用；不引入 Agent、自动 DDL、自动数据资产纳管或另一套同步 UI。

## 一、冻结交付边界

本次“闭环”严格指：从现有 J1 源表工作台发现 `trade_order_detail` → 创建或打开 ODS → 保存逐列映射 → 发布当前物理版本 → **人工作业**执行 DDL → 实时读取目标 Catalog → 保存不可变目标观察 → 导航至现有单表离线同步 → 人工配置、保存、发布 JobRevision → **首次手动运行** → 回到 ODS 工作区读取真实 Batch/Attempt 状态与引擎提交行数 → **独立核对目标数据库中的数据**。

每一步必须有服务端持久 ID、即时核验结果和明确失败处理；不可把页面点击、导航成功或 Catalog 列匹配当作数据库部署或同步成功。

**临时运行限制（签收时必须明确同意）：** ODS APPEND 当前为“同项目、同数据源、同名目标表只允许首次非空批次写入”的持久围栏。后续手动运行、Schedule、Workflow 的再次 APPEND、Retry、Backfill 均会被拒绝。围栏不自动释放；不得删除数据库行以实现重试。这是**首次交付安全闭环**，不是可周期运行的 ODS 增量生产能力。正式周期性运行需要新的重叠窗口账本、目标提交回执和 UNKNOWN 恢复合同。

## 二、最小 J1-B 实测环境

1. 在**隔离测试项目**中准备可读取的源库及可写入的目标库，MySQL 与 PostgreSQL 分别执行一遍；记录 DataSource ID、Database、Schema、表名、数据库方言和已安装迁移版本。
2. 源表实际准备一小组含主键、可空值、至少两行可验证数据的 `trade_order_detail`。保留事前真实行数与用于查询的主键/时间范围；不要把“预期行数”随意写为 2 或固定值。
3. 使用全新的、此前从未被同步写入的目标物理表（如 `ods_order_detail`）。使用当前发布版本的 DDL，由**数据库授权人员在库内执行**，留存实际 DDL 操作记录。
4. 真实连接 Link-Up 引擎、Offline Sync 服务及业务数据库。使用测试账号验证 Modeling READ/UPDATE、DataSource READ、同步任务创建/发布/运行操作的权限；另备一个被撤权账号与另一项目账号。
5. 核实 MySQL 与 PostgreSQL 的 `yak-offline-sync V2` 以及 `yak-modeling V5` Flyway 迁移实际成功，数据库唯一键 `(project_id,target_datasource_id,target_table_key)` 已存在。

## 三、必须留下证据的黄金路径

| 步骤 | 操作 | 判定标准 | 要保留的证据 |
|---|---|---|---|
| J1B-01 | 精确定位真实源表、打开 ODS | 来源 ID + Database + Schema + Table 不发生误匹配 | 源端 Catalog 截图/接口与 Model ID |
| J1B-02 | 保存源字段到 ODS 的逐列映射，发布当前物理版本 | 版本号与冻结列可重新读取；草稿不被误报为发布 | ModelVersion ID、Checksum |
| J1B-03 | 由操作者执行 DDL，并读取目标 Catalog | 物理列类型与可空性完全匹配；约束/索引仍显示未认证 | 数据库 DDL 审计、实时 Catalog Hash |
| J1B-04 | 保存目标观察并重新打开 | 观察 ID、模型版本 ID、目标数据源/Schema/Table/Hash 一致 | Observation ID 与回读响应 |
| J1B-05 | 在现有单表同步编辑器建任务、保存并发布 | `odsHandoff` 三元组保留在**冻结 JobRevision**；绝不自动建表或覆盖写入 | Job ID、Revision ID/版本与冻结定义 |
| J1B-06 | 第一次人工执行 | 创建单一受限 Batch 与 Attempt，目标级数据库围栏已预留 | Batch ID、Attempt ID、围栏行 |
| J1B-07 | 在 ODS 观察记录中“查看执行历史” | 精确读到同版本/观察 ID 的执行状态；支持进入已有任务详情 | executionId、状态、engineJobId、start/end、sourceRows、sinkCommittedRows |
| J1B-08 | 对真实目标库**直接查询并核对数据** | 每条预期主键/目标值符合当前手工测试设计；引擎“提交行数”不可代替此项 | 源/目标 SELECT 与差异明细 |
| J1B-09 | 刷新并返回相同模型 | 观察与执行历史不丢失，不额外建任务或修改来源身份 | 重新进入截图、历史回读 |

任一命令状态 `FAILED`、`UNKNOWN`、响应超时、回读无法解析、目标不一致时，**本次不能标记成功**；只允许重新核验而不是盲目重跑。

## 四、P0 负例（任何一项失败都阻断合并）

| 编号 | 场景 | 必须发生的行为 |
|---|---|---|
| N-01 | 不同项目或撤销模型/数据源权限 | 阻止核验、交接或回读；不得回显旧项目数据 |
| N-02 | 目标 Schema 不同、仅同名表；模型版本已变化；源字段映射漂移 | Offline Owner 发布/认领/提交时重新检查并拒绝 |
| N-03 | 目标缺列/类型或可空性不一致、Catalog 超时 | 显示不确定或结构差异，不允许确认目标就绪 |
| N-04 | `odsHandoff:null`、伪造模型/观察记录、SQL/多表配置、自动建表、OVERWRITE/UPSERT、隐藏 Connector 选项或覆盖表名 | 后端拒绝，不写入 JobRevision/Batch 的可执行路径 |
| N-05 | 两个 Job/两个 Worker 同时向同一目标表首次 APPEND | 数据库唯一键最多允许一方成功预留；失败方不创建 Batch/Attempt |
| N-06 | 已经成功、失败、提交未知后再次人工运行或 Schedule | 永久目标围栏拒绝第二次非空 APPEND，不因任务 ID 或执行状态变化绕过 |
| N-07 | Retry、Backfill 或复用旧 CREATED Attempt | 不得向 Link-Up 自动重复提交 ODS APPEND |
| N-08 | 目标库在执行中断连或引擎响应未知 | 记录真实 `UNKNOWN` 或失败；围栏保留；无回执不得重试、不得写“成功” |
| N-09 | 切换项目、关闭弹窗、切换发布版本时旧请求延迟返回 | 旧项目/旧版本执行数据不可覆盖新视图 |
| N-10 | Windows + PostgreSQL 与 MySQL 实例迁移 | Flyway V2/V5 与实际字段、唯一索引正常；回滚/数据库异常不留下错误的成功 UI |

## 六、下一阶段与本 PR 的边界

本 PR 仅交付人工 **首次 ODS 同步的安全闭环**。真正可重复生产运行是另一个明确门槛：受治理的物理目标 identity，窗口/分区/游标范围冲突判定，原子预留与已提交回执，UNKNOWN/部分提交对账、授权恢复与可追溯人工裁定。在这些能力完成前，不得宣称“自动定时 ODS 数仓建设已完成”。
