## 0. 设计判断

**不要重做五个顶层业务域**，也不要在当前阶段物理合并页面。现在用户抱怨的主要是：每个工程功能占一个常驻菜单，同一个目标要跨几层跳转；每页布局独立设计；多张“概览 / 列表 / 记录”信息重复；从一个对象跳到专业页时身份与返回来源丢失。

设计目标是从“静态能力目录”变成“角色可发现的任务导航 + 工作台组合”，让未来全站统一 UI 重构只需要遵守一套 IA 和页面原型，而不必再次决定业务功能放哪儿。

**实测口径修订（采纳评审）**：
- appRoutes = **106** 条；产品开关生效后 **62 非隐藏 / 44 隐藏**（含资源授权、系统配置两个关闭入口）。
- 业务五域非隐藏叶子 **54**；设置 **6**；工作入口 **2**。54 是全量授权视角的静态业务入口数，并不是某位用户登录后看到的条数。
- 17 导航组、6 个顶层组（5 业务 + 平台设置）。其中首页、我的待办是域外工作入口。
- 还有 config/routes.ts 中未属于 appRoutes 的 **4 条旧 Metadata 地址**；同样纳入兼容审查。
- 当前 menuCodes、permissionCodes、productFeatures 和 Project Scope 共同决定实际菜单可见性。不要把“减少可见入口”写成删除菜单授权。

### 设计目标与不做事项

目标：将 54 个业务叶子在默认导航中收敛为 **20 个候选任务入口**（3+4+3+6+4），并保留合法专业工具及全部旧路径；这个 20 是原型约束，不是签收 KPI，也不意味着所有角色看到全部 20 个。

不做：建立统一的业务状态表 / 大而全 Catalog 或 Run Owner；合并在线、离线与工作流执行真相；绕过 Asset PENDING 上架审查；放宽访问权限；删除旧路径；把 J1 的已实现代码当成 IA 新需求；在此 PR 重构视觉组件。

除上述五域外：**工作首页、我的待办**为快捷工作入口；**平台设置**按现有权限显示项目、组织身份、角色、审批配置、审计等，不另加“管理员”角色判定。项目切换是项目上下文控件，不能当作无权用户的提权入口。

专业工具必须在所属域工作台找到，例如页内“全部工具”面板与可搜索命令入口。**不是仅留一个陌生 URL 或“请去对象详情看看”**。专业能力首次发现不强制知道某个对象 ID；当已有对象时也允许详情内带筛选参数跳转。项目级能力仍按原菜单码与权限检查。

## 2. 页面组合的四种结果（后续统一 UI 重构的实际任务包）

统一术语：
- **PRIMARY / 保留主入口**：代表用户目标的默认工作台入口；
- **COMPOSE / 组合视图**：同一任务的概览、列表、配置、记录以工作台 Tab / 侧栏 / 流程内步骤组织，不立刻删除旧 React 页；
- **TOOL / 专业集合入口**：项目级、跨对象或反向查找工具必须可发现，且可独立直达；
- **DETAIL / 对象上下文**：编辑器、详情、映射、精确运行回执等从对象或任务的稳定身份进入；
- **COMPAT / 兼容旧路由**：旧版、功能开关关闭、重定向和特殊兜底路径，不新增菜单曝光。

**ACTUAL_MERGE / 物理合并代码** 尚不签收：要先证明相同 Owner、状态、操作、权限和生命周期确实一致；“标题相似”或“目前菜单太长”都不成立。

## 3. 任务与导航元数据必须解耦（签收前 P1）

当前 appRoutes.parentId 同时承担详情归属、高亮以及 canAccessNavigationRoute / resolveNavigationMenuCode 的权限继承。**在只读 IA 设计中可填写 proposedWorkspace/proposedView，但禁止直接把旧叶子 route 的 parentId 改到另一个受保护页面**。

拟定三轴设计合同，字段名在实施前由架构评审：
1. **访问轴**：existing route ID、leaf menuCode、permissionCodes、原有合法独立访问权；后端鉴权最终裁决；对有意义的详情保留原授权继承。
2. **呈现轴**：默认哪个工作台/哪个视图高亮；可被专业工具发现，不作为权限父节点；拥有哪条回链。
3. **上下文轴**：可选精确 ObjectRef/RunRef/VersionRef、待核验 projectHint、筛选/选中/返回来源；与授权无关。

工作台壳对**任何有权的子能力**可达；Tab/操作基于各自独立权限，默认选首个合法且确实支持的视图；无权 Tab 不读取受限 API。原叶子菜单码不因视觉合并被吊销。严格测试的最低权限反例：SQL 执行审计仅 resource:sql-execution:read；调用方仅 data-service:access；服务运行记录仅 data-service:observe；质量执行仅 quality:execution:read。还须测试撤权、旧 URL 直达、多个菜单 code 授权组合。

## 4. 跨页面交接合同：先保留原事实，再统一体验

| Journey | 发起与目的（组合视图概念） | 必须携带 / 重新核实的身份 | 返回/异常/证据 |
| --- | --- | --- | --- |
| J1 | 数据源 / 源表 → Metadata 采集任务或目录 → ODS → 建模与 DataDev | 当前项目待核验 Source ID，表/列结构指纹、任务 ID、冻结 RunScope、ODS 模型 ID；目的页重新查 Owner | 保存≠运行，Run 当前目录≠历史冻结清单，ODS 保存后返回正确来源；无 Asset 写权限不阻断建模 |
| J2 | 业务域/过程→标准字段→逻辑/物理模型→指标及反向影响 | ProcessRef、StdFieldRef、LogicalVersion、ModelVersion、MetricVersion | 历史版本与当前草稿显式区分；反向影响可从标准/模型项目级查询 |
| J3 | 消费目录→产品详情→Dataset Query 或 Service Invoke→Usage | ProductKey、Dataset/Service 源合同 ID、ConsumerRef、查询权限 | EMPTY/FORBIDDEN/UNAVAILABLE 区分，声明订阅≠真实 Usage |
| J4 | 项目运行异常→Execution/实例→血缘/下游→授权修复与重跑 | Owner 的 Run/Execution ID、事件时间、实际读写边、影响对象 | 没有证据不虚构影响或“已经恢复”；返回原告警或运行队列 |
| J5 | 分类→策略→访问请求→裁决→审计 | Project、Policy/DecisionRef、请求主体与目标资源 | 403/脱敏/拒绝可审计，不因选择菜单自动授权 |
| J6 | 业务提问→受治理产品/语义→允许查询→证据回答 | 用户授权范围、Metric/Data Product 精确合同、查询执行与证据 | 不批准的新 Agent 写入/发布/执行不能由导航跳转触发 |

目的地永不盲信 URL 中 projectHint；跨 Project / 权限变化要重新读 Owner 并清理旧选中项，迟到请求不得覆盖当前项目。未保存表单在跳转/退出时必须给保存/放弃/继续选项；真实已保存状态基于 Owner ID/版本恢复，不能声称刷新保留未保存内容。浏览器返回需要恢复合法筛选/Tab，敏感标识不塞入公开可传播的 URL。

## 5. 全站统一 UI 重构的前置页面原型体系（只定义，不开始编码）

**先 IA，再统一视觉系统，再域内重构**。未来所有页面先判“产品页面类型”而不是按旧文件目录套相同卡片：
- A. **工作首页/任务入口**：最近真实对象/进行中回执/待办；每条必须有 Owner、权限过滤、状态时间与去向。不新建全域统一任务状态机。
- B. **工作台 / 目录列表**：顶部页面目标与主 CTA，左侧可选实体目录，列表筛选、排序、空/错误态、项目范围，聚合但不假设所有列表都是 Asset。
- C. **对象详情 / 360**：统一身份栏、版本/状态/来源证据、主动作、分组 Tab 与上下游回链；操作权与只读查看明确。
- D. **编辑器 / 配置表单**：分组表单、逐步披露、校验/保存/发布/运行严格分开；脏数据离开确认和底部操作区统一。
- E. **运行与异常工作台**：状态、冻结范围、执行证据、日志、重试/恢复、未知态和当前目录分离。
- F. **专业管理 / 审计**：集合级检索、批量操作、规则、策略、跨对象影响；不要强制先打开对象。
- G. **分析展示与可视化**：Dashboard/大屏/图谱的画布、编辑与查看区别于 CRUD 表格；响应式策略按复杂度设计。

统一的设计令牌、导航布局、表格/表单密度、错误/权限/空态、数据加载骨架、对话框危险操作与键盘可访问性应在后续独立全站 UI 设计规范中冻结。宽度 1440/1024/768/390/320 CSS px 必须分别审核；二维图谱、长表可保留有明确提示的局部滚动。**不要求每页长成同一张 Dashboard**。

建议实际 UI 重构以“完整工作台+其全部表单/详情/失败/窄屏”为交付单元，而不是跨 60 页批量换颜色。菜单规划不会代替下一阶段的商业视觉样稿、交互原型、真实可用性验收。

## 6. 菜单迁移与回退合同（不写迁移代码）

1. 原 106/106 appRoutes 保留可访问，原 4/4 旧地址保留语义；不要重用旧 route ID 指向另一个业务 Owner；新工作台 URL 仍需单独审批。
2. 原 RBAC leaf menuCode 和业务权限不变；“隐藏于默认侧栏”是呈现层功能，不代表 Flyway 菜单 visible=0、active=0 或撤掉角色授权。
3. 如后续新增/调整菜单目录，**只新增迁移，不回改已执行 V2 baseline**；验证真正应用 baseline + 增量迁移的有效目录与前端契约，并覆盖 MySQL/PostgreSQL 支持环境、全新/升级、重复部署、发布顺序和回退；不要仅靠现有 V2 baseline 静态解析测试作证。
4. 回退开关只回退菜单呈现和导航映射；旧 URL / 角色授权 / 领域对象与日志不受影响。
5. 需校验所有 106 路由不同 project / restricted role / deep link / 刷新 / 返回 / 403 / 404 / 旧菜单 code / 旧别名参数完整；详情不因“视觉高亮改 parentId”扩大权限父链。

## 7. 与既有 J1 / 业务门禁区分

**已有并需复用**：#539 六屏 V3.1、#540 S1（来源→采集任务→ODS）、#544 S2（Metadata 提交事实→Asset PENDING 交付代码）、Asset Catalog 技术实体双视图、历史 Run 冻结范围、已有来源映射与权限负例。
**本次 IA 新增**：导航显示/高亮和工具可发现性、工作台组合方案与完整兼容/返回合同。
**不属于本次授权**：S2 真实环境部署开关、非 ODS 建模/完整 DataDev 业务合同（PD-010/F-040）、首页新增跨域真实聚合 API、自动执行发布或上架。

**J1 特别回归**：#539 的已签收流程不因 IA 改写，Asset 治理与 ODS 建模是并行操作；不能因为缺 Asset Write 权限使 ODS 不可保存。冻结 RunScope 必须与实时 Catalog 明确区分；元数据超时不冒充已成功。
