## 2. 三条「从用户目标到下一动作」端到端走查

### T1：订单运营日报（DWS → ADS）

`订单过程` → `已发布 DWD 事实` → `DWS-02 行粒度核查` → `DWS-03 时间×地区` → `DWS-04 COUNT DISTINCT(order_id) 与金额是否重复的逐项业务确认` → `DWS-05 设计审核` → `不可变 DWS ModelVersion` → `ADS-01 订单经营日报` → `ADS-02 明确汇总来源与粒度` → `ADS-03 输出日期、地区、订单数与金额` → `ADS-04 口径/刷新/使用者` → `ADS-05 发布**应用设计**` → `ADS-06 显示 Dataset/BI 交接待完成`。

完整行为必须包括「没有 DWD 版本」「支付金额为重复的订单头列」「Metric 未发布」「Modeling 已发布但 Dataset 不可用」四个异常断点。

### T2：订单明细 API（ADS 从 DWD 显式例外）

`ADS-01 明细查询用途` → `ADS-02 行粒度=订单明细行，用户显式选 DWD` → `ADS-03 输出 order_id/item_id 等稳定业务键、字段权限和参数` → `ADS-04 排序/分页/目标新鲜度` → `ADS-05 模型设计审核` → `ADS-06 交接 Service Owner；没有合法 Service 发布/授权时状态仍为不可调用`。

重点验证：切回 DWS 会丢失明细业务键，原型必须主动说明并阻止静默切换。

### T3：草稿恢复和权限变化（跨两层）

`保存未完成 DWS/ADS 草稿` → `退出` → `按 project/model/revision 重开` → `上游发布新版本或权限撤销` → `展示当前冻结/最新差异` → `保持原已保存草稿、审查迁移、或取消`。不应因只读缓存能显示结构，就继续允许正式发布或跨项目查看敏感数据。

## 3. UX-0 联合决策与建议默认值（用户未签收）

| 决策组 | 推荐方案 | 需要确认的产品分歧 |
|---|---|---|
| J-1 DWS 起点 | 先确认事实粒度，再设计汇总时间与度量 | 是否首期只准单一 DWD 主事实、多 Join 专题后置 |
| J-2 DWS 时间 | 业务时间 + 时区 + 周/月业务日历 + 桶为显式决定 | `ALL` 是否作为单独的无时间桶类型 |
| J-3 DWS 度量 | COUNT DISTINCT 必须显式业务键；SUM 必须显式来源字段、过滤/口径 | 业务负责人怎样确认口径、Metric 是否首期强依赖 |
| J-4 ADS 起点 | 使用目的和消费方先于数据来源 | 首期场景是否先覆盖报表/Dataset/API 三种、其它后置 |
| J-5 ADS DWD 例外 | 仅明细型明确进入 DWD，换源差异/数据丢失需人工确认 | 跨过程、多事实 Join 是否晚于首期 ADS |
| J-6 版本与发布 | 草稿可保留缺口；设计发布须过专业审核；真实运行/消费用独立状态 | 需不需要独立的“准备交付”审核环节 |
| J-7 页面结构 | 两套独立流程均嵌入同一个模型对象工作区，无新的专业工具菜单 | 页面操作应采用阶段页签还是上下文引导卡 |
| J-8 权限与治理 | Modeling / Metric / Semantic / DataDev / Security / Dataset/Service 各维护原域证据 | 不可用的权限请求应就地申请或跳转原域 |

**拟定默认：** J-1～J-8 均按「推荐方案」进入低保真**候选**；只有用户明确同意 UX-0 才启动下一阶段。讨论、提交 PR、文档合并、已有代码运行、GitHub CI PASS 都不等于产品签收。

## 4. 必须保留的认知与视觉约束

- 建模工作台**依对象组织**：DWS/ADS 的完整编辑对象可重开，结构/标准与粒度或消费合同有统一发布审核汇总；不能把每一项表单新造独立菜单。
- 用户应能清楚看到「来源已发布」「设计草稿已保存」「建模设计已发布」「DataDev 执行未知」「Dataset/Service 未发布」「消费者访问未获准」等互不等价事实。
- 来源和应用流程有快速返回上一事实的链接，跳转携带 `projectId / modelId / versionRef`，不会跨标签丢对象。
- 高保真最终遵守站点真实导航、Ant Design 组件/设计 tokens；**低保真阶段优先验证流程**，不得提前做成旧 IA 的复制稿或 UI 写死版。
- **默认先人工专业建模**，不增加 Agent 自动生成入口掩盖必填的时间、去重、来源/指标/权限专业判断。
- 正式数据库写入/Runtime/数据质量/Query/Invoke/Usage 的执行授权和真实 E2E 仍由 DR-07 #557 等原 Owner 掌控，不属于 UX 签收自动授权范围。

## 5. 用户怎样签收 UX-0

本轮请求两个独立的产品判定：
1. `DWS_UX0=ACCEPTED` / `REVISE`：是否接受 DWS 先来源事实粒度、再时间分组、再逐项度量、最后审核发布的完整链路及 DWS-D1～D6 的建议。
2. `ADS_UX0=ACCEPTED` / `REVISE`：是否接受 ADS 应用目标先行、显式来源模式、输出/消费合同和安全交接的链路及 ADS-D1～D6 的建议。

只有 **DWS UX-0 经评审** 才能新建独立 `R13-DWS-lowfi-v1.html`；ADS UX-0 经评审才能新建独立 `R13-ADS-lowfi-v1.html`。低保真同样必须经过用户实际审阅，才能基于它们**全新**制作各自高保真。即使 UX-0 两者都接受，仍**不得直接启动 R13-C 功能代码**。
