# R13-C3：ADS 只读交接证据 UX 设计

状态：UX Gate 初稿，待产品评审；不是生产实现。  
关联：Issue #602；前置依赖 PR #599（C1）与 PR #601（C2）。

## 1. 设计目的

C2 的第 6 步已经区分“合同已保存”和“数据已交付”，但当前只用一段说明文字提示 DataDev、Runtime、Quality、Dataset、Service、Usage 尚未接入。用户仍无法判断每个域到底是未配置、没有记录、暂时不可用，还是已经有可追溯证据。

C3 将第 6 步升级为**只读交接证据台**。它回答“每个下游真相域目前能证明什么”，不回答“能否直接生产消费”这种跨域综合结论。

## 2. 信息架构

第 6 步内部提供两个同级视图，默认进入「交接证据」：

1. **交接证据**（默认）：按事实所有权域分组展示 Metric / Semantic、DataDev / Runtime、Quality、Dataset / Service / Usage。
2. **修订历史**：保留 C2 的不可变合同修订列表，历史修订只能载入为新草稿，不可原地编辑。

页面头部保留当前合同修订、合同 SHA-256、保存人和保存时间。证据卡片必须绑定当前合同修订；切换历史修订只查看历史合同，不能让历史引用的下游状态冒充当前状态。

## 3. 交接证据卡片

每张卡片使用同一信息顺序：

- **域名称 + 明确状态**：状态来自源域真实响应，不由 Modeling 推断。
- **证据对象**：对象类型、ID、版本/运行 ID（如果源域实际返回）。
- **来源事实**：源域名称、更新时间/证据时间（如果源域实际返回）。
- **解释与下一步**：例如“配置 Metric 引用”“查看任务记录”“前往质量结果”。只有实际存在、且当前用户有权访问的目标才显示详情链接。
- **失败信息**：显示可安全公开的错误摘要；不把异常细节、跨项目对象是否存在等敏感信息暴露给无权用户。

四组域的职责与限制：

| 分组 | 负责真相 | C3 可展示 | 不可推断 |
|---|---|---|---|
| Metric / Semantic | 指标定义、发布版本、语义标准 | 指标引用 ID、实际版本、源域核验状态 | 只保存了 metricVersionId 就等于已发布或语义正确 |
| DataDev / Runtime | 任务、版本、运行记录与回执 | 真实任务/运行 ID、状态、开始/结束时间、失败摘要 | 没有记录不等于运行成功；未接入不等于未执行 |
| Quality | 规则、质量运行与结果 | 真实规则/运行 ID、结果状态、证据时间 | 没有质量结果不等于质量通过 |
| Dataset / Service / Usage | 交付对象、服务与消费授权 | 真实 Dataset/Service 引用、授权核验结果、范围/时间 | 服务存在不等于当前用户已授权或可消费 |

## 4. 状态词典

状态至少区分：

- `NOT_CONFIGURED`：用户尚未在合同中配置该类引用，且该事实由当前合同直接证明。
- `NOT_CONNECTED`：当前产品尚未接入对应源域只读查询；不是源域“没有数据”。
- `NO_RECORD`：已成功查询且有权读取，但源域明确返回没有对应记录。
- `PENDING` / `RUNNING`：源域明确返回待处理/执行中。
- `SUCCEEDED` / `FAILED`：源域明确返回的终态；保留源域状态和证据 ID。
- `STALE`：引用版本或证据与当前合同/上游指针不一致，且有真实比较证据。
- `FORBIDDEN`：当前调用无权读取；不泄露对象是否存在及其内容。
- `UNKNOWN`：源域响应无法核验、超时、结构不兼容或信息不足。
- `NOT_APPLICABLE`：该合同确实不适用该项能力，并有明确业务规则依据；不可当作通用兜底。

不得把 HTTP 404 一律解释成 `NO_RECORD`：先依据源域的项目授权和接口语义判断。超时、5xx、反序列化错误不能被折叠为空列表。

## 5. 首屏与交互规则

1. 顶部展示“当前合同 Rn · SHA-256 · 最后保存人/时间”。
2. 明确的提示条：“合同设计已保存不代表数据已运行、质量已通过或消费已授权。”
3. 默认显示四组只读证据卡片；未知/未接入状态使用中性或警示样式，不使用绿色成功色。
4. 不创建综合“已就绪”徽章，不计算一个看似权威的总成功率。允许展示已核验/待核验计数，但计数必须基于当前响应并注明查询范围。
5. 点开证据详情应导航到源域对象详情；没有真实 ID/URL 时不显示可点击的假按钮。
6. 重试只重新读取证据，不触发 SQL、任务、质量执行、发布或授权写入。
7. 进入「修订历史」后保持只读；“作为新草稿编辑”沿用 C2 的既有确认流程。
8. 源域超时/无权限/未接入必须保留可见状态；页面刷新不能回退到样例数据。

## 6. 必须先确认的技术问题

开发前需逐一从当前主线代码核验下列能力，禁止凭类名猜端点：

- Metric / Semantic：是否存在按项目授权的只读 Metric 版本查询；返回的发布状态、版本 ID 和语义标准如何表达。
- DataDev / Runtime：是否有从 ADS model ID / contract revision 追溯任务和运行证据的稳定关联键；若无，不允许按模型名模糊匹配。
- Quality：是否有可按关联对象查询最近真实结果的只读 API；规则定义存在不代表有运行结果。
- Dataset / Service / Usage：消费授权查询由哪个域持有，能否在当前项目上下文中核验用户、服务和资源范围。
- 所有域：项目隔离、读权限、超时、缺记录、状态枚举、更新时间、分页上限与详情链接。

若源域尚无可靠关联键或只读 API，本轮展示 `NOT_CONNECTED`，并单独提出域内能力 Issue；不能在 Modeling 内复制或重建源域真相。

## 7. 原型评审清单（UX Gate）

- [ ] 默认视图让用户一眼区分“合同设计”与“运行/质量/消费证据”。
- [ ] 四组卡片的命名符合各域所有权，不让用户误以为 Modeling 可以修改源域状态。
- [ ] `NOT_CONNECTED`、`NO_RECORD`、`UNKNOWN`、`FORBIDDEN` 文案与行动建议明确不同。
- [ ] 未授权/跨项目场景不会泄露资源是否存在。
- [ ] 修订历史保留，不被证据卡片挤出首屏；历史合同不会混用当前证据。
- [ ] 静态原型中的示例状态有醒目标识，不会被误认为真实数据。
- [ ] 产品评审签收后，才进入 API 盘点后的高保证实现设计。

## 8. 验收方向（供后续实现 Issue/PR 使用）

每个状态都有 API/组件测试；覆盖当前合同、历史合同、无引用、无记录、过期引用、运行中/成功/失败、质量无结果/失败、授权未知/拒绝、403/404、超时、源域不可用、跨项目 ID 和权限撤销。前端完整 Jest、类型基线、发布构建，后端架构/Product Guard 全部通过。API-backed 黄金故事必须使用真实服务端证据；测试 fixture 只允许用于自动化测试。
