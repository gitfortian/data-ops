## 1. 全局交互方案：不是再建一个新的平台

### 1.1 用户看到的导航

建议**不新增一级菜单**，在现有「标准、指标与建模」和各数据源/资产详情提供上下文入口。专业用户仍可从「数据标准」「标准字段」「物理模型工作台」「数据开发工作台」直接进入。

~~~text
现有来源、业务过程或业务目标
   │
   ├─「从来源继续建设」── 可信 ODS 镜像 ─┐
   │                                    ├─ 数据标准/标准字段治理
   └─「按业务目标设计」── 业务问题与过程 ─┘
                                        │
                              逻辑设计（实体、属性、关系、粒度）
                                        │
                         预览目标分层的物理模型/对齐既有模型
                                        │
                      发布设计（Model Version）≠ 物理部署
                                        │
                        交接原 DataDev/Integration 执行能力
                                        │
                     真实质量、安全、血缘与 Metric/Dataset 消费
~~~

主任务上下文推荐在页面顶部为**轻量导航进度条**；不创建新一套「建设任务」业务真相。跨页面跳转携带短期候选引用，目标页面用当前 projectId、权限、版本、证据重新加载；不从 URL 直接相信某个 StandardField / 来源字段已授权。

### 1.2 页面头部统一组件的内容（建议）

- 左侧：当前用户任务「建立订单数据模型」，来源上下文「交易 / 下单」、Project Space；
- 中部：阶段「业务理解 → 标准准备 → 逻辑设计 → 物理设计 → 开发运行 → 交付」，无可核验来源时显示“待核验”，不是灰色“已完成”；
- 右侧：主要下一步 CTA（每页最多一个），「查看来源证据」「待确认 3 项」等次级动作；
- 辅助：展开「对象/版本/权限/当前工作是否已保存」信息；
- 不提供一个跨域可编辑的“总状态”，模型版本和任务执行状态来自各自 Owner。

### 1.3 所有页面共用的五个动作词

| 动作文案 | 作用 | 必需回执 |
|---|---|---|
| 预览建议 | 计算候选，不写权威业务对象 | 证据覆盖、未知项、建议理由、过期风险 |
| 保存草稿 | 写当前拥有域的可编辑定义 | 正式对象 ID、revision、可重开链接 |
| 确认引用 | 按权限/版本/证据确认标准/来源/逻辑关系 | 原域写入结果、冲突项、审计记录 |
| 发布设计 | 固化某个确切设计定义版本 | 精确 version ID、摘要与差异 |
| 部署 / 执行 | 经专业环境及权限审批实际运行 | target、job/execution ID、结果/日志；不能用保存回执冒充 |

## 2. 逐屏故事与信息架构合同

### P01｜建设入口：从业务问题或已有数据开始

**服务故事**：US-00，US-01，US-04；**主角色**：业务负责人、建设实施者。

~~~text
我要建设什么？
┌─────────────────────────┐   ┌─────────────────────────┐
│ 我有业务问题             │   │ 我有业务数据             │
│ 每日订单量、支付金额…     │   │ 从已连接的数据源或资产出发 │
│ [说明目标并继续]         │   │ [选择已有数据并继续]       │
└─────────────────────────┘   └─────────────────────────┘
近期来源：订单库 / trade_db / trade_order         （仅显示当前用户可访问）
最近设计：订单（ods_orders）· 设计已发布 · 环境状态待核验
~~~

**加载依据**：仅从已有项目、正式元数据/资产/模型 API 获取已授权摘要。最近模型不是新实体；失败、空数据、无权限严格分开。

**主要动作**：
- 目标入口：提出用户要回答的问题，先得到需要确认的业务事件、日期、指标定义草稿，不自动创建 Semantic/Metric 正式定义。
- 来源入口：选择现有来源表/资产，进入 P02，不要求用户先知道 ODS/DWD/Doris。
- 已有工作入口：精确回到某个模型/业务过程对象，不因改名而丢失；不能只按名称重新搜索绑定。

**完成事件**：用户选择目标/来源的**导航上下文**建立。尚无“模型已创建”等写入回执。

**异常**：来源连接失效→“来源暂不可用”；无权→不展示敏感详情；没有任何源→有权限的“去连接数据源”。

**待裁决**：入口挂在现有模型工作台的默认空态、全局快捷创建还是业务过程页的辅助入口？PD-010 审批前不加顶级菜单。

### P02｜来源证据核对：确认这张表是什么

**服务故事**：US-02、US-03、US-09；**角色**：数据实施者。

~~~text
已发现：trade_db.trade_order     来源：订单库 / MySQL
采集：本次采集版本/时间/覆盖 [证据详情]
字段：当前采集列数（按真实快照计算）；主键：order_id（如果采集证据支持）
已知异常注释：order_time 时间格式不统一；order_amount 金额可疑
已关联模型：ods_orders（若正式来源身份可解析）  [查看]
[继续建立/补全 ODS 来源模型]      [先理解业务]
~~~

**展示规则**：
- 数据库类型/字段类型来自 Metadata 正式快照或有权访问的 DataSource Catalog，标记实时 vs 历史；
- “列注释声称 5% 不一致”仅是**源表注释**，不能显示“平台已检测 5% 异常”；
- 现有 ODS 模型必须按稳定来源身份发现，不只因名称相似推断同一对象；
- 来源元数据字段数与模型字段数分开计数：#512 的“采集 17 vs 模型血缘字段 19”须解释技术列、导入差异或版本差异，不能直接贴“100%”。

**下一步**：首次建模 P03；已有模型则 P03 的“补全/查看差异”模式。不得静默创建第二个 ods_orders。

### P03｜ODS 来源模型：一次性导入并确认来源映射

**服务故事**：US-09、US-10、US-11；**主角色**：数据架构师/实施者。

~~~text
来源模型草稿：订单主表              分层 ODS
来源：订单库 / trade_db.trade_order   来源快照：版本/时点
目标名称：ods_orders    物理方言：Doris（若尚无环境，明确“仅设计”）
──────────────来源字段与设计结果───────────────────────
目标列        来源列                 源技术类型   映射处理     证据/风险
order_id      trade_order.order_id   VARCHAR(32)  直通候选     PK 来源
order_time    trade_order.order_time VARCHAR(32)  直通候选     格式异常线索
order_amount  trade_order.order_amount VARCHAR(32)直通候选     脏金额线索
…              …                      …           …             …
技术生成列：单独分组，必须显示生成依据（不算来源同名列）
──────────────确认摘要────────────────────────────────
待确认直通 17 / 有冲突 0 / 无候选 0（示意，实时计算）
[审阅差异] [保存草稿并确认本次来源映射]
~~~

**关键设计**：物理结构、模型级 SourceRef、字段级映射**在一次明确的用户提交语义中一致写入**。如果底层暂未支持跨域原子提交，必须设计可重试/补偿/验证回读的服务端业务事务，不能靠前端依次调用三个 API 就称“同时成功”。导入选中的真实列候选可由名称、序号、来源证据建议；同名只有在 ID/类型/覆盖可核对时才能获得“待确认候选”，不是自动成为正式来源血缘。

**重新导入**：强制差异预览（新增列、删列、类型/长度变化、用户人工修改/标准引用冲突、目标技术列保护），明确取消/采纳选中；不通过 setRows 全量覆盖已治理的列。源表漂移、权限变更、已发布模型与当前草稿冲突必须阻断静默覆盖。

**ODS 特别规则**：可没有 StandardField；时间/金额脏原值保持原样，不能为了 Doris 类型校验悄悄选择 DECIMAL/DATETIME；若目标 Doris 不支持来源原生类型，要明确**源技术类型、目标存储类型、显式表达式/保真方案**三者，待工程确认。首次只保存模型草稿不代表物理表已创建。

**提交回执**：返回模型 ID/草稿 revision、来源表稳定引用、列总数/正式映射总数、存在冲突项；用户可逐列回读。**下一步**：「查看已保存的来源模型」或「继续确认业务语义」。

### P04｜业务理解与标准准备：明确业务过程和标准覆盖

**服务故事**：US-04～US-08；**主角色**：业务负责人、标准治理者。

页面对象不是再建一个“标准库”。页面是基于已确认业务过程的准备面板：

~~~text
交易 / 下单（order_create）
业务事实：一次下单事件          业务粒度：订单头 1 单；明细 1 行商品
来源支持：trade_order MAIN / trade_order_detail DETAIL（需要核对确认）
标准准备：已复用 0   待复核候选 12   冲突 2（示意）
----------------------------------------------------------
候选业务属性      正式标准字段         来源/结论            决策
订单号            未存在               需类型标准           [查看候选]
客户编号          可能同义字段         有冲突待合并         [核对]
下单时间          未存在               时间口径待确认       [核对]
订单金额          未存在               单位/异常策略待确认   [核对]
订单状态          未存在               跨年份码值不一致     [核对]
----------------------------------------------------------
[审阅并采纳标准字段]   [查看正式标准字段库]
~~~

**业务规则**：
- 类型/单位/口径/安全/码值/命名标准由 Semantic 权威维护；标准字段角色按既有 PROCESS/DIMENSION/METRIC 要求校验；
- “补齐预置标准”创建的是可复用基础标准，不是业务字段；标准字段库当前为空要明确说明；
- 候选可一键复用**精确已存在 stdFieldId**，不能仅按名称相同自动合并；
- 批量提交只通过 Semantic 原业务保存接口，显示**新增、复用、待生效、冲突、未执行、回执未知**各自数量；网络丢回执先重查正式 ID，不能按失败重试造成重复；
- 一条来源字段不必都成为独立标准字段：ODS 技术字段与脏值观察可保留不治理；但是后续非 ODS 字段准入受正式强制门禁，不能因为源字段存在就直接入模；
- 业务过程是否绑定某个字段是独立的**过程引用**事实，不等于该 StandardField 的存在或启用。

**下一步**：有已确认标准字段及过程引用→P05 逻辑设计；有缺口→返回原 Semantic 标准字段专业页并保留引用上下文。

### P05｜逻辑模型主页：以业务实体和关系作为第一视图

**服务故事**：US-11L；**主角色**：业务分析人员/数据架构师。

**建议首屏（不要求首版重型拖拽 ER 画布）**：

~~~text
逻辑模型：订单交易模型（草稿）    业务域 交易 / 关联过程 下单
说明：描述业务对象、属性与关系，不决定 Doris 物理表
[实体]     [关系]    [来源证据]   [版本与影响]
---------------------------------------------------------
实体清单              业务关系/问题             右侧属性
订单 Order            订单 —— 客户（1:N? 待确认）   属性 / 标准字段 / 角色
订单明细 OrderItem    订单 —— 明细（1:N? 待确认）   订单ID / 正式标准ID
客户 Customer         [待确认的来源证据]         下单时间 / 待定
                                                金额 / 待确认
[新增/复用实体]   [确认关系]   [保存逻辑草稿]   [审阅并固定逻辑版本]
~~~

**实体**：稳定实体 ID、名称/编码、业务定义、关联业务域与过程 Ref、业务角色、主标识候选、事实粒度、已有版本；**不写目标数据库、物理字段类型、索引和 TTL**。

**属性**：稳定 Attribute ID、逻辑名称、含义、是否逻辑标识、可空的业务解释、StdFieldRef（真实绑定/待补）、来源表列证据（若有），单独区分“业务属性”和“表里确实有同名物理列”。

**关系**：端点、业务语义、基数、链接字段/业务标识、证据来源与确认人。未证实的外键/同名推测保持“候选/未知”，不能自动登记可信血缘。

**版本**：逻辑模型保存草稿与正式确认版本区分；一个逻辑实体可有多个物理落地版本。用户修改逻辑版本不得静默重写已发布物理模型。

**旧代码复用限制**：目前 LogicalModel/Entity/Attribute/Version、EntityRelation、映射表等骨架存在，但 \`LogicalAttribute\` 当前没有 \`stdFieldId\`、过程 Ref、项目/权限版本合同；不能把旧 DAO 当现成的前后端完整服务。先核对引用设计、必要兼容迁移和版次身份，避免反向复制 Semantic。

**回执**：逻辑 Model ID + revision/版本、实体数量、待审关系/标准缺口、与物理模型已有关系。**下一步**：「预览物理设计」。业务概念未确认可保存草稿，但不能进入合规非 ODS 的正式发布。

### P06｜逻辑→物理方案：明确不是一键生成生产表

**服务故事**：US-11P、US-12、US-13；**角色**：模型工程师/业务审阅者。

~~~text
逻辑模型版本：订单交易模型 v1（精确）      [查看逻辑定义]
目标分层：DWD（或 DIM）   目标方言：Doris
目标环境：尚未绑定（仅允许设计）
----------------------------------------------------------
候选设计              建议动作             业务事实与来源引用
dwd_order             关联已有/新草稿      订单级事实、Order 属性
dwd_order_item        关联已有/新草稿      商品明细粒度、OrderItem
dim_customer          另一次实施范围       需要确认 SCD / 主数据历史
----------------------------------------------------------
字段检查：正式标准字段 12/12 · 类型转换待确定 3 · 来源待核对 1（示例）
[字段级详细差异] [目标模型关联/创建策略] [确认生成物理设计草稿]
~~~

**校验与决策**：
- 行/实体到物理表允许多对多建议，但首期真正生成规则需单独决策；不能仅凭业务命名自动批量生成 3 张表；
- 现有模型存在时默认**不复制**，展示合法引用/冲突/版本，用户可选择“复用并建立关联”“新建另一模型”“取消”；
- 物理字段由 StandardField 的业务语义、逻辑属性及目标方言类型三方审查，任何 VARCHAR→DECIMAL/TIMESTAMP 转换必须显式表达异常规则；
- 默认**所有非 ODS 目标字段**纳入标准字段强约束。若处理时间、审计列等需例外，必须按 PD-010 审批后的**明确技术列定义 + 来源/生成规则 + 审计**豁免，不能以“业务字段”模糊绕过；
- 无 StdFieldRef 的逻辑属性可继续留在草稿/待治理清单，但不能让目标非 ODS 已发布设计冒充标准合规。

**确认效果**：创建/关联**物理模型草稿及逻辑→物理映射**，返回稳定 Model ID 和版本/草稿 revision。**绝不执行 DDL、发布模型版本、创建调度或把建议的源字段直接视为真实数据血缘。**

### P07｜物理模型详情：按建设阶段展示成果

**服务故事**：US-11、US-12、US-15；**角色**：模型工程师。

建议顶部摘要，不再堆九个同权一级 Tab：

~~~text
物理模型：dwd_order（DWD · 订单级事实）
设计版本：草稿/已发布 vN    目标环境：未配置    运行任务：未关联
业务语义：交易 / 下单  →  逻辑模型 Order v1
来源：ods_orders v1（若已确认）     标准字段：12/12（示例）
待处理：来源映射 1、时间转换 1、目标环境 1
[继续完善模型]     [审阅设计发布]     [交接数据开发]
专业详情：结构 | 来源/转换 | 逻辑关联 | 版本 | 血缘 | 生命周期
~~~

**关键调整**：
- **结构**：保留技术方言、列类型、主键、分区等专业配置；
- **来源映射**：ODS 来源字段映射与非 ODS 的上游模型字段/转换表达式在同一专业区域不同模式展示；与“分层标准落地”不混成一张重复表；
- **业务过程**：提供真实 ProcessRef、过程字段/逻辑引用与跳转，不能保留空的 M4 占位假入口；
- **血缘**：拆分“模型包含 19 字段”与“真实上游/下游读写依赖”，不把前者称“下游 19”；
- **生命周期**：保留但只有目标分区和运行环境满足条件才给 TTL 下发，不能阻断来源设计；
- **版本**：简述快照与治理引用，首次发布展示人类可读字段增删改摘要，不用 \`columns[10]\` 的 JSON 路径作为主要对比；
- **加工任务**：当功能未打通时用**真正的交接动作**或“尚缺输入，先补什么”，不再把纯占位 Tab 当成用户完成状态。

### P08｜设计发布：分离“设计有效”和“可运行”

**服务故事**：US-11、US-12；**角色**：建模工程师/治理审阅者。

发布前“模型设计审阅”显示：
1. **版本范围**：当前保存的结构 revision、关联逻辑模型版本、源/标准引用的核验时点；
2. **模型粒度**：下单过程 / 每订单一条（如果确认）；
3. **结构摘要**：新增/删减/修改列（以业务列名为键）、关键字段、主键、分区；
4. **治理校验**：非 ODS StdFieldRef 全覆盖、项目/角色标准合法；ODS 贴源豁免；
5. **映射完整性**：来源已确认数、待治理数、版本漂移/权限失效；
6. **不妨碍设计的运行缺口**：Doris 未连接、目标库不存在（显式标注不执行部署）。

行动文案「**发布模型设计版本**」；提示“不会创建 Doris 表、不会迁移数据或启动加工任务”。实际保存后提供精确 VersionRef；一旦审批/版本引用未满足正式门禁，阻断并给出逐字段原因，不能把警告折叠成成功。

首次发布不能出现“删除 / 旧 null”伪删除的主视觉；技术 diff 可折叠查看。

### P09｜交接数据开发：受控传递不是复制系统

**服务故事**：US-15、US-16；**主角色**：数据开发者。

~~~text
准备创建数据加工任务（来自物理模型 dwd_order v1）
源：ods_orders v1（来源字段及映射已确认 / 部分待确认）
目标：dwd_order · Doris（目标实例未选择）
缺口：目标库连接、字段金额转换、增量策略选择…
操作模式：SQL 加工 / 离线同步 / 其他（仅提供真有 Provider 的类型）
[补充目标连接] [查看加工规则] [进入数据开发创建草稿]
~~~

**交接合同**：模型 ID + 精确版本、来源精确 Ref/列映射/转换规则摘要、过程和标准合法引用、目标环境（真实连接/权限）、当前用户权限。跳转原 DataDev Workspace 创建其**正式 Node/Task Draft**；没有现成 Model→Task 创建 API 时不能用 URL 参数/手工模板冒充正式交接完成。

后续状态独立显示：
- Model published: 设计发布；
- Development Draft/Revision: 开发定义保存/发布；
- Physical deployment: Doris 真实建表/变更结果；
- Execution: 实际作业实例成功/失败；
- Governed consumption: 数据集/服务访问/查询回执。

**未知值**不画“待处理 0 项”。Provider UNAVAILABLE ≠ 未发现数据；FORBIDDEN ≠ 任务不存在；运行失败要显示真实日志/权限和重试链路。模型版本被撤销/编辑、来源漂移、Project 变化重新审查。

### P10｜完成业务价值：返回业务可读结论

**服务故事**：US-17～US-20。订单量必须通过业务确认日期时区/取消状态/订单去重键，方可进入 Metric 正式定义验证/发布；不能把数据行成功迁移等于业务口径正确。

最终交付页展示：业务问题、口径精确版本、使用的 ModelVersion 和 DataDev Execution、质量规则结果、脱敏/权限裁决、Dataset / Data Service 的实际可执行链接、受治理 Query/Invoke 成功和 Usage Evidence 回链。

## 3. 全流程状态和界面呈现矩阵

| 事实维度 | 实际权威来源 | 用户应看到 | 禁止混同 |
|---|---|---|---|
| 已发现来源 | Metadata 采集证据 | 采集时间、范围、指纹、列覆盖 | 正常连接≠结构已采集 |
| 已确认标准字段 | Semantic | stdFieldId、角色、标准/生效状态 | 标准存在≠标准字段存在 |
| 已确认逻辑设计 | Modeling Logical | 逻辑版本、实体/属性/关系证据 | 逻辑草稿≠可信业务事实 |
| 已发布物理设计 | Modeling Physical | ModelVersionRef | 已发布≠Doris 已建表 |
| 加工定义/运行 | DataDev/Runtime | Task Draft/Revision、ExecutionRef | 发布任务≠执行成功 |
| 质量/安全/血缘 | 各正式 Owner | 执行证据、权限/来源、覆盖 | CONTAINS≠真实数据血缘 |
| 指标/消费 | Metric / Consumption | MetricVersion/Publication、查询/使用证据 | 已发布指标≠被使用 |

**横向异常词汇**：\`EMPTY\`（有权且查询成功但无记录）/ \`UNAVAILABLE\`（Provider 不可访问）/ \`FORBIDDEN\`（无权）/ \`STALE\`（过期）/ \`FAILED\`（操作确实失败）/ \`UNKNOWN\`（无法断定，回执丢失）。每个词需要不同恢复动作，不能通过默认 0 填充。

## 4. 评审顺序与“不可跳过”裁决

1. **业务用户评审**：P01→P05 是否用业务语言解释清楚订单、过程、实体、属性、粒度；是否会强迫他提前选择 Doris 和 SQL。
2. **Semantic 评审**：P04 的标准创建/复用/过程引用权限、版本、角色规则是否准确；逻辑属性可否暂缺 StdFieldRef、历史逻辑模型如何继承。
3. **Modeling 评审**：P03 的来源映射提交一致性、P05/06 逻辑→物理关系与版本、P08 非 ODS 强标准准入及技术列例外。
4. **DataDev/运行评审**：P09 的真实任务交接方式与已发布 Model Version 如何在原执行能力中落地，是否需要新的但受控的接口。
5. **Metric/Consumption 评审**：P10 正式指标定义/发布与真实数据访问、引用/使用证据是否吻合 PD-002/PD-003。
6. **安全与 QA 评审**：权限/版本/漂移/来源不完整/标准停用/Provider 失败/恢复每条路径有真实返回，不引入 Agent 自动写入。

上述评审未通过前，本文件不得升级为可执行开发范围。具体决策表与现有实现差距请读：[V2 领域交接与裁决清单](./F-040-domain-handoff-and-review-gates.md)。

## 5. 真实 E2E 设计验收场景（非执行记录）

- 正向订单库：从已采集 \`trade_order\` 进入 ODS 后，无需逐列重复选择来源，确认 17 个真实源字段及任何额外技术列的独立依据；保存/刷新来源关系可回读。
- 逆向业务语义：同一 \`order_create\` 可让订单主表和订单明细分别采用合法粒度模型，不自动将买商品当成另一个重复过程。
- 逻辑实体：确认订单实体与属性、主标识、关系基数，逻辑属性可追到 StandardFieldRef；草稿与确认版本可回读。
- 非 ODS 门禁：源表导入、手工添加、复制、按过程派生、逻辑生成、Agent 候选采纳都不允许在没有合法 stdFieldId 下直接发布正式模型；系统列例外仅走明确批准的策略。
- 物理和任务：逻辑→物理仅生成草稿；模型设计发布与物理部署/运行状态区分；从模型版本进入正式 DataDev Task Draft，运行后按实际 execution 回执展示。
- 真实消费：订单量口径确认后经过 Metric 定义验证/发布，Dataset/Service 真实访问、Query/Preview 成功并记录 Usage Evidence，错误和缺权限不伪装为“没有数据”。

**本 V2 定义设计验收，不声明任何一条 E2E 已执行。**

## 6. R-01/R-02 之后的首屏 AI 协作补充（非已实现功能）

GM-J1-16 是“从业务目标建设可信数据”的任务协作，不是 J6 的自然语言智能问数。P01 需展示有证据的“已发现事实/建议任务步骤/业务待确认问题/原域成果引用/下一步与专业接管”，P02–P08 可审阅采纳候选而不自动落库，P09 只能按已有 DataDev 的真实 Draft/Revision/Execution 保存/运行，P10 用真实 Metric/Dataset/Usage 判定是否交付。

AI 暂不可用或用户放弃候选时，业务手动入口保留。不要把“生成成功”显示成“已发布、已部署、已运行或已消费”。完整业务合同与 G1/G2 验收前提见 [F-040 首次价值交付门槛](./F-040-first-value-delivery-gates.md)。本交互文档仍为 DRAFT，未改变 PD-010 的审批状态。
