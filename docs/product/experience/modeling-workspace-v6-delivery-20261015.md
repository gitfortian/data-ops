## 范围与判断依据

用户最初要求完整业务操作、修复与清理，随后调整为先记录所有问题、不现修。依据 ACCEPTED PD-003、IMPLEMENTING F-029/F-037 与 Modeling 的现有领域/需求/架构/依赖合同。历史“DWS/ADS 暂不支持”已由同一 REQUIREMENTS 的后续 51/52 聚合/应用条款替代，按当前支持矩阵验收；旧单菜单/视图切换条款与用户已批准的五个子入口有差异，以用户当前授权为准。

- 在当前本地项目内新建明确标识的验收模型，避免修改原有业务模型与来源数据。保存、冻结、设计发布按真实页面门禁操作，不借数据库或 API 绕过业务步骤。
- 外部 DDL/加工实际执行不属于 Modeling 合同；验证生成内容和原 DataDev 交接，运行结果必须有真实执行证据才可宣称通过。
- 清理只针对重复入口、无效占位、误导性说明和已经不适用的内容；不因低频隐藏必要交付能力，不新建模块、状态机、一级导航或审批。
- 缺陷先定位真实拥有边界，登记后续最小修改建议，本轮不实施。服务端合同问题单独列证据和影响，不用前端伪造成功。

## 已登记问题

### M6-01 · P1 · DWS 分层映射读取失败被呈现为“没有映射”

- 复现：创建 DWS #10，回执为5字段、3业务字段，点击“核对分层映射”，进入 `/modeling/models/10?tab=layer-mapping`。
- 实际：显示“还没有分层映射”，没有稳定的失败面板或重试入口；创建成功回执无法在下一步核对来源。
- 预期：全部业务字段即使未关联标准，也能展示模型来源；查询失败应显示不可用而非空结果。
- 影响：DWS/ADS 的来源与口径交付、未治理字段追踪。责任边界：Modeling 映射 Query 与前端错误状态。
- 代码线索：`LayerFieldMappingService.toView` 无条件执行 `processApi.getField(po.getProcessFieldId())`；聚合映射允许该 ID 为空，而 Semantic 的 `get` 对不存在 ID 抛异常。前端 `layer-mapping/index.tsx` 捕获查询异常后仅短暂 toast，空数组继续触发“还没有”空态。此为代码定位证据，尚未通过服务端修复实验确认。

### M6-02 · P1 · 派生创建丢失业务域归属

- 复现：从过程 #3 进入向导，业务域为“交易”、过程为“验收·订单分析”，从上游创建 DWD #9，返回物理列表。
- 实际：模型业务域显示“未分类”。
- 预期：创建所展示并确认的业务域应保持一致；按业务域浏览能够找到已创建模型。
- 影响：业务域筛选与目录组织、创建前后信息一致性。责任边界：Modeling 原子派生命令。
- 代码线索：向导基础信息包含 domainId，但 `buildDerivePayload` 和既有派生请求没有透传；服务端派生使用不带 domainId 的 `catalogService.create` 重载。后续应决定以已核验业务过程解析归属的最小修复，本轮不通过补写掩盖断点。

### M6-03 · P2 · 缺 ODS 时只有阻断文字，没有回补动作

- 复现：在导入 ODS #8 之前，对 MAIN 表 trade_order_detail 发起 DWD 派生。
- 实际：正确显示“ODS 待准备”并禁用复核，但没有“准备 ODS/返回精确来源”等入口。
- 预期：保留阻断并提供已有来源路径，回补后可明确继续原过程。
- 影响：初次建模的用户必须自行退出寻找数据源，连续路径中断。
- 证据：[缺 ODS 的派生页](evidence/modeling-workspace-v6-20261015/dwd-missing-ods-before.png)。责任边界：建模派生前端交接。

### M6-04 · P2 · ODS 保存后状态文案相互矛盾

- 复现：ODS #8 完成结构与映射保存，停留在成功回执。
- 实际：成功区显示“ODS 已成功保存”，同时来源区仍显示“当前项目无精确 ODS”，目标区仍称“已保存空草稿 #8，字段映射已提交”。
- 预期：成功后按真实回执更新目标与来源提示，避免把已完整保存的设计继续称为空草稿。
- 影响：用户无法直接判断来源与模型是否已建立关联，可能误以为需要重复操作。
- 证据：[ODS 成功回执](evidence/modeling-workspace-v6-20261015/ods-saved.png)、[重新进入后的9条映射](evidence/modeling-workspace-v6-20261015/ods-mappings-readback.png)。责任边界：ODS 交接页展示状态。

### M6-05 · P2 · 发布确认混入内部元数据，且消费说明过度概括

- 复现：首次发布 ODS #8 或 DWD #9。
- 实际：确认表列出 `definition` 哈希、modelId、status、数组下标和“删除 / null”等原始 JSON 差异；9字段 ODS 显示62处差异，6字段 DWD 显示47处差异。说明称“血缘/派生/建库脚本等消费方从此读取该快照”，与当前 DDL 仍按已保存结构生成的领域合同不一致。
- 预期：优先呈现用户能理解的字段/主键/索引/分区变化，技术原文可折叠；准确说明哪些入口读取发布快照。
- 影响：发布复核被内部字段噪声干扰，容易误解发布版本与当前草稿的消费边界。责任边界：物理结构发布前端。

### M6-06 · P2 · 治理统计口径前后不一致，技术与维度约定列混入待治理数

- 复现：创建 DIM #12，回执显示8字段/待治理2；打开结构页，显示“8个字段未治理”；打开标准覆盖报告，显示缺标准8。
- 实际：process_time/event_time、代理键、start_time/end_time/is_current均被列为缺标准；DWS #10同样从创建待治理3变为详情5。结构页按缺stdTypeId计数，创建回执按业务字段的stdFieldId计数。
- 预期：区分业务字段治理、物理列标准引用覆盖，统一或清晰标注不同分母；技术/约定列不应与业务字段治理率混为一谈。
- 影响：完成度与待办数量失真，容易反复要求治理系统生成列。领域合同明确技术及维度约定列不计入派生治理率；全列覆盖报告的另一口径不能不加区分地当作同一“未治理”。
- 证据：[DIM结构提示](evidence/modeling-workspace-v6-20261015/dim-governance-count.png)、[覆盖报告](evidence/modeling-workspace-v6-20261015/dim-standard-coverage.png)。责任边界：Modeling 展示统计与只读覆盖证据术语。

### M6-07 · P2 · 关键分层设计约定在复核和详情中丢失展示

- 复现：ADS #11填应用编码qa_v6_dashboard、名称验收商品看板并提交；查看复核、成功回执和基本信息。DIM #12选择SCD2后查看复核和基本信息。
- 实际：ADS复核未列应用编码/名称，创建后基本信息也没有应用绑定、统计周期；DIM复核未独立显示SCD策略和代理键主键规则，只能从约定列猜测。当前 ModelRecord 类型与基础信息页没有相关元数据展示。
- 预期：提交前能复核应用与历史策略，提交后能明确回读保存的设计约定；无法读取的事实不能靠命名推断。
- 影响：应用绑定和周期难以验收，后续维护无法确定原设计。责任边界：分层元数据查询/展示契约、派生复核与模型详情。
- 证据：[ADS复核](evidence/modeling-workspace-v6-20261015/ads-review-missing-app.png)、[ADS基本信息](evidence/modeling-workspace-v6-20261015/ads-basic-missing-app.png)、[DIM复核](evidence/modeling-workspace-v6-20261015/dim-scd2-review.png)。

### M6-08 · P2 · 模型头部用版本记录ID冒充可理解的版本号

- 复现：DWS #10首次发布后进入版本页。
- 实际：头部显示“已发布设计版本 #5”，版本历史只有V1。代码展示publishedVersionId（版本行ID），没有使用latestVersionNo。
- 预期：面向用户统一显示V1，必要时将内部版本记录ID放在详细信息中并标明其含义。

### M6-09 · P1 · DWS/ADS 开发交接缺少精确模型版本上下文

- 复现：DWS #10发布V1后进入“开发交接”，点击“核对表结构与交接”。
- 实际：只切回表结构，DWS结构工具栏没有交接预检；“打开数据开发”固定导航到`/data-development`，不带当前模型、过程和精确版本。已有PhysicalDataDevHandoffPanel仅在DWD/DIM结构页挂载。
- 预期：DWS/ADS能够交接到已有开发能力，并保留可核验的当前对象和版本；若能力暂不支持，应明确显示缺口及下一步。
- 影响：从已发布聚合/应用模型到加工设计的链路在当前入口处中断，用户需重新定位对象；不能认定“全层建模→物理落地”已交付。责任边界：前端模型→DataDev交接，后续还需核对原DataDev能力是否支持该类型。

### M6-10 · P2 · 面向用户的报告暴露内部决策编号与待审批规则

- 复现：打开DIM #12标准覆盖报告，查看“核验适用范围”。
- 实际：正文包含“PD-010正式决策”“技术列豁免尚未获批”、StandardFieldRef、MISSING_STANDARD等内部术语；交接组件文案还使用DR-07等内部合同编号。
- 预期：用当前可用能力、检查范围和具体下一步说明结果；治理过程与内部编号留在产品/验收文档。不能把PROPOSED/DRAFT内容包装成用户需要学习的规则。
- 影响：正文噪声较多，用户难区分当前检查结果、产品边界和研发尚未决定的事项。责任边界：报告内容和术语收敛；清理候选，未实施删除。
