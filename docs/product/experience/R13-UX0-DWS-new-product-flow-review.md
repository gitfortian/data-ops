# R13 UX-0 / DWS｜全新产品流程与逐屏信息架构评审稿

> 2026-10-17 · 状态 `DWS_UX0_REVIEW_REQUIRED`，不是已签收原型。关联 [#593](https://github.com/gitfortian/data-ops/issues/593)、[#513](https://github.com/gitfortian/data-ops/issues/513)。本文件是**从用户工作与业务判定重构的新方案**，旧 IA-550 只能用于检查遗漏，不能作为本轮屏幕布局底稿；不创建 React 功能、不改变 API、不代表生产 SQL 已运行。

## 1. 任务定义与成功标准

**用户目标**：用多个可追溯的 DWD 事实生成一张在固定业务时间、固定粒度上可复用的 DWS 主题汇总模型，不依靠自己猜测 COUNT/SUM 的业务含义、关联扇出及来源最新版本。

**主角色**：数据建模人员完成草稿；业务口径负责人确认聚合意义；数据治理负责人核对标准；发布/审批人员确认设计证据；DataDev/Runtime 负责后续真实运行（**不在 DWS 模型按钮里隐式执行**）。非写权限用户可查看证据，不能通过前端控件绕过授权。

**本阶段可验证结果**：
- 在单一模型工作台中，新建/继续一份 **具名的 DWS 设计**，有明确过程、业务日历、来源版本、唯一行粒度、维度键、度量口径和标准字段。
- 用户可把不完整设计保存为 `DESIGN_DRAFT`，重开定位具体欠缺；只有完整审核后才能请求发布 `MODEL_DESIGN_PUBLISHED`。
- 任一上游变更要有明确「保持当前冻结版本继续设计 / 重新选择新版并审查差异 / 取消」操作；不能自动替换、新版静默覆盖草稿。
- 最终发布证据含准确的源版本和业务口径、设计指纹。绝不从“已发布模型”推导“已部署/有结果/已上架”。

### 1.1 订单黄金故事的关键陷阱

来源 `trade_order` / `trade_order_detail` 与已发布的 `dwd_order` / `dwd_order_detail` 可能存在订单头、订单行**两种事实粒度**。按日订单数是 **COUNT DISTINCT(order_id)** 的业务语义候选，而不是行数 COUNT(*)。支付金额如从行事实汇总，必须审查头部金额是否在每行重复、退款/折扣/取消/支付状态怎样处理。**没有业务口径确认和真实字段证据，不让「支付金额 SUM」从字段名直接过发布门禁**。示例目标 `dws_order_daily`，按业务日期、地区汇总；样例不是既有生产指标真相。

## 2. 业务模型与术语：一张 DWS 最少要回答的六件事

| 决策 | 必须给出的精确事实 | 用户如何理解 | 发布缺口 |
|---|---|---|---|
| 建模对象 | 项目 / 业务过程 / 目标 DWS 模型 ID | 汇总的业务对象是谁 | 无上下文不允许派生 |
| 来源版本 | 一个或多个同过程已发布 DWD ModelVersionRef；逐字段来源 | 表来自哪个不可变快照、粒度是什么 | 未发布/撤权/悬空/跨过程不得发布 |
| 行粒度 | 「每个统计桶 × 每组维度值一行」的文字与维度集合，含周期桶 | 一行代表什么，和订单头/明细行有何不同 | 无行粒度不得发布 |
| 时间约定 | 业务时间列、IANA 时区、1h/1d/1w/1m 或全量模式、边界和周起始规则 | 「今天」按谁的当地时间划分 | 时间/桶不一致不得发布 |
| 度量语义 | 输出名、源字段或 COUNT(*) 的行来源、函数、去重业务键、过滤/NULL/精度与 Metric 引用 | COUNT DISTINCT 和 SUM 的数字为什么可信 | 数值表达不明或业务口径未确认不得发布 |
| 治理与交付 | 标准字段 ID / 标准版本、设计校验、审批、ModelVersion 证据 | 设计已准备好不等于数据已生产 | 标准缺失或版本漂移不得发布 |

**建议**：先支持「单一 DWD 明细事实 + 可选择维度映射」的高可信路径；多事实 Join/Union 先作为独立高级分支，只有 Join 键、基数、重复计量与权限能被审查时才开放设计发布。此范围决定需要 Product Owner 在 UX-0 明确，不用“选多个上游”自动等价为可聚合。

## 3. 用户故事与状态（从头定义，不迁移旧原型）

### 3.1 黄金正向路径

`业务过程/建模工作台` → `选择 DWS 设计或继续草稿` → `确认已发布来源及事实粒度` → `定义业务时间和行粒度` → `定义分组维度与逐项度量` → `检查标准、差异和可发布性` → `保存草稿/关闭重开` → `确认发布设计` → `保留模型版本与来源可追溯回链`。

导航只在现有模型工作台增加对象内子视图/锚点，**不新增“DWS 专业工具”菜单**。页面必须在退出/刷新/后退时以 `projectId + modelId + draftRevision` 精确恢复工作。

### 3.2 四类状态，不复用一个「完成」标签

- `EMPTY`：还没选来源；允许查看当前过程与新建入口。
- `DESIGN_DRAFT`：可保存的不完整设计，展示待处理项；未建立正式运行任务。
- `REVIEW_READY`：所有强制设计证据在当前版本已校验；**并不自动发布**。
- `MODEL_DESIGN_PUBLISHED`：不可变 Modeling 版本已生成，来源和口径冻结；运行/质量/消费仍单独展示 `NOT_RUN / UNKNOWN / BLOCKED / VERIFIED` 等来自原 Owner 的事实，不从发布状态臆断。

版本漂移是叠加风险状态 `REVIEW_STALE`，保存草稿允许保留证据，**审批与发布必须重新核验**；已经发布的历史版本不可静默重写。

## 4. 全新低保真应采用的逐屏信息架构（待 UX-0 签收后绘制）

| 屏 ID | 页面目标 / 最关键问题 | 主区 | 侧区、底部或弹层 | 主动作 |
|---|---|---|---|---|
| DWS-01 入口/对象 | 我在给哪个业务过程建什么汇总？ | 目标模型/过程、已有草稿及已发布版本、上次工作 | 当前项目、上游与责任人证据 | 继续草稿 / 新建汇总设计 |
| DWS-02 来源/粒度 | 上游每行是什么、目标每行是什么？ | 仅已发布 DWD 来源卡、准确版本、字段/业务键/来源粒度 | 选中上游行数并不等于订单数的警示；不可用原因与返回源模型 | 确认来源并声明目标行粒度 |
| DWS-03 时间/维度 | 一个时间桶和维度组合代表一行吗？ | 业务时间、IANA 时区、统计周期、业务日切分、维度分组与周期桶 | 结构示意「2026-10-17 × 城市=上海 → 一行」，源字段/标准证据 | 保存时间与分组草稿 |
| DWS-04 度量/规则 | 每个聚合数字的公式与业务含义是什么？ | 逐项度量卡：源字段、COUNT/SUM/COUNT DISTINCT、去重键、过滤、NULL、业务口径/Metric 引用 | 同名冲突、头/行重复计量风险与源列定位 | 逐项确认度量 |
| DWS-05 审核/发布 | 哪些证据齐全、有什么风险、发布到底做什么？ | 四组检查：来源版本、粒度时间、度量与标准、草稿差异 | 具体可定位 blocker、冻结快照摘要、最近审核人与权限 | 保存草稿 / 提交审批 / 发布设计（按真实权限） |
| DWS-06 版本/恢复 | 怎么重开、追溯或从变化中恢复？ | 草稿修订/已发布版本时间线、版本差异、来源快照 | 回到业务过程/回到来源/继续 ADS 的**条件性**入口 | 恢复草稿或新建修订，不覆盖历史 |

**设计重点**：DWS-03/04 是专业工作的中心；目标粒度必须有文字说明和样例数据行对照，不把角色选择、时区、聚合函数挤成一张长表单。审核面板需把“可保存草稿”和“允许发布设计”拆成两种动作，不因数据验证不可达误判为已经运行。

## 5. 交互原则、风险路径与恢复

| 场景 | 用户应见到的状态 | 允许动作 | 禁止动作 |
|---|---|---|---|
| 没有已发布 DWD | 有业务过程但来源列表为空，附「去发布来源」入口 | 返回来源，保存空草稿（若有对象身份） | 默默读未发布结构 |
| 未获来源 READ 或权限撤销 | 受限状态，勿显示敏感列/SQL | 回业务过程、申请权限 | 用缓存的旧列数据继续正式发布 |
| 冻结上游产生新版本 | 两版差异：字段/类型/键/标准/时间列 | 保持旧版、显式迁移新版、取消 | 静默跟随 latest 覆盖草稿 |
| 无业务时间、跨时区或 DST 边界 | 说明时区和时间窗；无源时间时阻断时间汇总 | 改选来源时间列/周期、保存不完整草稿 | 把技术处理时间默认为业务时间 |
| 订单行上做金额 SUM | 明确警告「头部金额可能重复」并要求来源事实/业务签收 | 修改度量、查看源模型/口径、留草稿 | 直接以函数白名单即通过 |
| DISTINCT 缺业务键或 Join 扇出不明 | 指明哪一项度量/哪些关系造成风险 | 修复字段、拆分汇总目标 | 自动推断为 COUNT(*) |
| 结构未保存、切换来源/周期 | 草稿差异、保留/保存后继续/取消三选一 | 确认丢弃或保存 | 无提示覆盖用户编辑 |
| 保存超时、状态未知 | 根据对象 ID 和 revision 回读核对是否成功 | 刷新同一版本、只读比较 | 直接重复创建新的对象 |
| 审批期间来源变更 | 显示审核基线与当前差异 | 撤回/要求重审（遵循 Approval Owner） | 自动批准新的基线 |
| 无发布权限或发布失败 | 保存草稿不受影响，说明责任人/错误位置 | 请求审核、继续编辑 | 虚构“发布成功/已运行” |

**关于时间**：每周从星期一还是业务日历自定义、跨夏令时的日边界、迟到事实重算窗口属于**需要产品决策并且运行策略另行授权**的事项。原型必须暴露选择与影响，但不能在本 UX-0 虚构全部计算已实现。

## 6. 验收断言（设计验收，不是 E2E 假证据）

- H-DWS-01：从建模工作台进入同一个 `modelId`，页面 2 步内能看清当前业务过程和上游已发布版本。
- H-DWS-02：订单头/订单行来源不因都有 `order_id` 而被错误认为一行一订单。
- H-DWS-03：每日/每周/每月的周期桶和 IANA 时区能被非算法专家读懂；未确认业务时间不能发布。
- H-DWS-04：`COUNT_DISTINCT(order_id)` 和支付金额 `SUM` 必须各自解释业务键、过滤、可能重复计量与标准引用。
- H-DWS-05：跨项目/权限不足/未发布上游以及冻结版本漂移明确拦截正式发布。
- H-DWS-06：切换上游或粒度不丢失未保存草稿；保存后刷新/重开定位同一对象、同一草稿修订。
- H-DWS-07：页面不把 `MODEL_DESIGN_PUBLISHED` 表示为已运行、已质量验收或已可消费。
- H-DWS-08：有权读、无权写的用户能查看已发布设计，但不能保存或提交发布；权限不得只靠前端隐藏。
- H-DWS-09：高保真阶段在 1440/1024/768/390 宽度下检查表格横向滚动、键盘顺序、错误定位、对比弹层；浏览器实测证据是后续门禁，不提前宣称通过。
- H-DWS-10：新低保真包含至少「正常设计、版本漂移、来源撤权、度量重复计算、保存状态未知、只读权限」六个可操作分支，不能只提供静态截图。

## 7. 代码现实（用于确认可实现性，不是 UI 设计来源）

- 当前 `DwsGrainDesignService` 已持久化时间列、时区、周期桶、dimension/measure、来源版本摘要和 structure fingerprint；`ModelVersionService` 发布时会检查当前设计合同并冻结。这些是**已有能力，不是产品设计已经被用户签收**。
- 现有度量合同主要是 `column + function`；**没有足以表达去重业务键、源行重复计量、业务过滤和真正关联基数的完整产品级合同**。新 UX 必须先确定必须表达的内容，再决定是否需要扩展后端；不应降低 UX 以适配旧 DTO。
- 当前 UI `DwsGrainDesignPanel.tsx` 是一个长表单，并与其他物理结构页并列，容易让业务粒度解释隐形；后续高保真签收后再重构，不在 UX-0 修改 React。
- `PhysicalStandardCoveragePanel` 的能力范围当前主要为 DWD/DIM 只读证据，且 PD-010 的非 ODS 正式发布规则仍有待独立治理裁决；UX 不应假设所有字段都已达到 Semantic Owner 的正式授权。
- 现有 `ModelDeriveService` 支持上游结构选列、维度/度量白名单和只读预览；多输入自动并列合并可能遗漏真实 Join 基数，因此本轮要先完成 UX 审查。

## 8. 需要 Product Owner 在 UX-0 确认的方案决策

| 决策 | 推荐默认方案（待签收） | 影响 |
|---|---|---|
| DWS-D1 聚合来源范围 | 首版聚焦**单一已发布 DWD 事实**；多来源 Join/Union 在明确关系基数后另评审 | 防止自动同名列合并引入重复计量 |
| DWS-D2 粒度入口 | 把「一行代表什么」放在字段表之前；时间桶必须单独确认 | 避免按字段先建表、事后猜粒度 |
| DWS-D3 时间模型 | 首版必须选业务时间、IANA 时区、周期桶；全量无时间桶作为特殊类型单独审核 | 防止 `ALL` 与强制周期桶矛盾 |
| DWS-D4 度量口径 | 每项度量都需来源、业务解释和必要的 distinct key/过滤；引用 Metric 不等于自动口径获批 | 控制 COUNT DISTINCT、SUM 错误 |
| DWS-D5 草稿/发布 | 不完整可保存草稿；发布需要校验、可查看审批证据；不能隐式执行 | 提高可恢复性，保持 Owner 边界 |
| DWS-D6 页面架构 | 原建模详情对象内分段工作区 + 侧边问题定位；不新建独立菜单/第二套工作台 | 降低跳转、保持一致性 |
