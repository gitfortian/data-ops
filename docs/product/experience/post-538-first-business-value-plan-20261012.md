# #538 完成后的下一阶段：首个可信业务结果

日期：2026-10-12。性质：规划建议与当前事实核对，不自动批准 PD-010 / F-040，不启动新的业务功能。

## 1. 推荐结论

**#538 的 S1、S2 都完成后，下一阶段应沿已有建设链路交付一个真实可消费的业务结果，建议采用“每日下单订单量”作为首个金样本。**

#538 的成果是授权来源到可恢复的 ODS 设计，以及可靠的待治理纳管；它不包含实际数据同步/加工、正式资产自动上架、目标数据库部署、指标和真实消费。若只完成 S1，下一步仍是 #538 内部的 S2 安全协议评审与自动纳管，而非另开下一产品阶段。

新阶段用户结果：业务用户能够查询一份经确认口径、实际运行和质量校验的订单结果，并追溯到来源、模型版本、任务修订、执行回执和消费记录。

## 4. 依赖顺序：三个业务工作包

### P-1 业务定义与正式设计合同

输入：#538 可回读的 ODS、来源与映射，以及一个明确的业务问题。

用户完成：

- 确认“下单”业务过程，订单头与订单明细的粒度、来源 MAIN/DETAIL 角色。
- 确认需要的标准字段及有效引用；仅处理金样本需要的字段，不以“补齐整个标准库”为目标。
- 复用现有逻辑作者页确认实体、标识和关系，冻结可回读逻辑版本。
- 复用物理编辑器审阅或创建最小 DWD 设计，明确类型转换、来源、粒度和标准引用。
- 人工保存逻辑版本到物理字段的正式关联；已存在模型默认复用，不由候选预检自动生成或覆盖。

需先裁决：非 ODS 哪些列必须具备正式 `stdFieldId`、草稿/发布何时校验、技术列例外、历史模型如何兼容；逻辑/物理精确版本和映射由 Modeling 持有。

验收成果：重新打开相同业务过程与设计，可回读精确版本关系、真实标准引用和人工映射；标准停用、来源变化、并发编辑不能静默穿透。

### P-2 从已保存设计到实际数据生产

输入：P-1 的明确设计版本与经授权的来源/目标环境。

用户完成：

- 从精确物理版本进入现有 DataDev，人工选择/创建并保存任务。
- 正式保存模型版本与任务修订的关联，发布修订后关联不随可变草稿漂移。
- 审阅全量/增量、源/目标、类型转换和异常处理；任务草稿、发布、建表/部署、执行分别给回执。
- 在明确授权的隔离环境执行，核对目标数据，支持失败定位、修复和受控重跑。

DataDev 拥有任务定义/修订/运行和相应来源引用，Modeling 不增加执行引擎。已合并 #535 的 URL hint 与人工选择不能当持久化绑定。

验收成果：能回答“这个执行到底用了哪份任务、对应哪个设计版本、读写哪个目标、失败如何恢复”；实际目标行数/样本与执行证据一致，SQL SUCCESS 不单独证明数据业务正确。

### P-3 质量、指标与真实受治理消费

输入：P-2 的真实生产结果，及确认的业务口径。

用户完成：

- 对订单唯一性、重复明细关联、时间/类型异常等适用风险执行真实质量检查。
- 经业务确认定义并验证一项指标；Metric 保存、验证和发布继续遵循 PD-003。
- 由既有 Dataset 或 Data Service 交付结果，通过现有 Consumption 能力访问。
- 有权限角色成功使用，受限/跨项目角色被拒绝；成功与拒绝均有可核验审计，实际使用进入 Usage。
- 保留来源/生产者回链和失败恢复，不把结构血缘、订阅或页面浏览当真实消费。

验收成果：业务用户确实得到预期的每日结果，能说明来源与口径，并能追踪本次执行、质量、指标版本和合法消费。

## 6. 下一阶段先做一次集中合同裁决

在正式写入与运行关联前，集中确认四组事项即可：

1. 非 ODS 标准字段约束、技术列例外和旧模型兼容。
2. LogicalVersion→PhysicalVersion 正式关联、修改/重新发布及历史回读。
3. PhysicalVersion→TaskRevision→Execution 的身份、写入 Owner、并发/失败/重放边界。
4. 首个指标的业务口径和真实环境验收输入。

首个指标暂建议“每日下单订单量”，不能自动决定按创建还是支付时间、时区、取消单处理、订单去重键及统计范围。订单明细行数不得直接冒充订单数。

据正式批准的范围更新 PD-010、F-040 和相关原域合同；只读核验不因此失去价值，仍是正式写入前后复核的基础。

## 7. 建议交付粒度与推进纪律

- #538 内部保持既有 S1/S2 两个完整阶段，不把后续范围塞进 S1。
- #538 之后建议少量集中功能 PR：一组完成正式可信设计关联，一组完成真实任务生产到业务消费。具体合并边界根据领域合同/风险确认，不按按钮或 DTO 拆票。
- 第一轮只做单项目、MySQL 金样本及一个业务结果；保留必须的受限/跨项目反例。没有多源/多方言真实需求前，不把全平台适配当先决条件。
- J1 的 AI 协作可使用现有有证据建议和专业接管入口，人工路径始终可走；AI 不可用不阻断这条业务主线。J6 问答是另一条消费者旅程，不能替代实际数据建设。
- 消费者自主发现、复杂调度/异常恢复、安全治理深化、可信 AI 问答与 MDM，在首个可重复业务成果后按实际需求排序；基础权限/审计/版本和失败恢复从第一条链路就必须有。
- 不新增顶级“建设中心”、第二标准库、模型版本库、全局旅程状态机或任务引擎。
