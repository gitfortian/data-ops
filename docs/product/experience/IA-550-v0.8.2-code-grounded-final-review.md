## 0. 总结论与技术事实

**可以开始规划正式前端页面，但现在不能无条件宣布全部原型或接口合同已签收。** 最多是 **“交互层面的可评审冻结候选”**。原因不是后端没有开发，而是现有完整度**按域差别极大**：

- DataSource/Metadata、Semantic、Logical Draft、Physical Model、Metric、DataDev、Quality、Security、Dataset/Service、Consumption、MDM、Agent 与 Home **有丰富的后端 API 和真实前端页面**。正式前端应优先组合/重构它们，**不能按照纯原型重做一套丢失功能的简化 Demo**。
- **逻辑→物理**：Java `LogicalPhysicalHandoffReviewService` 文档明确 `Ephemeral`/read-only，`REVIEWABLE_ONLY` 仅人工审阅，可核验用户选择的逻辑属性 ID、物理列 ID、SHA256 和标准字段 ID，**一对一映射、无持久映射、无批准/发布**。派生/聚合/延期解释不是同一个正式写接口；当前原型仅能作为未来设计草稿。
- **物理→DataDev**：Java `PhysicalDataDevHandoffReadinessService` 明确仅适用**已发布 DWD/DIM** 精确 `modelId/versionId/versionNo` 的只读预检，`dataDevStatus='NOT_AUTHORIZED_FOR_TASK_CREATION'`，不自动生成 Node/Draft/TaskRevision。ODS、DWS、ADS 无法直接用这条读 API 声称就绪。
- **协作中心**：已核对的 Approval API 是通用流程、待办、批准/拒绝和 Flow 管理；未发现**数据需求/数据问题/口径确认**的独立事实 Owner、业务状态机与 ProductKey+版本写入/查询合同。不能把内存原型日志映射为 Approval 的正式业务表。
- **首页**：已有 `/api/v1/home/cockpit`、data-center/recent/schedule、assets、quality、resources、schedule-center 和 Approval todo。HomeCockpit 现有 `dataSourceCount`、`runningCount`，附来源可用性，Quality/Resources 可明确 `available=false`。原型“待连接”只表示静态 HTML 未连服务端，**不代表生产没有这些后端 API**。
- **Dataset/Service**：已有 Dataset `queryDataset`，Data Service `testDataService`、Runtime、Invocation Evidence、Call Logs、Key/IP/Auth 设置，Consumption `discoverProducts/getProduct/getConsumerImpact/listSubscriptions`。本版消费者模拟卡片不允许替代真实 Query、授权状态或 Usage。

## 3. 是否可以定稿？

**可以定稿的 UX 主轴**：
1. 首页按业务目标和当前职责引导，而不是重复数据大屏，保留真实数据源/模型/指标/资产/运行/消费总览。
2. ODS 不强制逻辑模型，业务 DWD/DIM 先逻辑身份和来源依赖，DWS/ADS 分别按指标和消费输出设计；以 `physicalModelId` 而不是 Layer 作为草稿身份。
3. 物理设计→DataDev 和消费者→问题反馈要携精确 Owner/version 回链；业务确认、设计保存、发布、实际执行、质量、消费分别展现。
4. J1 Agent 建设与 J6 数据问答分离，受治理的真实回答只读正式证据。

**不能签为“既有后端可直接做完”的功能：**
- `DR-06` 正式持久逻辑属性↔物理列映射（字段来源、多个属性到列、多列派生/聚合、历史版本关系和对应标准引用）；现有 Java **只读一对一临时审阅**。
- `DR-07` 不可变 `ModelVersionRef` 到 DataDev Task Draft/Revision 的正式 provenance、审批与运行权限；现有 Java **只读且 NOT_AUTHORIZED_FOR_TASK_CREATION**。
- 数据需求/问题/口径协作的 Owner、状态机、操作权限、ProductKey+Version 来源精确存储及回链；已有 Approval CRUD 不能直接代替。
- 逻辑多实体关系/复合主键/Join/Cardinality 与前端多选/撤销的实际领域设计，及全部 #513 J1–J6、MDM 真实 E2E。

### 建议下一阶段前端开发切片（遵守主线、不要从头复制旧功能）

A. **可先开发的整合**：首页读取真实 Home/Approval/Quality + 已有领域数据；导航/页面组合；已有 ODS/J1 source→model、逻辑 CRUD、Modeling 模型详情/字段继承/历史版本的 UX 重组，保留现有深链/角色/异常恢复。  
B. **有条件的前端联调**：逻辑↔物理只读 preview/review 与映射草稿；清楚展示结果不能保存/批准。Modeling 发布/真实设计审查与 DataDev 入口并排，但不虚构自动任务创建。  
C. **需 Owner 合同先定再完整开发**：DR-06/DR-07、新数据协作中心的真实持久流程、完整安全消费/J6 与跨域 golden E2E。提交约束、审批事件、版本快照和失败恢复由原 Owner 设计。

最终建议：**v0.8.2 标记“UX 定稿候选，待签收”。前端第一批可按 A 开发，但全域原型不能声称已完成生产实现。** 如果需求方想要“所有页面/功能原型签收后统一开发”，必须先针对上面新增契约出产品决策并进行真实浏览器验收；否则会重现后端能力存在但页面逻辑不符合业务的旧问题。
